# Extender Catalog and Version Probes — Design

**Status**: BUILT (2026-11-24). Requirements: [LMC-SCR-004, LMC-SCR-005 and LMC-SCR-010](../prd/legacy-mod-compatibility.md)
(PRD decision Q3, owner 2026-11-03), Phase 3 (#6672) on Phase 0 data. All three slices are built (§5, §6, §7); the
ObScript families' runtime probes wait on the NVSE byte forms (`mcm-host.md` §6.9).

A mod gates on its extender's version. If the probe answers "absent" or "too old", the mod disables
itself. The engine runs no extender binary (LMC-NG-001). It owns the script-facing surface instead,
so it must answer probes like `SKSE.GetVersionRelease()` or `GetNVSEVersion` from what it actually
serves.

Decision Q3 asks for a per-mod, per-family answer: the highest API level at which every function the
mod calls, from that level down, is served. If even the lowest level has an unserved call, the answer
is "absent". Three layers build to that answer, one slice each.

## 1. Slice 1: the per-function catalog (LMC-SCR-004)

One row per extender function. The row gives:

- its family;
- its script and function (Papyrus) or its command (ObScript);
- its declared signature;
- the version that introduced it, and where that version comes from.

The engine's coverage of each function is computed against the rows, never typed in by hand.

**Sources** (2026-11-23). Only facts are checked in: names, signatures, versions, and the source of
each. No extender file is redistributed (the SKSE readme forbids it).

| Family | Function list | Introduced-in |
|---|---|---|
| SKSE64 | `scripts/modified/*.psc` of github.com/ianpatt/skse64: SKSE's additions to vanilla scripts and its own scripts. The untouched copies are in `scripts/vanilla/`. | `skse64_whatsnew.txt`, the "added …" lines per release |
| F4SE | `scripts/modified/*.psc` of github.com/ianpatt/f4se | `f4se_whatsnew.txt` |
| xNVSE and the NVSE plugin families (JIP LN, JohnnyGuitar, ShowOff, lStewieAl's Tweaks, …) | GECK wiki function pages by their `origin`, from the local dump `/mnt/data/src/reference/geckwiki` | the page's `originVersion` where present (41 of 360 NVSE pages), else the page text |
| OBSE | CS wiki *Category: Oblivion Script Extender* pages, from the local dump `cs-uesp-wiki` | xOBSE's `obse_whatsnew.txt`, which lists commands per version |

A function no changelog names gets the family's first release as its introducing version. That's
labelled `first-release`, not presented as documented. SKSE64's history starts at 1.1.0
("everything!"), and F4SE's at 0.1.0 ("everything").

**Data.** The data is `docs/data/extenders/<family>.tsv`, generated by
`scripts/extender-catalog.py` from sources pinned by commit (Git) or by dump. Its columns are:

| Column | Holds |
|---|---|
| `family` | the extender family |
| `script` | the Papyrus script, or `-` for an ObScript command |
| `function` | the function or command name |
| `signature` | the declared signature |
| `global` | whether a Papyrus function is `Global` |
| `introduced` | the introducing version |
| `introduced_source` | `whatsnew:<version>`, `wiki:originVersion`, `wiki:text` or `first-release` |
| `source` | the file or page the row came from |

**Coverage.**

- *Papyrus.* A function is served when the Papyrus VM's own checker accepts a call of its declared
  signature. A generated script calls it with typed placeholder arguments, on a typed receiver for an
  instance function, and is checked as a quest script would be. So coverage is what the VM really
  runs, not a hand-kept list.
- *ObScript.* A command is served when the SDK catalog classifies it `Native`
  (`classify_obscript_command`). Today the ObScript VM runs no NVSE command (`mcm-host.md` §5.3).
- *Publication.* Coverage counts per family and per game are published here, and pinned by a test so
  they cannot drift silently.

The catalog also ranks what to serve next: the unserved functions a corpus calls most.

## 2. Slice 2: the eager scan (LMC-SCR-005)

The preflight (`--preflight`, LMC-DX-001) scans every script a mod root ships, archived and loose, not
only those attached at run time:

- each `.pex` is decompiled, and its calls are resolved to catalog rows;
- each plugin's `SCPT` `SCDA` is decoded for its extender calls (`obscript.rs`
  `decode_extender_calls`).

Ownership follows LMC-ID-012 (a script belongs to the root that wins it). The output is each mod's
call set per family. The preflight reports those calls that are not covered.

## 3. Slice 3: the probe answers (LMC-SCR-010)

- **The level.** For each mod and family, the answer is the highest introducing version at which
  every called function from that version down is served. It is "absent" when an unserved call sits
  at the family's first release.
- **Serving it.** The probes return that level in the family's own terms:
  - SKSE and F4SE: `GetVersion`, `GetVersionMinor`, `GetVersionBeta`, `GetVersionRelease` and
    `GetScriptVersionRelease`;
  - xNVSE: `GetNVSEVersion`, `GetNVSERevision` and `GetNVSEBeta`;
  - OBSE: `GetOBSEVersion` and `GetOBSERevision`;
  - for plugins: `IsPluginInstalled` and `GetPluginVersion`.
- **Release numbers.** Mapping a version to SKSE's and F4SE's release numbers (`GetVersionRelease`)
  needs a documented table: built from each version header's history (§7).
- **The caller.** The calling script's mod comes from the scan.
- **Reporting.** The preflight names the level chosen and the calls that capped it (LMC-DX-001). For
  ObScript, a script with a call above its mod's level is reported whole, as its author would have
  seen.

## 4. Not in scope

- Serving more extender functions. That's Phase 3's catalog growth, which slice 1's ranking steers.
- Extender language extensions, such as NVSE string variables and `let` (S3, LMC-SCR-008). Those
  belong to `mcm-host.md` §5.3's NVSE work.

## 5. Slice 1: built (2026-11-23)

**The data.**

- `scripts/extender-catalog.py` writes `docs/data/extenders/<family>.tsv` from the pinned sources:
  - SKSE64 at `ianpatt/skse64@25b72352adb6`;
  - F4SE at `ianpatt/f4se@6f6a7caa9aea`;
  - xOBSE's changelog at `llde/xOBSE@99930e168e73`;
  - the local GECK and CS wiki dumps.
- `crates/scripting/src/extender_catalog.rs` reads the tables and measures coverage.
  `coverage_counts_are_the_published_ones` pins the table below.

**Changelog parsing.**

- A changelog line counts as an addition when it names a catalogued function exactly:
  - SKSE and F4SE: the `added …` lines, with `Script/Script2.Func/Func2` expanded;
  - OBSE: the bare command lines and the early `NNNN: summary` lines, with `Get/SetX` expanded.
  Lines that start with a fix are skipped.
- An abbreviation that names no function exactly (`…/Magnitudes/Areas`) dates nothing. Its functions
  keep the first release, so a missed mention only makes a version earlier.

**Coverage.** These are 2026-11-23 counts. *Served* means the VM checker accepts the declared call
(*VM*), or the SDK catalog has a `Native` adapter (*SDK*).

| Family | Functions | Dated by a changelog or wiki | VM | SDK | Served |
|---|---|---|---|---|---|
| SKSE64 | 804 | 67 | 95 | 21 | 98 |
| F4SE | 227 | 13 | 19 | 3 | 22 |
| xNVSE | 565 | 50 | 0 | 4 | 4 |
| JIP LN | 733 | 0 | 0 | 0 | 0 |
| JohnnyGuitar | 142 | 31 | 0 | 0 | 0 |
| ShowOff | 122 | 69 | 0 | 0 | 0 |
| lStewieAl's Tweaks | 282 | 0 | 0 | 0 | 0 |

| OBSE | 644 | 92 | 0 | 5 | 5 |

**Caveats.**

- The VM's checker judges a native by its name and the receiver's kind, not its class. So an extender
  function that shares a name with a vanilla native of another class counts as served:
  `ActorValueInfo.GetBaseValue` matches the vanilla `Actor.GetBaseValue`. The VM column can only be
  too high this way.
- `ActiveMagicEffect.RegisterForModEvent` and its two kin count as served because the check matches the receiver's
  kind (an object), but the VM holds no effect values and runs no effect script, so none is ever called (§11).
- `ActorBase.GetWeight` is counted served because `Form.GetWeight` shares its name, but on an `NPC_` the run
  stops (§9).
- An instance function of `Quest` or an ancestor (`Form`, F4SE's `ScriptObject`) is also checked as the probe
  script's own call, since a script calls its own registrations: `RegisterForKey(57)`, not `akForm.RegisterForKey`.
- Each Papyrus family is checked for its own game: SKSE64's on Skyrim, F4SE's on Fallout 4. F4SE's `Form.GetName` and
  kin are not counted, because SKSE's `Form` reads run on Skyrim only.
- What the engine serves for MCM (`mcm-host.md`) is engine script, not extender natives, so it isn't
  counted here.
- The ObScript families are served only through the SDK's `Native` aliases (the load-order queries),
  because the ObScript VM runs no NVSE or OBSE command.

## 6. Slice 2: built (2026-11-23)

**Receiver types.**

- Each PEX call site now carries its receiver's declared type (`CallSite::receiver_type` in
  `crates/pex/src/call_sites.rs`):
  - a static call's provider;
  - a parent call's parent;
  - for a method call, `Self`'s object, or the parameter, local or object variable the receiver names.
- `extender_catalog::resolve_pex_call` walks up from that type to a catalog row. The walk goes
  through the mod's own scripts (the PEX's objects) and the game's vanilla hierarchy
  (`docs/data/extenders/<family>-scripts.tsv`, generated from the vanilla scripts the extenders ship).
  So an SKSE function on `Form` is reached from an `Actor` receiver, and a vanilla function is never
  mistaken for an extender one.
- `obscript_source_calls` matches the identifiers of an ObScript source against the game's command
  families. Comments and strings are skipped.

**The preflight.** `--preflight` folds both into each root's scan.

- **The report.** A root reports per family how many functions it calls, how many the engine serves,
  and the unserved ones with their introducing version:

  ```
    extender catalog (LMC-SCR-005): 0 method call(s) on receivers of a type no table names
      skse64: 12 function(s) called, 3 served, 9 not — UI.InvokeString (1.1.0), …
  ```

  The JSON carries every call as `catalog_calls`, with `unresolved_receivers`.
- **Unresolved receivers.** A method call whose receiver type is undeclared, or is a type neither the
  mod nor the game's table names, is counted. It could be an extender call the scan cannot see.

**Per game.**

| Game | Families scanned |
|---|---|
| Skyrim | SKSE64 |
| Fallout 4 | F4SE |
| New Vegas | xNVSE and its plugin families |
| Oblivion | OBSE |
| Fallout 3 | none (no FOSE catalogue has been read) |
| Starfield | none (SFSE publishes no script sources) |

**Not yet.**

- Compiled-only ObScript, a plugin's `SCDA` with no `SCTX` source, isn't matched against the catalog:
  its NVSE opcodes wait for `mcm-host.md` §6.9's derivation.
- The scan has run on unit fixtures only, since no mod is installed here.

## 7. Slice 3: built (2026-11-24)

**Release tables.** `scripts/extender-catalog.py` also writes `docs/data/extenders/skse64-releases.tsv` and
`f4se-releases.tsv`: each version's `GetVersionRelease()` index, read from the version header
(`skse64_common/skse_version.h`, `f4se_common/f4se_version.h`) at each commit that changed it. The header's history
starts at SKSE64 2.0.19 (release 65) and F4SE 0.6.21 (release 23). An earlier level answers release 0, the
conservative choice: mods read 0 as "no extender", never as a newer one.

**The level** (`extender_catalog::probe_answer`):

- The candidates are the family's documented releases and the catalog's introducing versions.
- A version older than the family's first runtime release counts as that release: SKSE64 2.0.0 carried every function
  SKSE (LE) had added, so `StringUtil.Split` (1.7.3) is a 2.0.0 function on Skyrim SE. F4SE starts at 0.1.0; any other
  family at its earliest catalogued version.
- No unserved call: the newest candidate. An unserved call at the first release: absent (every probe answers 0).
  Otherwise the newest candidate below the lowest unserved call's version.
- The answer is the level's first three numbers (`GetVersion`, `GetVersionMinor`, `GetVersionBeta`), the release at or
  below it, and the unserved calls at the lowest version: what capped it.

**The preflight** prints the answer under each family's line, and the JSON carries it as `probe_answers`:

```
    skse64: 2 function(s) called, 1 served, 1 not — UI.InvokeString (1.1.0)
      probes answer absent, capped by UI.InvokeString (1.1.0)
```

**At run time** (Skyrim and Fallout 4 sessions):

- The VM serves `SKSE` and `F4SE` as engine static classes (`fragment/vm/natives/extender_probes.rs`).
- The caller's mod is the source the running body's script resolves from: a mod root's loose scripts or a script
  archive (`ScriptProvider::source_of`). Its call set is every script that source owns: those it ships that no
  higher-priority source overrides (LMC-ID-012).
- `ExtenderProbes` computes a source's answer on its first probe, with the preflight's resolution
  (`pex_catalog_calls`), and keeps it for the session.
- A script no source holds answers absent.
- `GetScriptVersionRelease()` is no native: SKSE.psc and F4SE.psc return a constant compiled into the installed script
  (75 and 33 at the pinned commits), which mods compare with `GetVersionRelease()` to catch a mismatch. The engine owns
  the whole class, so it answers the same release, and a mod sees no mismatch.
- `GetPluginVersion(name)` answers -1, the scripts' declared "not loaded": the engine loads no extender plugin
  (LMC-NG-001).

**Not yet.**

- The ObScript families' probes (`GetNVSEVersion`, `GetOBSEVersion`, …) need the NVSE byte forms first
  (`mcm-host.md` §6.9). The preflight reports their levels already.
- A level below the oldest documented release answers release 0, so most of SKSE64's 2.0.x range reads as "absent" to
  a mod that checks the release alone.

## 8. Catalog growth: the pure SKSE / F4SE natives (2026-11-24)

The first functions served past the probes are the ones that need nothing from the world, and almost every SKSE
mod calls them: 30 SKSE64 functions and 8 F4SE ones, all from each family's first release, so an unserved one
caps a mod at "absent" (§7). They run in `fragment/vm/natives/skse_util.rs`.

| Script | Functions |
|---|---|
| `StringUtil` (SKSE64) | `GetLength`, `GetNthChar`, `IsLetter`, `IsDigit`, `IsPunctuation`, `IsPrintable`, `AsOrd`, `AsChar`, `Find`, `Substring`, `Split` |
| `Math` (SKSE64, F4SE) | `LeftShift`, `RightShift`, `LogicalAnd`, `LogicalOr`, `LogicalXor`, `LogicalNot`, `Log`; F4SE's `Exp` |
| `Utility` (SKSE64) | `Create{Bool,Int,Float,String,Form,Alias}Array`, `Resize{…}Array` |

**Behaviour** is the extenders' own native implementations at the pinned commits (SKSE64's
`PapyrusStringUtil.cpp`, `PapyrusMath.cpp`, `PapyrusUtility.cpp`; F4SE's `PapyrusMath.cpp`), read for behaviour
only, and pinned by `skse_util`'s tests:

- SKSE's strings are C byte strings; the engine's are Unicode decoded from the game's single-byte code page, so one
  character here is one byte there. The character classes are the C locale's: ASCII only.
- Index and size parameters are `UInt32`, so a negative Papyrus `Int` wraps: a negative start finds nothing, a
  negative `Substring` length reads to the end, a negative shift gives 0.
- `Find` and `Split` ignore ASCII case. `Split`'s delimiter is a set of characters, and empty tokens are dropped.
- `AsOrd` is MSVC's signed `char`: a byte past 127 is negative. A character no single byte holds has no answer, and
  the call stops with that reason.
- The array functions are bounded as `new` is (`MAX_SCRIPT_ARRAY_ELEMENTS`); SKSE has no bound, and a negative size
  would wrap to billions, so a size past the bound stops the call.

**Next** are the functions that read the world: `Form` names, types, weights and keywords, `Form`'s key, menu and
mod-event registrations, `Input`'s key state, `Utility.GetINI*`, and `Actor`'s equipment.

## 9. Catalog growth: SKSE's `Form` reads (2026-11-24)

Ten more SKSE64 functions read a form's record: `Form.GetType`, `GetName`, `GetWeight`, `GetNumKeywords`,
`GetNthKeyword`, `GetKeywords`, `HasWorldModel`, `GetWorldModelPath`, and the subclass functions sharing two of those
names (`HeadPart.GetType`, `ActorBase.GetWeight`, the second not served). They run in
`fragment/vm/natives/skse_form.rs` on Skyrim, from `crates/scripting/src/form_facts.rs`.

**The classes.** SKSE64's `PapyrusForm.cpp` casts a form to the component a read needs (`TESFullName`,
`TESWeightForm`, `BGSKeywordForm`, `TESModel`) and answers the empty value ("", 0, None, an empty array, false) for a
class without it. `scripts/extender-catalog.py` writes `docs/data/extenders/skse64-form-types.tsv` from SKSE64's
headers at the pinned commit: each `kFormType` (`GetType`'s number, counted from `kFormType_None = 0`), its record
signature and class, and the four components, followed through each class's base and its `// parents` fields.
For example, an `ARMO` has no `TESModel` (its world models are biped models), so `HasWorldModel` is false on armor;
an `NPC_` has no `TESWeightForm`.

**The values.** `FormFacts` is built from the ESM index at boot (Skyrim only):

- every base record's signature, from the index's `record_types` (placed records and world geometry left out);
- the names, weights, keywords and models the index's records keep: items, soul gems, NPCs (their Use Keywords
  terminal's keywords, as `KeywordTable` reads them), races, locations, containers, activators, head parts (and their
  type), trees, projectiles, grasses, and the names of classes, factions, spells, magic effects, enchantments, quests,
  perks, messages, actor values, eyes, explosions and waters; the placeable bases' models.

**The answers.**

| The form | A read answers |
|---|---|
| a base whose class lacks the component | SKSE's empty value |
| a base whose class has it, and the engine reads it | the record's value |
| a base whose class has it, and the engine does not read it (a door's or furniture's name, a spell's keywords) | stops, naming what is not read |
| a loaded reference | `REFR` (61) or `ACHR` (62), and the empty value for the rest: a reference has none of the components |
| a form the engine has no record of | stops |

`GetNthKeyword` takes a `UInt32` index (a negative one is past the end) and answers None for a null entry;
`GetKeywords` leaves null entries out, as SKSE does.

**Not yet.** `Form.IsPlayable` is a virtual function implemented in the game executable, not in SKSE's source, so
its answer per form type is undocumented: a declared gap. The `Set*` functions (`SetName`, `SetWeight`,
`SetGoldValue`, …) change a form for the session and need save coverage first. The key, control and menu
registrations and `Input`'s key state are §10, the mod events §11; the camera, crosshair, actor-action and NiNode
registrations, `Utility.GetINI*` and `Actor`'s equipment come next.

## 10. Catalog growth: key, control and menu registrations (2026-11-24)

SKSE64's `Form.RegisterForKey` / `UnregisterForKey` / `UnregisterForAllKeys`, the same for controls and menus, and
`Input.IsKeyPressed` / `GetNumKeysPressed` / `GetNthKeyPressed`; F4SE's `ScriptObject.RegisterForKey` /
`RegisterForControl` and their unregisters. The registrations live in `crates/scripting/src/fragment/input_events.rs`;
the host's key state comes from `byroredux/src/mcm_hotkeys.rs`, which the MCM Helper hotkeys share.

**The events** (SKSE64's `PapyrusEvents.cpp`, F4SE's `Hooks_Input.cpp`, at the pinned commits):

| Registration | Event |
|---|---|
| a key code (DirectInput scan code; a mouse button is 256 + its index) | `OnKeyDown(code)` as it goes down, `OnKeyUp(code, holdTime)` as it comes up |
| a control name | `OnControlDown(control)` / `OnControlUp(control, holdTime)` for the control the key is bound to |
| a menu name (SKSE) | `OnMenuOpen(name)` / `OnMenuClose(name)` |

- **Who hears it.** SKSE registers the object's handle, so the event reaches every script attached to the object that
  has the handler, and any of them unregisters it. F4SE registers the calling script, which alone hears it and alone
  unregisters it. Names compare without case.
- **When.** SKSE's input handler queues its events whatever menu is open, so the extenders' key state is not paused as
  MCM Helper's hotkeys are (they keep their own key state). A key the console or an engine overlay took is not seen.
  The events reach an owner while it stands: a running quest or alias, a loaded reference.
- **Saved.** Both extenders' co-saves keep the registrations (`KEYR`, `CTLR`, `MENR`), and a quest stopping does not
  remove them, so `InputEventRegistrations` is saved (format v151).
- **Controls.** A key's control is the one the engine's bindings give it, under SKSE's control names
  (`ActionBindings::papyrus_bindings`, the table `Input.GetMappedControl` reads): keyboard bindings only for now.
- **The menus.** SKSE's menu events come from the menu registry's openings and closings, in the same pass as Fallout 4's
  `OnMenuOpenCloseEvent`.
- **`Input`.** The keys held this frame, in ascending code order (SKSE64's `DIHookControl` walks codes from 0);
  `GetNthKeyPressed` past the end answers -1.

**Not yet.** A registration made on another object (`SomeQuest.RegisterForKey`) is declined. `Input.TapKey`,
`HoldKey` and `ReleaseKey` inject input, which the engine's input layer does not take from scripts yet. Gamepad
buttons and mouse bindings have no control names yet.

## 11. Catalog growth: mod events (2026-11-24)

SKSE64's `Form.RegisterForModEvent(eventName, callbackName)`, `UnregisterForModEvent`, `UnregisterForAllModEvents` and
`SendModEvent(eventName, strArg = "", numArg = 0.0)`, on the script's own object, in
`crates/scripting/src/fragment/mod_events.rs`.

**Behaviour** (SKSE64 at the pinned commit):

- The callback receives `(eventName, strArg, numArg, sender)` for a `SendModEvent` (`Form.psc`), the sender being the
  sending object, and the pushed values for an event built with `ModEvent.Create` / `Push*` / `Send` (`ModEvent.psc`).
- A registration is made on the object's handle with its callback (`PapyrusForm.cpp`): one per object and event, a
  second replaces the callback, and every script attached to the object with that function hears it. Event names
  compare without case.
- The registrations are saved (`MCBR`, saved and loaded back by `InternalSerialization.cpp`; format v152).
  `Form.psc`'s comment says they "have to be refreshed after each game load"; a script that does so registers the same
  thing again.

**One bus.** Mod events travel on the engine's shared bus (`legacy.skse.mod-event.<name>`, `byroredux_sdk::event`), which
the Papyrus provider lane and sandboxed guests already use:

- A VM script's send is published through the provider runtime's publisher under its source's principal
  (`crate::script_sources`, shared with the version probes); the host's dispatch copies every legacy mod event to the
  provider lane and to the VM's inbox, so a VM script, a provider-lane script and a guest hear each other.
- Without an extension host, a send goes to both lanes directly.
- The VM's inbox holds at most 256 events; a load empties it.

**The builder** (`ModEvent.Create` / `PushBool` / `PushInt` / `PushFloat` / `PushString` / `PushForm` / `Send` /
`Release`, `fragment/vm/natives/skse_mod_event.rs`) follows `PapyrusModEvent.cpp`:

- `Create` answers a positive handle (`0` for a name the shared bus cannot carry, which includes the empty name SKSE
  would accept) from one store for the whole session, `VmModEventBuilders`, the SDK's builder table (64 builders,
  128 arguments, a payload bound);
- `Push*` appends a typed argument and ignores a handle that is not live; a form outside the load order is pushed as
  `None`;
- `Send` takes the builder, publishes it under the calling script's source principal and answers true, false for a
  handle that is not live; `Release` drops it; the callback receives the pushed values as its arguments;
- SKSE's object storage is saved (`OBMG`), so the builders are saved (format v153).

**Alias and effect scripts.** Their calls on `Self` take the same path as a quest's: an alias script's registration
rides its alias owner id and its events reach its scripts there. An `ActiveMagicEffect` script passes the same check;
the VM does not run effect scripts yet, so nothing registers from one.

**Another object.** `akReceiver.RegisterForModEvent(event, callback)`, `UnregisterForModEvent` and
`UnregisterForAllModEvents` on a quest, a reference or an alias value (Campfire's shared `FallbackEventEmitter` helper
registers the aliases and references it is handed) register that object, as SKSE's registrations are on the receiver's
handle: its own scripts' callbacks hear the event, the calling script does not. The receiver is the quest's or
reference's form id, or the alias's script owner id; an alias with no scripts of its own has no owner id, nothing
could hear it, and the call changes nothing. A `None` receiver is the usual "called on None" ignore.

**Not yet.** `SendModEvent` on another object is declined. The provider lane keeps its own mod-event registrations
for the session only, following `Form.psc`'s comment rather than SKSE's serialization.

## 12. Catalog growth: `Actor` equipment reads (2026-11-24)

SKSE64's `Actor.GetWornForm`, `GetWornItemId`, `GetEquippedObject`, `GetEquippedItemId` and `IsSwimming`, on Skyrim
(`fragment/vm/natives/skse_actor.rs`), from the actor's worn slots, hands and inventory.

**Behaviour** (`PapyrusActor.cpp`, `HashUtil.cpp` at the pinned commit):

- `GetWornForm(mask)` is the first worn item, in the actor's inventory order, whose biped slots share a bit with the
  mask (`parts & mask != 0`). Only armor and clothes have biped slots, so a weapon never matches. The engine's worn
  slots are bit positions of the same mask, so the worn entries whose bit is in `mask` are the candidates and the
  lowest inventory entry is the first. Skyrim's inventory order is the container's; the engine's is the order items
  arrived, so two items sharing a mask bit can come out the other way round.
- `GetEquippedObject(slot)`: 0 is the left hand, 2 the voice, and any other number the right hand (SKSE tests
  `slot == kSlotID_Left` only). A hand holds a weapon, a shield, a torch or a readied spell, as the engine's hand
  model ([`hands`](../../crates/scripting/src/hands.rs)) reads them.
- `GetEquippedItemId(slot)` and `GetWornItemId(mask)` are `HashItemId(name, formID)`: the CRC-32 of the item's name
  with its register started from the plugin-local object id (24 bits, 12 for a light plugin), which is Python's
  `zlib.crc32(name, id)`. The name is the entry's display name when a mod renamed it (not served) else the base
  name; the id is `0` for an empty hand, a hand holding a spell (no inventory entry), an item the actor does not
  hold, and an item with no name. A name is hashed as the game's single-byte string, so a character past U+00FF is
  hashed as UTF-8 and may differ from SKSE's.
- `IsSwimming` is the character system's walk/swim verdict (`SwimQuery`); without that query the call stops.

**Not served, with the reason:**

| Function | Why |
|---|---|
| `GetEquippedObject(2)`, `GetEquippedItemId(2)` | the equipped shout is not tracked; the call stops |
| `Actor.GetSpellCount`, `GetNthSpell` | SKSE answers `addedSpells`, the spells a script added; the engine's `SpellList` joins the record's, the race's and the added ones, and the added ones cannot be told apart |
| `Actor.IsAIEnabled` | no AI-enabled state exists |
| `Actor.EquipItemEx`, `UnequipItemEx`, `EquipItemById` | they change the actor's equipment; the equip effects exist, but SKSE's slot, prevent-unequip and sound arguments are not modelled |
| `Utility.GetINI*` | a policy decision, not a build: the PRD says the engine does not read game INIs (LMC-SET-001, T5-T7), and the settings a game INI holds default from the executable |
