## Executive Summary

All nine dimensions were walked sequentially in one context with direct source
reads and disprove-first verification, cross-checked against the cached issue
list (`/tmp/audit/issues.json`, 2769 issues / 293 open) and the four most recent
prior ECS reports.

The ECS core itself is in good shape and got materially *better* since the last
pass: `4659cbe0` (#2675) replaced the ABBA detector's depth-1 reverse-edge test
with a DFS reachability probe, so cycles of length ≥3 spread across three
threads are now caught, and the write guard is released before the panic so the
detector no longer poisons its own graph. The soundness argument was re-derived
from scratch (the fast-path early-out cannot hide a cycle, because the slow path
never inserts a cycle-closing edge, so the graph is an invariant DAG) and holds.
Dimensions 1, 3, 4, 5/5b, 6 and 9 produced **zero new findings**; Dimension 2
produced zero new findings beyond three unfiled carry-overs.

The new findings are concentrated in the **extra scope** — the scripting attach
path and the M42.9 ambient-package runtime that landed since the last audit:

* **ECS-2026-08-13-01 (MEDIUM)** — `ambient_ai_package_system`, registered
  unconditionally in `Stage::Update`, deep-clones every ambient actor's
  `AmbientPackageRuntime` (which owns a `Vec<u32>`) *and* takes one storage
  RwLock per actor, **every frame, before its own once-per-in-game-minute
  gate**. Exactly the defect class as the already-accepted-and-fixed #2659.
* **ECS-2026-08-13-02 (MEDIUM)** — the VMAD attach loop dedups by *script name*
  but not by *emitted canonical component*, so two differently-named scripts on
  one REFR that both hit the generic `quest_stage_gate` recognizer silently
  collapse to one — and the survivor is the **base record's** script, inverting
  the REFR-over-base precedence the same function's doc comment promises.

One prior finding was **disproved** this pass rather than inherited:
`ECS-2026-08-10-02` claimed the seven resource-guard sites violate the #2149
defuse-after-wrapper contract. `ResourceRead::new` / `ResourceWrite::new` are
infallible (the downcast lives in `Deref`, not `new`), so nothing can unwind
between `defuse()` and the wrapper — it is a style inconsistency, not a defect,
and is not re-filed.

Two prior findings are confirmed **CLOSED and correctly implemented**:
`ECS-2026-08-10-01` (→ #2659/#2660 — `QuestDefinitionRegistry::clone` is now an

### ECS-2026-08-13-01: `ambient_ai_package_system` deep-clones every ambient actor's package-candidate `Vec` and takes one storage lock per actor, every frame, ahead of its own minute gate
- **Severity**: MEDIUM
- **Dimension**: 8 — Hot-Path Performance Invariants
- **Location**: `byroredux/src/npc_spawn/ai_package.rs:430-457`; registration at `byroredux/src/boot.rs:796`; component at `byroredux/src/components.rs:1230-1239`
- **Status**: NEW
- **Description**: The system's whole point is to be cheap on the ~59 out of 60 in-game seconds where nothing can have changed — `runtime.last_evaluated_game_minute == Some(minute)` is the gate. But the gate is evaluated *per actor, after* the system has already materialised a full clone of every ambient actor's runtime state. `AmbientPackageRuntime` derives `Clone` and owns `package_candidates: Vec<u32>` (one entry per `NPC_.PKID`), so the collect at :436-444 performs one heap allocation per ambient NPC per frame. Then, for each actor, `world.has::<EvaluatePackageRequest>(actor)` at :454 goes through `World::query::<T>()` — a `HashMap<TypeId,_>` probe, a `lock_tracker::TrackedRead` thread-local insert (active in **release** builds, not just debug), an `RwLock::read()`, a vtable downcast, a `contains`, and an untrack — once per actor, instead of one hoisted `QueryRead` reused across the loop. This is the same defect shape as #2659 (`DeferredFragmentEffects::new` deep-cloning the quest registry ahead of the early-bail), which was accepted as a real finding and fixed.
- **Evidence**:
  ```rust
  // ai_package.rs:436-444 — runs unconditionally, every frame
  let runtimes: Vec<(EntityId, AmbientPackageRuntime)> = world
      .query::<AmbientPackageRuntime>()
      .map(|query| query.iter().map(|(actor, runtime)| (actor, runtime.clone())).collect())
      .unwrap_or_default();
  ...
  for (actor, runtime) in runtimes {
      let explicitly_requested = world.has::<EvaluatePackageRequest>(actor);   // :454 — per-actor lock
      if !explicitly_requested && runtime.last_evaluated_game_minute == Some(minute) {
          continue;                                                            // :456 — the gate, too late
      }
  ```
  ```rust
  // components.rs:1230 — the cloned payload
  pub(crate) struct AmbientPackageRuntime {
      pub(crate) package_candidates: Vec<u32>,   // heap
      ...
  }
  ```
  ```rust
  // boot.rs:796 — unconditional, no env gate, exclusive Stage::Update
  scheduler.add_exclusive(Stage::Update, crate::npc_spawn::ambient_ai_package_system);
  ```
- **Impact**: One `Vec<u32>` allocation + one full storage-lock cycle per ambient NPC per frame, forever, on every game. A populated Skyrim/FNV interior or exterior cell carries tens of NPCs; at 60 fps that is thousands of allocations and lock acquisitions per second whose only outcome is `continue`. Unlike the M42 procedure runtimes, this system is **not** behind an env gate, so it is on by default. No correctness impact.
- **Related**: #2659 (same shape, accepted + fixed), #2033 (PERF-D1: "M42 AI-package systems allocate a fresh per-frame decision Vec" — closed, this is a fresh instance of the class), #2652 (the M42.9 feature that introduced it).
- **Suggested Fix**: Hoist a single `QueryRead<EvaluatePackageRequest>` outside the loop and test `.contains(actor)`. Move the minute gate ahead of the clone: iterate the `AmbientPackageRuntime` query in place, collect only `(EntityId, ...)` for actors that actually pass the gate, and clone the candidate list only for those. A persistent scratch `Vec` on a resource (the `FootstepScratch`/#932 pattern) removes the last allocation.

### ECS-2026-08-13-02: Two VMAD scripts on one REFR that recognize to the same canonical component silently overwrite each other — and the base record's script wins, inverting the documented REFR-over-base precedence
- **Severity**: MEDIUM
- **Dimension**: 7 — Component Lifecycles (extra scope: AST→ECS recognizer chain)
- **Location**: `byroredux/src/cell_loader/references/attach.rs:298-305` (the doc claim), `:337-371` (the loop), `:383-403` (`dedup_vmad_scripts`); recognizer spawn closures at `crates/scripting/src/translate/recognizers/quest_stage_gate.rs:111-118` and `two_state_activator.rs:36-46`
- **Status**: NEW
- **Description**: `attach_vmad_scripts` processes the placed reference's own VMAD script list first and the base record's second, and `dedup_vmad_scripts` suppresses the base copy **only when the two share a script *name*** (lowercased). It does not dedup by the *canonical component* the recognizer emits. `quest_stage_gate` is the chain's **generic family** recognizer — by design it matches many differently-named scripts (`defaultSetStageOnActivate`, `defaultSetStageTrigger`, the DA10/MG07/TG05 family, any script whose `OnActivate`/`OnTriggerEnter` reduces to a stage gate). When a REFR's own override script and its base record's script are two different names that both reduce to a stage gate, both are recognized and both spawn closures run against the same entity. Both do `q.insert(entity, component)` into `QuestAdvanceOnActivate` (`SparseSetStorage`, overwrite-in-place), so the **last** insert wins — which is the base record's script, because it is processed second. That is the exact opposite of the precedence the function's own doc comment states three lines above the loop. Nothing is logged when this happens; both attachments log a cheerful `M47.2: recognized …` at debug.
- **Evidence**:
  ```
  // attach.rs:302-305 — the documented contract
  //  Both are attached, mirroring Bethesda's additive
  //  objectReference semantics; on a name collision the REFR's script wins
  //  (it is processed first and the base copy is skipped), so a placement
  //  can override a base script's binding without dropping the rest.
  ```
  ```rust
  // attach.rs:337-371 — REFR-own first, base second, one spawn each, no archetype dedup
  let scripts = dedup_vmad_scripts(refr_script_instance, base_script_instance);
  for (script_instance, script) in scripts {
      ...
      (recognized.spawn)(world, entity);   // :361
  }
  ```
  ```rust
  // attach.rs:390-401 — dedup key is the script NAME only
  let mut seen: HashSet<String> = HashSet::new();
  for script_instance in [refr_script_instance, base_script_instance].into_iter().flatten() {
      for script in &script_instance.scripts {
          if seen.insert(script.name.to_ascii_lowercase()) { out.push((script_instance, script)); }
      }
  }
  ```
  ```rust
  // quest_stage_gate.rs:113-117 — overwrite-in-place, no presence check, no warning
  move |world, entity| {
      if let Some(mut q) = world.query_mut::<QuestAdvanceOnActivate>() { q.insert(entity, component.clone()); }
  }
  ```
  The same shape applies to `two_state_activator.rs:38-45`, which additionally does a **wholesale** `world.insert(entity, variables)` of a freshly-defaulted `ScriptVariables` — replacing, not merging, whatever that entity's `ScriptVariables` already held.
- **Impact**: A Skyrim+ placement that overrides its base activator's quest-advance behavior runs the *base's* quest/stage instead. Silent — no warning, no counter, and the `any = true` return makes the cell loader report a successful attach. Bounded to Skyrim+ content with both a REFR-own and a base-record VMAD (the #1737 additive path), and to script pairs that map to one archetype; the per-script recognizers (`rumble`, `two_state_activator`) are name-gated so they can only collide via the generic recognizer or via a `ScriptVariables` clobber.
- **Related**: #1737 (added the additive REFR+base attach this builds on), #1769 (made the name dedup case-insensitive), #2126 (fragment-dispatch nested-lock safety, same file family).
- **Suggested Fix**: Have `Recognized` carry a stable archetype *kind* discriminant (not the display `String`, which embeds the script name) and make `attach_vmad_scripts` skip a later script whose kind was already attached, logging a `log::warn!` naming both scripts. Alternatively reverse the iteration so the REFR's script is applied last, but the explicit skip is better: it preserves the "additive across *different* archetypes" semantics the doc actually wants.

### ECS-2026-08-13-03: `fragment_activation_flush_system` takes the pending queue before proving the sink exists, dropping the batch on the miss
- **Severity**: LOW
- **Dimension**: 7 — Component Lifecycles (extra scope: scripting runtime)
- **Location**: `crates/scripting/src/fragment.rs:205-222`
- **Status**: NEW
- **Description**: The system `std::mem::take`s `PendingFragmentActivations` (:213) and only then asks for the `ActivateEvent` storage (:215). If `query_mut::<ActivateEvent>()` returns `None`, the taken `(target, activator)` pairs are dropped on the floor with a `log::debug!` that says "skipped" — but the queue has already been emptied, so nothing will retry. Every other take-then-fail path in this crate restores its buffer (e.g. `SkinSlotPool::requeue_pending`, `FootstepScratch`'s restore). **Not live today** — `ActivateEvent` is registered by `byroredux_scripting::register` (lib.rs:100), which every production boot calls — so this is a latent hazard, not an observed loss. The same paragraph applies to the absence of a liveness check on `target`: an entity despawned by a cell unload between the fragment dispatch (frame N) and this flush (frame N+1) gets an `ActivateEvent` row resurrected on a dead ID. That row is harmless (drained at `Stage::Late`) but is worth a `contains`-style guard.
- **Evidence**:
  ```rust
  let pending: Vec<(EntityId, EntityId)> = {
      let Some(mut queue) = world.try_resource_mut::<PendingFragmentActivations>() else { return; };
      if queue.0.is_empty() { return; }
      std::mem::take(&mut queue.0)            // :213 — queue emptied here
  };
  let Some(mut events) = world.query_mut::<crate::ActivateEvent>() else {
      log::debug!("fragment Activate skipped: ActivateEvent component never registered");
      return;                                  // :217 — `pending` dropped, never restored
  };
  ```
- **Impact**: Silent, unrecoverable loss of a fragment-driven activation batch if the sink storage is ever absent. Latent only.
- **Related**: #2654 (introduced `PendingFragmentActivations`), #2394 (the closed `OneShotSound` "marker never cleared on the dispatch failure path" — the mirror-image defect).
- **Suggested Fix**: Acquire the `ActivateEvent` query first and only `mem::take` after it succeeds, or write the pairs back into the resource on the miss.

### ECS-2026-08-13-04: `FactionReputation` has two live CTDA consumers and a runtime-mutation API but no producer and no save-registry entry, outside the #1835 guard's reach
- **Severity**: LOW
- **Dimension**: 7 — Component Lifecycles / CHARAL component shape
- **Location**: `crates/core/src/character/components.rs:100-209`; consumers at `crates/scripting/src/condition.rs:695-730`; guard at `byroredux/src/save_io/round_trip_tests.rs:728-772`
- **Status**: NEW
- **Description**: `FactionReputation` is a fully-built, tested, mutable CHARAL component: `add_fame` / `add_infamy` / `reset` / `standing`, monotonic with a `REPUTATION_AXIS_MAX` clamp.   let Some(rep) = world.get::<FactionReputation>(entity) else { return 0.0; };

  `FactionReputation` is not among them.
- **Impact**: Today: `GetReputation`/`GetReputationThreshold` conditions silently evaluate as if the player has zero reputation with every faction, so any FNV dialogue/quest gate keyed on reputation takes the neutral branch. - **Related**: #1834 (`ActorValues` save-registry gap — the class), #1835 (the structural guard that only covers NPC-spawn stamps), the `charal-fnv-fo3-ruleset.md` reputation spec.
- **Suggested Fix**: Either register `FactionReputation` in `build_save_registry` now (it is flat plain data — `u32` + two `u16` — and delta-safe), or extend the #1835 guard's allowlist model to cover player-scoped CHARAL components so the gap is asserted rather than latent. Separately, open a tracker for the missing REPU producer so the two CTDA arms are not silently inert.

### ECS-2026-08-13-05: `TwoStateTransitionBatch` is a one-frame presentation boundary with zero production readers
- **Severity**: LOW
- **Dimension**: 7 — Component Lifecycles (extra scope: recognizer-emitted components)
- **Location**: `crates/scripting/src/vm_state.rs:69-75` (declaration), `:105-116` and `:164-175` (the two writers), `:120-132` (the drain)
- **Status**: NEW
- **Description**: The type is documented as "One-frame presentation boundary for model animation, collision, and audio." It is registered, written by both `set_two_state_open` and `two_state_activator_system`, and drained at the head of `two_state_activator_system` each tick. Nothing reads it: a repo-wide grep for `TwoStateTransitionBatch` outside `vm_state.rs` returns only the `lib.rs` re-export and a save-registry rationale note. So every `Opened`/`Closed` transition the two-state activator family produces is allocated into a `Vec`, stored, and discarded one frame later without ever reaching model animation, collision, or audio.
- **Evidence**:
  ```
  $ grep -rn "TwoStateTransitionBatch" --include "*.rs" . | grep -v vm_state.rs
  byroredux/src/save_io/registry_completeness_tests.rs:210: ("TwoStateTransitionBatch", "one-shot presentation batch drained every tick; …")
  crates/scripting/src/lib.rs:90:    TwoStateTransitionBatch,
  ```
- **Impact**: No runtime defect — but the door/gate/lever family's open/close transitions produce no animation, collision-state change, or sound, and the type's existence makes it look as though they do. Misleading to the next reader and a per-transition `Vec` allocation for nothing.
- **Related**: #2291 (registered `TwoStateActivator`/`ScriptVariables` for save), #2669 (`two_state_activator::vmad_bool` — OPEN, same family).
- **Suggested Fix**: Either wire the consumer (that is the actual gameplay gap — a door recognized as a two-state activator should swap its animation/collision state) or downgrade the doc comment to say plainly that the sink is unbuilt and reference the tracking issue.

### ECS-2026-08-13-07: `quest_fragment_dispatch_system`'s no-work early-return exits from inside the quest guard scope, bypassing `deferred.apply`
- **Severity**: LOW
- **Dimension**: 5 — System & Scheduler Wiring
- **Location**: `crates/scripting/src/fragment.rs:1535-1537` vs. the sole apply site at `:1585`

### ECS-2026-08-13-08: `SkinnedMesh`'s structural generation in the world-bound propagation key is permanently 0
- **Severity**: LOW
- **Dimension**: 2 — Storage Correctness / 8 — Hot-Path Invariants
- **Location**: `byroredux/src/systems/bounds.rs:136-139`; `crates/core/src/ecs/components/skinned_mesh.rs:203`
- **Status**: NEW (re-confirmed from `AUDIT_ECS_2026-08-10` ECS-2026-08-10-06; never filed)
- **Description**: `make_world_bound_propagation_system` keys its full-rebuild decision on a 4-tuple whose last element is `skin_q.storage().structural_generation()`. `SkinnedMesh` declares `type Storage = SparseSetStorage<Self>` and does **not** override `TRACK_CHANGES`, which defaults to `false`, so `SparseSetStorage::insert`/`remove` never bump `structural_gen` and the accessor returns 0 forever. - **Suggested Fix**: Either set `const TRACK_CHANGES: bool = true;` on `SkinnedMesh` (cheap — sparse tracking is a counter bump) or drop the fourth key element and the sentence that claims it works.
