seven pins), the BA2 exhaustive version match (#811), the BGSM

100.00%**, all `BSVER 130`, matching the #1593 figure and the 08-16

Findings this cycle are three, and the more interesting result is what the leads
*disproved*:

1. **The FO4 WATR decoder is confirmed as the reference implementation** —
   field-for-field correct against xEdit's FO4 definition, all 30 read offsets.
   But the brief's premise that Oblivion, FO3/FNV **and** Skyrim are each
   misaligned by one field is only **one-third true**: FO3/FNV and Skyrim are

4. **#973 (MSWP) is still not fixed** and is now measured at 239,573 affected

**Total findings: 3** — 1 HIGH (a carried, never-fixed CLOSED issue), 2 MEDIUM,

those meshes keep `TextureSlotLayout::default()` = `Skyrim`

| `BSEffectShaderProperty` | 20,360 | 12,135 |

**But the overlay side is where the blast radius actually lives, and on FO4 it

|---|---|---|

`RefrTextureOverlay`'s slot lanes (`glow`, `height`, `specular`, …) are populated

probe shows shipped cells hit it" clause is answered, and the answer is no.

**Conditional worth recording**: if #973's per-shape MSWP consumer is ever

### FO4-D6-2026-08-20-01: FO4's authored water colour-depth ramp is never read, and `fog_near` is hardcoded to zero on every FO4 water body

- **Severity**: MEDIUM
- **Dimension**: 6 (ESM records — FO4 data through the parser)
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:925-935`, `:952-957`
- **Status**: **NEW** (delta-local — the sibling `alpha_controls` capture landed
  in this cycle's `1a428278` "depth-dependent alpha controls"; the colour half
  did not follow)
- **Description**: xEdit's FO4 `WATR.DNAM` `Fog Properties` block authors two
  *pairs* of depth thresholds: a colour ramp (`Color Shallow Range` @12,
  `Color Deep Range` @16) and an alpha ramp (`Alpha Shallow Range` @28,
  `Alpha Deep Range` @32), each scaling the `Depth Amount` @0.
  `decode_dnam_fo4` captures the alpha pair into `alpha_controls[2..4]` and
  ignores the colour pair entirely. Instead it writes
  ```rust
  if let Some(depth_amount) = read_f32_at(data, 0) {
      p.fog_near = 0.0;                        // ← hardcoded, discards @12
      p.fog_far = depth_amount.max(1.0);       //   and @16
  }
  ```
  There is no deferral comment, no `TODO`, and no mention of either field
  anywhere in the tree (`grep -rn "color_deep_range\|Color Deep Range" crates
  byroredux docs` → 0 hits), unlike the several BGSM fields whose absent sinks
  carry explicit "deferred" notes.
- **Evidence**: measured over all 47 vanilla FO4-family `WATR` records with a
  `DNAM`:

  | DNAM offset | xEdit field | distinct values / 47 | read by engine |
  |---|---|---|---|
  | 0 | Depth Amount | 24 | ✔ → `fog_far` |
  | **12** | **Color Shallow Range** | **8** | ✘ |
  | **16** | **Color Deep Range** | **39** | ✘ |
  | 20 | Shallow Alpha | 6 | ✔ |
  | 24 | Deep Alpha | 1 | ✔ |
  | 28 | Alpha Shallow Range | 6 | ✔ |
  | 32 | Alpha Deep Range | 37 | ✔ |

  `Color Deep Range` is the *second most* individually-authored field in the
  whole fog block (39 distinct values across 47 records) — it is not a constant
  the parser can safely default. `fog_near` / `fog_far` are live all the way to
  the shader: `byroredux/src/env_translate.rs:556` → `day_fog_near`/`night_fog_near`
  → `byroredux/src/render/water.rs:187,235,241`, so the zero is not inert.
- **Impact**: Every FO4 water body blends shallow tint → deep tint starting at
  depth 0 and finishing at the full `Depth Amount`, instead of over the authored
  `[depth·shallow_range, depth·deep_range]` band. On the 38 records where
  `Color Shallow Range` is 1.0 the shallow tint should barely appear at all near
  the surface; the engine gives it the widest possible band. Diamond City's
  ponds, the Quannapowitt lake, and every Institute/Vault interior pool are in
  scope. It is MEDIUM, not HIGH: the water still renders and the alpha ramp
  (the more visually dominant of the two) is correct.
- **Related**: `1a428278` (the alpha-controls commit that established the sink
  shape); #2785 (CLOSED — `WaterMaterial::fog_near` travelling the EXAL arm
  unread; it is read now, which is what makes this live).
- **Suggested Fix**: Add a *color_range* `[f32; 2]` lane to `WaterParams` beside
  `alpha_controls` (or widen `alpha_controls` to a named 6-lane struct), read
  offsets 12/16, and set `fog_near = depth_amount * color_shallow_range` /
  `fog_far = depth_amount * color_deep_range` rather than `0.0 / depth_amount`.
  Pin with a fixture asserting a non-zero `fog_near` for an FO4 `DNAM` whose
  offset 12 is < 1.0.

### FO4-D6-2026-08-20-02: the Oblivion WATR decoder swaps the Rain and Displacement simulators' `Starting Size` fields — routed to `/audit-oblivion` / WATAL

- **Severity**: MEDIUM
- **Dimension**: 6 (raised here because this audit was tasked with
  characterising the FO4-as-reference delta; **the defect is not in FO4** and its
  owning audit is `/audit-oblivion` — file it there, not against `/audit-fo4`)
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:521-531`
- **Status**: **NEW**
- **Description**: xEdit `wbDefinitionsTES4.pas` lays TES4 `WATR.DATA` out with
  two five-float simulators: **Rain** at 60 (Force) / 64 / 68 / 72 /
  **76 (Starting Size)**, then **Displacement** at 80 (Force) / 84 / 88 / 92 /
  **96 (Starting Size)**. `decode_data_oblivion` gets the two Force/Velocity
  pairs and both Falloff/Dampner pairs right, then reads the two `Starting Size`
  fields **from each other's block**:
  ```rust
  for (slot, offset) in p.displacement.iter_mut().zip([76, 88, 92]) { … }
  //                                                  ^^ Rain Starting Size
  if let Some(value) = read_f32_at(data, 96) { p.rain_start_size = value.max(0.0); }
  //                                     ^^ Displacement Starting Size
  ```
  The `displacement` field's own doc says "starting size, radial falloff, and
  dampener" — so the intent is unambiguous and the offset is simply wrong.
  For comparison the FO3/FNV sibling twenty lines up reads `[72, 84, 88]` +
  `rain_start_size ← 92`, which **is** correct for its layout, and the FO4
  reference reads `[92, 84, 88]`, also correct.
- **Evidence**: measured over all 17 long (102-byte) vanilla `Oblivion.esm`
  `WATR.DATA` records — offsets 60..96 reproduce xEdit's declared defaults
  exactly, so the labelling is not in doubt:

  | offset | xEdit field | value on 17/17 records |
  |---|---|---|
  | 60/64/68/72 | Rain Force / Vel / Falloff / Dampner | 0.1 / 0.6 / 0.985 / 2.0 (majority) |
  | **76** | **Rain Starting Size** | **0.01** (16/17) |
  | 80/84/88/92 | Disp Force / Vel / Falloff / Dampner | 0.4 / 0.6 / 0.985 / 10.0 |
  | **96** | **Displacement Starting Size** | **0.05** (17/17) |

  So on every vanilla Oblivion water type the engine currently stores
  `displacement[0] = 0.01` (should be `0.05` — 5× too small) and
  `rain_start_size = 0.05` (should be `0.01` — 5× too large).
- **Impact**: Oblivion-only. Both values reach the canonical `WaterMaterial`, so
  every Oblivion water surface gets a ripple starting size five times smaller
  than authored and a rain ripple five times larger. Contained (two scalars, one
  game), hence MEDIUM rather than HIGH.
- **Related**: Lead A above (the FO4/FO76/FNV/Skyrim decoders in the same file
  are all correct — do **not** "fix" them to match); WATAL (`docs/engine/watal.md`).
- **Suggested Fix**: `zip([96, 88, 92])` and `rain_start_size ← 76`. Pin with a
  fixture built from the xEdit defaults so the two 0.01/0.05 constants can never
  cross again.

## Disproved candidates (investigated, then withdrawn)

Recorded so they are not re-derived next sweep:

1. **"The FO3/FNV and Skyrim WATR decoders are misaligned by one field in the
   rain/displacement block."** False for both. Verified against
   `wbDefinitionsFNV.pas` / `wbDefinitionsTES5.pas` *and* corroborated on shipped
   bytes (`FalloutNV.esm` 72..92 = `[0.01, 0.4, 0.6, 0.985, 10.0, 0.05]`;
   `Skyrim.esm` 56..68 constant at the vestigial rain defaults with 72..88
   authored). Only Oblivion diverges — FO4-D6-02.
2. **"FO4 effect-shader meshes with REFR texture overrides are common, so
   NIFAL-D8-01 should escalate to HIGH."** False on vanilla data: 35 REFRs total
   across every master, because `XATO` and `XTXR` are **zero** on FO4 and `XTNM`
   is 52. See Lead B, including the ~18,000-REFR conditional if #973 lands first.
3. **"The FO4 CHARAL Health formula is `80 + 5·END + (L−1)·(2.5 + END/10)`."**
   Rejected as an unsourced recollection. The project's own capture
   (`docs/engine/charal-fo4-ruleset.md`, triple-confirmed against two source
   pages and a worked example) locks
   `77.5 + 4.5·END + 2.5·L + 0.5·L·END`, and the code matches it exactly.
   No finding.
4. **"`derive_stored_actor_values` pushing DNAM after PRPS is a duplicate-key
   bug."** Investigated: `ActorValues::from_pairs` is documented last-wins, and
   on the 2,490 vanilla FO4 NPCs where the two disagree, PRPS carries the
   unscaled base and DNAM the level-scaled spawn value. Last-wins is the correct
   winner. No finding.
5. **"FO4 uses `XATO`/`XTXR` like Skyrim, so the alt-texture path is hot."**
   Zero occurrences across all seven vanilla masters. FO4's channel is `XMSP`.
6. **"BA2 entries can't be enumerated without the engine, so the UI menu corpus
   question is unanswerable."** False — the `/audit-ui` blocker was a
   double-compression artifact (BA2 zlib + SWF `CWS` zlib), not a capability
   limit. See Lead D.
