## Cross-referenced finding

### FO4-2026-08-24-D6-01: FO4 `WATR.DNAM` above-water fog near/far collapse to ~1–2 world units on every vanilla water body — cross-references ESM-2026-08-24-D5-01

- **Severity**: HIGH
- **Dimension**: 6 (ESM records — FO4 data through the parser) ∩ WATAL render sink
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:1068-1088` (`decode_dnam_fo4`)
- **Status**: **Existing: ESM-2026-08-24-D5-01** (filed today in
  `docs/audits/AUDIT_ESM_2026-08-24.md`, HIGH). Not re-filed. This entry adds
  FO4-specific gameplay-impact detail and an independent full-corpus
  verification the ESM audit's dimension scope did not need to produce.
- **Description**: Commit `7f752c0c` ("separate creation depth amount from
  fog") correctly fixed `decode_dnam_fo76` / `decode_dnam_starfield` to stop
  overwriting the canonical `fog_near`/`fog_far` defaults (80.0/600.0) with
  `depth_amount` (DNAM offset 0), instead carrying `depth_amount`
  independently. The FO4 arm in the same commit took a different, unverified
  path: it kept the `fog_near = 0.0 / fog_far = depth_amount` assignment from
  before, then added two brand-new reads claiming offsets 12/16 are "the
  authored above-water color-ramp near/far distances":
  ```rust
  if let Some(near) = read_f32_at(data, 12) {
      p.fog_near = near;
  }
  if let Some(far) = read_f32_at(data, 16) {
      p.fog_far = far.max(p.fog_near + 1.0);
  }
  ```
  No commit message, comment, or real-data check backs this claim; the only
  test that exercises the offsets is the synthetic fixture
  `parse_watr_decodes_fo4_visual_data_layout` (`water.rs:2072-2073`), which
  writes `86.0`/`580.0` at those offsets and asserts they read back
  unchanged — a tautology that cannot falsify the offset claim it encodes,
  the same defect class the 2026-08-20 report flagged for the sibling FO76
  fixture (`ESM-2026-08-20-D5-03`).
- **Evidence** (independently reproduced this session — full corpus, not a
  sample): a from-scratch GRUP walker + zlib-record decompressor read all 42
  `Fallout4.esm` `WATR` records with a `DNAM` sub-record. Offset 0
  (`depth_amount`, the field vanilla actually authors per-water) ranges
  18–8192 world units across the corpus, i.e. it *is* a plausible fog-ramp
  driver. Offsets 12 and 16 do not correlate with it at all:

  | Stat (offset 12 / "fog_near") | Stat (offset 16 / "fog_far") |
  |---|---|
  | 38/42 records read exactly `1.0000` | ranges `0.3000`–`0.9683`, no record ≥ `1.0` |
  | remaining 4 read `0.6000`, `0.9700`, `0.9791`, `0.9835`, `0.9942` | no record exceeds offset 12's value |
  | `ExtOceanWater` (depth 3007): `1.0000` | `ExtOceanWater`: `0.9299` |
  | `IntTroughWater` (depth 18): `1.0000` | `IntTroughWater`: `0.9275` |

  Because offset 16 is *always* smaller than `offset12 + 1.0` across every
  vanilla record sampled, `p.fog_far = far.max(p.fog_near + 1.0)` **never
  reads through** — it always resolves to the fabricated
  `fog_near + 1.0` (≈ `2.0`), a value present nowhere in the source bytes.
  Effectively every FO4 water body decodes to
  `fog_near ≈ 1.0, fog_far ≈ 2.0`, independent of the water's authored
  `depth_amount`, size, or type (interior pond vs. the 3007-unit exterior
  ocean read identically).
- **Impact (FO4-specific gameplay detail, beyond the ESM audit's scope)**:
  the sink chain is direct and unconditional —
  `byroredux/src/env_translate.rs:527-528` copies `params.fog_near`/`fog_far`
  verbatim into `WaterMaterial`, both `day_*` and `night_*` variants
  (`:576-582`, so there is no time-of-day escape), and
  `crates/renderer/shaders/water.frag:464-473` uses the pair as the literal
  clear-to-`deep_color` span (`t = clamp((hitDist - fogNear) / span, 0, 1)`
  with `span = max(fogFar - fogNear, 1.0)`). At `fog_near≈1.0, fog_far≈2.0`
  every FO4 water surface reaches full `deep_color` within ~1 world unit of
  view depth — i.e., **at any viewing angle other than looking straight down
  from just above the surface, the water renders as flat opaque
  `deep_color` with no visible depth gradient at all.** This affects every
  named water body in the game: Diamond City's moat, the Charles River, the
  Glowing Sea's irradiated lakes, Sanctuary's creek, every Vault/Institute
  interior pool, and the exterior ocean itself (`ExtOceanWater`, the game's
  single largest water body). It is a strict regression from the
  pre-`7f752c0c` state, where `fog_far = depth_amount` at least produced a
  per-water, hundreds-to-thousands-unit ramp (even though that pre-fix state
  was itself imprecise, per the commit's own stated intent). The alpha ramp
  (`alpha_controls`, DNAM 20/24/28/32) is unaffected and continues to blend
  correctly — this is specifically the RGB depth-fog term, not overall water
  transparency.
- **Related**: ESM-2026-08-24-D5-01 (primary filing, includes the FO76/
  Starfield-correct comparison and suggested fix); `1a428278` (established
  the `alpha_controls` sink shape this commit's sibling change should have
  followed for offsets 12/16 too, i.e. leave them unread and undocumented
  rather than guess); FO4-D6-2026-08-20-01 (superseded — the 2026-08-20
  report's finding was that offsets 12/16 were *unread*; `7f752c0c` changed
  that to *misread*, which is worse: the pre-fix state rendered a real,
  if imprecise, per-water ramp via `depth_amount`, the current state renders
  a near-constant ~1-unit ramp on every water body regardless of authoring).
- **Suggested Fix**: as filed in `ESM-2026-08-24-D5-01` — delete the two
  reads at offsets 12/16 from `decode_dnam_fo4`, letting `fog_near`/
  `fog_far` fall back to `WaterParams::default()` (80.0/600.0) exactly like
  the FO76/Starfield arms in the same commit, and restore
  `parse_rate_fo4_esm`'s assertions to match. `depth_amount` is already
  correctly decoded and available (`p.depth_amount`) for a future,
  verified FO4-specific fog treatment — offsets 12/16 are ruled out by the
  byte evidence above as that treatment's source.

## Dimension 2 — BGSM/BGEM consumption: #973 verified fixed

The 2026-08-20 report's sole finding (`FO4-D2-2026-08-20-01`, HIGH — the
resolved MSWP substitution table had zero production consumers beyond the
single eager `material_path` swap) is **fixed** as of `900aa081` (2026-08-23,
one day before this audit). Read end-to-end, not assumed from the commit
message:

- `RefrTextureOverlay` gained `material_swaps_filter` (`refr.rs:88-95`) so
  the source `MSWP`'s `FNAM` path-prefix filter travels alongside
  `material_swaps` instead of being applied only once at the REFR level.
- `resolve_mesh_paths` (`cell_loader/spawn/mesh_instance.rs:44-105`) now
  re-evaluates the filter and the swap table against **each shape's own**
  `material_path`, not the overlay's single shared one — the exact gap the
  prior audit described ("every other shape in a multi-shape mesh... kept
  its NIF-authored material untouched").
- When a shape's own path actually changes under the swap, a shape-scoped
  clone of the overlay re-walks the swapped target's BGSM/BGEM chain via
  `RefrTextureOverlay::fill_from_bgsm` (widened `pub(crate)` for exactly this
  reuse), so the shape's texture *slots* update, not just the `material_path`
  string used for diagnostics.
- Precedence is preserved correctly: the shape-scoped overlay is cloned
  *from* the REFR-level overlay, so any slot an `XATO`/`XTNM`/`XTXR` already
  populated stays put (`fill_from_bgsm`'s first-empty-wins fill never
  overwrites a non-empty slot) — the fix does not regress the REFR-level
  override precedence the 2026-08-16 slot→role work established.
- `mat_provider: Option<&mut MaterialProvider>` is threaded through
  `spawn_placed_instances` → its two callers (`spawn_synth_child`,
  precombined's equivalent path) — the precombined path always passes
  `refr_overlay = None`, so the per-shape logic is correctly a no-op there
  (precombines have no REFR-level MSWP; this matches the M49 pipeline's own
  material provenance, which comes from the owning REFR's shape-slot
  indices, not a swap table).
- Two new regression tests directly exercise the previously-broken case
  (`mswp_swaps_apply_per_shape_not_just_the_overlay_material_path`,
  `mswp_filter_is_re_evaluated_per_shape`), both asserting per-shape,
  per-source-path independence.

`cargo check -p byroredux` is clean at HEAD with this change present.
**No finding** — this is a real fix, correctly scoped and tested, and should
be treated as shipped going forward (the way the 2026-08-20 report treated
the CSG pipeline). Suggest closing #973 as fixed rather than carrying it into
the next FO4 audit cycle.

Otherwise Dimension 2 is unchanged from 2026-08-20: `bgsm_metalness`
(`byroredux/src/asset_provider/material.rs:255-268`) still branches
`pbr → luminance` / `non-pbr → saturation (max−min)/max` (#1476 holds);
`bgsm_blend_to_gamebryo` (`:903-905`) is still a bare `raw as u8` identity
narrowing (#1823 holds); `merge_external_material` (`:1001-1005`) still takes
`&mut ImportedMaterial`, not `&mut ImportedMesh` (the `05d68926` boundary
narrowing holds).
