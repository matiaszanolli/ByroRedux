## Findings

### ECS-2026-10-31-01: `improve_plan` reads `ItemInstancePool` under the `Inventory` guard
- **Severity**: HIGH (ECS deadlock potential; reddens the bin detector lane, so CI `ABBA lock-order detector` fails on every `main` run)
- **Dimension**: 1 Lock Ordering
- **Location**: `byroredux/src/crafting.rs:222-236` (`improve_plan`: `let inventory = world.get::<Inventory>(player)?` at :226 stays live through the `.map(|(stack, row)| (stack, stack_quality(world, row)))` at :232, and `stack_quality` (:205-210) takes `try_resource::<ItemInstancePool>()`). The test helper `quality_of` (`crafting.rs:768-771`) has the same shape.
- **Status**: NEW (introduced by 2c55546f4 "improving items at the grindstone and armor workbench", 2026-10-30; reached from `recipes_at`, `improve_item` and the bench page)
- **Description**: This records the edge `Inventory -> ItemInstancePool`. The rest of the engine takes the pool first: `validate_inventory_instances` (`crates/save/src/validate.rs:496`, with a source pin at :901 that says "resource before storage"), and the `capture` probes in `cell_loader/reference_state.rs` (:231, #4982). The scratch test at `reference_state.rs:1677` also pins `ItemInstancePool -> Inventory`. The two orders close an `ItemInstancePool -> Inventory -> ItemInstancePool` cycle. The same commit added three more `Inventory`-then-pool readers that are safe because they copy the stack out first (`inventory/actions.rs:601`, `armor.rs:150` after the clone at :134, `inventory/actions.rs:16` after the clone at :13). `improve_plan` is the one that keeps the guard.
- **Evidence**: `BYRO_LOCK_ORDER_CHECK=1 cargo test -p byroredux --bin byroredux` panics in `crafting::tests::improving_raises_a_held_item_in_place_and_never_hands_out_a_copy`: "attempted acquisition of `ItemInstancePool` while holding `Inventory` ... `ItemInstancePool` -> `Inventory` -> `ItemInstancePool`". Running that test alone passes, because the opposite edge comes from other tests. `cargo test ... -- crafting:: reference_state` reproduces it with a backtrace through `stack_quality` from `quality_of`. The CI log at `8985a2e99` shows the same single cycle.
- **Impact**: The bench action runs on the main thread today, so no live deadlock is reachable. But the process-wide graph now holds a real production inversion against the save path, and while the lane stays red it hides the next one (the 10-27 lesson).
- **Suggested Fix**: In `improve_plan`, clone the matching rows (`base_form_id`, `count`, `instance`) into a `Vec`, drop the `Inventory` guard, and then resolve quality for each row. The same pattern is used in `armor::totals`. Do the same in `quality_of` (copy the row first, then call `stack_quality`).

### ECS-2026-10-31-02: `mine_system` is a `HitEvent` producer outside the ordering pin
- **Severity**: LOW (no live bug; a guard gap)
- **Dimension**: 5 System & Scheduler Wiring
- **Location**: `byroredux/src/systems/mines.rs:280-297` (the `HitEvent` insert in `detonate`); registration `byroredux/src/boot/schedule/update/quest_scene.rs:19`; the pin `hit_event_consumers_run_after_every_producer` at `byroredux/src/boot/schedule/mod.rs:116-150`
- **Status**: NEW (c36ab4125, placed proximity mines)
- **Description**: `HitEvent` is a one-frame marker that `event_cleanup_system` drains. `mine_system` writes it for every actor in the blast. Today it sits correctly in the `quest_scene` segment, which runs before `script_runtime` (`hit_event_system`, `reference_script_hit_system`, `obscript_hit_system`) and `player_animation` (`combat_damage_system`). The pin's producer list (`pending_trap_hit_flush_system`, the two script-event systems, `projectile_flight_system`, `combat_input_system`, `make_npc_combat_ai_system`) does not name it, so moving the segment or the system would silently stop mine damage landing. The skill's rule is: "A new producer outside that list needs a name in the test."
- **Impact**: None today. A reorder of the Update segments would fail no test.
- **Suggested Fix**: Add `"crate::systems::mines::mine_system"` to the producer array. Note for the same change: `detonate` uses `events.insert`, which overwrites a `HitEvent` already on that target in the same frame (a melee hit and a blast on one actor). That matches the other producers' one-slot model, so it is a design note and not a defect.
