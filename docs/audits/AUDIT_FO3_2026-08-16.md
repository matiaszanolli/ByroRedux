#### FO3-D4-01: `PLAYER_BASE_FORM_ID = 0x14` matches no `NPC_` record in any game — the player spawns with no inventory, no armor and no weapon
- **Severity**: HIGH
- **Dimension**: FO3 Cell Loading End-to-End (Dim 4) — un-owned P2 gameplay slice
- **Location**: `byroredux/src/inventory.rs:17` (constant), `:119-121` (`build_player_template` early return), `:242-252` (`attach_to_player`), `:476` (the test that cements it)
- **Status**: NEW
- **Description**: `const PLAYER_BASE_FORM_ID: u32 = 0x0000_0014;` is used as the
  key into `EsmIndex::npcs` to build the player's starting loadout. `0x00000014`
  is `PlayerRef` — an **ACHR reference**, not a base record. The Player `NPC_`
  base record is `0x00000007` in every title in the lineage. The lookup therefore
  always misses, `build_player_template` returns
  `PlayerInventoryTemplate::default()`, and `attach_to_player` stamps an empty
  `Inventory`, an empty `EquipmentSlots`, and never inserts `EquippedWeapon`.
- **Evidence**: probed the live index for both candidate FormIDs across four
  vanilla masters:
  ```
  Fallout3.esm    0x00000007: npcs=Some("Player")   0x00000014: npcs=None
  FalloutNV.esm   0x00000007: npcs=Some("Player")   0x00000014: npcs=None
  Skyrim.esm      0x00000007: npcs=Some("Player")   0x00000014: npcs=None
  Fallout4.esm    0x00000007: npcs=Some("Player")   0x00000014: npcs=None
  ```
  `inventory.rs:120` — `let Some(player) = index.npcs.get(&PLAYER_BASE_FORM_ID)
  else { return PlayerInventoryTemplate::default(); };`
  The guarding test `player_template_uses_authored_inventory_and_equipment_slots`
  (`inventory.rs:476`) constructs a synthetic `EsmIndex` and inserts its NPC at
  `PLAYER_BASE_FORM_ID`, so it passes no matter what the constant is — the test
  can never detect the mismatch.
- **Impact**: On FO3 (and every other title) the player has an empty native
  inventory menu, no equipped armor, and no `EquippedWeapon` — combat falls back
  to `UNARMED_DAMAGE = 8.0` permanently. The whole authored-loadout pipeline
  (`resolve_inherited_inventory`, `expand_leveled_form_id`, `equip_armor`,
  `prefer_weapon`, the OTFT path) is dead code at runtime. Not FO3-exclusive, but
  it is on the FO3 cell-load path and blocks the corpse-loot / equip half of the
  P2 vertical slice.
- **Related**: none open (searched `/tmp/audit/issues.json` for
  inventory/player/loadout/equip and `docs/audits/` for `PLAYER_BASE_FORM_ID` /
  `0x0000_0014` — no prior coverage). Adjacent: #2956 (CHARAL template-inheritance
  flags).
- **Suggested Fix**: Change the constant to `0x0000_0007` and rename it to match
  (`PLAYER_NPC_FORM_ID`); then change the test fixture to insert at a *different*
  synthetic FormID and assert the production constant resolves against a real
  master in an integration test, so the fixture can no longer launder the value.

#### FO3-D4-02: FO3/FNV ship a complete baked terrain-LOD asset tree that no code path consumes, and `baked_lod_supported`'s doc asserts it doesn't exist
- **Severity**: MEDIUM
- **Dimension**: FO3 Cell Loading End-to-End (Dim 4) — exterior
- **Location**: `byroredux/src/cell_loader/lod_support.rs:35-52` (`baked_lod_supported` + its doc-comment), `byroredux/src/cell_loader/terrain_lod.rs:57-94` (`LOD_TEXTURE_QUAD_CELLS`, `lod_quad_texture_path`), `:752-790` (the two-tier texture priority)
- **Status**: NEW
- **Description**: `baked_lod_supported` returns `true` only for
  `Skyrim | Fallout4`, and its doc-comment states that "Oblivion and FO3/FNV
  predate the scheme and keep the synthesized heightmap ring". That premise is
  factually wrong for FO3 and FNV. Both ship a full baked distant-terrain LOD
  set — meshes *and* diffuse *and* normal textures — indexed by quadtree level
  and quad coordinate exactly as `.btr` is, only under a different naming
  convention (`<world>.level<N>.x<X>.y<Y>` instead of `<world>.<N>.<x>.<y>`).
  Neither `baked_lod_supported` nor `placement_lod_supported` recognises it, and
  `terrain_lod.rs::lod_quad_texture_path` can only build the Oblivion
  `textures\landscapelod\generated\<fid>.<x>.<y>.32.dds` name, so the baked
  lookup at `terrain_lod.rs:764-766` always misses on FO3 and the block falls to
  tier 2 — a synthesized decimated heightmap draped with one tiled BTXT base
  LTEX.
- **Evidence**: archive probes over vanilla content:
  ```
  FO3  Fallout - Meshes.bsa    "landscape\lod"  → 2 232 matches
       e.g. meshes\landscape\lod\wasteland\wasteland.level16.x-32.y-64.nif
  FO3  Fallout - Textures.bsa  "landscape\lod"  → 3 870 matches
       e.g. textures\landscape\lod\wasteland\diffuse\wasteland.n.level4.x-64.y-12.dds
            textures\landscape\lod\wasteland\normals\wasteland.n.level8.x48.y48.dds
  FNV  Fallout - Meshes.bsa    "landscape\lod"  → 2 663 matches
  FNV  Fallout - Textures2.bsa "landscape\lod"  → 4 986 matches
  FO3  "distantlod"                             → 0 matches (confirms #2086)
  ```
  `lod_support.rs:51` — `matches!(game, GameKind::Skyrim | GameKind::Fallout4)`.
- **Impact**: FO3 and FNV exteriors render distant terrain with a single tiled
  ground texture instead of the authored per-quad blended diffuse + normal,
  so distant landmass colour and silhouette diverge visibly from vanilla across
  the whole Capital Wasteland and Mojave. Not a crash and not a regression — the
  synthesized ring is a working fallback — but ~6 100 shipped FO3 assets and
  ~7 600 FNV assets are inert, and the false premise in the doc-comment is what
  keeps anyone from finding it.
- **Related**: #2086 (CLOSED — resolved the *placement*-LOD half correctly, and
  its own evidence noted the `landscape\lod` mesh tree but its suggested
  option (b) was never taken); #2371 (OPEN — broad "complete distant LOD bands"
  umbrella, but scoped to `.btr`/`.bto` bands and does not name this scheme);
  `AUDIT_FO3_2026-07-16.md` FO3-D4-01 flagged the mesh tree only, not the texture
  tree.
- **Suggested Fix**: Add a third per-game predicate next to `baked_lod_supported`
  / `placement_lod_supported` for the Fallout-era `landscape\lod\<world>\` scheme,
  correct the `baked_lod_supported` doc-comment (FO3/FNV *do* bake LOD, just under
  another name), and give `terrain_lod.rs` a second baked-texture path builder
  for `<world>.[n.]level<N>.x<X>.y<Y>.dds` before the tier-2 LTEX fallback.

- `eval.rs::apply_morphs` bounds both loops (`morphs.len().min(weights.len())`,

is resolve-or-skip, so **one shared SkillSet IS correct for both** once the `AV`
prefix is stripped — the union is not the bug, the missing prefix strip is. FO3's
vestigial `AVThrowing` (a cut skill with no GECK skill slot) is correctly omitted
from the union.

**#2941** (FO3 silently receives FNV's leveling model; `fallout3_ruleset` and
`LevelingModel::FO3` unreachable) reconfirmed OPEN — `npc_spawn.rs:188-192`
documents the collapse explicitly, and `GameKind` itself has no FO3 arm
(`crates/plugin/src/esm/reader.rs:96-100` folds FO3 and FNV into `Fallout3NV`).

**Scripting gap** (FO3-distinctive, a known blocker rather than a bug): 1 257
SCPT records parse on `Fallout3.esm`; no runtime executes pre-Papyrus bytecode.
Confirmed current. Owned by `/audit-scripting`, not deep-audited here.

## Disproved candidates (investigated, not reported)

- **`NifVariant::detect` ambiguity on FO3 (#1219, CLOSED "needs sample data").**
  The warning does fire on vanilla FO3 — `meshes\triggers\collisionboxstatic.nif`
  (v20.0.0.4, user_version 11/11) routes to `NifVariant::Oblivion`. Traced the
  consequence: `NifVariant` is consumed at exactly one site
  (`crates/nif/src/lib.rs:86-101`), where it selects a Havok scale constant, and
  `Oblivion` and `Fallout3` both yield 7.0. `bhkRigidBody` CInfo decode is gated
  on the *version* tuple, not the variant. The misroute is provably inert on this
  file — the only cost is one WARN line per corpus sweep. Not filed.
- **`skyrim_slsf1` / `fo3nv_f1` bit-12 semantic collision.** FO3 sets f1 bit 12
  on 1 731 properties (correlating 1:1 with `NiAdditionalGeometryData`), and
  Skyrim's bit 12 is `Model_Space_Normals`. Chased every
  `MODEL_SPACE_NORMALS` test site; the only one reading a NIF shader word is in
  the `BSLightingShaderProperty` arm, which FO3 never enters. No leak.
- **TXST `DNAM` / `DODT` width on FO3.** Suspected an FO4-shaped read; the FO3
  schema is genuinely 2-byte `DNAM` and 36-byte `DODT`, so the shared parse is
  correct.
- **`CLAS DATA` gated at `len() >= 16`.** Suspected an FNV-only offset; FO3's
  CLAS DATA is the same 28-byte layout and only the 4 tag-skill `u32`s are read.
  Correct.
- **`SkillSet::FALLOUT_FO3_FNV` being a union.** Initially looked like a
  correctness problem per CHAR-D2-02; resolve-or-skip against per-game AVIF sets
  makes the union right for both titles. Recorded in Dimension 7 as a partial
  disproof rather than a finding.
