### ECS-2026-08-10-01: `#2539`'s quest-lifecycle lock fix deep-clones the entire `QuestDefinitionRegistry` every frame, before the dispatch system's own early-out — independently found by three dimensions
- **Severity**: MEDIUM
- **Dimension**: 1 (Lock Ordering), 4 (Resource Lifetimes), 5 (System & Scheduler Wiring) — merged
- **Location**: `crates/scripting/src/fragment.rs:336-345` (`DeferredFragmentEffects::new`), call site `crates/scripting/src/fragment.rs:1334` inside `quest_fragment_dispatch_system`, early-out it precedes at `crates/scripting/src/fragment.rs:1372-1374`; registration at `byroredux/src/boot.rs:718` (`scheduler.add_exclusive(Stage::Update, quest_fragment_dispatch)`, unconditional)
- **Status**: NEW (introduced by `6ad64ef6`, which closed #2539)
- **Description**: `#2539`'s fix removed the nested `QuestStageState → QuestDefinitionRegistry` lock acquisition by snapshotting the registry into `DeferredFragmentEffects` *before* the quest guards are taken — the lock-ordering intent is correct and verified sound. The chosen isolation mechanism is a **full deep clone** of `HashMap<QuestFormId, QuestDefinition>`, where each `QuestDefinition` owns two `String`s, three `Vec`s, and two `HashMap`s (`stage_logs: HashMap<u16, Vec<QuestStageLogEntry>>`, each entry carrying authored journal `text`/`note` strings plus a `ConditionList`; `objective_records: HashMap<i32, QuestObjective>` similarly). `install_start_game_quests` inserts *every* parsed QUST record, not only Start-Game-Enabled ones, so on a Skyrim/FO4-class load order this is hundreds of quests and thousands of strings. `quest_fragment_dispatch_system` constructs this clone unconditionally at line `:1334`, **38 lines before** its own `if queue.is_empty() || frags.is_empty() { return; }` early-out at `:1372` — the path taken on essentially every frame, since a pending quest-stage transition is rare relative to 60 Hz. `save_io.rs:1984` documents the registry as "populated once from parsed QUST records, only ever read afterward" — the clone defends against a mutation that structurally cannot happen. Only five cheap accessors are ever read off the snapshot. The sibling `fragment_continuation_system` gets this right: its identical constructor call (`:1103`) sits *after* its own early-out (`:1098`), which is what makes `quest_fragment_dispatch_system` the outlier, not the pattern.
- **Evidence**:
  ```rust
  // crates/scripting/src/fragment.rs:337-345
  pub fn new(world: &World) -> Self {
      Self {
          quest_definitions: world
              .try_resource::<crate::QuestDefinitionRegistry>()
              .map(|definitions| definitions.clone()),   // ← full deep clone
          ...
  ```
  ```rust
  // crates/scripting/src/fragment.rs:1331-1374 — dispatch system, per frame
  let frags = world.resource::<QuestStageFragments>().clone();
  let mut chained: Vec<QuestStageAdvanced> = Vec::new();
  let mut deferred = DeferredFragmentEffects::new(world);   // :1334 — unconditional
  ...
  let (mut stages, mut objectives) = world.resource_2_mut::<QuestStageState, QuestObjectiveState>();
  ...
      if queue.is_empty() || frags.is_empty() {
          return;                                          // :1372-1374 — the common path
      }
  ```
  Contrast the correctly-placed sibling at `fragment.rs:1098-1103`.
- **Impact**: Thousands of heap allocations plus hundreds of KB of `String`/`Vec`/`HashMap` copying per frame on any Skyrim/FO4-class load order, on the serial `Stage::Update` exclusive lane, on frames that do zero fragment work — unhidden by parallelism, invisible to `cargo test` (fragment tests build ~1-quest worlds), and scaling with load-order size rather than scene complexity. Not a leak (dropped at end of frame) and not a deadlock — MEDIUM rather than HIGH — but a CPU-side regression on a project where "CPU bottleneck = bug", landing hardest on the exact configuration (`--scripts-bsa` + a full-size ESM) the M47 scripting milestone targets.
- **Related**: `#2539` (closed by `6ad64ef6`, the commit that introduced this), `#2269`/`dc9ba0e5` (the sibling defer fix, which added no per-frame cost), `#2388`/ECS-D1-06 (the wider "exclusive scheduling is the only thing making these orders safe" family), ECS-2026-08-10-03 below (a distinct LOW consequence of the same two lines — the early-return also silently drops the deferred batch un-applied).
- **Suggested Fix**: Hoist the `queue.is_empty() || frags.is_empty()` early-out above the `DeferredFragmentEffects::new` call (cheapest, one-line — requires moving the `resource_2_mut` scope), or make the snapshot an `Arc<QuestDefinitionRegistry>` clone instead of a deep clone — the registry is write-once at load, so an `Arc::clone` preserves the `#2539` lock-isolation guarantee at O(1) cost with no call-site reordering needed.

### ECS-2026-08-10-02: The seven resource-guard acquisition sites defuse the tracker scope *before* constructing the wrapper — the inverse of the `#2149` contract the query paths follow
- **Severity**: LOW
- **Dimension**: 1 (Lock Ordering), 3 (Query Borrow Safety) — merged, independently found
- **Location**: `crates/core/src/ecs/world.rs:681-686` (`resource`), `:710-715` (`resource_mut`), `:761-791` (`resource_2_mut`, both branches), `:808-813` (`try_resource`), `:828-833` (`try_resource_mut`); contrast the correct query-side form at `:444-454`/`:470-482`; regression test at `crates/core/src/ecs/world_tests.rs:1557-1614`
- **Status**: NEW
- **Description**: `#2149` established that a `lock_tracker` scope must only be defused *after* the guard-owning wrapper exists — the wrapper's `Drop` is the sole untrack path, so defusing first orphans the thread-local row if construction panics between the two. All six *query* sites follow this. All seven *resource* sites do the opposite: `scope.defuse();` then construct the wrapper. This is **safe today only by coincidence**: `ResourceRead::new`/`ResourceWrite::new` are plain infallible struct moves, because unlike the `#1367`-treated query wrappers, resource wrappers still defer their `downcast_ref().expect(...)` to `Deref`, which runs after the wrapper already owns the tracker row. The `#2149` regression test hard-codes only the four `query*` function names, so it cannot see a resource-side violation, and the `ResourceRead::new`/`ResourceWrite::new` doc comments are copied verbatim from the query wrappers without noting the different fallibility contract. `resource_2_mut` is the sharpest shape: **both** scopes are defused, then two `ResourceWrite::new` calls run inside one tuple expression — if the second could ever panic, the first temporary's `Drop` would untrack `id_a` while `id_b`'s row is owned by nobody.
- **Evidence**:
  ```rust
  // world.rs:681-686 — resource(): defuse BEFORE the wrapper exists
  let scope = lock_tracker::TrackedRead::new(type_id, std::any::type_name::<R>());
  let guard = lock.read().unwrap_or_else(|_| resource_lock_poisoned::<R>());
  scope.defuse();
  ResourceRead::new(guard, type_id)
  ```
  ```rust
  // world.rs:452-454 — query(): the #2149-fixed ordering, wrapper first
  let query = QueryRead::new(guard, type_id);
  scope.defuse();
  ```
- **Impact**: No live defect — zero runtime consequence on current code, since neither resource wrapper constructor can panic today. The cost is a latent regression trap: extending `#1367`'s "cache the downcast in `new()`" optimization to resources is an obvious next perf step (`ResourceRead::Deref` still pays a vtable downcast on every deref, including hot-path resources like `DeltaTime`/`TotalTime`), and the moment that lands, all seven sites silently become the `#2149` bug simultaneously — an orphaned tracker row producing a spurious "ECS deadlock detected" panic on the next acquisition after any `catch_unwind` (rayon's per-task catch, the debug server) — with the existing regression test staying green throughout.
- **Related**: `#2149` (CLOSED — established the invariant for queries only), `#137` (CLOSED — the original orphaned-row failure mode this guards against), `#1367` (the cached-downcast optimization whose future extension is the trigger), `#2384`/ECS-D1-03 (the other known way a tracker row is orphaned, via an ABBA panic).
- **Suggested Fix**: Reorder all seven sites to construct the wrapper before calling `scope.defuse()`, matching the query sites, and extend `defuse_follows_wrapper_construction_at_every_query_site` to also walk `pub fn resource<`, `resource_mut<`, `try_resource<`, `try_resource_mut<`, and both branches of `resource_2_mut<`.

### ECS-2026-08-10-09: `PackedStorage`'s batch paths cost more than their docs promise — no disjointness early-out on removal, whole-array re-sort on insert, and a capacity-retention correction to `#2395`
- **Severity**: LOW
- **Dimension**: 2 — Storage Correctness (batch paths / documented complexity)
