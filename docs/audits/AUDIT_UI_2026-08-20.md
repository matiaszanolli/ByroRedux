### The carry-over the dispatch named: `KNOWN_MISSING_ON_DESTROY_TRAIT`

**Verified fixed at HEAD.** `7a97b423` (#2963) removed the exclusion list
entirely — `grep -rn KNOWN_MISSING_ON_DESTROY_TRAIT crates/ byroredux/`
returns nothing, and `still_missing_on_destroy` is gone too. The lifecycle-class
predicate in `crates/ui/src/avm2_host.rs`:80-99 now requires only
`[object.property, object.on_create]`, so `DialogueMenu`,
`MultiActivateMenu`, `SPECIALMenu` and `Terminal` **do** inject at HEAD. The
sweep test `all_installed_fallout4_swfs_round_trip_through_injection` no
longer excludes anything. That fix is real and the green gate is now honest.

**But the fix traded a hard failure for a silent one**, which is UI-D3-03
below: the movie's `has_destroy_trait` never leaves
`inject_host_object_adapter`, so those four menus report
`ScaleformHostObjectState::AdapterInjected` while their destroy lifecycle is
absent, with no log line, no state variant and no accessor. The counter
`docs/engine/ui.md` calls the evidence that the lifecycle completed stays at
zero for them forever, indistinguishable from a destroy hook that fired and
failed.

#### UI-D5-02: the archive-backed menu-load path has no engine consumer — the shipped binary cannot open any vanilla Bethesda menu

- **Severity**: HIGH
- **Dimension**: Resource Navigator
- **Profile**: both
- **Location**: `crates/ui/src/lib.rs`:86-102 · `crates/ui/src/player.rs`:203-266 · `crates/ui/src/navigator.rs` (all 911 lines) · `byroredux/src/scene.rs`:1330-1356
- **Status**: NEW
- **Description**: `UiManager::load_swf_from_resource_provider`,
  `SwfPlayer::from_resource_provider`, the whole `navigator.rs` module and the
  `ScaleformResourceProvider` impls for `BsaArchive`/`Ba2Archive` are reachable
  **only from tests**. The single engine construction site is
  `byroredux/src/scene.rs`:1330, behind `--swf`, and it does
  `std::fs::read(swf_path)` → `UiManager::load_swf` → `SwfPlayer::new`, which
  passes `navigator: None`. Every vanilla Bethesda menu ships inside a
  BSA/BA2, so no vanilla menu can be opened by the engine as built.
- **Evidence**:
  ```
  $ grep -rn "load_swf_from_resource_provider\|load_swf_with_profile\|\
    UiManager::close\|set_input_focus\|invoke_callback" byroredux/src/
  (no output)
  $ grep -rn "UiManager::new\|load_swf" byroredux/src/
  byroredux/src/scene.rs:1333:   let mut ui = UiManager::new(w, h);
  byroredux/src/scene.rs:1334:   match ui.load_swf(&swf_data, swf_path) {
  ```
  `player.rs`:288-303 — `navigator_runtime` is `Some` only when
  `from_movie` is handed a navigator, which only `from_resource_provider` does.
  The docs assert the opposite: `docs/engine/ui.md`:39 lists "BSA/BA2-relative
  `ImportAssets` loading" under **Status**, and its Pending row (line 40) does
  not mention archive loading. `ROADMAP.md`:759 likewise presents the navigator
  as delivered and lists only "method behavior, `_global.gfx` stubs, font
  fidelity/menu lifecycle, Papyrus/ECS ↔ UI callbacks" as remaining.
- **Impact**: The entire Dimension-5 investment — #2720's degrade-to-placeholder
  path, #2734's lazy futures, #2967's dedup/cap, the URL confinement — is dead
  code in the shipped binary. Consequently every runtime claim about vanilla
  menus rests on `#[ignore]`d or self-skipping tests. The obvious workaround
  (hand-extract a `.swf` and pass `--swf`) is fragile in exactly the way the
  severity file means: `hudmenu.swf` imports `fonts_en.swf`, and the loose path
  has **no navigator at all**, so the import cannot resolve by any means. This
  is the same class as #2714 ("host bridge has no engine consumer"), which was
  accepted, filed and fixed.
- **Related**: UI-D3-01/#2963's impact paragraph assumed this path was live;
  it is not. #2968 (redundant parses) is on the same unreached path. #3103.
- **Suggested Fix**: Add an archive-backed launch route — e.g. `--menu
  interface\hudmenu.swf` resolving through the existing
  `asset_provider::GameArchive` — so `load_swf_from_resource_provider` has one
  real caller. Until then, correct `docs/engine/ui.md`:39 and `ROADMAP.md`:759
  to place archive-backed *menu* loading in Pending, leaving only the
  already-true `ImportAssets` claim in Status.

### MEDIUM

#### UI-D3-03: after #2963 a missing destroy trait is invisible — `AdapterInjected` no longer means the lifecycle is wired

- **Severity**: MEDIUM
- **Dimension**: AVM2 Adapter Injection
- **Profile**: `Fallout4Avm2`
- **Location**: `crates/ui/src/avm2_host.rs`:78, 94-99 · `crates/ui/src/avm2_host.rs`:36-42 · `crates/ui/src/player.rs`:484-486, 643-650 · `crates/ui/src/host.rs`:351-356
- **Status**: NEW (successor to `Existing: #2963`, which is correctly CLOSED)
- **Description**: `has_destroy_trait` is a local `bool` in
  `inject_host_object_adapter`. It selects whether `build_adapter_abc` emits the
  destroy helper and its `addCallback`, and is then discarded. The public
  `ScaleformHostObjectState` still has exactly three variants, so a movie whose
  lifecycle class lacks `onCodeObjDestruction` reports `AdapterInjected` —
  byte-identical to a movie with the full contract. There is no
  `log::warn!`/`log::info!` on the `false` branch and no accessor.
  The skill's Dim-3 checklist requires the state to distinguish the cases and
  the destroy path to be observable, because `code_object_destruction_count()`
  is "the only evidence the lifecycle completed".
- **Evidence**: `grep -n "has_destroy_trait" crates/ui/src/player.rs` → no
  matches; the value never crosses the module boundary.
  `SwfPlayer::drop` (`player.rs`:643-650) gates on
  `has_callback(DESTROY_CALLBACK)`, which is `false` for these movies, so
  `record_call`'s `DESTROYED_EVENT` arm (`host.rs`:379-386) never runs and
  `code_object_destructions` stays 0. The lifecycle test
  (`host/tests.rs`:625-630) asserts
  `code_object_destruction_count() == u64::from(state == AdapterInjected)` —
  an invariant that is now **false** for `DialogueMenu`, `MultiActivateMenu`,
  `SPECIALMenu` and `Terminal`; it only stays green because it covers HUD and
  Pip-Boy, which do carry the trait.
- **Impact**: Four shipped vanilla menus load (the #2963 win) but close without
  ever notifying the engine. When menu-stack/focus policy lands — the Pending-row
  work this audit is meant to protect — "the menu released its host object" will
  be unreadable for exactly those menus, and the zero counter will look like a
  destroy hook that fired and failed rather than one that was never installed.
- **Related**: #2963 (CLOSED, the fix that introduced this), UI-D3-04.
- **Suggested Fix**: Add a fourth state (e.g.
  `AdapterInjectedWithoutDestroyHook`) or return `has_destroy_trait` alongside
  the state, and `log::info!` it at injection. Then relax
  `installed_fallout4_representative_menus_obey_host_object_lifecycle`'s
  destruction assertion to key off that flag instead of off `AdapterInjected`.

#### UI-D3-04: `InitCodeObj` / `ReleaseCodeObj` are dropped from the host-call inventory with no justification, and the corpus test cannot see past the exclusion

- **Severity**: MEDIUM
- **Dimension**: AVM2 Adapter Injection
- **Profile**: `Fallout4Avm2`
- **Location**: `crates/ui/src/avm2_host.rs`:291-293
- **Status**: NEW
- **Description**: `referenced_host_methods_in_tags` — the #2718 scan whose whole
  purpose is to install a forwarder for every `BGSCodeObj.X` call site a movie
  actually contains — silently discards two names:
  ```rust
  if matches!(method.as_slice(), b"InitCodeObj" | b"ReleaseCodeObj") {
      continue;
  }
  ```
  There is no comment, no issue, no doc reference, and neither name appears in
  the 269-entry catalog. It landed in `3a02b02d` (the original FO4 feature
  commit, pre-#2718) and survived both the #2718 union rewrite and the #2966
  regeneration without being re-examined. Contrast `OBJECT_PROTOTYPE_MEMBERS`
  ten lines below, which carries a full docstring explaining why shadowing an
  `Object` member would be wrong.
- **Evidence**: `grep -rn "InitCodeObj\|ReleaseCodeObj" crates/ docs/ .claude/issues`
  returns exactly the one line above. Because the exclusion lives *inside*
  `referenced_host_methods`, the corpus gate
  `installed_fallout4_host_calls_are_all_forwarded`
  (`avm2_host.rs`:1362-1372) consumes the already-filtered set: if a shipped
  menu calls either name, `uncataloged` is still empty and the assertion is
  still green. The test asserts on the output of the thing it is meant to audit.
- **Impact**: If any of the 311 movies calls `BGSCodeObj.InitCodeObj(...)`, no
  forwarder is installed, the property resolves to `undefined` on a dynamic
  object, and AVM2 raises Error #1006 — aborting the executing frame handler, so
  the menu renders and then stops responding. That is precisely the failure mode
  #2718 exists to remove, re-armed for two names, and structurally invisible to
  the gate that is supposed to catch it.
- **Premise honesty**: I could **not** confirm whether either name appears in
  shipped content. A raw byte scan of `Fallout4 - Interface.ba2` returns 0 hits
  for `InitCodeObj`, `ReleaseCodeObj` **and** the control string `BGSCodeObj`,
  which only proves the entries are compressed — it is not evidence either way,
  and extracting them needs code this audit may not run. The finding therefore
  rests on the *structural* defect (an unjustified exclusion that its own gate
  cannot see past), which holds regardless.
- **Related**: #2718, #2966, UI-D3-03.
- **Suggested Fix**: Either document why the two names are not host methods
  (with the same rigour as `OBJECT_PROTOTYPE_MEMBERS`), or lift the skip to a
  named `const` applied *outside* `referenced_host_methods` so the corpus sweep
  can report when a real menu names one.

#### UI-D6-02: nothing in the UI follows a window resize — `UiManager`, the `TextureTarget` and Ruffle's viewport are all pinned at construction

- **Severity**: MEDIUM
- **Dimension**: Render & Device Lifecycle
- **Profile**: both
- **Location**: `byroredux/src/app_events.rs`:308-325 · `crates/ui/src/lib.rs`:48-63 · `crates/ui/src/player.rs`:283-303 · `byroredux/src/scene.rs`:1332-1352
- **Status**: NEW
- **Description**: The Dim-6 checklist asks whether `UiManager.width/height`, the
  `TextureTarget` size and `register_ui_quad`'s descriptor move together on a
  resize. They do not move at all. `WindowEvent::Resized` recreates the
  swapchain and updates the camera aspect and stops there. `crates/ui` has no
  resize API of any kind — no `fn resize`, and
  `with_viewport_dimensions(width, height, 1.0)` (`player.rs`:298) is called
  once at build. `UiManager.width/height` are `pub` fields nothing ever writes
  after `UiManager::new`.
- **Evidence**:
  ```
  $ grep -rn "fn resize\|set_viewport_dimensions" crates/ui/src/   # none
  $ sed -n '308,325p' byroredux/src/app_events.rs                  # swapchain + camera only
  ```
- **Impact**: After a resize the overlay keeps rendering at the original menu
  resolution and is stretched to the new window by the fullscreen quad, so a
  16:9 menu in a 21:9 window is geometrically wrong; and because Ruffle's stage
  never learns the new viewport, the movie's own `Stage.scaleMode`/align logic
  cannot compensate. Menu-authored layout is a Pending-row concern, but the
  *mechanism* that would carry it is absent, which is what this dimension is
  asked to flag.
- **Two adjacent hazards checked and cleared** (recorded so the next sweep does
  not re-open them): there is **no** stride/size mismatch —
  `TextureRegistry::update_rgba` (`crates/renderer/src/texture_registry.rs`:1596-1626)
  rebuilds the `VkImage` at the `ui_w`/`ui_h` it is handed, which stay in lockstep
  with `pixel_buffer`; and pointer input stays **correct**, because
  `ui_input::cursor_to_ui` (`byroredux/src/ui_input.rs`:137-146) scales live
  `window_size` into the fixed `ui_size`. `register_ui_quad` has no size to
  drift — `fullscreen_quad_ui_vertices` is NDC.
- **Related**: #2972, #2722.
- **Suggested Fix**: On `WindowEvent::Resized`, update `UiManager.width/height`
  and either call Ruffle's `set_viewport_dimensions` with a rebuilt
  `TextureTarget`, or rebuild the player from its current movie. The UI texture
  needs no separate handling — `update_rgba` already re-creates it per upload.

## 4. Verified clean (checked this cycle, no finding)

**Dimension 1 — profile selection.** Unchanged since 08-16; items 1-3 of the

**Dimension 2 — transport.**
1. Eviction is `VecDeque::pop_front` in a `while` loop, O(1), `dropped_calls`
   incremented once per eviction; the overflow warn is latched by
   `overflow_warned` and cannot re-arm (`host.rs`:443-457).
2. **No `RefCell` re-entrancy hazard.** `record_call` clones the response

## 5. Pending-Row readiness

Invariants pinned this cycle for work that is deliberately unbuilt (**not**
findings):

- **Host-method handlers**: `register_method` / `set_response*` correctly clear
  `unknown_methods`/`unanswered_methods` on registration, so landing a handler

  filed above: the warn is deduplicated process-wide rather than per menu

  exist and are correct, but have **no** engine caller — there is no runtime way
  to close a Scaleform menu today. Combined with UI-D5-02, menu-stack work needs
  a load/close entry point before it needs a policy.

  implemented and tested but likewise has no engine caller yet. The `None`
  return correctly distinguishes "no such callback" from "returned Null", which
  is the property that bridge will depend on.
- **Font fidelity / full menu pack**: blocked on UI-D5-02 first and UI-D6-02
  second — a menu pack cannot be loaded from archives, and would not survive a
  window resize if it could be.
