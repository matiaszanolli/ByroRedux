### The one thing to take away

The dispatch asked whether the `watr_data_layout_shift` memory note ("`wind_speed`
is a constant 90.0 on ~88 % of vanilla WATR; the Oblivion fog/colour offsets look
wrong too") is genuinely resolved after Session 70's ~48 WATR commits.

**Half of it is resolved; half of it moved four bytes.**

- **Oblivion fog/colour offsets: FIXED and verified.** `decode_data_oblivion`
  reads fog at DATA 36/40 and the three byte-colours at 44/48/52. Byte-walking
  all 17 of `Oblivion.esm`'s 102-byte WATR DATA records confirms exactly that
  layout (offsets 44/48/52 read as f32 denormals — the signature of packed RGBA
  bytes — on 17/17 records). This half of the memory note is now stale.
- **The constant-90.0 drift is still live, on the field next door.** 70 of
  `FalloutNV.esm`'s 78 WATR records and 42 of `Fallout3.esm`'s 53 carry their
  visual data in a **196-byte `DNAM`**, and `parse_watr`'s `_ =>` arm routes
  those to `decode_dnam_pre_fo4`, a **52-byte prefix reader**. It sets
  `wind_speed` from DNAM 0 (three distinct values across all 69 FNV records) and
  `wind_direction` from **DNAM 4, which is 90.0 on 69/69 FNV and 31/31 Skyrim
  records** — stored raw into a field the renderer reads as radians. The 144
  bytes after the prefix — underwater fog ramp, all three noise-layer wind
  vectors, UV scales, amplitudes, rain and displacement simulators, reflection
  HDR multiplier, specular tail — are **never read at all** for those records,
  even though the identical fields at the identical offsets *are* read for
  Skyrim (`apply_skyrim_dnam_tail`) and for the 8–11 FO3/FNV records per game
  that happen to use the legacy 186-byte `DATA` instead (`decode_data_fo3nv`).

The same byte-walk turned up two further per-game layout errors that the crate's
own tests certify as correct, because every WATR unit test builds its fixture
from the parser's own offset map and asserts it reads back — the
`feedback_audit_findings` / ESM-D2-07 tautology, one layer down.

### Ground truth established this pass (durable artefact)

The FO3/FNV 186-byte `DATA`, the FO3/FNV 196-byte `DNAM` and the Skyrim
228-byte `DNAM` are **the same structure**. Verified by census across 17 + 69 +
31 vanilla records: the GECK's documented default rain-simulator tuple
(force 0.1, velocity 0.6, falloff 0.985, dampener 2.0, start size 0.01) and
displacement-simulator tuple (force 0.4, velocity 0.6, falloff 0.985,

## Findings — HIGH (2)

### ESM-2026-08-20-D5-01: FO3/FNV `WATR.DNAM` — the sub-record carrying 80–90 % of vanilla visual data — is decoded by a 52-byte Skyrim *prefix* reader; the other 144 bytes are silently dropped
- **Severity**: HIGH
- **Dimension**: CELL / WRLD Walkers (WATR record schema)
- **Record / Sub-record**: `WATR` / `DNAM`, cross-checked against `WATR` / `DATA`
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:1359` (the
  `_ => decode_dnam_pre_fo4(&sub.data)` arm of `parse_watr`'s `DNAM` match),
  `:694-759` (`decode_dnam_pre_fo4`), contrasted with `:760-923`
  (`apply_skyrim_dnam_tail`) and `:555-692` (`decode_data_fo3nv`)
- **Status**: NEW
- **Description**: `parse_watr`'s `DNAM` dispatch has explicit arms for
  `Fallout4`, `Fallout76`, `Skyrim` and `Starfield`. `Fallout3NV` falls to the
  catch-all, which calls `decode_dnam_pre_fo4` — a function that
  `return`s early on `data.len() < 52` and reads nothing past byte 52 by
  construction. Skyrim reaches the *same* function and then gets
  `apply_skyrim_dnam_tail`, which decodes offsets 56..232 of the identical
  structure. FO3/FNV get no tail pass, so every field from byte 52 onward is
  left at its `WaterParams::default()` sentinel for the majority of every
  Fallout 3 / New Vegas water record.
- **Evidence**: Byte census of `FalloutNV.esm` (n = 69 records with
  `DNAM` len 196) and `Fallout3.esm` (n = 41), against the same census of
  `Skyrim.esm` (n = 31, `DNAM` len 228):
  ```
  FalloutNV.esm DNAM196     Skyrim.esm DNAM228       field (per the layout table above)
    0: distinct=3 (0.1/3.0)   0: distinct=1 (0.1)     wind speed   — read by both
    4: distinct=1 (90.0)      4: distinct=1 (90.0)    wind dir     — read by both
   56: distinct=2 (0.1)      56: distinct=1 (0.1)     rain force   — FNV: DROPPED
   92: distinct=3 (0.05)     92: distinct=1 (0.05)    disp start   — FNV: DROPPED
  112: distinct=22           112: distinct=24         noise 1 spd  — FNV: DROPPED
  144: distinct=8  (-2500…)  144: distinct=11         u/w fog near — FNV: DROPPED
  148: distinct=9  (5500…)   148: distinct=10         u/w fog far  — FNV: DROPPED
  172: distinct=5  (100.0)   172: distinct=20         uv scale 1   — FNV: DROPPED
  184: distinct=23          184: distinct=27          amplitude 1  — FNV: DROPPED
  ```
  The two payload shapes are the same structure: `FalloutNV.esm`'s
  `DupontFontWaterType` ships its visual data as a 186-byte `DATA` whose fields
  land on exactly the offsets `Skyrim.esm`'s `DefaultWaterKatariahWorld` uses in
  its 228-byte `DNAM` (rain sim `0.1/0.6/0.985/2.0/0.01` at 56..72, displacement
  sim `0.4/0.6/0.985/10.0/0.05` at 76..92 in both). So the tail decode already
  exists in this file, at the right offsets, and simply is not run for
  `GameKind::Fallout3NV`.

  Two further consequences fall out of the same arm:
  1. **Unit error.** `decode_dnam_pre_fo4:706` does `p.wind_direction = v` with
     no `.to_radians()`. Every other producer in the file converts
     (`decode_data_fo3nv:661`, `apply_skyrim_dnam_tail:836`,
     `decode_dnam_fo4:1024`, `decode_dnam_starfield:1236` all call
     `.to_radians()` on the noise-layer direction). `byroredux/src/env_translate.rs:962`
     consumes `rec.params.wind_direction` as radians (`theta.sin_cos()`), so
     every FO3/FNV river/rapids plane flows at a fixed `90 rad mod 2π ≈ 2.04 rad`
     — one wrong constant heading for the entire game.
  2. **Same-game divergence.** `env_translate.rs:876-1028` builds `scroll_a/b/c`
     from `noise_wind_speeds`/`noise_wind_directions`. Those are zero for the
     `DNAM` records and authored for the `DATA` records, so two vanilla FNV
     waters authored identically in the GECK produce materially different
     materials depending only on which sub-record the record happens to use.
- **Impact**: FNV is the project's declared reference title. For 90 % of its
  water records the engine loses: the underwater fog ramp (`underwater_fog_near`
  / `_far` stay 0.0, so `env_translate` falls back to the above-water ramp), all
  three noise-layer scroll vectors (calm water gets no authored UV motion at
  all), all three noise UV scales and amplitudes, the noise falloff, the rain and
  displacement simulator tuples, the reflection HDR multiplier, the specular
  radius/magnitude tail, and the above/under-water fog amounts. FO3 loses the
  same on 79 % of its records.
- **Related**: root cause shared with ESM-2026-08-20-D5-04 and -D5-05.
  `watr_data_layout_shift` (project memory) — this is that note's surviving half.
  Renderer half of the consequence is `/audit-renderer` Dim 15.
- **Suggested Fix**: Give `Fallout3NV` its own explicit `DNAM` arm that runs the
  prefix and then the shared 56..196 tail. The cleanest shape is to split
  `apply_skyrim_dnam_tail` into a shared `apply_fo3nv_dnam_tail` (56..196, gated
  on `len >= 196`) plus the Skyrim-only 196..232 extension, and call the shared
  half from both arms — `decode_data_fo3nv` can then be reduced to
  `decode_dnam_pre_fo4` + the same shared tail, which removes the divergence in
  (2) as well. Pin it with a `#[ignore]` real-data test asserting
  `underwater_fog_far > underwater_fog_near` and `noise_wind_speeds[0] > 0` on a
  named `FalloutNV.esm` record.

### ESM-2026-08-20-D5-02: Skyrim `normal_magnitude` is read from the displacement simulator's *starting size* (a constant `0.05`), attenuating every Skyrim water surface's normal amplitude ~20×
- **Severity**: HIGH
- **Dimension**: CELL / WRLD Walkers (WATR record schema)
- **Record / Sub-record**: `WATR` / `DNAM`
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:884-886`
  (`apply_skyrim_dnam_tail`, `p.normal_magnitude = read_f32_at(data, 92)`);
  the field's own doc at `:216-218` (*"Skyrim stores this at DNAM 92"*);
  consumer `byroredux/src/env_translate.rs:815-822`
- **Status**: NEW
- **Description**: DNAM offset 92 is the Displacement Simulator's *Starting
  Size*, not a normal-magnitude control. The parser treats it as
  `normal_magnitude`, whose documented neutral is `1.0`, and
  `env_translate` multiplies every authored noise amplitude by it.
- **Evidence**: Census of `Skyrim.esm`, all 31 records with `DNAM` len 228:
  ```
   88: distinct=6   top=[(0.98, 25), (0.99, 2), (1.1, 1)]   displacement dampener
   92: distinct=1   top=[(0.05, 31)]                        <-- read as normal_magnitude
   96: distinct=11  top=[(4007.0, 6), (5000.0, 6), …]       noise falloff
  184: distinct=27  top=[(0.6957, 4), (0.9022, 2), …]       noise amplitude 1
  ```
  A field that is bit-identical on 31/31 vanilla records is not a per-water
  authored magnitude; `0.05` is the GECK's documented Displacement Simulator
  Starting Size default, and it sits at the end of the
  force/velocity/falloff/dampener/start-size run that begins at 76. The same
  `0.05` appears at offset 92 on 63/69 `FalloutNV.esm` records and 17/17
  `Oblivion.esm` records (at Oblivion's shifted offset 96). By contrast the
  arms that *are* correct read a varied field: `decode_dnam_fo4` takes
  `normal_magnitude` from FO4 DNAM 52 (34 distinct values over 40 records) and
  `decode_dnam_starfield` from SF DNAM 48 (4 distinct over 15).

  Consumer chain at HEAD:
  ```rust
  // env_translate.rs:815-822
  let normal_magnitude = if …params.normal_magnitude > 0.0 {
      rec.params.normal_magnitude.clamp(0.01, 8.0)   // 0.05
  } else { 1.0 };
  for amplitude in &mut mat.noise_amplitude_scales {
      *amplitude = (*amplitude * normal_magnitude).clamp(0.0, 8.0);
  }
  ```
  `mat.noise_amplitude_scales` is seeded from the authored DNAM 184/188/192
  amplitudes (`env_translate.rs:777-785`), which census at ≈0.5–0.9 on vanilla.
  0.65 × 0.05 = **0.0325** — every Skyrim water plane ships normal amplitudes at
  ~5 % of authored.
- **Impact**: All 34 vanilla `Skyrim.esm` water types render near-mirror-flat:
  the normal-map perturbation that produces ripple shading is scaled to 5 % of
  authored on a fully-supported game with live exterior cell loading. This is
  the WATAL render half's most visible per-record parameter, and it is wrong on
  100 % of Skyrim water.
- **Related**: ESM-2026-08-20-D5-04 reads the *other* half of the same
  displacement run at the wrong offset, from the same two functions.
- **Suggested Fix**: Delete the `normal_magnitude` read from the Skyrim tail —
  there is no such field in the 228-byte layout; leaving the `1.0` default is
  correct. Then take DNAM 92 as `displacement[0]` (see D5-04). If a Skyrim
  normal magnitude is wanted later it must be identified from a field that is
  not constant across vanilla, and cited.

### ESM-2026-08-20-D5-03: Fallout 76 `WATR.DNAM` is decoded with the Fallout 4 offset map; vanilla FO76 ships the Starfield layout
- **Severity**: MEDIUM
- **Dimension**: CELL / WRLD Walkers (WATR record schema)
- **Record / Sub-record**: `WATR` / `DNAM`
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:1059-1157`
  (`decode_dnam_fo76`, added this cycle by `01718467 fix(water): decode Fallout
  76 visual data`); dispatch at `:1349`; its test at `:1963-2028`
- **Status**: NEW
- **Description**: `decode_dnam_fo76`'s docstring asserts *"FO76 has a compact,
  explicit fog/physical/specular layout; it is not the FO4 noise-tail layout"*,
  and then reads the FO4 offset map (colours at 4/8/36/96, alpha controls at
  20/24/28/32, reflectivity 64, Fresnel 68, displacement 92/84/88, sun specular
  100/104). Byte-walking all 47 `SeventySix.esm` WATR records shows the real
  FO76 layout is Starfield's, truncated by one trailing float.
- **Evidence**: `SeventySix.esm` (n=47, DNAM 148) vs `Starfield.esm` (n=15,
  DNAM 152) — same fields, same offsets, throughout:
  ```
   off   FO76 top values          Starfield top values     field
     0   86.0 (39/47)             8.0 / 4.0 / 12.0         depth amount
     4   0.70 / 0.0655 / 0.30     0.1656 (14/15)           colour-absorption range R
     8   0.4751 / 0.3368          0.0962                   … range G
    12   0.50 / 0.20 / 1.0        0.0763                   … range B
    16   0.025 / 0.0024           8.84 / 2.682             concentration 1
    32   0.0 (47/47, denormal)    0.0 (15/15, denormal)    underwater RGBA   <-- a real colour
    36   1.0 (46/47)              1.0 (14/15)              underwater fog amount
    40   -9000 / -6400            -150                     u/w fog near
    44   850 / 1300               75                       u/w fog far
    48   0.333 / 0.1848           0.5471                   normal magnitude
    64/68 0.1 / 0.85              0.4 / 0.5                displacement force / velocity
    80   0.05 (47/47)             0.05 (15/15)             displacement starting size
    84/88/92  232/331/108 deg     40/78/178 deg            noise layer wind directions
   132/136/140 4096               100                      noise falloffs
   144  1.0 (47/47)               1.0 (15/15)              flow-map scale
   148  —                         0.08 / 0.05 / 0.12       surface roughness (SF only)
  ```
  Note offset 32: an f32 read of a packed RGBA byte triple is a denormal, which
  rounds to `0.0` — it is `0.0` on 47/47 FO76 and 15/15 Starfield records and on
  *nothing else in the buffer*. `decode_dnam_fo76` instead reads colours from
  offsets 4 and 8, which hold ordinary floats (`0.70`, `0.4751`), so
  `shallow_color` becomes the byte pattern of a float — e.g. `0.7f32` →
  `[0x33,0x33,0x33,0x3F]` → RGB(51,51,51) mid-grey.

  Downstream numbers this produces on the first record walked
  (`Burn_ExtToxicAbraxoWaterBasin`): `fog_near` ← 1.0 (absorption B),
  `fog_far` ← `max(0.0839, fog_near+1)` = 2.0 — the above-water fog ramp
  collapses from ~86 world units to 2; `underwater_fog_amount` ← −9420 →
  clamped to 0 (no underwater fog); `fresnel` ← 0.85 (displacement velocity);
  `displacement` ← [62.4, 239.3, 331.8] (three noise-wind *degree* values);
  `sun_specular_power` ← 0.0279 → clamped up to the 1.0 floor.
  The absorption/concentration data that `WaterParams` has dedicated fields for
  (`absorption_ranges`, `concentration`) is dropped entirely for FO76.
- **Impact**: Every `SeventySix.esm` water record decodes to a plausible-looking
  but wrong material. `docs/feature-matrix.md:18` lists FO76 as *"parse only"*
  for interiors with no exterior grid, so **nothing renders this today** — which
  is why this is MEDIUM rather than HIGH. It escalates to HIGH the moment FO76
  cell loading lands, and the decoder currently presents itself (and is
  test-certified) as correct, so the error is not discoverable from inside the
  crate.
- **Evidence that the test cannot catch it**: `parse_watr_decodes_fo76_visual_layout`
  (`water.rs:1963`) builds a synthetic 148-byte buffer by *writing* values at the
  parser's own offsets (`data[4..8] = [10,20,30,0]`, `data[64..68] = 0.35f32`, …)
  and asserts they read back. A fixture that encodes the hypothesis under test
  cannot falsify it — the same defect class as **ESM-D2-07** (2026-08-13) and the
  `AVIF` fixture called out on 2026-08-16.
- **Related**: ESM-2026-08-20-D8-01 (`installed_masters_water_fields_are_finite_and_ordered`
  does not include FO76 at all).
- **Suggested Fix**: Route `GameKind::Fallout76` to `decode_dnam_starfield` and
  delete `decode_dnam_fo76`; the Starfield decoder's every read is bounds-checked
  through `read_f32_at`, so its 148-byte roughness read simply returns `None`
  and the sentinel is preserved. Replace the synthetic fixture with a
  `#[ignore]` real-data assertion (e.g. `absorption_ranges[0] > 0` and
  `underwater_fog_far > 0` on a named `SeventySix.esm` record).

### ESM-2026-08-20-D5-04: The rain-simulator and displacement-simulator *starting size* fields are swapped in three of the five WATR arms
- **Severity**: MEDIUM
- **Dimension**: CELL / WRLD Walkers (WATR record schema)
- **Record / Sub-record**: `WATR` / `DATA`, `WATR` / `DNAM`
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:524-537`
  (`decode_data_oblivion`, `displacement.zip([76, 88, 92])` + `rain_start_size`
  ← 96), `:585-604` (`decode_data_fo3nv`, `displacement.zip([72, 84, 88])` +
  `rain_start_size` ← 92), `:833-837` (`apply_skyrim_dnam_tail`,
  `displacement.zip([72, 84, 88])`)
- **Status**: NEW
- **Description**: `WaterParams::displacement` is documented (`:222-224`) as
  *"starting size, radial falloff, and dampener"*. Three arms source slot 0 from
  the **rain** simulator's starting size and — where they populate it at all —
  source `rain_start_size` from the **displacement** simulator's. The two arms
  that get it right are the two written most recently against a real byte dump:
  `decode_dnam_fo4:1013` uses `[92, 84, 88]` and `decode_dnam_starfield:1231`
  uses `[80, 72, 76]`, both of which put the displacement start size in slot 0.
- **Evidence**: The two five-float simulator runs are unambiguous in the data
  because Bethesda's GECK defaults appear verbatim and back-to-back. On
  `FalloutNV.esm` (n=69):
  ```
   56: 0.1  (67/69)   rain force        76: 0.4   (63/69)   displacement force
   60: 0.6  (63/69)   rain velocity     80: 0.6   (45/69)   displacement velocity
   64: 0.985(67/69)   rain falloff      84: 0.985 (43/69)   displacement falloff
   68: 2.0  (67/69)   rain dampener     88: 10.0  (42/69)   displacement dampener
   72: 0.01 (43/69)   rain START SIZE   92: 0.05  (63/69)   displacement START SIZE
  ```
  `(0.1, 0.6, 0.985, 2.0, 0.01)` and `(0.4, 0.6, 0.985, 10.0, 0.05)` are the
  documented GECK Rain Simulator and Displacement Simulator defaults; the same
  two runs appear at 56..92 in `Skyrim.esm`'s DNAM and at 60..96 in
  `Oblivion.esm`'s DATA (shifted by the two scroll floats at 28/32).
- **Impact**: `env_translate.rs:794-801` maps `params.displacement` straight into
  `mat.displacement` and `params.rain_start_size` into `mat.rain_start_size`, so
  the two ripple systems' spatial scales are exchanged on Oblivion, on the
  FO3/FNV `DATA` records, and on Skyrim. Bounded (both are small positive
  floats), which is why this is MEDIUM rather than a HIGH: it degrades ripple
  shape rather than breaking the surface.
- **Related**: ESM-2026-08-20-D5-02 misreads the other end of the same run.
  Fix both together — the Skyrim arm's `normal_magnitude` read at 92 and its
  `displacement[0]` read at 72 are the same one-field shift seen twice.
- **Suggested Fix**: `displacement` ← `[92, 84, 88]` and `rain_start_size` ← 72
  on the FO3/FNV and Skyrim arms; `[96, 88, 92]` and 76 on the Oblivion arm.
  Pin each with a real-data assertion that `displacement[0] == 0.05` (the vanilla
  constant) rather than a synthetic round-trip.

### ESM-2026-08-20-D5-05: `wind_direction` is read in degrees and stored as radians on the Oblivion and FO3/FNV arms
- **Severity**: MEDIUM
- **Dimension**: CELL / WRLD Walkers (WATR record schema)
- **Record / Sub-record**: `WATR` / `DATA`, `WATR` / `DNAM`
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:706`
  (`decode_dnam_pre_fo4`), `:473-478` (`decode_data_oblivion`'s field loop,
  `(&mut p.wind_direction, 4usize)`)
- **Status**: NEW (the surviving half of the `watr_data_layout_shift` memory note)
- **Description**: Both arms assign the raw `f32` to `WaterParams::wind_direction`,
  whose consumer treats it as radians. Every other direction producer in the file
  calls `.to_radians()`. `env_translate.rs:960-963` documents the contract
  explicitly — *"Bethesda's wind_direction is in radians from north (UESP)"* —
  and then does `theta.sin_cos()`.
- **Evidence**: `Oblivion.esm` DATA offset 4 censuses to `35.0 / 100.0 / 90.0`;
  `FalloutNV.esm` DNAM offset 4 is `90.0` on 69/69 records and `Skyrim.esm`
  DNAM offset 4 is `90.0` on 31/31. Values in [0, 360) with a 90.0 mode are
  degrees. Skyrim is unaffected in practice because
  `apply_skyrim_dnam_tail:836,847` overwrites `wind_direction` from the
  `.to_radians()`-converted noise layer 1; Oblivion and FO3/FNV keep the raw
  value, so `90.0 rad mod 2π ≈ 2.04 rad ≈ 117°` becomes the flow heading for
  every FNV `River`/`Rapids` plane.
- **Impact**: Wrong, and *identical*, current heading for every classified
  flowing water body on Oblivion and FO3/FNV. Rivers in different worldspaces
  all flow the same wrong way.
- **Related**: subsumed by ESM-2026-08-20-D5-01's suggested fix if the shared
  tail is adopted (the tail sources `wind_direction` from the converted noise
  layer, as Skyrim already does). Not the same as **#2872** (CLOSED), which was
  the shader-scroll-vs-BU/s *unit* seam on `WaterFlow::speed`, not the parse-side
  angle.
- **Suggested Fix**: Prefer the noise-layer-1 direction (already
  `.to_radians()`-converted) on both arms, as every modern arm does. If the
  legacy prefix field is kept as a fallback, convert it.

### ESM-2026-08-20-D5-06: Oblivion `WATR` damage and flags are never decoded, so the live `WaterPlane::damage_per_second` path is dead for every Oblivion lava plane
- **Severity**: MEDIUM
- **Dimension**: CELL / WRLD Walkers (WATR record schema)
- **Record / Sub-record**: `WATR` / `DATA`, `WATR` / `FNAM`
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:1303-1320` (the
  `FNAM` arm's `matches!` guard excludes `GameKind::Oblivion`), `:1332` (the
  2-byte-`DATA` damage arm is guarded `!matches!(game, GameKind::Oblivion)`),
  `:468-553` (`decode_data_oblivion` never reads offset 100); consumer
  `byroredux/src/cell_loader/water.rs:492-502`
- **Status**: NEW
- **Description**: Oblivion packs the damage `u16` in the *tail* of its 102-byte
  `DATA` rather than in a separate 2-byte `DATA`, and its `FNAM` is deliberately
  excluded from the flags arm. Neither `legacy_flags`/`water_flags` nor
  `legacy_damage` is therefore ever populated for Oblivion, and the cell loader
  requires both (flag bit 0x01 **and** a `Some(legacy_damage)`) before it will
  set a non-zero `damage_per_second`.
- **Evidence**: Reading `u16` at DATA offset 100 across `Oblivion.esm`'s 17
  full-length WATR records yields `OblivionCitadelLavaPlane = 5000`,
  `OblivionLavaTest01 = 50`, and 0 for the remaining 15; the one 2-byte-`DATA`
  record, `CamoranLava`, carries `65535`. All 23 records ship a 1-byte `FNAM`.
  At HEAD, `parse_watr(…, GameKind::Oblivion)` returns `legacy_flags: None`,
  `water_flags: None`, `legacy_damage: None` for all 23, and the `CamoranLava`
  stub is routed into `decode_data_oblivion` (harmless — every read is out of
  bounds — but its damage byte is discarded).
- **Impact**: Standing in Oblivion's Citadel lava or the Camoran lava does
  nothing. The consumer exists and works (`cell_loader/water.rs:492`), so this is
  a parser-side gap with a live, correct reader on the other end — the WATAL
  physics half is wired for a signal the ESM layer never emits on TES4.
- **Related**: `docs/engine/watal.md` physics half; `/audit-physics` Dim 6 owns
  the consumer.
- **Suggested Fix**: Read `u16` at DATA offset 100 into `legacy_damage` inside
  `decode_data_oblivion`'s caller (or return it alongside `WaterParams`), accept
  the 2-byte Oblivion `DATA` as a damage stub like every other game, and drop
  `Oblivion` from the `FNAM` arm's exclusion list — TES4's FNAM bit 0x01 is the
  same "causes damage" gate.

## Disproved Candidates (recorded so they are not re-litigated)

- **"FO4 `WEAP.DNAM` is decoded at the wrong offsets."** The 132-byte packed
  layout added by `0a220b68` is **correct**. Byte-checked against
  `Fallout4.esm`: `10mm` → clip 12 / weight 3.0 / value 45 / damage 18;
  `GaussRifle` → clip 5 / weight 8.0 / value 150 / damage 110;
  `MissileLauncher` → clip 1 / weight 20.0 / value 300 / damage 15. These match
  vanilla FO4 exactly. (A first sample of `VRWorkshopShared_*_NonPlayable`
  records looked wrong — 1018, 1110 — but those are genuinely-authored
  non-playable VR variants, not a decode error.)
- **"FO4 `WATR.DNAM` shares the FO76 problem."** It does not. `decode_dnam_fo4`
  reads real colours at 4/8/36/96 (all four census as denormal-`0.0` on 40/40
  records — the packed-RGBA signature) and takes `displacement` from
  `[92, 84, 88]`, which is the correct run. This arm is one of the two that get
  D5-04 right.
- **"`decode_dnam_starfield` guesses its absorption/concentration block."** It
  does not; offsets 4/8/12 and 16/20/24/28 hold ordinary floats while 32 holds a
  denormal (a packed colour), which is exactly the split the decoder assumes.
- **"`decode_dnam_fo76`'s bogus `noise_wind_speeds` make FO76 water strobe."**
  Disproved — `decode_dnam_fo76` never writes `noise_wind_speeds` at all, so the
  `NAM0` fallback in `parse_watr:1400-1418` populates all three layers from the
  record's linear velocity. FO76 scroll is fine; only the material is wrong.
- **"`FormIdRemap::remap`'s new `raw == 0` early return breaks the four
  documented arms."** It does not: NULL is not a form and the standalone /
  out-of-range arms are untouched. The ESL rationale in the comment checks out —
  without it a `GlobalSlot::Light` self-slot would compose `0` into
  `0xFE00_7000`.
- **"`read_file_header`'s `self.data[header_start + 20]` can panic."** It cannot:
  the preceding `read_record_header()?` has already validated 24 readable bytes
  for `EsmVariant::Tes5Plus`, and the read is gated on that variant.
- **"A dispatch label routes to a router with no matching arm."** Re-checked
  across all 8 routers after the delta: 0 gaps.
- **"Interior cells lose the XCLW no-water sentinel."** They do not — interiors
  have no worldspace default, so both "absent" and "explicitly dry" correctly
  collapse to "no plane"; the distinction only matters on the exterior path,
  where it is preserved.
- **"Gamebryo WATR colours need an sRGB→linear conversion."** Not re-litigated
  (`feedback_color_space`); `u8_to_linear` is a plain `/255.0` and that is
  correct.
