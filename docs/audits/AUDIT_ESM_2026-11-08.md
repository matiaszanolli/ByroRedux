**The two MEDIUMs**

- **ESM-5-01 (Dim 5): Starfield `EXPL`/`PROJ` distances and `TXST` `DODT` sizes are never lifted by `spatial_units::normalize`.** #6679 decoded them at wire (metric) values. `mines.rs` and `projectiles.rs` read them as Bethesda units, so a frag mine's 2.0 proximity triggers at about 3 cm. Same regression class as #5001/#5002/#5151. A few vanilla rows already look BU-like, so each row needs a unit decision when the lift is added.
- **ESM-D7-01 (Dim 7): Starfield `ARMO`/`ARMA` biped masks decode to 0.** Starfield authors the mask in a u64 `BO64` sub-record that nothing reads. `Spacesuit_Constellation_01` sits at bit 35 ("SS BODY"), which neither `main_body_bit(Starfield)` nor a u32 mask can express. An end-to-end Starfield dress-up was not run, so visible impact is unconfirmed.

**Themes in the LOWs**

- **Inverse-shape FormID remap** (ESM-D3-01, -02, -03): WEAP `ETYP` on FO3/FNV (s32 enum) and REGN `RDMD` (enum) go through `remap_fid`; the public `parse_musc` wrapper passes `&None`. All latent: no consumer reads the fields. Real data: all 421 FO3/FNV WEAP `ETYP` values are 0–7.
- **Convention drift after #6586** (ESM-D2-01 to -03): decoders added since use bare numeric gates, hand-chunked FormID arrays, and `f32_or_default` mid-layout (`GDRY.DATA`). Every width and offset is correct against xEdit and the shipped masters; no decode bug found in any touched decoder.
- **Per-game gates that xEdit and data contradict** (ESM-D4-01/-02/-03, ESM-5-02): FO76 `PERK` entries (2-byte `PRKE`), FO4/FO76 `MUSC`/`MUST` (identical to Skyrim; only Starfield differs), FO76 `VOLI`, and `XCCM` on FO76/Starfield (a REGN, 36/36 and 41/41 in real data). All are un-consumed today.
- **Localized strings** (ESM-D6-01 to -06): BPTD `BPNN`/`BPNT`/`BPNI` are plain strings read as lstrings (31 FO4 / 58 FO76 `<lstring>` placeholders), the loose-override probe ignores a lowercase `strings/` directory, and `resolve()` is table-agnostic (one wrong PERK description in Dragonborn).
- **Doc/test rot** (ESM-D1-01, D2-05, D4-04, D7-02..06, D8-03): FO76 HEDR is now 280.0 / rv 210; `categories()` is 117 not 115; `plugin-loading.md` still says ESH is unmodelled; `memory-budget.md` EsmIndex RSS is 6–11 % low; stale `sf-esm` leaf baselines.
- **Hygiene** (ESM-D1-02, ESM-D8-02): one example still hand-rolls an unbounded recursive GRUP walk; 25 `#[ignore]`d real-data tests skip silently on the strict lane.

**Coverage posture.** All seven masters parsed with 0 walker errors (Oblivion, FO3, FNV, Skyrim SE, FO4, `SeventySix.esm` HEDR 280.0 → `Fallout76`, Starfield). No regression against the 10-31 matrix and no dropped Starfield baseline row. The only top-group movement is four newly handled groups (`MUST`, `MATT`, `GDRY`, `VOLI`); the unhandled-record deltas reconcile exactly (Skyrim −336, FO4 −760, FO76 −2,217, Starfield −526). Parse time and peak RSS are within noise of 10-31 (e.g. Starfield 7.15 s / 3.91 GB, FO76 6.45 s / 4.19 GB; measured at load ≈7, so upper bounds).

**Closed since 10-31.** The two 10-31 EXPL LOWs (FO4 form versions below 97, FO76 at FO3 offsets) are fixed in code and re-verified against real `DATA` lengths. The 10-31 doc-rot and clamp items stay fixed.

**Dedup.** No finding duplicates an open issue; the closest are open #3816 (music; D3-02, D4-02) and #6048 (terrain Havok data), and closed #4074, #4176, #5819, #6184. Issue search used the 200 most recent issues (all states) plus the open `esm-plugin` label list.

- **Severity**: LOW (latent - nothing reads `equip_type` outside `items.rs`)
- **Dimension**: 3
- **Record/Sub-record**: WEAP / ETYP, GameKind::Fallout3NV
- **Location**: `crates/plugin/src/esm/records/items.rs:593-595` (arm), field doc `items.rs:233-236`
- **Status**: NEW (the arm is #3715's Skyrim fix, never game-gated; the field was renamed `skill_form` -> `equip_type` by
  `a9748e54c`, #6350, which corrected the doc but left the remap)
- **Description**: The arm is ungated:
  `b"ETYP" => { equip_type = remap_fid(SubReader::new(&sub.data).u32_or_default(), remap); }`.
  xEdit FNV and FO3 define it as `wbInteger(ETYP, 'Equipment Type', itS32, wbEquipTypeEnum)`
  (`wbDefinitionsFNV.pas:3464`, `wbDefinitionsFO3.pas:2864`). Only Skyrim/FO4/FO76/SF define it as an `EQUP` FormID.
  The field's own doc comment says "on FO3/FNV an enum ... not a form at all", and the test
  `fallout_dnam_decodes_the_weapon_skill` asserts `equip_type == 3` only because it passes `&None`.
- **Evidence**: Scanned the WEAP records of the shipped masters (`etyp.py` in the session scratchpad):
  FalloutNV.esm 261 WEAP, ETYP values `{0:41, 1:49, 2:69, 3:59, 4:19, 5:15, 6:8, 7:1}`;
  Fallout3.esm 160 WEAP, `{0:27, 1:26, 2:44, 3:43, 4:8, 5:7, 6:5}`. Every value is a small enum, none a FormID.
  `FormIdRemap::remap` (`reader.rs:562-611`): a masterless plugin has `mod_index 0 == master_slots.len()`, so
  `3` composes to `plugin_slot << 24 | 3`. A masterless FNV/FO3 plugin loaded at slot N>0 gets `0x0N000003`. A plugin whose first
  master is not at slot 0 gets the same corruption. The `(raw == 0 -> 0)` short-circuit hides enum value 0 only.
  Vanilla masters at slot 0 happen to map identically, so the bug is invisible on a vanilla-only load.
- **Impact**: Wrong `equip_type` for mod-added FO3/FNV weapons in a non-trivial load order. No runtime consumer reads
  it today, so no visible failure yet. It re-opens as soon as the equip/VATS layer reads the field.
- **Suggested fix**: Branch on game. FO3NV stores the raw s32 (preferably in its own field or an enum, not the FormID
  slot). Skyrim+ keeps `remap_fid`. Add a `weap_etyp_enum_stays_raw_under_remap` test modelled on
  `pkin_vnam_version_stays_raw_under_remap`, using a non-identity remap on a FO3NV record.

#### ESM-D6-01: BPTD `BPNN` / `BPNT` / `BPNI` are plain strings but are read through the lstring helper
- **Severity**: LOW (latent; becomes MEDIUM when VATS-FO4-007 / an FO4 targeting scan consumes `vats_target_node`)
- **Dimension**: 6 (Localized Strings; the inverse hazard: a non-lstring field decoded as lstring)
- **Record/Sub-record**: BPTD `BPNN` "Part Node", `BPNT` "VATS Target", `BPNI` "IK Data - Start Node"
- **Location**: crates/plugin/src/esm/records/misc/equipment.rs:280-282
- **Status**: NEW (BPTD issues #6448/#6465 are about BPND, not these)
- **Description**: `read_lstring_or_zstring` treats any exactly-4-byte payload of a localized plugin as a `u32` string id. `BPTN` is `wbLString` (FO4.pas:11564 area, FO76.pas:12623 area, tes5.pas:9257 area), but `BPNN`, `BPNT` (and Skyrim's `BPNI`) are `wbString(..., 0, cpNormal, True)`, not lstrings. A node name of exactly 3 characters plus NUL (`COM`, `gun`, `Eye`, `Arm`) is 4 bytes and so becomes a table lookup.
- **Evidence**: the probe finds 17 `node` and 14 `vats_target_node` placeholders in Fallout4.esm, 2 in DLCCoast, 32 + 26 in SeventySix.esm, e.g. `BptdPart { name: "Barrel", node: "<lstring 0x006E7567>", vats_target_node: "<lstring 0x006E7567>" }`. `0x006E7567` is the little-endian bytes of `"gun\0"`, `0x004D4F43` is `"COM\0"`, `0x00657945` is `"Eye\0"`, `0x006D7241` is `"Arm\0"`. Skyrim.esm shows 0 (its node names are long), so this only bites FO4/FO76 (and mods).
- **Impact**: body-part node / VATS target bone names are replaced by `<lstring 0x…>` for the shortest node names on every FO4/FO76 load. `byroredux/src/systems/vats.rs:528` does `bone_position(world, entity, &part.vats_target_node).unwrap_or(center)`, so the FNV/FO3 scan is unaffected today, but any FO4/FO76 targeting reads the placeholder and silently falls back to the actor centre.
- **Suggested fix**: use `read_zstring` for `BPNN`/`BPNT`/`BPNI` (keep `BPTN` on the lstring path). Add a localized-plugin unit test with a 3-char node name.

#### ESM-D6-02: the loose-override case-insensitive probe covers the file name, not the `Strings` directory
- **Severity**: LOW
- **Dimension**: 6
- **Location**: crates/plugin/src/esm/strings_table.rs:370-398 (`strings_dir = ...join("Strings")`, `loose_candidate`)
- **Status**: NEW (incomplete fix of #4176, which closed after fixing only the file-name segment; the regression test `loose_companion_file_is_found_case_insensitively` builds a `Strings/` dir with a lowercase file name only)
- **Description**: `loose_candidate` tries `Strings/<name>` exactly, then `read_dir("<dir>/Strings")` and matches file names case-insensitively. If the directory itself is spelled `strings/` (what BSArch-style extractors and many mod packagers emit, and exactly the archive's own lowercase `strings\` spelling) on a case-sensitive filesystem, both `is_file()` and `read_dir()` fail and the loose file is never seen, so the archive wins: the same inverted Bethesda override order #4176 set out to close.
- **Evidence** (probe `dircase`, loose file with id 1 = "Loose Override", archive callback returns "Archive"):
  `dir Strings -> Some("Loose Override")` / `dir strings -> Some("Archive")` / `dir STRINGS -> Some("Archive")`.
- **Impact**: a mod's lower-case-directory translation/override of a vanilla string table is silently ignored on Linux (the project's dev platform); #4073's warning does not fire because the archive supplies tables.
- **Suggested fix**: resolve the directory component the same way (case-insensitive `read_dir` of the plugin directory for an entry equal to `Strings`), then the file name; extend the existing test to a lowercase directory.

#### ESM-D6-03: `StringTableSet::resolve` is table-agnostic, so an id present in two tables resolves to the wrong one
- **Severity**: LOW (1 hit in Skyrim's shipped masters, measured)
- **Dimension**: 6
- **Location**: crates/plugin/src/esm/strings_table.rs:447-453 (`resolve`: STRINGS, then DLSTRINGS, then ILSTRINGS), called from records/common.rs:211
- **Status**: NEW
- **Description**: the three companion files are separate id namespaces. The reader picks the first table that has the id regardless of which sub-record asked. Bethesda content mostly avoids overlap by sharing one counter, but not always.
- **Evidence**: id collision census over the shipped `_en`/`_english` tables (probe `collide`): Skyrim.esm family 1 (`dragonborn_english`, id 148), Fallout4_en 2 (ids 224439, 224441), Starfield 0, FO76 0. For Dragonborn id 148: `.STRINGS` = "Quick Test Cell", `.DLSTRINGS` = "Protection spells like Stoneflesh are 2.5 times as strong if...". Parsing Dragonborn.esm gives `PerkRecord { editor_id: "DLC2MageArmor50NPC", description: "Quick Test Cell" }` (the CELL FULL string wins over the PERK DESC string). The FO4 pair collides with stray Japanese text in `Fallout4_en.DLSTRINGS`, benign in practice.
- **Impact**: one wrong perk description in vanilla Dragonborn; modded plugins can collide more (each mod allocates ids per table). No crash, wrong text.
- **Suggested fix**: pass the preferred table to the lookup (DESC and long-text sub-records -> DLSTRINGS, INFO `NAM1` -> ILSTRINGS, everything else -> STRINGS) and keep the current order only as the fall-through. - **Status**: NEW (closed #4074 only marked the arm provisional)
- **Description**: xEdit's Starfield definition has no `BOD2` on ARMO/ARMA.
