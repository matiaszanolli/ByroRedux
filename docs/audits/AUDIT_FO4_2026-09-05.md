## Executive Summary

**4 findings — 0 CRITICAL, 1 HIGH, 2 MEDIUM, 1 LOW.**

The FO4 path is in good shape. NIF (BSVER 130 + Next-Gen), BA2 v1/v7/v8, the
BGSM/BGEM parser, SCOL/PKIN expansion and the **M49 CSG precombine pipeline** are
all landed and all their regression pins survive. Re-measured this audit:

```

  Fallout4 - Meshes.ba2       41 697      DLCRobot - Main.ba2          3 647
  Fallout4 - MeshesExtra.ba2 124 871      DLCworkshop01 - Main.ba2       242
  DLCCoast - Main.ba2         34 411      DLCworkshop02 - Main.ba2       387
  DLCNukaWorld - Main.ba2     27 511      DLCworkshop03 - Main.ba2     2 316
```

Every checklist pin in Dimensions 1, 3, 4, 6, 7, 8 and 9 verified INTACT — see
the per-dimension sections. In particular the three "invisible if reverted"
pins the preset cares about are all live: `merge_external_material` still takes
`&mut ImportedMaterial` (not `&mut ImportedMesh`), `bgsm_metalness` still derives
legacy metalness from spec-colour **saturation** and not luminance (#1476), and
the `1.0 - smoothness` inversion is applied exactly once.

**The one substantive result of this audit is a role-consumption gap, not a
role-mapping error.** The 2026-07-27 unification and its follow-ups (#2997,
#2998, #2999, #3085) routed FO4's slots into the right canonical roles — the
corpus census below reproduces every occupancy claim those issues made. What
was never wired is the *enable signal* for one of those roles on the lit path:

> FO4 authors a greyscale→palette remap on **30 166** `BSLightingShaderProperty`
> blocks and on **282** vanilla BGSMs. The LUT texture reaches the GPU. The
> enable bit never does. The shader branch that would consume it
> (`crates/renderer/shaders/triangle.frag:1202-1212`) is dead code on FO4 content.

That is FO4-2026-09-05-D5-01 (HIGH), with an independent second gate on the
BGSM lane as FO4-2026-09-05-D2-01 (MEDIUM).

**Still open forward scope** (do NOT re-file): `_precomb.nif` collision, `.uvd`
occlusion volumes, MOVS physics runtime, FaceGen NIF truncation tail, deeper cell
coverage (LIGH power state / CONT leveled items / NPC_ face morph),
`BSBehaviorGraphExtraData` parse-only. The CSG reader, the BGSM parser and
SCOL/PKIN expansion are **shipped** and are not listed as pending anywhere in
this report.

## Dimension Findings

### FO4-2026-09-05-D5-01: FO4's greyscale→palette remap is unreachable on the lit path — the LUT binds, the enable bit never does

- **Severity**: HIGH
- **Dimension**: 5 (FO4 shader flags & BGSM PBR routing) — consumed at Dimension 7
- **Location**: `crates/nif/src/import/material/mod.rs:1530-1535` (the hardcoded
  `false`s) · `crates/nif/src/import/material/shader_data.rs:12,48-56` (the only
  reader of the palette bits) · `byroredux/src/cell_loader.rs:318-325` (the packer)
  · `crates/renderer/shaders/triangle.frag:1202-1212` (the dead branch)
- **Status**: NEW
- **Description**:
  `slot_to_role` routes FO4 `BSShaderTextureSet` slot 3 to
  `TextureRole::GreyscaleLut` (`crates/nif/src/import/material/slot_role.rs:352-354`,
  the #2997 fix), and `MaterialInfo::into_imported_material` copies
  `greyscale_lut_map` into `ImportedMaterial.textures.greyscale_lut`
  (`crates/nif/src/import/material/mod.rs:1307`). The role therefore reaches
  `MaterialTextureHandles`, `DrawCommand::greyscale_lut_index`
  (`byroredux/src/render/static_meshes.rs:349`) and
  `GpuMaterial::greyscale_lut_index` — the texture *is* bound.

  What never reaches the GPU is the **enable flag**. `crates/renderer/shaders/triangle.frag`'s lit-path
  remap is gated on `MAT_FLAG_EFFECT_PALETTE_COLOR`, and the only producer of
  that bit for a non-effect material is `pack_imported_material_flags`, which
  gates it on `material.bgsm_greyscale_lut_enabled`
  (`byroredux/src/cell_loader.rs:318`). `into_imported_material` hardcodes that
  field — and its sibling `bgsm_greyscale_lut_color` — to `false`:

  ```rust
  // crates/nif/src/import/material/mod.rs:1529-1535
  grayscale_to_palette_scale: self.grayscale_to_palette_scale,
  bgsm_greyscale_lut_is_alpha: false,
  // #2108 — no BGSM/BGEM has merged yet at this NIF-import stage …
  bgsm_greyscale_lut_color: false,
  bgsm_greyscale_lut_enabled: false,
  ```

  The NIF's own authored signal is available and is simply not read. FO4
  properties carry `SLSF1::Greyscale_To_PaletteColor`
  (`fo4_slsf1::GREYSCALE_TO_PALETTE_COLOR = 0x0000_0010`,
  `crates/nif/src/shader_flags.rs:177`), and the decoder helpers already exist —
  `is_palette_color_from_modern_shader_flags` /
  `is_palette_alpha_from_modern_shader_flags`
  (`crates/nif/src/import/material/mod.rs:242,261`). They have **exactly one
  caller**: `capture_effect_shader_data(shader: &BSEffectShaderProperty)`
  (`crates/nif/src/import/material/shader_data.rs:12,48,53`), reached only from
  the `BSEffectShaderProperty` arm at
  `crates/nif/src/import/material/dedicated_shader.rs:604`. The
  `BSLightingShaderProperty` arm never looks at the bit.
- **Evidence** (measured this audit, `Fallout4 - Meshes.ba2` +
  `Fallout4 - MeshesExtra.ba2`, 810 489 non-stub properties):

  ```
  slot 3 non-empty (any):                     31 303
  SLSF1 Greyscale_To_PaletteColor set:        30 166   (of which slot 3 non-empty: 30 155)
  SLSF1 Greyscale_To_PaletteAlpha set:             0
  ```

  and from `Fallout4 - Materials.ba2` (6 616 BGSM / 283 BGEM parsed):

  ```
  BGSM authoring grayscale_to_palette_color:     282   (all 282 also author a LUT texture)
  BGEM authoring grayscale_to_palette_color:      37
  BGEM authoring grayscale_to_palette_alpha:      26
  ```

  Both independent signals say "remap on"; neither reaches
  `GpuMaterial.material_flags`. Sample affected assets (LUT path shown is the
  slot-3 binding):
  `meshes\actors\character\characterassets\hair\male\hair24.nif` →
  `Actors/Character/Hair/HairColor_Lgrad_d.dds`;
  `meshes\armor\minuteman\foutfit.nif` →
  `Armor/CombatArmor/CombatArmor_palette_d.dds`;
  `meshes\interiors\hightech\floors\hitfloorsolidfull01.nif` →
  `Interiors/HighTech/Grads/MetalFloorTiles01Grad.dds`;
  `meshes\scol\fallout4.esm\cm00179b49.nif` →
  `Architecture/Buildings/Bricks01Grad01.dds`.
- **Impact**: every vanilla FO4 surface authored as "greyscale ramp + palette
  LUT" renders as the raw greyscale ramp. That is all hair and facial hair
  (`HairColor_Lgrad_d`), power/combat armour palettes, vehicle rust and paint
  variants, Institute / high-tech interior panelling, and brick / painted-wood
  architecture — ~30 k shader properties, i.e. a large fraction of the game's
  colour variation. Blast radius is FO4-only (Skyrim's slot 3 is Height, FO76's
  greyscale path is BGSM-driven), which is exactly the class the preset was
  looking for: correct in one game, silently wrong in another.
- **Related**: #2997 (routed slot 3 into the role), #2108 (fixed the enable-bit
  derivation for the BGSM lane), #890 / #2610 / #3589 (wired the effect-shader
  and particle lanes). The lit + inline-NIF lane was never wired. This finding
  is the missing third lane, not a regression of any of them.
  Pairs with FO4-2026-09-05-D2-01 below.
- **Suggested Fix**: read
  `is_palette_color_from_modern_shader_flags(shader.shader_flags_1, &sf1_crcs,
  &sf2_crcs)` (and the alpha sibling) in the `BSLightingShaderProperty` arm of
  `crates/nif/src/import/material/dedicated_shader.rs`, carry them on `MaterialInfo`, and let
  `into_imported_material` forward them instead of hardcoding `false`. Keep the
  existing `greyscaleLutIndex != 0` guard. **Caveat for the fix**: 1 132 of the
  31 303 slot-3 bindings are `shared/cubemaps/mipblur_defaultoutside1_dielectric.dds`
  — a cubemap authored into the gradient slot. Those would begin sampling a
  cubemap as a 1-D LUT; consider rejecting cubemap-shaped LUTs at resolve time
  or auditing that sub-population separately before enabling.

### FO4-2026-09-05-D2-01: the BGSM palette-enable bit is dropped whenever the NIF already filled the `greyscale_lut` role

- **Severity**: MEDIUM
- **Dimension**: 2 (BGSM/BGEM consumption)
- **Location**: `byroredux/src/asset_provider/material.rs:1480-1485`
- **Status**: NEW
- **Description**: the #2108 enable-capture is gated on the LUT slot still being
  empty:

  ```rust
  if material.textures.greyscale_lut.is_none() && !bgsm.greyscale_texture.is_empty() {
      material.bgsm_greyscale_lut_enabled = bgsm.base.grayscale_to_palette_color;
      material.bgsm_greyscale_lut_color   = bgsm.base.grayscale_to_palette_color;
  }
  ```

  That guard was written when nothing on the FO4 NIF side wrote
  `textures.greyscale_lut`. Since #2997 (2026-08-16) the FO4 importer fills it
  from `BSShaderTextureSet` slot 3 *before* `merge_external_material` runs, so
  on FO4 the `is_none()` test is false for exactly the population that authors
  the palette — and the whole BGSM template chain's enable bit is discarded,
  not merely deprioritised. The `is_none()` precedence is right for the
  *texture*; it is wrong for the *flag*, which is a property of the material
  file regardless of who won the slot.
- **Evidence** (measured this audit):
  - 28 467 non-stub FO4 `BSLightingShaderProperty` blocks have **both** a
    `.bgsm` material name **and** a non-empty slot 3.
  - 246 unique BGSM paths are referenced by such a property; **239 of those 246**
    author `grayscale_to_palette_color = true`.
  - Consequence chain identical to D5-01: `bgsm_greyscale_lut_enabled` stays
    `false` → `pack_imported_material_flags` (`byroredux/src/cell_loader.rs:318`)
    omits `EFFECT_PALETTE_COLOR` → `crates/renderer/shaders/triangle.frag:1202-1212` never runs.
- **Impact**: an independent second gate on the same failure. Fixing D5-01 alone
  covers the 30 155 properties that set the NIF bit, but leaves the ~1 100
  slot-3 properties that rely purely on BGSM authoring, plus any modded or
  override material that supplies the enable bit externally, still dark. Both
  gates must open.
- **Related**: #2108, #2643, #1353, #1580; FO4-2026-09-05-D5-01.
- **Suggested Fix**: split the two concerns — capture
  `bgsm.base.grayscale_to_palette_color` (child-first, i.e. behind its own
  `set_palette_enable` latch like every other scalar in that loop) independently
  of whether `fill` won the texture slot, and keep the `is_none()` guard on the
  texture fill only.

### FO4-2026-09-05-D2-02: `peek_magic` re-extracts and re-inflates the whole material file on every merge, bypassing both material caches

- **Severity**: MEDIUM
- **Dimension**: 2 (BGSM/BGEM consumption) — performance
- **Location**: `byroredux/src/asset_provider/material.rs:787-790` (definition),
  `:1266` (unconditional call site)
- **Status**: NEW
- **Description**: `merge_external_material` resolves its BGSM-vs-BGEM dispatch
  by file magic (#758, correct), but does so via

  ```rust
  fn peek_magic(&self, path: &str) -> Option<MaterialKind> {
      let bytes = self.extract_from_archives(path)?;   // full archive read + zlib inflate
      byroredux_bgsm::detect_kind(&bytes)
  }
  ```

  called unconditionally at `:1266`, before dispatch. It has no memo of its own
  and consults neither `bgsm_cache`, `bgem_cache` nor `failed_paths`. So for
  every `ImportedMesh` at NIF-cache-fill time — including every mesh whose
  material is already parsed and cached, and every mesh whose material is
  already a known failure — the provider takes the archive's file-handle
  `Mutex`, seeks, reads and zlib-inflates the whole material file just to look
  at four bytes, then throws the buffer away. Under `#3637`'s last-listed-wins
  loop this can also miss through several archives before hitting.
- **Evidence**: `extract_from_archives` (`:637-660`) → `Archive::extract` →
  `Ba2Archive::extract` (`crates/bsa/src/ba2.rs:391-...`), which locks
  `self.file` and decompresses. Both caches sit *downstream* of this call, in
  `resolve_bgsm` (`:664`) and `resolve_bgem` (`:816`). Note also that #2615
  ("`Archive::open` reads a multi-GB archive into RAM just to sample 4 magic
  bytes") is the same anti-pattern one level up, and was fixed; this instance
  was not covered by it.
- **Impact**: load-time / streaming-worker cost that scales with mesh count and
  serialises on the archive mutex, on the same `byroredux/src/cell_loader/references/import.rs` path the
  M40 cell streamer runs under a work budget. The wall-clock magnitude was
  **not measured** in this audit — the mechanism is what is being reported.
- **Related**: #758 (the magic-vs-extension dispatch this implements), #2615.
- **Suggested Fix**: memoise the detected `MaterialKind` per normalised path
  alongside the existing caches (or derive it from the cached parse result and
  only call `peek_magic` on a cache miss), and short-circuit on `failed_paths`.

### FO4-2026-09-05-D2-03: `record_external_texture_sources` hand-lists all 22 canonical roles with no exhaustiveness guard

- **Severity**: LOW
- **Dimension**: 2 (BGSM/BGEM consumption) — test-gap
- **Location**: `byroredux/src/asset_provider/material.rs:1053-1091`
- **Status**: NEW
- **Description**: the provenance recorder that decides which roles get tagged
  `Bgsm`/`Bgem`/`Mat` in `MaterialTextureDebugInfo` re-types the role list by
  hand as a `record!(field)` macro sequence plus a decal loop, instead of using
  the generic walkers `MaterialTextureSet` exists to provide
  (`map_ref`, `zip_map_ref`, `roles()`, `values()` —
  `crates/nif/src/import/types.rs:361-500`). It has no caller other than the one
  at `:2037` and **no test at all**. This is precisely the drift class that
  `roles_covers_every_field_in_the_set` and `values_covers_every_field_in_the_set`
  (#3734) were added to close for the other two walkers, and that
  `documented_texture_role_list_matches_the_struct`
  (`byroredux/src/material_translate.rs:1835`) closes for the prose.
- **Evidence**: the macro list is currently complete and correct — 22 named
  roles + the 4-decal loop, matching the struct. Add a 23rd role and it compiles
  clean while silently reporting that role's provenance as the `Default`
  (`NifTextureSet`) even when a BGSM filled it.
- **Impact**: diagnostic-only. `mat.dump` and `tex.missing` would mislabel a
  newly-added role's provenance, which is the exact oracle used to prove an
  XTXR/TXST override landed in the intended semantic role. No runtime rendering
  effect.
- **Related**: #3734, #3465, #3349.
- **Suggested Fix**: rewrite as a `before.zip_map_ref(&material.textures, …)`
  producing the source set, so the compiler enforces exhaustiveness the way it
  already does for `map_ref`.
