## Findings — HIGH (1)

### ESM-2026-08-24-D5-01: Fallout 4 `WATR.DNAM` above-water fog near/far, added this cycle at offsets 12/16, are not fog distances — real data collapses the fog ramp to ~1 world unit on every vanilla FO4 water body

- **Severity**: HIGH
- **Dimension**: CELL / WRLD Walkers (WATR record schema)
- **Record / Sub-record**: `WATR` / `DNAM`
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:1068-1088`
  (`decode_dnam_fo4`); regression surfaced by
  `crates/plugin/tests/parse_real_esm.rs:1414-1435` (`parse_rate_fo4_esm`,
  pre-existing, untouched by the commit that introduced the bug)
- **Status**: NEW
- **Description**: Commit `7f752c0c` ("separate creation depth amount from
  fog") correctly split FO76 and Starfield's `decode_dnam_fo76` /
  `decode_dnam_starfield` so `depth_amount` (DNAM offset 0) no longer
  overwrites the canonical `fog_near`/`fog_far` defaults (80.0/600.0). For
  FO4 it did something different and unverified: it kept `depth_amount` at
  offset 0 (correct, and it *is* what vanilla ships — see evidence) but
  **also** added two new reads, claiming "the authored above-water color-ramp
  near/far distances are the floats at 12/16":
  ```rust
  if let Some(near) = read_f32_at(data, 12) {
      p.fog_near = near;
  }
  if let Some(far) = read_f32_at(data, 16) {
      p.fog_far = far.max(p.fog_near + 1.0);
  }
  ```
  The function's docstring says this is "byte-checked against vanilla
  `ExtOceanWater`" — but that docstring predates the change (it was not
  updated when 12/16 were added) and describes the *original* prefix decode,
  not this new pair. No commit message, code comment, or test evidence ties
  offsets 12/16 to fog distances against real bytes; the only test that
  exercises them is the synthetic fixture at `water.rs:2072-2073`
  (`parse_watr_decodes_fo4_visual_data_layout`), which — like the FO76
  tautology flagged in the 2026-08-20 report — writes `86.0`/`580.0` at
  those offsets and asserts they read back. It cannot falsify the offset
  claim it encodes.
- **Evidence**: Independent GRUP walk of `Fallout4.esm` (not through this
  parser), all 15+ WATR records with a 201-byte `DNAM` inspected. Offset 12
  is **constant 1.0 on 14/15 records** (0.97 on the 15th); offset 16 ranges
  **0.56–0.93** with no record above 1.0:
  ```
  EDID                             off 0 (depth)  off 12   off 16
  ExtOceanWater                        3006.9998   1.0000   0.9299
  ExtLakeQuannapowittWater             1087.000    1.0000   0.8479
  IntWestonWater                        471.000    0.9835   0.8045
  ExtBloodyWater                        580.000    1.0000   0.9267
  IntTroughWater                         18.000    1.0000   0.9275
  ExtRiverCharlesUpper                  435.000    1.0000   0.5638
  ... (15 records sampled, same pattern throughout)
  ```
  A near-constant `1.0` and a `0.56–0.93` range are not plausible authored
  fog-ramp distances (compare to `depth_amount` at offset 0, which is
  authored per-water in the hundreds-to-thousands range, or to the
  DNAM-20/24/28/32 `alpha_controls` block, which is the same 0–1 magnitude
  and is *already* the parser's own documented home for values in this
  range). For `ExtOceanWater` specifically: `fog_near` reads back `1.0`,
  `fog_far` reads back `far.max(near+1.0) = max(0.9299, 2.0) = 2.0` — a value
  that is not present anywhere in the source bytes; it is fabricated by the
  clamp because the "far" read is smaller than the "near" read plus one.
- **Impact**: `byroredux/src/env_translate.rs:527-528` copies
  `params.fog_near`/`fog_far` straight into `WaterMaterial` with no other
  gate, and `crates/renderer/shaders/water.frag:437-470` uses that pair as
  the literal span of the above-water depth-fog ramp (clear at `fog_near`,
  fully `deep_color` at `fog_far`). At `fog_near=1.0, fog_far=2.0` every FO4
  water surface reaches full fog color within ~1 world unit of view depth —
  every vanilla FO4 lake, river, and ocean body renders as near-opaque
  `deep_color` at essentially any viewing angle, instead of the intended
  hundreds-to-thousands-unit ramp `depth_amount` (still correctly decoded
  and available) was meant to drive. This is FO4-only; FO76 and Starfield
  were fixed correctly in the same commit and are unaffected.
- **Related**: Introduced by the same commit (`7f752c0c`) that correctly
  fixed the equivalent FO76/Starfield case — the FO4 arm is the one outlier
  that added a new, unverified offset claim instead of following the
  established pattern (keep `fog_near`/`fog_far` at their canonical
  defaults, carry `depth_amount` independently). Same tautological-fixture
  defect class as 2026-08-20's ESM-2026-08-20-D5-03 (`decode_dnam_fo76`) and
  the project's standing `feedback_no_guessing` policy.
- **Suggested Fix**: Delete the two new reads at offsets 12/16 from
  `decode_dnam_fo4`; let `fog_near`/`fog_far` stay at `WaterParams::default`
  (80.0/600.0), matching the FO76/Starfield arms in the same commit and the
  the pre-`7f752c0c` behavior this function had before the regression.
  `depth_amount` is already correctly decoded and is the field that should
  eventually drive an FO4-specific fog treatment once its true shader role
  is worked out — not offsets 12/16, which the byte evidence above rules
  out. Restore `parse_rate_fo4_esm`'s original assertions
  (`fog_near == 0.0` was itself an artifact of the pre-`depth_amount` split
  and should become `fog_near == 80.0`/`fog_far == 600.0` to match the
  restored default-carrying behavior) and replace the synthetic
  `parse_watr_decodes_fo4_visual_data_layout` assertions on offsets 12/16
  with real-data assertions or remove them.
