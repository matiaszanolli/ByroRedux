### Sibling cross-findings — verified FNV-side, deliberately NOT re-filed

Per the dispatch, these were confirmed against FNV data rather than re-derived:

1. **FO3/FNV `WATR.DNAM` decoded by the 52-byte Skyrim prefix reader** —
   `ESM-2026-08-20-D5-01` / `LC-D6-01`. Reproduced exactly: `FalloutNV.esm` carries
   78 `WATR`, of which **69 use a 196-byte `DNAM`** (+1 at 184 B) = 88.5 %, all

   (`crates/plugin/src/esm/records/misc/water.rs:1358`), which returns after byte 52.
   **New corroborating evidence this audit adds**: the FNV 196-byte `DNAM` and the
   FNV 186-byte `DATA` are the *same* layout, byte for byte —

   ```
   NVCleanWater      DNAM[0..56] = 3.0  90.0 0.2 0.25 826.0 0.6  0.75 0.0 -80.0   850.0 …
   WaterTypeDirty    DNAM[0..56] = 0.1  90.0 0.5 1.00 355.0 0.1  0.80 0.0 -700.0   36.0 …
   DupontFontWater   DATA[0..56] = 0.1  90.0 0.5 1.00 1000.0 0.87 0.03 0.0   0.0   72.0 …
   d5TerribleWater   DATA[0..56] = 0.1  90.0 0.5 1.00  50.0 0.5  0.02 0.0 -1000.0 1000.0 …
                                                  ^16   ^20  ^24  ^28  ^32     ^36
                                            specular  refl fresnel pad fog_near fog_far
   ```

   `decode_data_fo3nv` (`:555-688`) and `decode_dnam_pre_fo4` (`:694-753`) already
   agree field-for-field on offsets 16–52; the only divergence is the 0–16 prefix
   (which `decode_data_fo3nv` calls opaque and `decode_dnam_pre_fo4` reads as
   wind/wave) and the 56–192 tail (which only `decode_data_fo3nv` reads). So the fix
   is a one-line dispatch change — route `GameKind::Fallout3NV` `DNAM` to
   `decode_data_fo3nv` — not a new decoder. Filed under the ESM audit; not re-filed here.
2. **Rain/displacement simulator block misaligned by one field in the FO3/FNV
   decoder** — `LC-D6-01`. Confirmed present at HEAD
   (`decode_data_fo3nv:585-604`, `displacement.zip([72, 84, 88])` /
   `rain_start_size` ← 92 / `normal_magnitude` ← 96). Not re-filed.
3. **`wind_direction` = constant `90.0` stored raw into a radians field** —
   verified: **69/69** 196-byte FNV `DNAM` records carry exactly `90.0f` at offset 4,
   and `decode_dnam_pre_fo4:706` assigns it with no `to_radians()` while the sibling
   `decode_data_fo3nv:661` *does* convert its equivalent. Already covered by
   `ESM-2026-08-20-D5-01` and the `watr_data_layout_shift` memory note. Not re-filed.
   Blast radius on FNV is currently **nil** because of FNV-2026-08-20-D1-02 below
   (the value is only read for non-`Calm` water, and no FNV record is non-`Calm`) —
   fixing D1-02 without fixing the unit error would make it live.

## Findings

### FNV-2026-08-20-D1-01: the new `FNAM & 0x02` reflective gate zeroes authored reflectivity on 36 of 78 vanilla FNV water records — and FNV's own data disproves the premise

- **Severity**: HIGH
- **Dimension**: 1 — Cell Loading End-to-End (WATR → canonical water); impact lands in Dimension 3 (RT reflections)
- **Location**: `byroredux/src/env_translate.rs:716-725` (`resolve_water_material`),
  fed by `crates/plugin/src/esm/records/misc/water.rs:1305-1307` (`legacy_flags`)
- **Status**: NEW — introduced in this delta by `02c0d4b6` ("fix(water): honor legacy
  reflective flags", 2026-08-19), a 51-line commit whose body is its subject line
- **Changed File**: yes (`env_translate.rs` is #3 on `/tmp/audit/hot_files.txt`)
- **Description**: `resolve_water_material` reads authored reflectivity out of the
  record and then overrides it to zero when the `FNAM` byte does not have bit `0x02`:

  ```rust
  mat.reflectivity = rec.params.reflectivity;
  // FO3/FNV's legacy FNAM bit 0x02 is an explicit reflective
  // surface gate. Preserve authored reflectivity when the flag is
  // present; when it is explicitly absent, suppress the RT
  // reflection contribution instead of making non-reflective
  // sludge/puddle records mirror-bright.
  if rec.legacy_flags.is_some_and(|flags| flags & 0x02 == 0) {
      mat.reflectivity = 0.0;
  }
  ```

  `mat.reflectivity` is uploaded as `tint_reflect.w`
  (`byroredux/src/render/water.rs:271`, `crates/renderer/src/vulkan/water.rs:88-96`)
  and multiplies the entire Schlick-Fresnel RT reflection term in
  `crates/renderer/shaders/water.frag:40`. Zero means no reflection at all.

  The premise is a generalisation from Oblivion (where `LC-D5-01` shows the
  correlation is exact). It does not transfer to FO3/FNV, and FNV ships the
  counterexample.
- **Evidence** — all from vanilla `FalloutNV.esm` (78 `WATR` records, 245 650 747 B master):

  **1. FNV authors reflectivity as a float in `DNAM`, not as an `FNAM` bit.**
  `NVCleanWater` (`001009CA`) and `NVCleanWaterNoReflect` (`0017B612`) have
  **byte-identical 196-byte `DNAM` payloads except for one f32**:

  ```
  DNAM offset 20:  NVCleanWater = 0.6 (9a99193f)  →  NVCleanWaterNoReflect = 0.0 (00000000)
  every other one of the 49 f32 slots: identical
  FNAM:            NVCleanWater = 0x02            →  NVCleanWaterNoReflect = 0x02   (unchanged)
  ```

  Offset 20 is exactly what `decode_dnam_pre_fo4:719` already reads into
  `p.reflectivity`. The author who needed a non-reflective variant of a water type
  zeroed that float and **left `FNAM` bit 0x02 set**. The bit is not the reflectivity
  channel on FO3/FNV, and the authored float already carries the "not reflective"
  signal the new gate was written to supply.

  **2. `FNAM` bit 0x02 is clear on 44 of 78 records, 36 of which author non-zero
  reflectivity.** Ranked by how many `CELL` `XCWT` references point at them:

  ```
  EDID                              FormID    FNAM  DNAM refl   cells
  WaterTypeUtility                  000B03A7  0x00     0.100       18
  PPurityWater01Murky               000AED89  0x00     0.020       18
  BuzzardPointWater                 000881EE  0x00     0.180       14
  WaterTypeDirty                    00075387  0x00     0.100        8
  WaterTypeIrradiated               000B03A9  0x00     1.000        4
  RadioactiveWater                  0015F8B2  0x00     0.180        2
  CreekWater02AVGnv                 00172DF0  0x00     0.230        1
  WaterTypeDirtyDark                0007538A  0x00     0.100        1
  d4BadWater10r20h                  000AFB9A  0x00     0.370        1
  … 27 more with 0 direct XCWT refs (WaterTypeCave 0.75, WaterTypeVault92 1.00,
    LamplightWater 1.00, DCMallWater 1.00, ReflectingPoolWaterType 0.29,
    TakomaParkMuddyWater 0.53, TGWater03 0.82, WaterTypeOasisClean 0.50, …)
  ```

  **67 of 451 `XCWT`-bearing cells** lose their authored reflection outright.

  **3. The gate is purely destructive — it can never add correct behaviour.** Because
  FNV encodes "not reflective" as `DNAM[20] == 0.0`, every record the gate zeroes was
  already going to be correct without it, and the four cells using
  `NVCleanWaterNoReflect` — the one record whose EditorID states the intent — are
  *unaffected* by the gate (bit set) and correct only because of the float. The gate
  therefore has a 100 % false-positive rate on this corpus.

  **4. The name-based read is inverted in both directions.** `ReflectingPoolWaterType`
  (`00074893`, reflectivity `0.29`) is gated OFF; `NVCleanWaterNoReflect` is gated ON.
- **Impact**: On the reference title, RT reflections vanish from 15.3 % of
  `XCWT`-referenced water cells, including the Goodsprings-era `CreekWater02AVGnv`,
  the 18-cell `WaterTypeUtility` and `PPurityWater01Murky` families, and all
  irradiated/toxic water — with no log line, no telemetry counter and no test that can
  see it. The change is a delta-local regression: before `02c0d4b6` these surfaces
  rendered with their authored `0.02`–`1.00` reflectivity. Same code path, same bit,
  same era gate on FO3 (`Fallout3.esm` shares most of these very records), so treat
  the blast radius as both pre-FO4 Fallout titles. Scored HIGH per the severity
  table's "affects rendering correctness" row and the skill's "a defect that reaches
  FNV is higher-impact" rule; it is not CRITICAL because nothing crashes or corrupts.
- **Related**: `LC-D5-01` (the Oblivion half, where the bit-0x01/bit-0x02 correlation
  *does* hold — that finding's suggested fix explicitly claims the FO3/FNV meaning is
  the same, which this data contradicts; the two should be reconciled before either is
  implemented). `ESM-2026-08-20-D5-01` (the `DNAM` prefix reader that makes offset 20
  one of the few tail-adjacent fields that *does* survive today). FNV-2026-08-20-D4-01
  below (the sibling bit-0x01 claim, disproved the same way).
- **Suggested Fix**: Delete the `legacy_flags & 0x02` override from
  `resolve_water_material`. The authored `DNAM`/`DATA` offset-20 scalar is already the
  reflectivity channel on FO3/FNV and already encodes zero for non-reflective records.
  If a gate is still wanted for Oblivion (where `LC-D5-01`'s correlation stands),
  scope it to `GameKind::Oblivion` explicitly rather than to the presence of
  `legacy_flags`, which is set for five game kinds. Pin the fix with a fixture built
  from the `NVCleanWater` / `NVCleanWaterNoReflect` pair — they differ in exactly one
  float and are a ready-made two-row regression test.

### FNV-2026-08-20-D1-02: every vanilla FNV water record classifies `Calm` — the `WaterKind` token set has no FO3/FNV vocabulary, so `WaterFlow` is unreachable on the reference title

- **Severity**: MEDIUM
- **Dimension**: 1 — Cell Loading End-to-End (WATAL flow arm)
- **Location**: `byroredux/src/env_translate.rs:912-947` (the `WaterKind` classifier
  inside `resolve_water_material`), consumers at `:961-1010` (flow synthesis + scroll
  bias) and `byroredux/src/cell_loader/water.rs:531` / `:858` (the
  `if let Some(flow) = flow` inserts)
- **Status**: NEW
- **Changed File**: yes — the classifier's `has_authored_linear_flow` /
  `flow_noise_texture_path_is_enabled` arms and the `WATER_SCROLL_UV_PER_BU_PER_S`
  conversion are delta work (`#2872`-era commits in `commits_since_last.txt`)
- **Description**: A cell's water becomes `Rapids` / `River` (and therefore gets a
  `WaterFlow` component, `foam_strength > 0`, and a flow-biased UV scroll) only if one
  of five signals fires:

  ```rust
  lowered.contains("rapid")            // EDID token
  lowered.contains("waterfall") | "falls" | "river" | "stream"
  rec.flow_noise_texture_path_is_enabled()   // NAM5 — Skyrim SE+
  has_authored_linear_flow                   // NAM0 — FO76/Starfield
  authored_flow_speed >= WaterFlow::SPEED_RAPIDS
  ```

  **None of the five can fire on FNV.** The token list is Skyrim vocabulary; FNV names
  its moving water `Creek*`, `Potomac*`, `*Spill`, `*Fountain`. And FNV's `WATR`
  sub-record set does not contain `NAM0` or `NAM5` at all.
- **Evidence** — full sub-record census over all 78 `FalloutNV.esm` `WATR` records:

  ```
  EDID 78 · NNAM 78 · ANAM 78 · FNAM 78 · MNAM 78 · XNAM 73 · DATA 78 · DNAM 70 · GNAM 78 · SNAM 32 · FULL 40
  NAM0: 0     NAM1: 0     NAM2/3/4: 0     NAM5: 0
  ```

  and the complete EditorID roster contains zero occurrences of
  `rapid` / `waterfall` / `falls` / `river` / `stream`. The flowing-water records FNV
  actually ships are `CreekWater01`, `CreekWater02nv`, `CreekWater02AVGnv`,
  `CreekWater02nvbetter`, `RockCreekEstatesWater`, `Potomac`, `PotomacNRShallow`,
  `DLC03TBPotomacWater`, `ToxicSpillPuddle`, `TenPenWaterFountain`, `VStripULFountain`
  — all `Calm`. `Potomac` (`00030009`) is the **`WRLD` `NAM2` default water for
  WastelandNV** and nine other worldspaces, so the exterior grid the engine benches on
  is classified `Calm` too.
- **Impact**: Three shipped WATAL behaviours are dead on the reference title and
  cannot regress visibly there: the physics current (`WaterFlow` → `WaterCurrentVolume`
  → buoyancy drift, `crates/physics/src/water.rs`), the flow-biased shader scroll
  (`mat.scroll_a/b/c` keep their static defaults), and `foam_strength` (stays at the
  `WaterMaterial` default instead of `0.20`/`0.85`). Because FNV is the title with the
  bench-of-record and the only non-Skyrim smoke gate, the flow half of WATAL is
  exercised by **no** FNV path — which is also why the `wind_direction` radians unit
  error (cross-finding 3) is currently invisible here: the value is read only inside
  the `!matches!(kind, WaterKind::Calm)` block. Fixing this classifier without fixing
  that unit error would turn a dormant bug into a live one, giving every FNV river a
  flow direction of `(cos 90 rad, sin 90 rad) = (-0.448, 0.894)`.
- **Related**: `LC-D5-02` (the *other* `WaterKind` classifier,
  `material_translate.rs::water_kind_from_mesh_name`, has a third token set including
  `canal` — but it is called only from `byroredux/src/scene/nif_loader.rs:1028`, the
  loose-NIF path, so it never runs during an FNV cell load and does not compensate);
  `ESM-2026-08-20-D5-01` (the `wind_direction` unit error this masks);
  `PHYS-D6-05`/`PHYS-D6-04` (the physics end of the same flow path).
- **Suggested Fix**: Add the FO3/FNV vocabulary to the shared token list —
  at minimum `creek`, `canal` (already in the mesh-side list) and `spill` — and, better,
  hoist the two divergent token sets into one shared classifier as `LC-D5-02` proposes
  so a token added for one producer reaches both. Do not land it before the
  `wind_direction` radians conversion is fixed, or gate `WaterFlow` synthesis on a
  finite, converted direction. Pin with a fixture asserting `CreekWater02nv` →
  `WaterKind::River`.

### FNV-2026-08-20-D4-01: `watal.md` records FO3/FNV water damage as AUTHORED via `FNAM` bit 0x01 — no vanilla FNV record sets that bit and none authors a non-zero damage value

- **Severity**: MEDIUM
- **Dimension**: 4 — ESM Record Parser (this game's data through it)
- **Location**: `byroredux/src/cell_loader/water.rs:492-502` and `:825-835` (the two
  `damage_per_second` filters), `crates/plugin/src/esm/records/misc/water.rs:1327-1345`
  (the `DATA` arm that populates `legacy_damage`), spec claim at
  `docs/engine/watal.md:479` and `:309`
- **Status**: NEW
- **Description**: Both `WaterPlane` spawn sites gate the canonical damage channel on

  ```rust
  record.water_flags.or(record.legacy_flags).is_some_and(|flags| flags & 0x01 != 0)
  ```

  and then take `record.legacy_damage`, which is populated only from a **2-byte**
  `DATA` sub-record. `docs/engine/watal.md`'s §4 provenance table asserts that for
  FO3/FNV this row is **AUTHORED**:

  > `| legacy water damage | SENTINEL | AUTHORED when FNAM bit 0x01 is set | SENTINEL | DATA uint16 damage + FNAM |`

  Vanilla FNV satisfies neither half of the gate.
- **Evidence** — from `FalloutNV.esm`:

  ```
  FNAM byte histogram over all 78 WATR records:   { 0x02: 34, 0x00: 44 }
                                                    ← bit 0x01 never set, on any record
  2-byte DATA damage values (70 records carry one): all zero
                                                    ← including RadioactiveWater, WaterTypeIrradiated,
                                                      ToxicDumpPool01/02, d5TerribleWater20r4h
  The 8 records with a long 186-byte DATA never reach the `sub.data.len() == 2` arm at all,
  so they cannot populate `legacy_damage` under any flag value.
  ```

  FNV's actual water-hazard channel is `XNAM`, present on **73 of 78** records (a
  4-byte FormID pointing at the radiation/poison actor effect — e.g. `0x00045656`,
  `0x000B878F`, `0x00020D78`). `parse_watr` has no `XNAM` arm; the field is discarded.
- **Impact**: `WaterPlane::damage_per_second` is structurally `0.0` for every FNV cell.
  The consumer is live and runs every frame
  (`WaterContact::damage_per_second` → `water_damage_for_contact`,
  `byroredux/src/systems/character.rs:1048`, applied at `:480-481`), so the reference
  title exercises the code path with a permanently-zero input — the same
  green-by-construction shape catalogued elsewhere in this sweep. The concrete
  consequence is that swimming through Vault 22's irradiated water or the toxic dump
  pools is free, and the spec table tells a reader checking it that this is correct
  FNV behaviour. Scored MEDIUM, matching `LC-D5-01`'s scoring of the structurally
  identical Oblivion defect, even though FNV is the higher-impact title — because
  unlike Oblivion, FNV genuinely authors `0` in the field the gate reads, so the
  parser is not *losing* data; the doc is simply describing a channel FNV does not use.
- **Related**: `LC-D5-01` (Oblivion's version — there the flag *is* authored and the
  damage value *is* non-zero, so the two games need opposite fixes and `watal.md`'s
  single row cannot describe both); FNV-2026-08-20-D1-01 (the sibling `FNAM` bit-0x02
  claim, disproved by the same census). Wiring `XNAM` to a real effect needs a
  SPEL/magic-effect runtime that does not exist yet — **that** part is a missing
  foundation and is deliberately not scored here.
- **Suggested Fix**: Correct `docs/engine/watal.md:479` to mark the FO3/FNV column
  SENTINEL-on-vanilla with a note that the era's hazard is authored through `XNAM`
  (actor effect), not the `DATA` damage word. Optionally decode `XNAM` into a
  `WatrRecord::actor_effect_form_id` now — it is a 4-byte FormID needing only a
  `remap_fid` — so the provenance is captured at the parse boundary and a future
  effect runtime has a landing site, rather than re-discovering the field later.

## Disproved candidates

Recorded so the next audit doesn't re-derive them.

- **"FNV `WATR.NNAM` paths start with `Data\` and won't resolve."** 78/78 FNV `NNAM`
  values are `Data\Textures\Water\*.dds` (`WastelandWaterPotomac.dds` ×33,
  `WaterFlowRippleNoise01.dds` ×23, `TestWaterNoiseGrant.dds` ×11, empty ×6). But
  `asset_provider/archive.rs:264` `normalize_texture_path` strips a leading `data\`
  case-insensitively before prefixing `textures\`, with an explicit citation to the
  2026-05-26 FaceGen `leading-data` case. Resolves correctly. Not filed.
- **"FNV water damage is silently dropped by the `FNAM` bit-0x01 gate."** Half true and
  filed as D4-01, but *not* as a data-loss bug: all 78 records author damage `0` in the
  2-byte `DATA`, so nothing authored is being lost. The defect is the spec claim plus
  the undecoded `XNAM` channel.
- **"The FO3/FNV RACE `DATA` reader mis-parses the 7-skill + 2-unused layout as 8
  skill pairs."** `records/actor/mod.rs:1172-1181` reads 8 pairs, which happens to
  consume the same 16 bytes; the 8th pair lands on the 2 unused bytes. On real FNV
  data those bytes are `0x0000` on all 22 races, so skill index `0` with bonus `0` would
  be pushed — but every FNV race authors an empty skill-bonus set anyway (Fallout races
  don't use the TES4 field), so nothing observable changes. Cosmetic at most; the
  `0xFF` sentinel skip is the documented guard. Not filed.
- **"PACKAL leaked Skyrim ambient behaviour into FNV NPC spawning."** Disproved by the
  `PKCU`/`ANAM` census above — see the Regression Guard List row.
- **"`systems/water.rs`'s per-frame `HashMap`/`HashSet`s go stale across cell
  unloads."** `wet_last_frame` / `wet_now` / `ripple_by_surface`
  (`systems/water.rs:356-437`) are rebuilt inside the system closure every frame and
  `wet_last_frame` is cleared when the water set is empty. The `#2923` hot-path hashing
  concern is already filed as `PERF-D1-02`; there is no staleness bug. Not filed.
- **"The `render/water.rs` inline copy of `weather_wave_adjustment` is an FNV
  divergence."** Already relayed to `/audit-tech-debt` by the concurrency audit
  (`CROSS_FINDINGS.md` § RELAYS). Not re-filed.
