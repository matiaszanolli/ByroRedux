### UI-D7-2026-09-29-01: `raster::wrap` is quadratic in the string length when `wrapwidth` exceeds the text width, and it runs on every HUD render
- **Severity**: MEDIUM
- **Dimension**: MenuXml & HUD Drivers
- **Profile**: MenuXml
- **Location**:
  - `crates/menuxml/src/raster.rs:465-494` (`wrap`)
  - Call chain: `raster.rs:422-458` (`draw_text_item`) ← `crates/menuxml/src/menu.rs:398` (`render_frame`) ←
    `byroredux/src/hud.rs:698` (every changed HUD frame, up to 30 Hz)
  - `wrap_width` comes from `crates/menuxml/src/layout.rs:225`, which has no upper cap
- **Status**: NEW. The #4715 fix bounded the pixel loops; the text path's pre-raster work was outside its scope. No
  matching open or closed issue.
- **Description**:
  - For each space-separated word, `wrap` builds `candidate = format!("{current} {word}")` and measures the whole
    candidate again with `Font::measure_width`, which walks it byte by byte.
  - While the text still fits (a large `wrapwidth`), `current` only grows. A text of n words therefore costs O(n²) in
    copying and measuring.
  - Menu XML is untrusted input (`ui.md`, #4715). A `<string>` literal or a `strings.xml` entity has no length cap,
    and `wrapwidth` accepts any finite value.
  - Wrapped lines are not cached between renders.
- **Evidence**: probe `/tmp/audit/ui/probe_wrap`. It is a release build that calls the public `raster::wrap` and
  `Framebuffer::text_line` with a synthetic font (9-px advance) and `wrapwidth = 1e9`:
  ```
   5000 words ( 15000 B): wrap    22.5 ms -> 1 line; text_line 0.3 ms
  10000 words ( 30000 B): wrap    89.3 ms
  20000 words ( 60000 B): wrap   359.1 ms
  40000 words (120000 B): wrap  1425.8 ms -> 1 line; text_line 1.0 ms
  control wrapwidth=300, 40000 words: 2.2 ms (3077 lines)
  ```
  - Doubling the word count quadruples the time.
  - The clipped glyph draw stays around 1 ms, and the control run shows that the cost is in `wrap`.
- **Impact**:
  - The trigger is one HUD text of about 100 KB with a large `wrapwidth`, in a replaced or modified
    `Oblivion - Misc.bsa` / `Fallout - Misc.bsa`. It stalls the main thread for about 1.4 s on every HUD render.
  - With the camera turning, the compass changes every frame, so the HUD re-renders on every 33 ms cadence tick and
    the game effectively freezes.
  - Vanilla strings are short, and the corpora pass. Only hostile or malformed content triggers this.
  - This is the same class and severity as the parse-side PAR-D1-2026-09-29-02.
- **Related**: #4715 (closed), PAR-D1-2026-09-29-02, #4570 (raster preflight duplication, tech debt)
- **Suggested Fix**: Keep a running width: add `space + measure_width(word)` for each word, and append into one
  `String` instead of calling `format!` again. Pin the fix with a linear-time test (for example, 40k words under a
  small time budget).

### UI-D1-2026-09-29-01: `canonical_menu_name` ignores the profile and mixes Skyrim and FO4 menu-name conventions, so `UI.IsMenuOpen` still misses the real HUD on Skyrim
- **Severity**: MEDIUM (matches #4757's label; no shipped script calls it today)
- **Dimension**: Profile & Bridge
- **Profile**: both
- **Location**:
  - `crates/ui/src/lib.rs:146` (`install_player`) and `crates/ui/src/lib.rs:360-383` (`canonical_menu_name`)
  - Consumer chain: `byroredux/src/app_events.rs:629-634` → `byroredux/src/extensions/systems.rs:373-381` →
    `crates/sdk/src/compatibility/input_ui.rs:142-149` (an exact, case-sensitive compare)
- **Status**: Existing: #4757 (OPEN). 63c0aee3b, an env-var refactor that does not reference #4757, added a partial
  fix, and that fix introduces the defects below. Update #4757; do not file a new issue.
- **Description**: `install_player` rewrites `menu_name` through one flat table that maps SWF stems to names, and the
  table is the same for both profiles.
  - **Skyrim:**
    - `hudmenu.swf` → `HUDMenu`, but the engine name is `HUD Menu`.
    - `loadingmenu.swf` → `LoadingMenu`, but the engine name is `Loading Menu`.
    - Six table stems match no Skyrim SWF: `questjournal`, `crafting menu`, `mapmenu`, `messageboxmenu`, `mainmenu`,
      `pausemenu`. The real files are `quest_journal`, `craftingmenu`, `map`, `messagebox` and `startmenu`, and there
      is no pause SWF. Those menus keep their raw archive path as the name.
  - **FO4:**
    - `dialoguemenu.swf` → `Dialogue Menu`, which is Skyrim's spelling. FO4's name is `DialogueMenu`.
    - `pipboymenu.swf` is not mapped.
- **Evidence**:
  - `SkyrimSE.exe` (`strings -t x`): the menu registry string table at `0x1a99fe8`, next to
    `Error, BSScaleformFileOpener failed…`, reads `Dialogue Menu`, `HUD Menu`, `MessageBoxMenu`, `Fader Menu`,
    `Overlay Menu`, `Loading Menu`, `MapMenu`, `Lockpicking Menu`, `Sleep/Wait Menu`, `LevelUp Menu`, `Journal Menu`,
    `Book Menu`, `Crafting Menu`, and more. `HUDMenu` appears once, at `0x1975390`, next to
    `HUDMovieBaseInstance.RegisterComponents`/`RegisterHUDComponents`: that is the movie name, not the menu name.
  - `Fallout4.exe` contains `HUDMenu`, `DialogueMenu`, `MainMenu`, `LoadingMenu`, `PauseMenu` and `PipboyMenu`, and no
    `Dialogue Menu`.
  - SWF lists from `Skyrim - Interface.bsa` and `Fallout4 - Interface.ba2` are in `/tmp/audit/ui/dim_1.md`.
  - The only test (`archive_and_dev_paths_resolve_to_bethesda_menu_names`) uses synthetic names, and none of them is
    checked against a game.
- **Impact**:
  - The SDK route `UI.IsMenuOpen` is declared, dispatched and fed on every frame.
  - With the Scaleform HUD up, it answers false for Skyrim's `HUD Menu` and FO4's `DialogueMenu`, and for every
    unmapped Skyrim menu.
  - #4757's TESTS completeness check is not met.
- **Related**: #4757, TOOL-D3-2026-09-22-01, AUDIT_UI_2026-09-21 §6 item 4
- **Suggested Fix**:
  - Key the table by `(ScaleformProfile, SWF stem)`; `install_player` already has `player.profile()`.
  - Take the stems from each game's interface archive and the names from its executable.
  - Pin one real archive path per profile.

### UI-D7-2026-09-29-03: `launch_hud` leaks the overlay textures that did register when one of its three registrations fails
- **Severity**: LOW
- **Dimension**: MenuXml & HUD Drivers
- **Profile**: MenuXml
- **Location**: `byroredux/src/hud.rs:575-613` (`match (register(ctx), register(ctx), register(ctx))`, `_ =>` arm at
  `:610`)
- **Status**: NEW (the pattern dates from dc306a6a0, 2026-09-18)
- **Description**:
  - All three swapchain-extent `register_rgba` calls run before any result is checked.
  - If any of them returns `Err`, the `_ =>` arm logs the failure and returns `None`. The handles that succeeded are
    dropped without being released, so they stay in the `TextureRegistry` and in VRAM for the whole session.
- **Impact**:
  - This happens only when an allocation fails at launch, most likely under memory pressure, which the leak then makes
    worse.
  - Up to two images are orphaned: 8.3 MB each at 1080p, 33 MB each at 4K.
  - It happens once, not per frame.
- **Related**: #4892 (collapsing the now-unneeded 3-handle rotation to a single handle removes this path)
- **Suggested Fix**: Register the handles one at a time and release the earlier ones if a later one fails, or register
  a single handle as #4892 proposes.

  - The new dialogue page keeps the scheduler running (`simulation_paused` excludes it) but still owns input through

## 6. Pending-Row Readiness (invariants for unbuilt work; not findings)

Deliberately unbuilt, re-verified against `docs/engine/ui.md:41`: host-method behaviour, the remaining GFx stubs, the
Papyrus↔UI bridge, menu-stack/focus policy, font fidelity, the full menu pack, and the Starfield HUD (#4470).

1. **Papyrus bridge naming.** The first mechanism now exists: `canonical_menu_name` → `extension_ui_menu_sync` →
   `UI.IsMenuOpen`. It must become per-profile before the bridge carries `RegisterForMenu` / `OnMenuOpen` events,
   otherwise every event keyed on a menu name inherits UI-D1-2026-09-29-01. It also exposes exactly one active menu,
   so a stack needs a list, not an `Option`.
2. **Menu stack.**
   - The Scaleform HUD is a visible but unfocused layer. It correctly receives no pointer events.
   - #4723 shows that a stack policy must own focus and ticking together.
   - `host_call_gap_for_menu` keys on the menu name, and names now collapse to canonical names. A same-name reload, or
     two movies that map to one canonical name, needs a bridge generation counter.
3. **Host-method handlers.** Measure the Skyrim `kind`s by arity (#4720) before handlers land.
4. **Render pacing for future menus.** Modal menus are unpaced by design. A menu that stays open for long, such as a
   map or a journal, should opt in with the same `RenderPacing` type. Any new host-write path must call
   `SwfPlayer::invalidate`, or the menu can look stale for up to one idle interval.
5. **Loose-file MenuXml.** A loose-file `MenuAssets` implementor would expose UI-D7-2026-09-29-01 and
   PAR-D1-2026-09-29-02 to every UI mod (DarNified, MTUI). Close both first.
6. **Resize.** Still untracked by either overlay. The effect is a visual stretch only, and the extent checks cannot
   fire.
