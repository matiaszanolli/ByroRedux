### REN-D5-01: After a failed one-time layout walk, the G-buffer, bloom and the resize paths of SVGF/TAA/caustic keep the pass alive with its images still `UNDEFINED`, while every consumer declares `GENERAL` / `SHADER_READ_ONLY`
- **Severity**: HIGH (Vulkan spec violation floor; error path only — the trigger is a failed command-buffer allocation, begin/end, or a `vkQueueSubmit` OOM; downgrade to MEDIUM if likelihood is weighed over the floor)
- **Dimension**: Memory/Lifecycle (found independently by Dim 4 as REN-D4-01, Sync/Barriers; merged here)
- **Location**:
  - `VulkanContext::new` (`crates/renderer/src/vulkan/context/init.rs`): the G-buffer arm ("G-buffer layout init failed") and the bloom arm ("Bloom pyramid layout init failed", then `Some(b)`).
  - `recreate_swapchain` helpers in `context/resize.rs`: "G-buffer post-resize layout init failed" and "Bloom layout re-init after resize failed".
  - `TaaPipeline::recreate_on_resize` (`taa.rs`), `SvgfPipeline::recreate_on_resize` (`svgf.rs`), `CausticPipeline::recreate_on_resize` (`caustic.rs`): `if let Err(e) = unsafe { self.initialize_layouts(...) } { log::warn!("... layout re-init after resize failed: {e}"); } Ok(())`.
- **Status**: NEW. Sibling of closed #1389 ("Volumetrics survives failed initialize_layouts leaving froxel images UNDEFINED"), which fixed volumetrics only. #6146 (closed) fixed the *destroy/leak* half of these callers; these *keep* arms consume no in-flight class and were out of its scope. #677 and #1031 (closed) added the resize walks but left the failure arm log-only.
- **Description**: `submit_initial_layouts` (`texture.rs`) is the only thing that moves these images out of `UNDEFINED`. When it fails with `OneTimeCommandError::NotSubmitted` (allocate, begin, end, reset-fence or create-fence failure) the command buffer was never queued; a `vkQueueSubmit` OOM classed `MaybeInFlight` has the same effect, because a failed submit leaves the referenced resources unaffected. The listed arms only `log::warn!` and keep the pass. The next frame's commands then assume the walked layout:
  - bloom's per-dispatch barriers use `.old_layout(vk::ImageLayout::GENERAL)` (`bloom.rs`) — an image actually in `UNDEFINED` breaks VUID-VkImageMemoryBarrier-oldLayout-01197;
  - SVGF samples the previous-frame G-buffer slot as `SHADER_READ_ONLY_OPTIMAL` (the doc comment on `GBuffer::initialize_layouts` names this exact validation error);
  - SVGF, TAA and caustic bind their history/accumulator images as `GENERAL` storage.
  The policy is also asymmetric: the init arms for SVGF and TAA disable the pass on the same failure (`svgf.take()` / `taa.take()` + `release_after_failed_submit`), volumetrics follows the #1389 rule, and caustic init returns `Err` — but the resize arms inside those same passes keep running and report `Ok(())`, so the context cannot tell.
- **Evidence**: orchestrator re-read the warn-and-continue arms in `init.rs` (bloom at "Bloom pyramid layout init failed", G-buffer at "G-buffer layout init failed"), `resize.rs` ("G-buffer post-resize layout init failed") and `taa.rs` (`recreate_on_resize`); the contrast arms are the TAA init arm and the volumetrics init arm.
- **Impact**: after a transient one-time-submit failure, every later frame records layout-mismatched barriers and descriptor reads for these passes: validation errors and undefined image contents — garbage history, bloom and indirect, not a crash. No use-after-free: nothing is destroyed on these arms, so the #6146 in-flight policy is not violated. Composite binds bloom's views (binding 7) and SVGF/TAA history, so bloom and the G-buffer cannot simply be dropped.
- **Related**: #1389, #6146, #6063, #677, #1031, #905 (bloom binding 7 must not dangle), REN-D5-02.
- **Suggested Fix**: a failure-policy change, not a barrier edit. Make the pass-internal `recreate_on_resize` bodies return the layout error so `recreate_swapchain` can apply `release_after_failed_submit` + `None` like its TAA/water-caustic arms; for bloom and the G-buffer (mandatory for composite) propagate `Err` as caustic init already does rather than run with `UNDEFINED` images. **NEEDS-RENDERDOC / `BYRO_VALIDATION=1`**: confirming the VUID needs a fault-injected one-time-submit failure during resize; no such hook exists (it would need an env switch in the style of `BYRO_FSR_FORCE_DISPATCH_FAIL`).

### REN-D7-01: #6247 is only half fixed — the exterior sun's `GpuLight` still folds the clock-driven sun direction and colour bit-exactly into `caustic_scene_key`, so SVGF progressive accumulation (and the caustic EMA) re-key every frame in a daytime exterior with the clock running
- **Severity**: MEDIUM (denoiser convergence; visual only, no memory or sync hazard; the same class #6247 was filed for)
- **Dimension**: Denoiser/Composite (also touches Dim 8 caustics and the ReSTIR parked mode)
- **Location**: `VulkanContext::build_and_upload_instances` (`crates/renderer/src/vulkan/context/build_and_upload_instances.rs`): the `for light in lights { ... fold_caustic_key_f32(caustic_scene_key, *v) }` loop over `position_radius` / `color_type` / `direction_angle` / `params`, which runs before `fold_svgf_scene_inputs`, `caustic_key_static` and `svgf_scene_static`; producer `collect_lights` (`byroredux/src/render/lights.rs`); writer `weather_system` (`byroredux/src/systems/weather.rs`).
- **Status**: NEW — incomplete fix of closed #6247 (`68ecd0819`); not covered by open #6315 (that one is the per-frame material re-hash cost).
- **Description**: #6247 removed `sky.sun_direction`, `sky.sun_color`, `sun_illuminance`, the TOD colours, fog and DALC lanes from the discrete key because `weather_system` re-interpolates them from the fractional hour every frame, and moved them to the drift-tolerant `svgf_continuous_inputs_jumped`. The same per-frame quantities still enter the key through the light rig. In exteriors `weather_system` writes `cell_lit.directional_dir = sun_dir` and `cell_lit.directional_color = sunlight` every frame (the `if !cell_lit.is_interior` block). `collect_lights` pushes that as `lights[0]` (`direction_angle = cell_lit.directional_dir`, `color_type` from `cell_lit.directional_color`). `build_and_upload_instances` folds every float of every light with `fold_caustic_key_f32` = `(key ^ v.to_bits()).wrapping_mul(PRIME)` — bit-exact, no tolerance. Any ULP of sun drift therefore changes `caustic_scene_key`, so `caustic_key_static = caustic_scene_key == self.prev_caustic_scene_key && !continuous_jumped` is false; `svgf_scene_static`, `svgf_history_valid` and `caustic_history_valid` fall with it, and so does ReSTIR mode 2 (`scene_static_last_build`). That is the #6247 symptom: a parked camera never leaves the recovery alpha floor and the caustic accumulator restarts every frame. Interiors are unaffected (the XCLL directional is constant; `weather_system` skips `cell_lit` when `is_interior`); a paused clock is unaffected.
- **Evidence**: orchestrator re-read: `for light in lights { for v in light.position_radius.iter().chain(light.color_type.iter()).chain(light.direction_angle.iter()).chain(light.params.iter()) { caustic_scene_key = fold_caustic_key_f32(caustic_scene_key, *v); } }` sits immediately above `fold_svgf_scene_inputs(caustic_scene_key, ...)`; `weather.rs` assigns `cell_lit.directional_color = sunlight; cell_lit.directional_dir = sun_dir;` unconditionally every frame beside `cell_lit.ambient = ambient`. Why the guards miss it: `material_and_sky_discrete_changes_rekey_progressive_history`, `per_frame_animated_material_lanes_do_not_rekey_history`, `continuous_sky_and_fog_reset_history_on_a_jump_not_on_drift` and `continuously_scrolling_clouds_do_not_rekey_history` call `fold_svgf_scene_inputs` / `svgf_continuous_inputs_jumped` directly; none drives the light-rig fold or composes the full `caustic_key_static` expression with a drifting sun light. They are not vacuous for the helpers, but they cannot see this. The magnitude is **derived from the code trace, not measured** (no engine launched).
- **Impact**: every daytime exterior with the game clock running (the normal case) keeps SVGF indirect at the recovery floor with the camera parked and restarts the caustic accumulator each frame — the residual still-camera boiling #6247 was meant to remove — and pays the #6247 per-frame continuous-input comparison for no benefit in exteriors.
- **Related**: #6247 (closed), #4046 (light rig added to the SVGF gate), #5369 (`light_rig_geometry_key` is intensity-blind but keys on the sun *direction*, so ReSTIR mode 3 has the analogous exterior drift), #6315.
- **Suggested Fix**: fold the scene-key directional (slot 0, identity `[0, 2, 0, 0]` in `light_ids`) out of the bit-exact rig fold and into `svgf_continuous_inputs` (its colour and direction lanes), so it is jump-compared like `sky.sun_direction`; keep point and spot lights in the exact fold. Pin it with a test that drives the composed key: a one-frame sun-light drift keeps `caustic_key_static`, a `time.set`-sized jump clears it once. **NEEDS-RENDERDOC**: parked camera in a sunny FNV/Skyrim exterior with the clock running — `svgf_history_valid` (the progressive flag in `params.w`) should engage after the fix; today it should read the recovery floor every frame.

### REN-D2-01: After the terrain parallax march, the terrain base layer (BTXT diffuse, material decals, base normal map) takes implicit LOD and derivatives of the *displaced* UV, while every splat layer uses the pre-displacement gradients
- **Severity**: MEDIUM (visual only: wrong mip and a skewed tangent frame on the base layer at relief edges, within the parallax range). NEEDS-RENDERDOC.
- **Dimension**: Tangent-Space
- **Location**: `crates/renderer/shaders/triangle.frag` `main()`: `sampleUV = terrainParallaxDisplaceUV(...)` (new in `b81a43443`, part of #6197), followed by `vec4 texColor = texture(textures[nonuniformEXT(fragTexIndex)], sampleUV);`, the `materialDecals` loop, and `N = perturbNormal(N, fragWorldPosRel, sampleUV, normalMapIdx, fragTangent);` (`perturbNormal` in `include/material_sampling.glsl` forwards `dFdx(uv)` / `dFdy(uv)` to `perturbNormalGrad`).
- **Status**: NEW (`b81a43443`, part of #6197 — #6197 is the feature tracker; this is a defect in its landed slice).
- **Description**: `splatUVdx/dy` and `splatPosdx/dy` are captured before the march from the undisplaced `sampleUV`; the march then overwrites `sampleUV` for terrain fragments. The splat diffuse/specular/normal loops, `byroTerrainHeightBlend` and `byroTerrainSplatAlbedo` all use `textureGrad` with the undisplaced gradients, which is standard POM practice. Three base-layer reads are still implicit, so their derivatives are taken of the displaced UV: the BTXT base diffuse sample, the decal samples, and the base normal map (LAND tiles bind one through `MaterialTextureHandles { normal: base_normal_index, .. }` in `byroredux/src/cell_loader/terrain.rs`; near LAND vertices carry no tangents, so `perturbNormalGrad` takes Path 2 and builds the TBN from `dFdx(displacedUV)`). The displaced UV's screen derivative is `dUV/dx` plus the derivative of the slide, which jumps where neighbouring quad lanes stop on different march layers. The reads sit in uniform control flow, so this is wrong LOD and a wrong TBN, not undefined behaviour.
- **Evidence**: orchestrator re-read: `vec2 splatUVdx = dFdx(sampleUV);` (before the march), `sampleUV = terrainParallaxDisplaceUV(...)` (the overwrite), then `texture(textures[nonuniformEXT(fragTexIndex)], sampleUV)`, the decal `texture(...)` loop and `perturbNormal(N, fragWorldPosRel, sampleUV, ...)` after it. `triangle_frag_displaces_before_the_blend_with_the_painted_weights` pins only that the gradients are captured before the call. Before `b81a43443` the terrain `sampleUV` was the plain BGSM-transformed UV, so implicit and explicit derivatives agreed.
- **Impact**: LAND within the parallax range (default 20 m, fading from 10 m) wherever the BTXT base shows through (weight-0 splat regions) or a base normal map is bound: blur or sparkle and normal-map orientation flicker along relief edges, worse at grazing angles. Not measured.
- **Related**: #6197, #4016 (the explicit-gradient capture), #3622.
- **Suggested Fix**: when `terrainSplatActive`, read the base diffuse and decals with `textureGrad(..., sampleUV, splatUVdx, splatUVdy)` and call `perturbNormalGrad(N, sampleUV, normalMapIdx, fragTangent, splatPosdx, splatPosdy, splatUVdx, splatUVdy)` for the base normal, as the layer loop already does; extend the pin test to cover it. Confirm with a RenderDoc capture or a screenshot A/B (`terrain.parallax 20 0.08` against `off`, grazing-angle LAND close-up).

### REN-D2-02: `terrainParallaxDisplaceUV` does not clamp its step count after the float→int conversion, and its interpolation epsilon sits on the wrong side of a non-positive denominator
- **Severity**: LOW (hardening; neither case is reachable from finite, non-degenerate inputs)
- **Dimension**: Ray Queries (shader robustness)
- **Location**: `crates/renderer/shaders/include/material_sampling.glsl` `terrainParallaxDisplaceUV`: `int steps = int(mix(maxSteps, minSteps, clamp(vz, 0.0, 1.0)) + 0.5);` and `float weight = afterDepth / (afterDepth - beforeDepth + 1.0e-6);`
- **Status**: NEW. The epsilon form is inherited verbatim from `parallaxDisplaceUV` and `ray_hit.glsl`.
- **Description**: (a) `vz` is NaN if `normalize(fragNormalEffective)` is NaN (a zero interpolated normal, or the flat-shading `normalize(cross(dFdx, dFdy))` on a degenerate quad). `clamp(NaN)` is implementation-defined and `OpConvertFToS` of NaN is undefined, so the loop bound is not provably in [6, 20]; each iteration costs up to 9 `textureGrad` reads (`byroTerrainBlendCore` loops 8 lanes plus base). The CPU mirror `step_count` uses Rust's saturating `as i32`, so the tests cannot see the difference. (b) After the `break`, `afterDepth <= 0 < beforeDepth`, so `afterDepth - beforeDepth` is strictly negative; adding `+1e-6` moves it toward zero and it reaches zero when `beforeDepth - afterDepth == 1e-6`, giving 0/0. The epsilon should be subtracted.
- **Evidence**: settings cannot inject inf or NaN: the sliders are bounded (0–0.3 m / 0–60 m), the `terrain.parallax` command filters `is_finite() && >= 0`, and `push_terrain_parallax` writes depth 0 unless both settings are > 0; a degenerate fade range (`end <= start`) is a hard cut with no division, and depth <= 0 returns early. All verified.
- **Impact**: none from authored data; a degenerate-geometry hazard only.
- **Suggested Fix**: `steps = clamp(steps, 6, 20)` (the generated-constant form) and `weight = afterDepth / min(afterDepth - beforeDepth, -1e-6)` in all three marchers; mirror both in `terrain_parallax_tests::step_count`.

### REN-D5-03: `byte_view`'s doc claims no hand-rolled `from_raw_parts` crate-wide bar one exemption, but `GpuBuffer::create_device_local_buffer` still hand-rolls one
- **Severity**: LOW (doc drift; the cast is sound)
- **Dimension**: Memory/Lifecycle (byte views)
- **Location**: the `byte_view` doc and `create_device_local_buffer<T: NoUninit>` in `crates/renderer/src/vulkan/buffer.rs`
- **Status**: NEW (residue of #6270, which added the "holds crate-wide" sentence)
