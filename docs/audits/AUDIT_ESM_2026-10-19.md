## Findings

### MEDIUM

### ESM-SD-2026-10-19-01: A REFR an override plugin moves into another cell keeps its base copy, so both spawn
- **Severity**: MEDIUM
- **Dimension**: CELL / WRLD Walkers (cross-plugin merge as consumed by the cell loader) / ESM→ECS Handoff
- **Record / Sub-record**: REFR / ACHR / ACRE (placement), CELL child GRUPs
- **Location**: `crates/plugin/src/esm/cell/index.rs:464` (`EsmCellIndex::merge_from`), tombstone sweep `:515-535`, per-cell merges `:537-580`; `merge_placed_references` `:173`; consumer `locate_refr` `:624`
- **Status**: NEW. Searched `/tmp/audit/issues.json` (121 open) and closed issues for `REFR moved cell override duplicate`; nothing. Related, not the same: #3362 (cross-cell **tombstone**, closed; the sweep at `:515` fixed only deletes) and #1546 (partial override keeps base REFRs).
- **Description**: A REFR is globally unique by FormID. When a later plugin overrides a placement and authors it under a different CELL (the CK regroups a moved object under its new cell), the engine has one object at its new position. `merge_from` keys placements per cell: the override lands in the new cell's list, and the base copy stays in the old cell's list. The only cross-cell removal is the tombstone sweep (`tombstones` built from `deleted_refs`, `:515`). Nothing compares an override's placement FormIDs against the other cells' lists.
- **Evidence**: independent Python census (no Rust parser), walking GRUP type 6 labels, skipping Deleted records, FormIDs normalised to (originating master, low 24 bits):
  - Skyrim SE (Skyrim + Update + Dawnguard + HearthFires + Dragonborn): 22 of 872,414 placements are non-deleted in two cells. Examples: `ACHR 03C57D` Skyrim.esm cell `0x9749` (temporary) and Dragonborn.esm cell `0x0D74` (persistent); `ACHR 084625` Skyrim.esm `0x9291` and HearthFires.esm `0x9292`; REFR `0B60B3`/`0B60B8`/`0B60B9`/`0DDD35` Skyrim.esm `0x7158` to Update.esm `0x7157`.
  - FO3 + 5 DLCs: 16 (6 `ACRE` `03E49x`/`03E4A5` moved from `0x0E13` by PointLookout.esm into its persistent-children cell `0x2DB4`; 10 REFR, e.g. `0A6028` into BrokenSteel's persistent cell).
  - FO4 + 6 DLCs: 7 (e.g. `065543` Fallout4.esm `0xE2A9` to DLCworkshop03.esm `0x18AA2`; DLCCoast moves).
  - FNV + 4 DLCs: 0 of 427,387.
  Reproduce: `python3 -I /tmp/audit/streaming-deep/esm/moved.py 24 <plugins in load order>`.
  Code path: `merge_from` interior loop `:537-558` and exterior loop `:560-568` each call `merge_cell_override(base, &mut over)` only against the same key (`:560` the same `(x, y)`); no code path outside `tombstones` ever removes a `PlacedRef` from a cell that `other` did not author. `cell_loader` has no spawn-time dedup by FormID (grep of `references/mod.rs`, `load.rs`, `exterior.rs`, `spawn.rs` found none).
- **Disproof attempted**: (1) the census double-counts when a plugin lists the same REFR under two cells of its own — I checked per-plugin, every case is one cell per plugin, base vs override. (2) A DLC "move" could be a delete plus a new FormID — the FormID is identical in both, and the deleted-flag records were excluded. (3) The Rust walker might file the REFR under a different cell than the GRUP label — the walker derives `group_type` and the cell from the nesting (`walkers.rs`, `parse_refr_group_inner`), the same structure my census uses. (4) A later dedup in the loader — none found. What I did not verify at runtime: that both entities render (needs an engine run, not available here).
- **Impact**: the stale base copy renders at the old position next to the moved one. For the 2 Skyrim ACHRs and 6 FO3 ACREs this is a duplicated actor/creature: the persistent-cell actor stubs (`exterior.rs`, `prepare_logical_actor_stubs`) and `SceneAliasCandidate` key by FormID, so two live entities share one FormID and `resolve_entity_by_global_form_id` picks one arbitrarily. For a moved door, `locate_refr` scans three `HashMap`s in iteration order, so the destination cell of an XTEL can differ between runs. Mod load orders (and the unofficial patches, which move objects routinely) hit this at far higher volume than the 45 vanilla cases.
- **Related**: #3362, #1546, ESM-SD-02 (same merge function).
- **Suggested Fix**: in `merge_from`, before the per-cell loops, collect the placement FormIDs `other` authors per destination cell and `retain` away any copy of those FormIDs in `self`'s other cells (the same sweep shape as the tombstone one, with the destination cell exempt). Pin it with a `merge.rs` test that moves a REFR from cell A to cell B in a child plugin and asserts one copy.

### ESM-SD-2026-10-19-02: `merge_cell_override` resurrects CELL-record fields the winning override dropped
- **Severity**: MEDIUM
- **Dimension**: CELL / WRLD Walkers (cross-plugin merge) / ESM→ECS Handoff
- **Record / Sub-record**: CELL `XCWT`, `XLCN`, `XCLR`, `XEZN`, `XCRI` (+ `PCMB`/`VISI`/`RVIS` previs data, undecoded)
- **Location**: `crates/plugin/src/esm/cell/index.rs:245-312` (`merge_cell_override`); the unmerged-field gap at `cell_data.rs` (`encounter_zone_form`, `pathgrids`)
- **Status**: NEW. Searched open and closed issues for `override inherit CELL field`; nothing. The inheritance design comes from #1546 (partial DLC override keeps base REFRs), which is right for the **child records** (REFR, LAND, NAVM) but was extended to fields stored in the CELL record itself.
- **Description**: a plugin that overrides a CELL carries the whole CELL record (the CK rewrites it); the engine's winning override replaces the record. A sub-record that is absent from the override is therefore absent on purpose. `merge_cell_override` instead fills every `None` / empty field from the base: `water_type_form` (`:272`), `regions` (`:293`), `location_form`, `lighting`, `image_space_form`, `acoustic_space_form`, `music_type_*`, `climate_override`, `precombined_mesh_hashes` (`:305`), and it **extends** `absorbed_ref_bakes` from the base unconditionally (`:309`). Only the child-record inheritance (`references`, `landscape`, `navmeshes`) matches how the data is authored. The field set is also incomplete in the other direction: `encounter_zone_form` and `pathgrids` are not inherited at all, so the policy is neither engine-faithful nor consistent, and unlike `EsmCellIndex::merge_from` (#4904) the function has no exhaustive destructure to force a decision when a field is added.
- **Evidence**: `cellsubs.py` compared sub-record sets of each override CELL with its base (union over earlier plugins):
  - Skyrim SE: 2,982 override CELLs; the override omits `XCWT` in 39 (Update.esm 28: `DefaultMarshWater` ×15, `RiverWaterFlowNE` ×12, `DefaultCreekWater` ×1; Dragonborn 5, Dawnguard 4, HearthFires 2), 394 other Update.esm overrides keep `XCWT`. Also `XLCN` ×3, `XCLR` ×3 (HearthFires and Dragonborn on the Tamriel persistent cell `0x0D74`), `XEZN` ×1 (Update.esm `0x16BCF`, consumed by `scripting/src/encounter_level.rs:98` and `obscript_more/tail.rs:41`, never inherited, so that cell reads no zone while the base had one).
  - Sample: Skyrim.esm `0x91A3` has `DATA EDID LTMP MHDT TVDT XCLC XCLR XCLW XCWT`; Update.esm's override has the same set minus `XCWT`. Every other field is re-emitted, which shows the record is whole and the `XCWT` removal is authored.
  - FO4: DLCNukaWorld.esm override of `Fallout4.esm` `0x1F7A9` drops `XCRI` (the CK does this when a baked reference is edited, to disable the cell's precombine). The merge keeps the base `precombined_mesh_hashes` and extends `absorbed_ref_bakes`, so the base's combined mesh is loaded and its absorbed refs are skipped, hiding the DLC's edit.
  Pinned the other way by `cell/tests/merge.rs::merge_from_partial_exterior_override_preserves_authored_payloads`.
- **Disproof attempted**: (1) the base `XCWT` might be redundant with the worldspace default — if it were, the inherited value would still be wrong only visually, but it is a different WATR (`DefaultMarshWater` vs the worldspace default) in 28 Update cells, so the patch is the one that changed it. (2) The fields may be inherited because the Rust walker fails to read them from the override — `walker_equivalence.rs` and the census show the sub-record is genuinely absent. (3) The inheritance protects against vanilla partial CELL records — the census (2,982 Skyrim, 752 FO4, 351 FO3, 73 FNV overrides) found no override missing `DATA`/`XCLC`/`XCLL`/`LTMP`/`XCLW`, i.e. no partial CELL records, so the only fields the inheritance ever fills are deliberate removals. Not measured: how the engine falls back for a missing `XCWT` (assumed worldspace default water; the record-replacement semantics are standard Bethesda conflict resolution, not engine-code verified).
- **Impact**: wrong water type in at least 39 Skyrim exterior cells (the patch's marsh/river water assignment is undone); 3 wrong location refs, 3 wrong region lists, 1 wrong encounter zone; on FO4, a cell whose override breaks its precombine still renders the stale combined mesh (1 vanilla DLC cell, and every modded cell that edits a baked ref, where it hides the edit).
- **Related**: ESM-SD-01 (same merge), #1546, #4904, #5484.
- **Suggested Fix**: limit the inheritance to the child-record vectors (`references`, `landscape`, `navmeshes`, `pathgrids`, `deleted_refs` handling) and let every CELL-record field come from the winning override; if a deliberate exception is wanted, make it an explicit per-field list behind an exhaustive destructure of `CellData`, with a test per field.

### LOW

### ESM-SD-2026-10-19-03: `resolve_precombine_owner` treats the FormID slot byte as a load-order position
- **Severity**: LOW
- **Dimension**: FormID & Load Order (ESL space) / ESM→ECS Handoff
- **Record / Sub-record**: CELL (FO4 precombine ownership), `XCRI`
- **Location**: `byroredux/src/cell_loader/precombined.rs:765-776` (callers `:214`, `:1015`, `:1041`)
- **Status**: NEW; Regression-shaped sibling of #3366 (closed; `plugin_for_form_id`, `load_order.rs:351`, decodes the slot with `global_slot_of` first, this site was not touched).
- **Description**: `let idx = (form_id >> 24) as usize; load_order_paths.get(idx)` indexes the load-order-aligned path list by the top byte of a remapped FormID. That byte is a **slot**; `allocate_global_slot` (`load_order.rs:762`) draws regular plugins and light (ESL) plugins from independent counters, so position equals slot byte only while no ESL precedes a regular plugin. FO4 supports ESL (TES4 flag `0x200`), and ESM-flagged and ESL files load before ESPs. A regular plugin after k ESLs has slot `position - k`, so its cell resolves to a different plugin's path and `<name>.esm` subdirectory; a cell owned by an ESL has top byte `0xFE`, is out of range, and falls back to the active plugin at the root directory.
- **Evidence**: the code above; the only tests (`precombined.rs:1375`, `:1926`) use all-regular orders (Fallout4 + DLCs, slots 0..2). `allocate_global_slot_partitions_medium_light_and_regular` (`load_order.rs:1584`) and `esl_plugin_own_forms_land_in_light_space` show the divergence is real.
- **Disproof attempted**: vanilla FO4 and its DLCs are all regular masters, so the vanilla gate passes; the defect needs an ESL ahead of a precombine-owning plugin (a CC `.esl` before a settlement `.esp` that bakes new cells). The failure mode is a missed `_oc.nif` lookup, which `PrecombinedSpawnJob` already treats as a miss (refs spawn individually, because `absorbed_ref_bakes` skips only refs whose bake actually spawned, #5484), so the result is lost precombine batching, not a double draw. Not exercised at runtime (no FO4 ESL load order here).
- **Impact**: precombined cells owned by mod plugins in an ESL-bearing FO4 load order silently fall back to per-REFR rendering (draw count, BLAS count); the CSG routing (`blobs_for_cell`) can also open the wrong plugin's blob. No vanilla impact.
- **Related**: #3366, #1590, #2369.
- **Suggested Fix**: resolve the owner through `global_slot_of(form_id)` and the slot table (`LoadOrder::slots`) instead of the raw byte; add an ESL-before-regular case beside `resolve_precombine_owner_follows_form_id_mod_index`.

## Verified clean in area (no finding)

- **Slot allocation / remap (Dim 3)**: `allocate_global_slot` keeps Regular `0x00..=0xFD` (`0xFC` once a medium master exists), Light `0xFE` 12-bit, Medium `0xFD` 8-bit disjoint; `FormIdRemap::remap` arms match the checklist (raw `0` → `0`, self-reference, in-range master, no-master pass-through at `debug`, out-of-range-with-masters pass-through at `warn`); `GlobalSlot::compose` masks 24/12/16 bits. `build_remap_for_plugin` fails loudly for a missing or later master. Duplicate basenames are rejected before any read.
- **Parallel walk (Dim 3)**: slot allocation, remap, `read_archive`, `.STRINGS` loading and the `merge_from` fold stay on the calling thread in load order (`load_order.rs:654-742`); the `StringsTableGuard` is installed inside `walk_plugin` on the walking thread (`:707-709`). A failed plugin parse degrades to `EsmIndex::default()` plus a warning, and `EsmIndex::merge_from`'s `other.total() > 0` guard protects `game`. `synthesize_wths_weathers` runs after the fold (`:746`).
- **Strings (Dim 6)**: Skyrim SE ships every master's `.STRINGS` family inside `Skyrim - Interface.bsa` (strings in the archive: `skyrim_`, `dawnguard_`, `hearthfires_`, `dragonborn_`, `update_` for 8+ languages; no loose `Strings/` directory in this install). `ArchiveStringSource::discover` reaches it for Dawnguard/HearthFires/Dragonborn/Update through the `shared_archive` clause (` - interface` suffix) and for `Skyrim.esm` through the plugin-prefix clause; CC plugins match their own `.bsa` by stem. The bare-name `parent() == ""` case is handled (#5303). Not tested at runtime. One cost note: the archive set is cached per plugin path, so `Skyrim - Interface.bsa` is opened once per plugin of the order (5 times for Skyrim + 4 DLCs); it is a small archive, not filed.
- **Handoff (Dim 7)**: no production `World::find_by_form_id` call remains (only comments in `boot/world.rs`, `spawn.rs`, `synth_child.rs`); the consumers sampled (`barter.rs`, `travel.rs`, `follow.rs`, `script_requests.rs`, `projectiles.rs`, `app_step.rs:945`) resolve through `resolve_entity_by_global_form_id`. `LoadedCellIndex` is installed on both arms (`index.rs` `boot_arm_coverage_tests`). `pre_parse.rs:684-730` reads the shared `Arc<EsmIndex>` read-only from pool tasks. The #5505 commit `75b921cf4` (`inherit_parent_landscapes`, called from `build_exterior_world_context`, Oblivion-gated) mutates the index before it is wrapped in the `Arc`, so no consumer sees a half-built index.
- **Interior key collisions**: interior EDID collisions across distinct FormIDs exist only for test cells (`testphil`, `testtony`, `testcory01`); `merge_from` would silently overwrite there, with no gameplay content affected.
