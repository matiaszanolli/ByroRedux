**The two MEDIUMs**

- **ESM-03: one `Starfield.esm` load on the engine path logs 62,576 spurious `warn!("Starfield FormID … names a master this plugin does not list")` lines.** Dim 8 measured this with the release `byroredux --esm Starfield.esm --list-cells` and attributed every line by backtrace. The causes are four decoders that feed non-FormID words to `remap_starfield`:
  - `NPC_.PRPS`: 12-byte entries read as 8 (23,981 lines, ESM-D8-02).
  - `LCTN` `ACSR`/`LCSR` and `ACPR`/`LCPR`: Starfield's extra `wbUnknown(4)` per entry is not stepped over (37,800 lines, ESM-D8-01).

  Bare `parse_esm` passes no remap, so no plugin example, test or `sf_smoke` baseline ever shows these lines. The flood buries the genuine out-of-range warning that #5075/#5076 kept at `warn`, and formats 62k lines on every Starfield boot.
- **ESM-02: the Oblivion `ALCH` effect chain is decoded with `&None`.** The `SCIT` script reference skips the load-order remap, and `cast_effect` runs that script.
  - Vanilla is masked: `Oblivion.esm` sits at slot 0.

### MEDIUM

#### ESM-03: the Starfield load path logs 62,576 spurious `remap_starfield` warnings per `Starfield.esm`
- **Severity**: MEDIUM (every Starfield session; masks the genuine warning class; four decoder causes)
- **Dimension**: Real-Data Validation (Dim 8), with Dims 2/3/4/5 for the `DOOR` slice
- **Record / Sub-record**: `NPC_` `PRPS`, `LCTN` `ACSR`/`LCSR`/`ACPR`/`LCPR`, `DOOR` `ANAM`/`BNAM`, `CTDA` `param_1`
- **Location**: the warn is `crates/plugin/src/esm/reader.rs:617-645` (`remap_starfield`, the `None =>` arm). The callers are:
  - `records/actor/npc.rs:1154-1171`
  - `records/misc/location.rs:62-112`
  - `cell/support.rs:90-103`
  - `records/condition.rs:638-641`
- **Status**: NEW
- **Description**: `Starfield.esm` lists no masters, so any non-zero top byte that is not `0xFE`/`0xFD` cannot be resolved. `remap_starfield` then logs at `warn` and passes the value through. Four decoders hand it words that are not FormIDs:
  - The second half of a mis-strided 12-byte `PRPS` entry (ESM-D8-02).
  - The `wbUnknown(4)` / grid words of Starfield's longer `LCTN` ref entries (ESM-D8-01; xEdit `wbDefinitionsSF1.pas:13401-13470`, re-verified by the orchestrator).
  - `DOOR` component strings and the Facing Axis enum (ESM-01).
  - The `0xFFFFFFFE` CTDA sentinel (ESM-D8-03).

  `parse_esm` passes no remap, so the flood appears only on the real `parse_esm_with_load_order` path. No plugin example, test or `sf_smoke` baseline shows it.
- **Evidence**: release `byroredux --esm Starfield.esm --list-cells` (9.1 s, 4.07 GB RSS) logs 62,581 warn lines; 62,576 come from `remap_starfield` (247 distinct values). Each line was attributed by a backtrace-capturing `log::Log` in a scratch probe crate:

  | Source | Warn lines |
  |---|---|
  | `npc.rs:1169` | 23,981 |
  | `location.rs:106` | 33,735 |
  | `location.rs:68` | 4,065 |
  | `support.rs:91` | 620 |
  | `condition.rs:640` | 175 |

  The commonest values are `ffffffff` (23,557), `7fff7fff` (11,655) and `40a00000` = 5.0f (8,116).
- **Impact**:
  - Every Starfield boot formats and emits about 62k warn lines.
  - A genuine "names a master this plugin does not list" case (a mis-ordered or missing master, the reason #5075/#5076 kept this at `warn`) cannot be seen in the noise.
  - The underlying fabricated data is listed per cause.
- **Suggested Fix**: Fix the four decoders (ESM-01, ESM-D8-01..03). Then add a guard that parses `Starfield.esm` through the load-order path and counts remap pass-throughs. A fixture-scale variant could run in the default lane: a synthetic master-less Starfield plugin per affected record. Separately, consider aggregating the pass-through into one summary line per plugin (count + first N values), as the #1308 Oblivion `0x01` path does at `debug`.

#### ESM-02: Oblivion `ALCH` script-effect `SCIT` is decoded through a hard-coded `&None` remap
- **Severity**: MEDIUM (a live consumer runs the unremapped id; vanilla masked)
- **Dimension**: FormID Remap (shared decoder called with an identity remap). Found independently as D3-01 and D4-07.
- **Record / Sub-record**: Oblivion `ALCH` / `SCIT` (script FormID @0)
- **Location**: `crates/plugin/src/esm/records/misc/magic.rs:896-904` (`oblivion_effect_chain` → `chain.feed(sub, &None)`). It is reached from `crates/plugin/src/esm/records/items/consumable.rs:29-46`, whose Oblivion early return drops the `remap` it holds, and consumed at `crates/scripting/src/magic_effects.rs:99-102` (`cast_effect`, `item.script_form_id`).
- **Status**: NEW (introduced by `9cb2703b3`, Refs #7045)
- **Description**: xEdit TES4 `wbEffects` (`wbDefinitionsTES4.pas:1492-1517`) defines `SCIT` as `wbFormIDCk('Script effect', [SCPT, NULL])` followed by school, visual char4 and hostile byte. The shared `MagicEffectAccumulator::feed` remaps `SCIT` @0, and SPEL/ENCH pass their remap. The new ALCH route builds its own accumulator and feeds it `&None`. `EFID` (char4) and `EFIT` stay correctly unremapped, so the one FormID this helper decodes is the one it skips. `no_parser_with_a_remap_in_scope_passes_an_identity_remap` scans only `parse_*` bodies, so it cannot see this.
- **Evidence**:
  - `Oblivion.esm` has 253 ALCH, 9 of them with a `SCIT`, all at master index 0, so the identity remap is harmless on vanilla.
  - The DLCs author `SCIT` only on INGR/ENCH/SPEL, which do remap.
- **Impact**: A mod's potion whose script effect names its own (or a non-slot-0 master's) script runs the wrong script, or none, on a multi-plugin Oblivion load order.
- **Suggested Fix**: Give `oblivion_effect_chain` a `remap` parameter and pass `parse_effects`' remap through it. Add a non-identity-remap Oblivion ALCH `SCIT` test modelled on `parse_spel_efid_is_remapped`. Consider widening the identity-remap guard to non-`parse_*` helpers that call `feed`/`push_ctda`.

#### ESM-01: Starfield `DOOR` `ANAM`/`BNAM` are read as door sound FormIDs
- **Severity**: LOW (decode defect, no audible effect; its log impact is counted under ESM-03)
- **Dimension**: Sub-Record Byte Accounting / FormID & Load Order / Record Schema Dispatch / CELL Walkers. Found independently as D2-06, D3-02, D4-06 and D5-01.
- **Record / Sub-record**: Starfield `DOOR` / `SNAM`, `ANAM`, `BNAM` (and the `BFCB`…`BFCE` component block)
- **Location**: `crates/plugin/src/esm/cell/support.rs:90-103`. The arm `b"SNAM" | b"ANAM" | b"BNAM" if is_door && sub.data.len() >= 4` has no game gate. Also affected: the `DoorData` doc in `cell/base_objects.rs` ("FO4/Starfield read as Skyrim's layout until checked") and `.claude/commands/audit-esm/SKILL.md` (Dim 5 `DOOR` bullet).
- **Status**: NEW. Introduced by `50abfd008` (#7059, DRT-REC-002). Adjacent to open #7061 (M66 Phase 3 Starfield census), which does not name the decode.
- **Description**: In xEdit `wbDefinitionsSF1.pas:11575-11626`, Starfield `DOOR` sounds are `wbSoundReference` structs `DOSH`/`DCSH`/`DLSH`. `ANAM` is `wbInteger('Facing Axis Override', itU32)` (0 X, 1 Y, 2 Based on Bounds). The `wbBaseFormComponents` block contributes string `ANAM`/`BNAM` sub-records (animation-graph paths). Oblivion, FO3, FNV, Skyrim, FO4 and FO76 all author `SNAM`/`ANAM`/`BNAM` as SOUN/SNDR FormIDs, so the arm is right on those six games. On Starfield it reads the first four bytes of a component string, or the axis enum, as a FormID.
- **Evidence**: `Starfield.esm` holds 339 `DOOR` records:
  - Codes: `DOSH` ×310, `DCSH` ×303, `DLSH` ×1, `SNAM` ×0, `ANAM` ×649, `BNAM` ×310.
  - The trailing 4-byte `ANAM` is 2 on 326 records, 0 on 10 and 1 on 3.
  - Component `BNAM`/`ANAM` payloads begin with ASCII, e.g. `0x70696873` "ship", `0x6D696E41` "Anim".
  - `Starfield.esm` lists no masters. `remap_starfield` (`reader.rs:617-645`) takes an ASCII top byte such as `0x70` as regular-master ordinal 112, cannot resolve it, and logs `warn!("Starfield FormID … names a master this plugin does not list")`. The orchestrator verified this path in source. Dim 3 counted about 620 such sub-records; Dim 8 measured the real warn count (see Part A).
- **Impact**:
  - `StaticObject::door.close_sound` / `loop_sound` / `open_sound` hold fabricated ids on about 329 of 339 doors, and `commands/door.rs` prints them.
  - `systems/door.rs::play_door_sound` misses `index.sounds` and logs at `debug`, so nothing plays wrong today.
  - Every Starfield session start carries hundreds of spurious `warn!` lines, which buries a genuine out-of-range FormID warning.
  - Starfield's real `DOSH`/`DCSH` sounds are never read.
- **Suggested Fix**: Pass `game` into `build_static_object_from_subs` and decode `SNAM`/`ANAM`/`BNAM` only when `game != Starfield`. Leave the three sounds `None` on Starfield until `DOSH`/`DCSH`/`DLSH` are decoded as `wbSoundReference` (#7061). Pin it with a Starfield fixture: a `BFCB` string `ANAM`/`BNAM` plus a trailing `ANAM` = 2 must leave all three sounds `None` and log no warning. Correct the `DoorData` doc and the skill bullet: flags bits 1–5 are verified on FO4/FO76/Starfield, sounds only on FO4/FO76.

##### ESM-D1-01: `esm_dim8_coverage` still hand-rolls an unbounded recursive GRUP walk
- **Severity**: LOW (dev-only example, no engine reach)
- **Dimension**: 1, universal GRUP bound
- **Record / Sub-record**: n/a (GRUP)
- **Location**: `crates/plugin/examples/esm_dim8_coverage.rs:128-153` (`fn walk`, raw `group_content_end` at `:139`; the top-level loop at `:77`)

- **Description**: `walk` recurses as `walk(reader, inner_end, census)` with no depth parameter. Its only guard is `inner_end > end`, a parent clamp reported as an error, so how far is covered but how deep is not. About 100k nested minimal GRUPs overflow the native stack.

- **Suggested fix**: Replace `walk` with `reader.for_each_record(end, None, ..)`; the per-record `pairs` / `cur_top` bookkeeping fits the callback. Alternatively thread a `depth` into `walk` and gate it on `MAX_GRUP_NESTING_DEPTH`.

##### ESM-D1-02: the ESM compressed-record inflate is a hand-copied twin of `bsa::safety::inflate_bounded_zlib`, with no parity guard
- **Severity**: LOW (duplication, not a live divergence)
- **Dimension**: 1, `FLAG_COMPRESSED` bound
- **Record / Sub-record**: any record with `FLAG_COMPRESSED`
- **Location**: `crates/plugin/src/esm/reader.rs:1018-1075` against `crates/bsa/src/safety.rs:176-207`; the doc claim at `reader.rs:1015-1017`; `crates/bsa/src/lib.rs:35` (`mod safety;` is private)
- **Status**: NEW. No open or closed issue found; #3812 ported #3720's recovery into `inflate_bounded_zlib` and left the ESM copy standing.
- **Description**: Both sides run the same algorithm. Each takes `take(declared + 1)` through a zlib decoder. On a zlib error each retries as raw DEFLATE over `[2..]` and accepts only an exact length match. Each ends with a `len <= declared` check. I compared them line by line and they agree, so the checklist's "implementations diverging" regression is **not** present today. But the logic exists twice. The `reader.rs` comment says it mirrors `byroredux_bsa::safety::inflate_bounded` (#3410), which is the generic variant; the zlib sibling `inflate_bounded_zlib` is the actual twin. `safety` is not exported (`pub use safety::{MAX_CHUNK_BYTES, MAX_ENTRY_COUNT}` only), so that path cannot even be named from the plugin crate. `byroredux-bsa` is a normal dependency of the plugin crate (added for `bscrc32`, #6048), so sharing is cheap.
- **Impact**: None today. The next change to the Adler-32 recovery or to the bomb bound, such as the flate2 1.1.10 truncated-stream semantics of #5660, has to be made in two crates by hand. A divergence would be silent.
- **Suggested fix**: `pub use safety::inflate_bounded_zlib` from `byroredux-bsa`. Call it from `read_sub_records` with `declared = decompressed_size`, mapping the error to the form-id context. Keep `record_inflation_ceiling` in the plugin crate. Fix the doc reference.

##### ESM-D3-01: Oblivion `ALCH` script-effect `SCIT` is read through a hard-coded `&None` remap (shape 1)
- **Severity**: MEDIUM
- **Dimension**: 3 (shared decoder called with an identity remap; guard blind spot)
- **Record / Sub-record**: Oblivion `ALCH` / `SCIT` (script-effect FormID at offset 0); also any CTDA after `EFIT` (none exist on Oblivion)
- **Location**: `crates/plugin/src/esm/records/misc/magic.rs:896-904` (`oblivion_effect_chain` → `chain.feed(sub, &None)`), reached from `crates/plugin/src/esm/records/items/consumable.rs:30-46` (`parse_effects`, which has `remap` in scope and drops it on the Oblivion early-return), consumed at `crates/scripting/src/magic_effects.rs:99-102` (`cast_effect`, `item.script_form_id`).
- **Status**: NEW (introduced by `9cb2703b3`, "Oblivion ingestibles reach the catalog", Refs #7045).
- **Description**: xEdit TES4 `wbEffects` (`wbDefinitionsTES4.pas:1492-1517`): `SCIT` is `wbFormIDCk('Script effect', [SCPT, NULL])` then `Magic school` u32, `Visual effect name` char4, `Hostile` u8. The shared `MagicEffectAccumulator::feed` remaps it (`item.script_form_id = remap_fid(.., remap)`), and the SPEL/ENCH callers pass their remap (`magic.rs:962`, `:1435`). The new Oblivion ALCH route instead builds a fresh accumulator inside `oblivion_effect_chain` and feeds it `&None`, so for ALCH the script FormID stays plugin-local. EFID is a char4 on Oblivion (correctly not remapped), so the only FormID the helper decodes is the one it forgets. The three test guards cannot see it: `oblivion_effect_chain` is not a `pub fn parse_*`, and `no_parser_with_a_remap_in_scope_passes_an_identity_remap` only scans `parse_*` bodies.
- **Evidence**: Oblivion.esm ships 253 ALCH, 9 of them with a `SCIT` (census, `Oblivion.esm`, header 20 B). Vanilla is masked because Oblivion.esm sits at slot 0 with no masters (identity). A modded potion whose script effect points at its own script (`0x01xxxxxx` local) lands in `ConsumableEffect.effect.script_form_id` as that raw value; `cast_effect` then takes `script = item.script_form_id` (non-zero) and the VM resolves it in the *global* script table. With one master at slot 0 and the plugin at slot 1 the local id coincides; with 2+ masters, or any plugin not at slot == master-count (every realistic modded Oblivion list), it points at the wrong script or none.
- **Impact**: Mod-authored Oblivion potions with a script effect cast the wrong script (or nothing) on a multi-plugin load; vanilla unaffected. Reachable through `consumable_cast_effects` → inventory catalog.
- **Related**: #4071, #5076 (the accumulator's own remap rules), #7045.
- **Suggested Fix**: give `oblivion_effect_chain` a `remap` parameter and thread `parse_effects`' remap through it; add a test with a non-identity `FormIdRemap` and `SCIT` on an Oblivion ALCH, modelled on `parse_spel_efid_is_remapped`.

##### ESM-D4-06: Starfield `DOOR` `ANAM` (and `BNAM`) are read as sound FormIDs, so `DoorData` carries garbage sounds on 326 of 339 doors
- **Severity**: LOW (latent: the door runtime does not play Starfield doors, and a garbage id misses `index.sounds`; but the decoded field and the `door.state` output are wrong, and the skill claims the layout is settled)
- **Dimension**: 4
- **Record / Sub-record**: Starfield `DOOR` `ANAM` / `BNAM` / `SNAM`
- **Location**: `crates/plugin/src/esm/cell/support.rs:92-107` (`b"SNAM" | b"ANAM" | b"BNAM" if is_door && sub.data.len() >= 4`, no game gate); `crates/plugin/src/esm/cell/base_objects.rs:229-248` (`DoorData` doc: "read as Skyrim's layout until checked"); `.claude/commands/audit-esm/SKILL.md:425`
- **Status**: NEW (adjacent to open #7061 "M66 Phase 3: Fallout 4 graph doors and a Starfield census")
- **Description**: xEdit `wbDefinitionsSF1.pas:11598-11626` defines Starfield `DOOR` with sound references `DOSH` / `DCSH` / `DLSH` (`wbSoundReference`), and `ANAM` is **Facing Axis Override**, a `u32` enum (0 X, 1 Y, 2 Based on Bounds). `SNAM`/`BNAM` are not door sounds there. The arm reads the first `u32` of every `SNAM`/`ANAM`/`BNAM` as a remapped sound FormID on every game. `FNAM` bits 1-5 do match Skyrim's names on Starfield (bit 0 is "No Quest Target", bit 7 "No Direct Activation", unmodelled), so only the sounds are wrong. FO4 and FO76 are correct: their `SNAM`/`ANAM`/`BNAM` are `SNDR` references (`wbDefinitionsFO4.pas:6493-6495`, `wbDefinitionsFO76.pas:8530-8532`) and their `FNAM` bits 1-5 match Skyrim's.
- **Evidence**: a raw walk of `Starfield.esm` (339 `DOOR`): `ANAM` is 4 bytes on 336 records (value 2 on 326, 0 on 10). So `close_sound = Some(2)` on 326 doors. Longer `ANAM`/`BNAM` bodies (49-120 bytes, component payloads whose first dword is text, e.g. `0x6D616341`) also pass the `len >= 4` gate and set `close_sound` / `loop_sound` to remapped text. `FNAM` is 1 byte on all 339.
- **Impact**: `StaticObject::door.close_sound` and `loop_sound` hold fabricated ids on Starfield, and `commands/door.rs` prints them. `systems/door.rs::play_door_sound` drops them with a `debug!` ("not a sound record"), so nothing audible breaks today. It would corrupt any Starfield door-sound work (#7061) and violates the no-fabrication rule.
- **Suggested fix**: gate the `SNAM`/`ANAM`/`BNAM` arm to `!= Starfield` and leave the three sounds `None` there until the `DOSH`/`DCSH`/`DLSH` `wbSoundReference` is decoded. Add a Starfield fixture to `tests/door.rs`. Correct the skill text at `SKILL.md:425` (FO4 and FO76 are verified, Starfield is verified for flags only).

##### ESM-D4-07: the Oblivion ALCH effect chain is decoded with `&None`, so a script effect's `SCIT` FormID skips the plugin remap
- **Severity**: LOW (latent: no vanilla Oblivion ALCH in a non-zero-index plugin authors a `SCIT`)
- **Dimension**: 4
- **Record / Sub-record**: Oblivion `ALCH` `SCIT` (`MagicEffectItem::script_form_id`)
- **Location**: `crates/plugin/src/esm/records/misc/magic.rs:896-904` (`oblivion_effect_chain` calls `chain.feed(sub, &None)`); `crates/plugin/src/esm/records/items/consumable.rs:29-45` (the Oblivion early return that ignores its own `remap` parameter)

- **Description**: `SPEL`/`ENCH` feed the same accumulator with the plugin's remap, so their `SCIT` script reference is load-order-remapped (`remap_fid(..., remap)` at `magic.rs:874`). The ALCH path added for Oblivion ingestibles discards the `remap` it was handed. `EFID` and `EFIT` are unaffected (4-char codes and raw actor-value indices are correctly un-remapped); only `SCIT`'s script FormID is a cross-reference. `cast_effect` (`scripting/magic_effects.rs:99`) then uses it as the script a potion's effect runs.

The DLCs author no `ALCH` with `SCIT`: `DLCMehrunesRazor` / `DLCVileLair` `SCIT` appear only on `INGR`/`ENCH`/`SPEL`, whose paths remap. Mod ALCH is where a non-zero index would appear.
- **Impact**: a modded Oblivion potion with a script effect referencing its own or a master's script resolves the wrong (or no) script.
- **Suggested fix**: thread `remap` through `oblivion_effect_chain(subs, remap)` and keep `EFID` on the `remap_efid` rule that `feed` already applies.

###### ESM-D5-01: Starfield `DOOR` sound arms read component-block `ANAM` / `BNAM` strings and the `ANAM` Facing-Axis enum as sound FormIDs
- **Severity**: LOW (wrong decode on Starfield; the only consumer misses harmlessly and Starfield door sounds are not decoded anyway)
- **Dimension**: Base-object records read through the cell walker (DOOR)
- **Record / Sub-record**: Starfield `DOOR` `ANAM` / `BNAM` (and `FNAM`, correct)
- **Location**: `crates/plugin/src/esm/cell/support.rs:90-103` (the `b"SNAM" | b"ANAM" | b"BNAM" if is_door && sub.data.len() >= 4` arm, added by `50abfd008`); doc on `DoorData` in `cell/base_objects.rs`; consumer `byroredux/src/systems/door.rs:33,42` (`door_sound`, `play_door_sound`)
- **Status**: NEW (door-runtime M66 Phase 3 "a Starfield census" is #7061, still open; this is the decode defect that census would hit)
- **Description**:
  - The arm is gated on `is_door` only, with no game gate and no component-block awareness. xEdit gives each game a different `DOOR` layout. TES4 / FO3 / FNV / TES5 / FO4 / FO76 author `SNAM` open, `ANAM` close, `BNAM` loop as sound FormIDs (`SOUN` or `SNDR`).
  - Starfield (`wbDefinitionsSF1.pas:11575-11620`) authors sounds as `DOSH` / `DCSH` / `DLSH` `wbSoundReference` structs, and `ANAM` is `Facing Axis Override` (u32 enum 0 / 1 / 2). Starfield `DOOR` also carries `wbBaseFormComponents` (`BFCB` ... `BFCE` blocks) whose payload uses its own `ANAM` / `BNAM` / `CNAM` strings.
  - `build_static_object_from_subs` has no `game` parameter and does not skip `BFCB` blocks, so on Starfield the arm reads the first four bytes of a component string as a FormID into `open_sound` / `close_sound` / `loop_sound`, and the trailing 4-byte Facing-Axis `ANAM` overwrites `close_sound` last (value 0 maps to `None`, 1 and 2 to a bogus remapped FormID).
- **Evidence** (Starfield.esm, stdlib raw walker, `scratchpad/door_sf.py`, `door_sf2.py`):
  - 339 `DOOR` records. Codes seen: `DOSH` 310, `DCSH` 303, `DLSH` 1, no `SNAM`, `FNAM` 339 (1 byte, correct), `BNAM` 310 and `ANAM` 649 (more than one per record).
  - Record `0x1b9e`: `... BFCB, ANAM(54), BNAM(105), CNAM(87), BFCE ... DOSH(40), FNAM(1), DEVT(4), ANAM(4)`. Component `BNAM` payloads begin with ASCII (`"ship"` = `0x70696873`, `"arch"` = `0x68637261`).
  - The trailing 4-byte `ANAM` (Facing Axis) is `2` on 326 records, `0` on 10, `1` on 3.
  - FNV / FO3 / Skyrim / FO4 / FO76 `DOOR` layouts in `/mnt/data/tmp/wbDefinitions*.pas` all match the arm; only Starfield diverges.
- **Impact**:
  - 310 of 339 Starfield doors get a garbage `loop_sound`; 329 of 339 get `close_sound = Some(remap(1 or 2))`.
  - `door_sound` returns `close_sound` when a door closes, and `play_door_sound` does `index.sounds.get(&sound)`, which misses (no `SOUN` has that id), so the effect is a `log::debug!` per close, not a wrong sound. `loop_sound` is not played (#7062).
  - A wrong decode that a future Starfield door-sound phase would trust. Starfield's real sounds (`DOSH` / `DCSH`) are never read.
- **Suggested fix**:
  - Thread `game` (or a "inside a `BFCB` block" flag) into the arm. For Starfield, leave the three sounds `None` until `DOSH` / `DCSH` / `DLSH` are decoded as `wbSoundReference`.
  - Pin it with a Starfield `DOOR` fixture carrying a component `BNAM` string and a trailing `ANAM` = 2 that must leave all three sounds `None`.
  - Also update the `DoorData` doc: "FO4 and Starfield read as Skyrim's layout" is right for `FNAM` bits 1-5 (Starfield bit 0 is *No Quest Target*, bit 6 *No "To" Text*, bit 7 *No Direct Activation*, all unnamed here) but wrong for the sounds.

- **Description**: `travel_data` rebuilds `SpaceGraph` (every placed load door of every cell, `index.navmesh_door_links()`) and `interior_actors` only when the pointer key changes. The slot stores the derived `TravelData`, not the `Arc<EsmIndex>`, so nothing keeps the old index allocated. `SharedParseCache` also holds only the most recent plugin set. Sequence: load A (cache built for address a) → live load B (new `Arc` allocated while A is still alive, so address b ≠ a; A freed once the resource and the parse cache both drop it) → no Travel actor ticks while B is current (an interior with none) → live load C allocates its `Arc` while B is alive and reuses A's freed chunk at address a (same-size allocation, glibc reuse is the likely outcome) → `travel_data` sees `built_for == key` and returns A's graph for C. The load-order discriminator `LoadOrderBasis` from `load_order.rs:354` is exactly what `0e8053225` introduced to avoid this class.
- **Evidence**: `rg 'Arc::as_ptr' byroredux/src` shows the three sites. `TravelIndex` is only `init_resource`d at boot (`boot/world.rs:462`) and never removed (`rg TravelIndex` outside tests: boot + definition). The music catalog and story memo refresh every frame, so a stale address cannot survive there unless their systems are skipped; only the Travel cache is lazy.
- **Impact**: cross-space Travel (`route_toward`, `plan_journey`) would route through door FormIDs of another load order: `resolve_entity_by_global_form_id(first.door)` misses and the actor reports `Unroutable`, or, if the slot layouts coincide, walks to a wrong door. No save corruption (the cache is `NOT_SAVED_BY_DESIGN`).
- **Suggested fix**: key the cache on something that cannot be recycled: a monotonically increasing generation stamped on `LoadedCellIndex` when it is replaced, or `Weak<EsmIndex>` with `ptr_eq` plus a live `upgrade()`. Do not store the strong `Arc` (it would pin a ~1 GB index).

###### ESM-D7-03: `npc_dialogue_follow_up` rescans every `DIAL` record's INFOs each frame while a finished line's follow-ups all fail their gates
- **Severity**: LOW (per-frame linear scan of an `EsmIndex` map, but only in one rare conversation state)
- **Dimension**: 7 (EsmIndex → ECS handoff, per-frame scans)
- **Record / Sub-record**: `INFO` `TCFU` follow-ups (`InfoRecord::follow_ups`)
- **Location**: `byroredux/src/systems/npc_dialogue.rs:743-788` (the scan is `:774`), called every frame from `npc_dialogue_selection_system_inner` (`:875`)
- **Status**: NEW (`0d1c81b7b`, 2026-11-11)
- **Description**: once the open line's `line_ends_at` has passed, the function looks up the current INFO's `follow_ups`; for each it does `index.dialogues.values().find_map(|record| record.infos.iter().find(|info| info.form_id == follow_up) ...)`, a scan over every topic and every INFO in the load order, then clones the info and the topic header into a one-INFO `DialRecord` and evaluates its conditions. - **Evidence**: the only writers of `line_ends_at` are `npc_dialogue.rs:469` (presenting a line) and `scaleform_dialogue.rs:161` (clamping it); the failure path of `npc_dialogue_follow_up` (`continue` at `:775`, `:779`, `:782`, end of loop) writes nothing. `rg 'info_to_topic|topic_of_info|infos_by'` over `crates` and `byroredux/src` is empty: there is no INFO → topic reverse index.

- **Suggested fix**: remember the checked `(topic, info)` pair on `DialogueSurfaceState` (or clear `line_ends_at` once the follow-up decision is made) so the decision runs once per line; and resolve a follow-up INFO's topic through a once-built `info_form_id → topic` map on `EsmIndex` (or on the dialogue runtime) instead of a scan.

#### Findings

##### ESM-D8-01: Starfield `LCTN` `ACPR`/`LCPR` and `ACSR`/`LCSR` are decoded with FO4's entry sizes; 37,800 spurious warns and wrong location refs
- **Severity**: LOW
- **Dimension**: Real-Data Validation
- **Record / Sub-record**: `LCTN` `ACPR`, `LCPR` (persist location refs), `ACSR`, `LCSR` (special refs); Starfield only
- **Location**: `crates/plugin/src/esm/records/misc/location.rs:62-112`
- **Status**: NEW (not in the 120 open issues; the orchestrator's ESM-01 covers only DOOR)
- **Description**: the decoder walks `ACPR`/`LCPR` in 12-byte steps (ref, cell/world, grid y i16 + x i16) and `ACSR`/`LCSR` in 16-byte steps (ref type, ref, cell, grid). xEdit `wbDefinitionsSF1.pas:13400-13470` appends a `wbUnknown(4)` to both structs: `ACPR`/`LCPR` are 16 bytes per entry, `ACSR`/`LCSR` are 20. FO4 and FO76 have the shorter layout, so the code is right for them and wrong only for Starfield (which dispatches through the same arms).
- **Evidence**: `Starfield.esm` `LCPR` lengths are 517/517 multiples of 16, and 269+35 of them are not multiples of 12; `LCSR` 714/714 are multiples of 20 while only 135 of 714 are multiples of 16. FO76 and FO4 `LCPR` are 100% multiples of 12 and `LCSR` 100% multiples of 16, so the shared decoder is right for them. Backtrace attribution on the real load path: `location.rs:106` (`ACSR` ref type and ref) 33,735 warns, `location.rs:68` 4,065 warns. Values such as `ffffffff` and `7fff7fff` are the next entry's grid/unknown words read as FormIDs.
- **Impact**: `LocationRecord::editor_location_refs` and `ref_type_refs` hold fabricated references for Starfield locations (6,017 `LCTN`; `crates/scripting/src/location.rs` reads them for `GetInCurrentLocFormList` / location aliases). Practically no Starfield script consumer runs yet, so the visible effect is 37,800 of the 62,576 warns per load. It also adds to ESM-01's "buries the genuine out-of-range warnings" impact.
- **Related**: orchestrator ESM-01 (`DOOR`), ESM-D8-02, ESM-D8-03 (same warn source).
- **Suggested fix**: make the stride a per-`GameKind` constant (Starfield 16 / 20, others 12 / 16) and gate the trailing `wbUnknown(4)`. Add a real-data pin that Starfield `LCPR`/`LCSR` payload lengths are exact multiples of the stride.

##### ESM-D8-02: `NPC_.PRPS` entries are 12 bytes on Starfield and FO76 (an AV, a float and a Curve Table FormID); decoded as 8-byte pairs
- **Severity**: LOW
- **Dimension**: Real-Data Validation
- **Record / Sub-record**: `NPC_` `PRPS`; Starfield (7,131 records) and FO76 (6,552 records)
- **Location**: `crates/plugin/src/esm/records/actor/npc.rs:1154-1171` (`parse_npc_actor_values`, `sub.data.as_chunks::<8>()`)
- **Status**: NEW
- **Description**: xEdit defines the property struct with `wbFromVersion(152, wbFormIDCk('Curve Table', [CURV, NULL]))` appended to the AV + value pair (`wbDefinitionsSF1.pas:5677-5686` and `wbDefinitionsFO76.pas:7002-7009`). The census agrees: every Starfield and FO76 payload is a multiple of 12. FO4 (`wbDefinitionsFO4.pas:5266`) has no curve and stays 8 bytes, which is why the decoder is right for FO4. Other `PRPS` readers (`RACE` 31 on Starfield, 45 on FO4, and the `ACTI`-family) were not checked for the same stride.
- **Evidence**: Starfield `PRPS`: 7,131 of 7,131 payloads are multiples of 12, and 3,132 of them are not multiples of 8, so every chunk after the first is misaligned for those; a 12-byte payload is read as one good pair plus a 4-byte tail, and larger ones are misread from entry two on. FO76: 6,552 of 6,552 are multiples of 12, 1,498 not multiples of 8. FO4: 3,015 of 3,015 are multiples of 8 and 2,317 of them are not multiples of 12, so FO4 stays correct. With the engine's remap this site produces 23,981 of the 62,576 Starfield warns.
- **Impact**: `NpcRecord::actor_value_props` holds wrong (AV id, value) pairs for 13,683 Starfield and FO76 NPCs. `derive_npc_actor_values` consumes it only on the FO4 arm (`actor_value_derive.rs:564`; FO76/Starfield "no longer inherit FO4's Stored", line 1777), so nothing visible changes today. It would the moment a Starfield/FO76 ruleset reads it. LOW as a latent decode error with no consumer.
- **Suggested fix**: choose the stride from `GameKind` (12 for `Fallout76 | Starfield`) or from the record form version (`>= 152`), keeping the Curve Table FormID.

##### ESM-D8-03: CTDA `param_1 = 0xFFFFFFFE` is remapped as a FormID on Starfield (175 warns)
- **Severity**: LOW
- **Dimension**: Real-Data Validation
- **Record / Sub-record**: `CTDA` (QUST 147, SCEN 21, PACK 4, INFO 1), function 1 (172 of 174) and function 32 (1)
- **Location**: `crates/plugin/src/esm/records/condition.rs:638-641` (`remap_condition_form_ids`), `param1_is_form_id` at `condition.rs:542-546`
- **Status**: NEW, same family as the closed #6786-class "inverse-shape remap" and Dim 3's `GetActorValue` finding
- **Description**: `param1_is_form_id(1)` marks function 1 (`GetDistance`, target FormID in Skyrim/FO4) as FormID-bearing. On Starfield every occurrence in `Starfield.esm` carries the sentinel `0xFFFFFFFE` (a "none/self" marker), which `remap_starfield` cannot resolve and logs. The function table is the Skyrim/FO4 one; Starfield re-uses these indices for other meanings.
- **Evidence**: probe over every CTDA/CTDT in `Starfield.esm`: 174 conditions where `param1_is_form_id(fn)` is true and `param_1 >> 24 != 0`, all `param_1 == 0xFFFFFFFE`, `param_2 == 0`.
- **Impact**: 175 warns per Starfield load and a no-op pass-through. The value is left unchanged, so no condition is evaluated differently. Log noise only.
- **Suggested fix**: skip `0xFFFFFFFE` (and `0xFFFFFFFF`) in `remap_condition_form_ids`, or gate `param1_is_form_id` on `GameKind` (there is no Starfield function catalog yet).

##### ESM-D8-04: FO76 `CELL.XCRI` uses `u64` counts and 8 / 16-byte entries; the FO4-shaped decoder rejects all 1,182 FO76 occurrences
- **Severity**: LOW
- **Dimension**: Real-Data Validation
- **Record / Sub-record**: `CELL` `XCRI` on Fallout 76
- **Location**: `crates/plugin/src/esm/cell/helpers.rs:155-198` (the `XCRI` arm is not gated by game)
- **Status**: NEW
- **Description**: xEdit `wbDefinitionsFO76.pas:8069-8085` defines `XCRI` as `u64 meshes count`, `u64 references count`, then 8-byte `Mesh` entries (hash + 4 unknown) and 16-byte `Reference` entries (ref, 4 unknown, combined mesh, 4 unknown). The decoder implements the FO4 layout (`wbDefinitionsFO4.pas:6088`: `u32` counts, 4-byte mesh hashes, 8-byte ref pairs).
- **Evidence**: 1,182 FO76 `XCRI` size-mismatch warns, `hdr=1+0 expected=12 actual=40`, `hdr=2+0 … actual=64`, `hdr=3+0 … actual=88`: the "second count" is the high dword of the first `u64`, and 40 = 16 + 8×1 + 16×1, 64 = 16 + 8×2 + 16×2, 88 = 16 + 8×3 + 16×3. The arm warns and skips, so the data is dropped, not mis-read.
- **Impact**: FO76 precombined-mesh dedup (`precombined_mesh_hashes`, `absorbed_ref_bakes`) is inactive for 1,182 cells, and the log carries 1,182 warns per load. There is no FO76 render path that consumes it. FO4 and Starfield do not hit this warn (Starfield has no `XCRI`).
- **Suggested fix**: add a FO76 arm with the `u64` header and wider entries (or log at `debug` and document FO76 as unsupported); keep the FO4 arm for `Fallout4`.
