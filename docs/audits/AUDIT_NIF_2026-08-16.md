# NIF Parser Audit — 2026-08-16

Deep audit of the NIF binary-format parser (`crates/nif/src/`) across all 6
dimensions: Stream Position Integrity, Version Gating, Block Dispatch Coverage,
Geometry Extraction & Import Handoff, Collision & Shader Block Parsing, and
Allocation Hygiene.

**Scope**: the parser *as a parser*, across its full supported version range
(Oblivion v10.x / v20.0.0.5 → Starfield). No `--game` restriction. Corpus
evidence was gathered from all seven shipping titles.

## Executive Summary

The wire-level parser is in excellent health and **measurably better than the
checked-in documentation claims**. Every dimension that concerns byte accuracy
came back clean:

- **Zero** consumed-vs-`block_size` drift on Oblivion / FO3 / FNV meshes
  (`nif_stats --drift-histogram`).
- **Zero** `NiUnknown` fallbacks on all seven games.
- **All 7** checked-in `per_block_baselines` PASS (DLC-wide), including
  Oblivion — which means the OPEN **#2574** ("the opt-in regression gate
  currently FAILS") is no longer reproducible.
- **1 037** `byroredux-nif` unit tests green, 0 failed.
- Oblivion truncations are down from the documented 6 to **1**
  (`meshes\marker_map.nif`, the tracked out-of-scope NetImmerse marker family
  #1843).

All three new findings are in **one place**: the shared `BSShaderTextureSet`
slot→role table introduced two days before this sweep
(`crates/nif/src/import/material/slot_role.rs`, `0d68574c`, 2026-08-14). Its
signature is `(shader_type, slot, model_space_normals)` — **it carries no
`bsver`**, and every per-arm rule in it was measured on `Skyrim - Meshes0.bsa`
only. Applied unchanged to FO4 and FO76 content, whose slot occupancy is
measurably different, it mis-routes one slot and silently drops two.

The FO4 arms are not inferred from naming conventions — they are proven by
cross-referencing each mesh's texture-set slots against that same mesh's own
`.bgsm` out of `Fallout4 - Materials.ba2`.

**Total new findings**: 3 (0 CRITICAL, 0 HIGH, 3 MEDIUM, 0 LOW).
**Total stream-position mismatches found**: 0.
**Critical coverage gaps**: none — 252 live top-level dispatch arms, 0%
`NiUnknown` on every game.

## Findings

### MEDIUM

#### NIF-D4-2026-08-16-01: FO4 texture-set slot 3 is the BGSM grayscale-to-palette LUT, and `slot_to_role` routes it into the POM height role

- **Severity**: MEDIUM
- **Dimension**: Geometry Extraction & Import Handoff
- **Game Affected**: Fallout 4 (`bsver` 130–139). Skyrim (`bsver` 83–129) is
  correct via the `FACE_TINT` arm; FO76 (`bsver` 155) populates slot 3 only 68
  times; Starfield (`bsver` ≥ 172) authors no inline texture sets at all.
- **Location**: `crates/nif/src/import/material/slot_role.rs:118-121`
  (the `3 =>` arm) and `:37-54` (`TextureRole`, which has no greyscale
  variant); consumed at
  `crates/nif/src/import/material/dedicated_shader.rs:144-176`
- **Status**: NEW
- **Description**: `slot_to_role`'s slot-3 arm is
  `FACE_TINT => Detail, _ => Height`. The `_` default sends the slot into
  `info.parallax_map`. On FO4 that slot is not a height field: it is the
  grayscale-to-palette LUT the BGSM calls `greyscale_texture`. Proven by
  cross-referencing each mesh's populated slots against that same mesh's own
  `.bgsm` from `Fallout4 - Materials.ba2` — of the slot-3 entries in an
  8 000-file sample, **464 match `greyscale_texture` byte-for-byte and 0 match
  any height or displacement field** (22 unmatched). `TextureRole` has no
  `Greyscale` variant, so there is no arm that could route it correctly even
  though the canonical destination role exists
  (`MaterialTextureSet::greyscale_lut`, `crates/nif/src/import/types.rs:328`,
  bindless index 15) and is already wired for both the BGSM merge and the
  `BSEffectShaderProperty` path
  (`crates/nif/src/import/material/mod.rs:1177`). What it lacks is a
  `MaterialInfo` field for the inline `BSLightingShaderProperty` path —
  that gap is why the slot falls into `Height` instead.
- **Evidence**:
  ```
  # full-slot semantic cross-check, FO4 Meshes.ba2 vs Materials.ba2
  slot 0: diffuse=8952, unmatched=93
  slot 1: normal=8885,  unmatched=90
  slot 2: glow=230,     unmatched=14, diffuse=2
  slot 3: greyscale=464, unmatched=22          <-- routed to TextureRole::Height
  slot 7: smooth_spec=8603, unmatched=63, normal=4
  ```
  ```rust
  // slot_role.rs:118-121 — no bsver, no greyscale destination
  3 => match shader_type {
      bs_lighting::FACE_TINT => Some(TextureRole::Detail),
      _ => Some(TextureRole::Height),
  },
  ```
  The consumer chain is unconditional: `info.parallax_map`
  (`crates/nif/src/import/material/mod.rs:1163` → `MaterialTextureSet::height`) →
  `texture_indices.height` (`byroredux/src/render/static_meshes.rs:267`) →
  `GpuMaterial::parallax_map_index` → `crates/renderer/shaders/triangle.frag:208`,
  whose POM branch gates on `mat.parallaxMapIndex != 0u` alone, with no
  material-kind check.
- **Impact**: **5 456** texture-set-bearing FO4 `BSLightingShaderProperty`
  blocks in vanilla `Fallout4 - Meshes.ba2` populate slot 3, so every one of
  them makes the geometry pass ray-march parallax-occlusion mapping over a
  colour palette LUT — UVs are displaced by data that has no height semantics
  whatsoever. The BGSM merge cannot rescue it: `fill` is first-wins and
  `byroredux/src/asset_provider/material.rs:1229-1233` sources
  `textures.height` from `bgsm.displacement_texture`, so the NIF's LUT keeps
  the role whether or not the mesh resolves a BGSM. Simultaneously the LUT
  never reaches `greyscale_lut` on any mesh that has no external material.
  Visual-only — no corruption, no crash.
- **Related**: Exactly the failure mode #2694 fixed for Skyrim FaceTint
  (`crates/nif/src/import/material/slot_role.rs:112-117` documents it verbatim:
  *"Feeding that to the height role made triangle.frag ray-march POM over a
  face complexion map — its POM branch gates only on parallaxMapIndex != 0u,
  with no material-kind check"*). Same
  bug, different band. Sibling of NIF-D4-2026-08-16-02/-03 (same root cause).
  Adjacent but distinct from #2594 (BGSM→role forwarding) and #2713 (REFR
  overlay `inner`).
- **Suggested Fix**: Give `slot_to_role` a `bsver` parameter (the REFR overlay
  can supply it the same way it already recovers `shader_type` from
  `ImportedMaterial`), add a `TextureRole::Greyscale` variant plus the
  `MaterialInfo` field it needs, forward that field into
  `MaterialTextureSet::greyscale_lut` alongside the existing effect-shader
  source, and route slot 3 to it for `bsver >= FALLOUT4`. Pin the new band with
  a test — `crates/nif/src/import/material/slot_role.rs` contains zero `bsver` references today and no
  existing test exercises `slot_to_role` at any band other than Skyrim's.

#### NIF-D4-2026-08-16-02: `slot_to_role`'s slot-7 model-space-normals gate is Skyrim-only evidence; it drops FO4's smooth-spec map on 63 253 of 63 314 properties

- **Severity**: MEDIUM
- **Dimension**: Geometry Extraction & Import Handoff
- **Game Affected**: Fallout 4 (`bsver` 130–139). Skyrim is correct (see
  Evidence). FO76 and Starfield never populate slot 7.
- **Location**: `crates/nif/src/import/material/slot_role.rs:151-155`
  (the `7 =>` arm)
- **Status**: NEW
- **Description**: The arm is
  `(MULTI_LAYER_PARALLAX, _) => None, (_, true) => Specular, (_, false) => None`.
  Its doc cites #2742's measurement — *"390/390 slot-7-bearing SkinTint
  properties in `Skyrim - Meshes0.bsa` are MSN"* — as the justification for
  requiring model-space normals. That measurement is Skyrim-only and does not
  transfer: on FO4, slot 7 is populated on 93% of texture-set-bearing
  properties while MSN is set on essentially none of them, so the gate rejects
  the slot wholesale.
- **Evidence**:
  ```
  # Skyrim SE Meshes0.bsa — the gate is exactly right here
  slot 7 populated = 5537,  MSN = 3603,  '_s.dds' names = 3603   (exact match)

  # Fallout4 - Meshes.ba2 — the gate rejects the slot wholesale
  slot 7 populated = 63314, MSN = 61,    '_s.dds' names = 59400
  shader_type spread among them: {0:37195, 1:19596, 2:2533, 4:1229, 5:1348, 6:1411, 16:2}
  # semantic proof vs each mesh's own BGSM:
  slot 7: smooth_spec=8603, unmatched=63, normal=4
  ```
  FO4 slot 7 is therefore the BGSM `smooth_spec_texture` — *"smoothness in
  alpha, specular RGB"* (`crates/bgsm/src/bgsm.rs:26-27`), whose canonical role
  `MaterialTextureSet::smooth_spec` already exists and already feeds
  `gloss_map` (`byroredux/src/material_translate.rs:138`).
  The MSN flag itself is read correctly — `fo4_slsf1::MODEL_SPACE_NORMALS` and
  `skyrim_slsf1::MODEL_SPACE_NORMALS` are pinned equal by an explicit lockstep
  assertion at `crates/nif/src/shader_flags.rs:426-427` — so the 61 count is
  real, not a bit-vocabulary mistake.
- **Impact**: Of the 63 314 slot-7-bearing FO4 properties, **47 966 resolve an
  external `.bgsm`/`.bgem`/`.mat`** (via `net.name` or `root_material_path`),
  and for those the BGSM merge backfills `textures.smooth_spec` from the same
  texture, so nothing is lost. The remaining **15 348 carry no external
  material path at all** — their authored gloss/specular map is dropped
  outright and those surfaces render with no smoothness/specular response.
  Samples: `meshes\scol\fallout4.esm\*.nif` (static collections),
  `meshes\landscape\rrtracks\*`, `meshes\setdressing\institute\*`,
  `meshes\interiors\vault\*`.
- **Related**: Sibling of NIF-D4-2026-08-16-01/-03 (same root cause: the table
  has no `bsver`). Distinct from #2594 (which is about the BGSM→role
  forwarding, i.e. the path that *does* work here).
- **Suggested Fix**: With the `bsver` parameter from finding -01, route slot 7
  to a `TextureRole::SmoothSpec` (→ the existing `MaterialInfo::gloss_map`,
  which already forwards to `MaterialTextureSet::smooth_spec` at
  `crates/nif/src/import/material/mod.rs:1161`) for
  `bsver >= FALLOUT4` unconditionally, and keep the existing MSN-gated
  `Specular` behaviour for the Skyrim band, where the evidence supports it.

#### NIF-D4-2026-08-16-03: FO76 populates texture-set slot 6 on 1 622 properties; `slot_to_role`'s only slot-6 arm is a Skyrim shader-type that FO76's enum cannot produce, so all of them are dropped

- **Severity**: MEDIUM
- **Dimension**: Geometry Extraction & Import Handoff
- **Game Affected**: Fallout 76 (`bsver` 155). FO4 never populates slot 6;
  Starfield authors no inline texture sets.
- **Location**: `crates/nif/src/import/material/slot_role.rs:143-146`
  (the `6 =>` arm); `crates/nif/src/import/material/dedicated_shader.rs:49-59`
  (`normalize_shader_type`)
- **Status**: NEW
- **Description**: The slot-6 arm is
  `MULTI_LAYER_PARALLAX => InnerLayer, _ => None`, where
  `MULTI_LAYER_PARALLAX = 11` is a `BSLightingShaderType` value. FO76 numbers
  its shader types with `BSShaderType155`, whose entire roster is
  `{0 Default, 2 Glow, 3 Face Tint, 4 Skin Tint, 5 Hair Tint, 12 Eye Envmap,
  17 Terrain}` (nif.xml; the parser's own
  `parse_shader_type_data_fo76` implements exactly this set). **11 is not a
  legal FO76 value**, so the arm can never fire on FO76 content and the slot is
  always dropped. `normalize_shader_type` rescues only the `Fo76SkinTint` case
  by inspecting `shader_type_data`; raw FO76 types 3/5 still resolve against
  Skyrim's numbering everywhere else in the table.
- **Evidence**:
  ```
  # SeventySix - Meshes.ba2 (bsver histogram: {155: 58469})
  BSLightingShaderProperty total = 137327
    material-reference stubs (early-return)  = 133891
    with an inline BSShaderTextureSet        =   3436   (0 of them stubs)
  slot 6 populated = 1622   slot 7 populated = 0
    of the 1622: 1574 (97%) end in '_s.dds'
                 model_space_normals = 0
                 root_material_path  = 52
                 net.name is a material path = 0
    shader_type spread: {0:1548, 2:59, 3:1, 4:2, 5:12}   <-- none is 11
  samples: meshes\lod\buildings\smalltown\bld02addbalcony01_lod.nif
             -> textures\lod\BrickAHouseLOD_s.dds
           meshes\dlc06\interiors\vault\workshop\vltworkshoputilstairs01.nif
             -> textures\Interiors\Vault\Util_Column01_S.dds
  ```
- **Impact**: All 1 622 authored slot-6 textures are dropped at import, and
  **1 570 of them have no external material of any kind** to backfill from — so
  the texture never reaches the GPU on any FO76 mesh that uses it. Affected
  content is concentrated in distant-LOD building meshes and Vault interiors.
  The **exact canonical role is unconfirmed**: only one FO76 mesh in the corpus
  resolves to a non-template `.bgsm`, so the BGSM cross-check that proved the
  FO4 slots cannot be run here. What is certain is the drop. The 97% `_s.dds`
  naming, combined with FO4's proven `_s.dds`-in-texture-set = `smooth_spec`,
  points at smooth-spec/specular — but that must be byte-confirmed against
  FO76 template materials before being encoded, not assumed.
- **Related**: Sibling of NIF-D4-2026-08-16-01/-02. Adjacent to OPEN **#2579**
  ("FO76 `BSShaderType155` numbering leaks into the Skyrim-numbered
  `material_kind` consumer") — same *class* of numbering leak, but a different
  consumer: `crates/nif/src/import/material/slot_role.rs` did not exist when #2579 was filed (it landed
  2026-08-14 in `0d68574c`), and the impact here is dropped textures rather
  than a wrong `material_kind`. Not a duplicate.
- **Suggested Fix**: Add the `bsver` parameter (finding -01), then either route
  FO76 slot 6 to the role a byte-level check against `SeventySix -
  Materials.ba2` templates confirms, or — if that cannot be established — make
  the drop *explicit and logged* rather than a silent fall-through of an arm
  that structurally cannot match. Independently, translate FO76's
  `BSShaderType155` values into the `BSLightingShaderType` vocabulary once, at
  the parser boundary, so every downstream consumer (`slot_to_role`,
  `material_kind`/#2579) stops re-deriving it.

## Candidates Investigated and Disproved

These looked like findings and did not survive verification. Recorded so the
next sweep does not re-derive them.

1. **`read_byte_bool` used where nif.xml declares the version-dependent `bool`
   basic type** (59 call sites, e.g. `crates/nif/src/blocks/particle.rs:1198`,
   `crates/nif/src/blocks/skin.rs:263`). Disproved by reachability: `read_bool` is a single
   byte from v4.1.0.1 onward, and the oldest live band Redux targets is
   Oblivion's v10.0.1.0. The two functions are behaviourally identical
   everywhere the engine can reach. Same class as the already-fixed #2526.
2. **`NiGeomMorpherController.Always Update` read unconditionally** though
   nif.xml gates it `since="4.0.0.2"`. Below that version is pre-Morrowind;
   unreachable by any target game.
3. **`NiGeomMorpherController` on file-versions 20.1.0.0–20.1.0.2** reads
   `Num Interpolators` block refs where nif.xml declares neither
   `Interpolators` (`until="20.0.0.5"`) nor `Interpolator Weights`
   (`since="20.1.0.3"`). Real spec gap, but no shipping title is in that band
   (Oblivion 20.0.0.4/5 + v10.x, FO3/FNV/Skyrim+ 20.2.0.7) and no corpus file
   hits it.
4. **`slot_to_role` reading `skyrim_slsf1::MODEL_SPACE_NORMALS` against an FO4
   property** (`crates/nif/src/import/material/dedicated_shader.rs:117`) — looked like the #2604
   wrong-vocabulary bug. Disproved: `crates/nif/src/shader_flags.rs:426-427` pins
   `fo4_slsf1::MODEL_SPACE_NORMALS == skyrim_slsf1::MODEL_SPACE_NORMALS`
   (both `0x0000_1000`) with an explicit lockstep assertion, so the read is
   correct-by-construction.
5. **`parse_shader_type_data_fo76` applied to Starfield (`bsver` 172/173)**
   via the `parse_fo76_plus` `>= 155` band, where nif.xml's `#BS_F76#` is
   `#EQ# 155` exactly. Disproved as a live defect: Starfield parses 100% clean
   across all three mesh archives with 0 drift, and the residual opaque-tail
   telemetry concern is already tracked as #2622/#2625.
6. **Missing `bhkConvexTransformShape` resolve arm.** Disproved: it is an
   alias dispatch arm onto `BhkTransformShape`, which has a resolve arm.
   Parity holds.

## Prioritized Fix Order

The three findings share one root cause and one fix site, so they are best
landed together as a single change to `slot_to_role`'s signature:

1. **NIF-D4-2026-08-16-01** (FO4 slot 3 → POM over a palette LUT) — the only
   one of the three that produces *actively wrong* output rather than a missing
   texture, and it fires on all 5 456 affected meshes regardless of BGSM
   presence. Fix first.
2. **NIF-D4-2026-08-16-02** (FO4 slot 7 smooth-spec dropped) — larger raw
   count (63 314) but 76% of it is backfilled by the BGSM merge; the real loss
   is the 15 348 material-less meshes.
3. **NIF-D4-2026-08-16-03** (FO76 slot 6 dropped) — smallest count (1 622) and
   the only one whose correct destination role still needs byte-level
   confirmation. Do the confirmation before encoding a mapping; per the
   no-guessing rule, an explicit logged drop is better than a guessed role.

Plus the free housekeeping: close **#2574**, and add
`has_skin_data_vertex_weights_flag` to `.claude/commands/audit-nif/SKILL.md:72`.

No stream-position, version-gating, dispatch-coverage, collision-parsing or
allocation-hygiene work is indicated this cycle, so the usual
rendering-blocking → animation → collision fix tiers collapse to the single
