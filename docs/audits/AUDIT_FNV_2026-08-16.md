## Findings

### FNV-2026-08-16-D1-01: `BSXFlags` bit 5 drops the whole NIF, deleting 223 real FNV meshes
- **Severity**: HIGH
- **Dimension**: 1 — Cell Loading End-to-End
- **Location**: `byroredux/src/cell_loader/references/import.rs:84-98`,
  `byroredux/src/cell_loader/partial.rs:55-66`
- **Status**: NEW
- **Description**: Both NIF-import entry points (the synchronous REFR path and the
  exterior-streaming drain) treat `BSXFlags & 0x20` on pre-FO4 content as "this whole NIF is an
  editor marker" and return `None`, discarding meshes, collision, lights and emitters alike.
  nif.xml is explicit that the bit means the file **contains** editor-marker children:

  > `/mnt/data/src/reference/nifxml/nif.xml:4305` — `Bit 5 : EditorMarkers present, bEditorMarker(Skyrim)`

  The correct behaviour is to cull the marker child node, not the model. The over-broad drop was
  introduced by `docs/audits/AUDIT_POSITIONING_DECALS_2026-04-13.md` PD-01, which stated
  "BSXFlags bit 5 marks an **entire NIF** as 'editor marker — do not render'". The 2026-07
  `bsver < FALLOUT4` carve-out narrowed the damage to exactly the pre-FO4 games — Oblivion,
  FO3 and FNV.
- **Evidence**:
  - Live, Prospector Saloon (`mesh.cache failed` over `byro-dbg`):
    `meshes\furniture\stool01.nif`, `meshes\furniture\barkeep.nif`,
    `meshes\effects\ambient\fxbasicglowbillboard.nif`.
  - `stool01.nif` is a genuine stool, not a marker. `trace_block` shows a `BSFadeNode` root, a
    `BSFurnitureMarker`, a `bhkRigidBody` + `bhkMoppBvTree` collision chain, and **two**
    `NiTriStrips` — one small one with `BSShaderNoLightingProperty` + `NiAlphaProperty` (the
    marker), one with `BSShaderPPLightingProperty` and a `BSShaderTextureSet` pointing at
    `textures\furniture\Stool01.dds` + `Stool01_n.dds` backed by a 30 190-byte
    `NiTriStripsData`. Its `BSXFlags` = `0x22` = bit 1 (collision) | bit 5 (markers present).
    `barkeep.nif` (`0x20`, 1 node, 0 meshes) genuinely *is* a pure marker and is correctly skipped.
  - Live, exterior `--grid 0,0 --radius 3` WastelandNV — three more real assets in
    `mesh.cache failed`, each verified to carry geometry:
    `inddoorsmanim01.nif` (BSX `0x2B`, 3 meshes / 2 colliders),
    `barrel02firelight.nif` (`0x33`, 1 / 1),
    `supermutantbedding01.nif` (`0x22`, 2 / 1).
  - Corpus sweep over all 14 881 NIFs in `Fallout - Meshes.bsa` (throwaway example calling
    `extract_bsx_flags` + `import_nif_with_collision`, since removed):
    ```
    pre-FO4 with BSX bit5 set:                              336
      ... pure markers (0 meshes, 0 colliders):             113
      ... carrying real geometry/collision (DROPPED TODAY): 223
    ```
    Sample of the 223: `vehicles\vertibirdencount02.nif` (39 meshes / 9 522 tris / 6 colliders),
    `traps\brahmincorpsetrap1.nif` (9 / 2 641 / 9),
    `traps\trapswingingibeam02.nif` (14 / 2 784 / 16),
    `terminals\mq05openterminal.nif` (9 / 646 / 1),
    `furniture\suburban\subdiningchairdirtyt.nif` (1 / 1 000 / 1),
    `markers\furnituremarker11.nif`, plus dozens of `effects\ambient\fx*`.
- **Impact**: ~1.5% of the FNV mesh corpus never renders and never contributes collision, on
  the title the engine treats as its reference. It removes visible world content (vehicles,
  traps, terminals, seating) *and* physics, so it is also a silent contributor to
  "actor floats / falls through" reports and to thinned particle stacks. Same code path, same
  bit, same era gate on FO3 and Oblivion — treat the blast radius as all three pre-FO4 games.
- **Related**: supersedes the premise of PD-01 (`AUDIT_POSITIONING_DECALS_2026-04-13.md`);
  adjacent to the FO4+ `MultiBoundNode` carve-out noted in
  `docs/audits/AUDIT_TECH-DEBT_2026-07-16.md:147` (that half is fixed — `partial.rs` now carries
  the `bsver` gate).
- **Suggested Fix**: Stop returning `None` on bit 5. Keep the model and cull only the marker
  subtree — extend the existing name-based `is_editor_marker` cull in
  `crates/nif/src/import/walk/mod.rs:1786` so it also runs on geometry leaves
  (`NiTriShape`/`NiTriStrips`), and drop the whole NIF only when the post-cull import yields
  zero meshes, zero collisions, zero lights and zero emitters — which is already the exact
  condition the `#1215` zero-contribution warning at `references/import.rs:150-161` computes.

### FNV-2026-08-16-D6-01: every female and child FNV NPC spawns with the male body mesh
- **Severity**: HIGH
- **Dimension**: 6 — Animation, Skinning & Particles
- **Location**: `byroredux/src/npc_spawn.rs:272-352` (`humanoid_body_paths`)
- **Status**: NEW
- **Description**: `humanoid_body_paths(game: GameKind)` takes no gender parameter and returns
  one hardcoded triple for Oblivion/FO3/FNV: `upperbody.nif`, `lefthand.nif`, `righthand.nif`.
  Its doc comment justifies this with:

  > "Female humanoids on FNV vanilla re-use the male body (verified 2026-04-28 — `_female\`
  > directory not present in vanilla Fallout - Meshes.bsa). … See TD8-018 / #1117 for the
  > placeholder-arg removal rationale."

  The observation is correct and the inference is not. FO3/FNV place **both** genders in the
  same `_male\` directory, distinguished by a filename prefix — so the absence of a `_female\`
  directory says nothing. The gender argument was removed under #1117 on the strength of that
  bad inference.
- **Evidence**: complete listing of `meshes\characters\_male\*.nif` in vanilla
  `Fallout - Meshes.bsa` (via `listbsa`), excluding `idleanims\`/`locomotion\`:
  ```
  childfemaleupperbody.nif   childupperbody.nif
  femaleupperbody.nif        femalelefthand.nif      femalerighthand.nif
  femalelefthand1st.nif      femalerighthand1st.nif
  femalelefthandpipboyglove.nif  femalelefthandpipboyglove1st.nif
  upperbody.nif              lefthand.nif            righthand.nif
  lefthand1st.nif            righthand1st.nif        skeleton.nif   …
  ```
  The gender bit is already decoded and already reaches this call site:
  `crates/plugin/src/equip.rs:49-63` defines `Gender::from_acbs_flags` (ACBS bit 0), and
  `byroredux/src/npc_spawn.rs:37` imports it and passes it at `:688` into `resolve_armor_mesh`.
  Only the body-path selector ignores it.
- **Impact**: `FalloutNV.esm` carries 3 816 NPC_ records; every female one (Sunny Smiles,
  Trudy, Cass, the Legion/NCR female troopers, every female generic) renders with the male
  torso and male hands, and every child renders adult-sized. Wrong silhouette, wrong skin
  weights against the shared skeleton, and armour that was authored to layer over the female
  body sits on the male one. No workaround.
- **Related**: #793 (hands) — the only aspect prior audits checked. Seven earlier reports
  (`AUDIT_FNV_2026-05-30.md:299`, `AUDIT_FNV_2026-06-18.md:144`, `AUDIT_FO3_2026-06-14.md:369`,
  `AUDIT_FO3_2026-06-23.md:95`, `AUDIT_FO3_2026-07-05.md:196`, `AUDIT_FO3_2026-07-16.md:235`,
  `AUDIT_FO3_2026-08-03.md:293`, `AUDIT_FO3_2026-08-07.md:317`) marked
  `humanoid_body_paths` "CLEAN" while only verifying the hand paths.
- **Suggested Fix**: Restore the gender parameter — `humanoid_body_paths(game, gender)` —
  returning the `female*` triple for `Gender::Female` on `Oblivion | Fallout3NV`, and correct
  the doc comment so the `_female\`-directory observation is not re-used as evidence. The child
  variants (`childupperbody.nif` / `childfemaleupperbody.nif`) need a RACE-driven discriminator
  and can follow separately.

### FNV-2026-08-16-D1-02: `NifImportRegistry` cache key diverges between the sync and streaming loaders
- **Severity**: MEDIUM
- **Dimension**: 1 — Cell Loading End-to-End
- **Location**: `byroredux/src/cell_loader/references/synth_child.rs:362-381` vs
  `byroredux/src/streaming.rs:1168`, `byroredux/src/streaming_helpers.rs:270`,
  `byroredux/src/cell_loader/partial.rs:25`
- **Status**: NEW
- **Description**: Both loaders key the shared `NifImportRegistry` on
  `model_path.to_ascii_lowercase()`, but they build `model_path` differently. The synchronous
  REFR path prefixes `meshes\` when the authored `StaticRecord.model_path` lacks it:
  ```rust
  let model_path = if model_lower.starts_with("meshes\\") || model_lower.starts_with("meshes/") {
      stat.model_path.clone()
  } else {
      format!("meshes\\{}", stat.model_path)
  };
  ```
  The streaming worker uses the raw authored path with no prefixing. Both then write into the
  same registry, so one asset occupies two entries.
- **Evidence**: live `mesh.cache failed` on the exterior 7×7 WastelandNV grid returned 17
  entries containing **7 duplicate pairs** of the same asset under both key forms:
  ```
  \wastelandshrub01.spt                              meshes\\wastelandshrub01.spt
  clutter\barrel02firelight.nif                      meshes\clutter\barrel02firelight.nif
  clutter\supermutantcamp\supermutantbedding01.nif   meshes\clutter\…\supermutantbedding01.nif
  effects\ambient\fxdustwhirlwind01.nif              meshes\effects\ambient\fxdustwhirlwind01.nif
  effects\ambient\fxradiationdust1x2.nif             meshes\effects\ambient\fxradiationdust1x2.nif
  effects\ambient\fxradiationdust1x4.nif             meshes\effects\ambient\fxradiationdust1x4.nif
  effects\nv\fxflyswarm.nif                          meshes\effects\nv\fxflyswarm.nif
  ```
  `TextureProvider::extract_mesh` normalises internally
  (`byroredux/src/asset_provider/texture.rs:50/66`), so both keys resolve the *same* archive
  entry — the divergence exists only in the cache key.
- **Impact**: every model reached from both paths is parsed and imported twice (full
  `parse_nif` + `import_nif_with_collision` + BGSM merge + clip conversion), the `#862`
  `cached_keys` pre-filter can never match a sync-path entry so the streaming worker
  re-does work the main thread already did, and the 2048-slot LRU fills at roughly double
  rate — which makes eviction (and the `#863` clip-handle release churn) start earlier than
  the budget in `docs/engine/memory-budget.md` assumes. Compounds per cell-streaming cycle.
- **Related**: FNV-2026-08-16-D1-01 (the duplicated entries are all `None` because of the BSX
  drop — fixing D1-01 turns these into duplicated *positive* entries, i.e. duplicated
  `CachedNifImport` allocations).
- **Suggested Fix**: Hoist the `meshes\` prefixing into one shared helper (next to
  `normalize_mesh_path` in `byroredux/src/asset_provider/archive.rs`) and call it at both key
  sites, or key the registry on `normalize_mesh_path(model_path).to_ascii_lowercase()`
  everywhere.

### FNV-2026-08-16-D8-01: the playable-slice smoke gates are Skyrim-only; the reference title has none

  `docs/smoke-tests/p1-character-traversal.sh:13`, `docs/smoke-tests/p2-melee-core.sh:14`
- **Status**: NEW
- **Description**: All three P0/P1/P2 gates for the project's active execution focus (the

  has a gate only for ragdoll (`docs/smoke-tests/m41-ragdoll.sh:33`, `FNV_DATA`). Nothing
  exercises door interaction, character traversal or melee combat against FNV content.
- **Evidence**: live probe on the FNV bench-of-record cell shows the slice is not merely
  ungated but non-functional:
  ```
  byro> combat.approach 7
  "combat.approach: entity 7 is not a damageable actor"
  byro> input.press attack
  "input.press: queued Attack through the R binding"
  byro> combat.status
  "cooldown=0.450 blocking=false attacks=1 hits=0 kills=0  last_target=none"
  ```
  Entity 7 is `lvlgoodspringspowderganger`, a fully spawned FNV NPC with a resolved skeleton

  directly from the master).
- **Impact**: the reference title's gameplay path can regress arbitrarily far without any gate
  noticing, and it has already done so — the P2 combat core was declared passing on
  2026-08-16 while being inert on FNV.
- **Related**: ESM-2026-08-16-D7-01 (root cause of the inertness — not re-filed);
  CHAR-2026-08-16-D2-02. `docs/engine/p2-combat-fixture.md`.
- **Suggested Fix**: Fix ESM-2026-08-16-D7-01 first (strip the `AV` prefix or match both
  forms), then add an FNV arm to `p2-melee-core.sh` in the same shape as `m41-equip.sh`'s
  two-game structure — a Goodsprings powder ganger is a ready-made frozen fixture.

### FNV-2026-08-16-D4-01: the `recipes` counter tracks an empty group; FNV's real recipes are EDID-only stubs
- **Severity**: LOW
- **Dimension**: 4 — ESM Record Parser
- **Location**: `crates/plugin/src/esm/records/index.rs:240-241` and `:318-320`,
  `crates/plugin/src/esm/records/dispatch_misc_stub.rs:184`
- **Status**: NEW
- **Description**: `index.rs:240` documents `recipes: HashMap<u32, CobjRecord>` as
  "`COBJ` constructible-object records — **FNV crafting recipes**", and `:319` documents
  `RCPE` as "recipe — **superseded by COBJ**; FNV ships both". Both claims are inverted.
  `FalloutNV.esm` contains exactly one `COBJ` occurrence, at offset 13 130 513, and it is a
  `GRUP` header of size `0x18` = 24 bytes — an **empty** group with zero records. That is why
  the living baseline line reports `recipes=0`. FNV's actual crafting data is `RCPE`, which is
  routed only into the `MinimalEsmRecord` (EDID + FULL) stub bucket, discarding the
  `RCOD` / `RCIL` / `RCQY` output/input/quantity sub-records and the `RCCT` category link.
- **Evidence**: byte scan of `FalloutNV.esm` (245 650 747 B): `COBJ` ×1 (empty GRUP header),
  `RCPE` ×106, `RCCT` ×11, `RCOD` ×144, `RCIL` ×374, `RCQY` ×407. Test output at HEAD:
  `recipes=0`.
- **Impact**: no runtime cost today — no crafting subsystem consumes either field — but the
  `recipes=0` line in the ROADMAP-tracked baseline reads as "FNV authors no recipes", and the
  inverted doc claim has already propagated verbatim into
  `docs/audits/AUDIT_FNV_2026-05-03_DIM2.md:202`. A future crafting milestone that trusts
  `EsmIndex::recipes` on FNV will find it permanently empty.
- **Related**: `docs/audits/AUDIT_FO3_2026-05-25_DIM3.md:260/267` (already records
  `recipe_records (RCPE) | 105 | 0 | FNV-only` and "COBJ — both empty in vanilla", so the
  correct facts were known and the doc comment was never updated).
- **Suggested Fix**: Correct both doc comments, and either rename the baseline field to
  `constructible_objects` or promote `RCPE` to a real record with its `RCOD`/`RCIL`/`RCQY`
  arrays when a crafting consumer lands.
