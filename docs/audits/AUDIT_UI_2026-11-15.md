### MEDIUM

#### UI-D4-2026-11-15-01: a `CFX` / `GFX`-signature movie bypasses the #5719/#5966/#6225 declared-length ceiling everywhere (root, import, runtime fetch)
- **Severity**: MEDIUM (defence-in-depth on untrusted archive content; same class and rating as #5966 and #6225)
- **Dimension**: Resource Navigator
- **Profile**: both (Skyrim AVM1 and FO4 AVM2 share the navigator)
- **Existing**: none. A residual of closed #5966 / #6225 (their guard `every_decode_site_is_behind_the_declared_length_ceiling` only counts `decompress_swf(` call sites, so it is blind to a signature the check ignores).
- **Location**:
  - `crates/ui/src/prepare.rs:211` (`ensure_declared_len_within` returns `Ok` unless the first three bytes are `FWS|CWS|ZWS`)
  - `crates/ui/src/prepare.rs:105-109` (shim: `_ => return None` for anything else)
  - `crates/ui/src/prepare.rs:375` (`stock_inflates` counts only `CWS|ZWS`)
  - `crates/ui/src/navigator.rs:658` (`is_swf`: same three signatures)
  - The decision points that consume it: `navigator.rs:283-287` (ceiling), `:300` (`normalize_scaleform_dialect`), `:306-326` (`prepare_import_asset_swf` / `import_asset_paths`).
- **Evidence**:
  - The workspace's pinned Ruffle (`rev=2edfd97`, `~/.cargo/git/checkouts/ruffle-b1b568dcb5621339/2edfd97/swf/src/read.rs:2584-2594`): `read_compression_type` maps `b"FWS" | b"GFX"` to `Compression::None` and `b"CWS" | b"CFX"` to `Compression::Zlib`. `decompress_swf` then reads `take(uncompressed_len - 8)` from the zlib stream, so the header's `u32` bounds the inflate (the #5719 shape).
  - The shipped corpus carries `CFX`: scanning the installed archives, `Skyrim - Interface.bsa` has 6 `.gfx` entries, all `CFX` (the other 53 movies are 51 `CWS`, 2 `FWS`), and `Fallout4 - Interface.ba2` has 4 `.gfx`, all `CFX`. No vanilla movie names a `.gfx` or `exported\` path, so vanilla content never fetches them. A mod or replacement movie can.
  - Probe in the worktree (`navigator.rs` test, removed with the worktree), 1.2 MB of zlib over 256 MiB of zeros, signature changed to `CFX`, header claim `u32::MAX`:
    - `ensure_declared_len_within_ceiling(&cfx)` -> `Ok(())` (the same body with `CWS` is refused).
    - `ScaleformNavigator::fetch("bomb.gfx")` served the archive bytes unchanged (`body == cfx` true), recorded `errors=[]`, and recorded a normal `loads` entry.
    - `swf::decompress_swf` on the served body returned `Ok` with 268,435,451 bytes in 146 ms (ceiling is `MAX_SWF_BODY_BYTES` = 128 MiB, `prepare.rs:143`); `prepare_movie(&cfx, None, None)` is `Ok` in 167 ms, i.e. the root route is open too.
  - `navigator::is_swf(CFX)` is `false`, so a `CFX` dependency also skips `prepare_import_asset_swf` and the nested `ImportAssets` scan (it still reaches Ruffle, which parses it as a movie).
- **Impact**: a hostile or corrupt `CFX` movie in an interface archive inflates to the header's `u32` (up to 4 GiB) inside Ruffle's own `SwfMovieData::from_data`, with no error and no ceiling; this is the same memory-DoS the ceiling was added for on `CWS`. It needs attacker-controlled archive content, hence MEDIUM, not HIGH. Because `CFX` is Scaleform's native compressed form, a mod movie using it is not exotic.
- **Suggested Fix**: one shared predicate, one place. Make `prepare::is_swf_signature` (or the existing `ensure_declared_len_within` match) accept `FWS|CWS|ZWS|GFX|CFX`, have `navigator::is_swf` call it (it is a duplicate of the `matches!` at `prepare.rs:211` and `:375`), and treat `CFX` like `CWS` in the shim / `stock_inflates` accounting (or refuse `CFX`/`GFX` outright as a navigator-served movie, since vanilla never fetches them). Extend the source guard to pin the signature list, and add a unit test beside `dependency_decodes_refuse_an_over_ceiling_claim` with the `hostile_cws_header_bomb()` signature flipped to `CFX` for the root, import and runtime-fetch routes.

### MEDIUM, existing (root cause added, not re-filed)

#### UI-D7-2026-11-15-03: Font glyph metrics are read with u/v and width/height swapped (root cause of #6994; Oblivion text is affected too; the new FNV test passes on scrambled text)
- **Severity**: MEDIUM
- **Dimension**: MenuXml & HUD Drivers
- **Profile**: MenuXml (Oblivion, FO3, FNV)
- **Location**: `crates/menuxml/src/font.rs:99-126` (`Font::parse`; doc table `font.rs:8-34`), consumed at `raster.rs:389` (`texel_rect`) and `raster.rs:300-340` (`text_line`)
- **Status**: Existing: #6994 (do not re-file). This note adds the root cause and the scope.
- **Description**: `Font::parse` takes record float `[1]` as `v0` (atlas row), `[2]` as `u0` (column), `[3]` as `v1`, `[6]` as `u1`, `[10]` as glyph width and `[9]` as glyph height. The data says the opposite: `[1]` / `[3]` are the **x** edges, `[2]` / `[6]` the **y** edges, `[9]` is the glyph **width** and `[10]` the glyph **height**.
- **Evidence** (scratch probe over the real archives, atlas ink inspected):
  - FNV `Glow_Monofonto_Large` ('H', point size 31, 512 x 512 DDS atlas): the record reads `u0=0, v0=0.291, u1=0.0586, v1=0.3242, width=30, height=17`. The atlas rect that implies (x 0..30, y 149..166) holds fragments of two different glyphs side by side; with the fields swapped the rect is 17 wide x 30 tall, which is the glyph and matches the point size (31).
  - A cleanliness test over printable ASCII (a glyph rect is "clean" when none of its border pixels carries ink; glyph cells are padded, so a correct rect is clean): current reading / swapped reading: FNV Glow_Monofonto_Large 0 / 60 of 94 (34 still cut when swapped, glow halos overlapping neighbouring cells is the likely cause, not investigated), FNV Monofonto_Large 0 / 44, FNV Baked-in_Monofonto_Large 0 / **94**; **Oblivion** `kingthings_shadowed` 1 / **93**, Oblivion `handwritten` 0 / 74. The same swap fixes both families, so this is not an FNV-specific layout.
  - Rendering `[HIDDEN]` through `Framebuffer::text_line` with the font as parsed gives unreadable fragments; with the six fields swapped the visible part of the strip (I cut the output at 210 columns) reads `[HIDDE`.
  - The issue's other observations are consistent: atlas order (`.dds` vs `.tex`) gives the same output (both atlases show the same glyph layout), and "cut at top and bottom" is consistent with the y rect being the 17-px x extent, and Oblivion images render correctly because they do not touch `Font`.
  - `font.rs`'s doc table claims "`[1]  v0 ... verified against atlas ink`", and `crates/menuxml/src/tests.rs:1244` (`text_line_advances_and_tints`) builds a synthetic `Font` rather than parsing a `.fnt`, so no test has ever rendered a parsed font. `git log` shows `font.rs` untouched since d574d9bd1 (09-19).
- **Impact**: every MenuXml text tile (Oblivion HUD text, the FO3/FNV label the new sneak element draws, any future menu text) renders garbled. This also means the new `the_fnv_hud_draws_the_sneak_label` passes while the label is unreadable: its assertion is `changed > 100` pixels (`hud.rs:1007`), and the run printed 4197.
- **Related**: #6994 (acceptance asks for a per-glyph-coverage real-data test; the border-cleanliness measure above is a cheap one that needs no reference images), 014e64ef1, `docs/engine/ui.md` MenuXml font section.
- **Suggested Fix**: swap the reads in `Font::parse` (`u0 = f(1)`, `v0 = f(2)`, `u1 = f(3)`, `v1 = f(6)`, `width = f(9)`, `height = f(10)`; advance / y-offset stay at `[13]` / `[12]`), correct the doc table, and add a real-data test that renders a known string per game and asserts glyph rect cleanliness (or a coverage comparison), plus a synthetic test that parses a hand-built `.fnt` record.

#### UI-D6-2026-11-15-01: Keyboard, mouse and save hotkeys still reach the world and the native menus while a Bink movie covers the game
- **Severity**: LOW
- **Dimension**: Engine Wiring & Input
- **Profile**: n/a (engine input gate; affects every game's start movie)
- **Location**: `byroredux/src/app_events.rs:1152-1157` (window_event discard), `:1458` (device_event), `byroredux/src/main.rs:1255` (`capture_world_input`); the helper that should be used is `cover_holds_game` at `main.rs:1235-1237`
- **Status**: NEW (no matching issue; searched "movie input", "Bink input cover")
- **Description**: 6e64c453b added a second full-screen cover, the Bink movie, and a helper `App::cover_holds_game()` (`loading_screen.active() || video.active()`) whose doc says "simulation time is held still and world input is released". It was applied only in `about_to_wait` (`app_events.rs:1522` release and `:1543` dt). The three *event-time* quarantines the loading cover has were left on `loading_screen.active()` alone: the `window_event` discard of keyboard / mouse / wheel / touch / IME events (`app_events.rs:1152-1157`), the `device_event` mouse-look release (`:1458`) and `capture_world_input` (`main.rs:1255`). The only movie-specific input handling is Escape (`app_events.rs:1206-1210`, `video::VideoPlayer::request_skip`). So while a movie plays, every other press runs the full dispatch below the `video.active()` Escape check.
- **Evidence**: with `video.active()` true and no loading cover, a window event reaches: the inventory binding -> `open_inventory_menu()` (`app_events.rs:1372`) which sets `game_menu.visible` and `release_world_input_for_ui()`; `F` -> `toggle_player_mode` (`:1392`); `V` -> `toggle_third_person` (`:1400`); the quicksave / quickload binding -> `queue_player_save_action` (`:1290-1305`), so a quickload keypress during the intro queues a load of another timeline; a left click -> `capture_world_input()` which grabs and hides the cursor (`main.rs:1254-1268`), which `about_to_wait` then releases next tick (cursor flicker). The comment at `app_events.rs:1348-1354` lists "the loading cover, the bench harness, egui, the native menus and a focused Scaleform menu" as the things that return above the world-input arm; the movie is not in that list, so a key press during a movie also reaches `ExplicitStartPin::release` (`:1359`; only relevant for a named-location launch, which does not play start movies, so a note not a separate defect). Once the inventory page is open over a movie, Escape is owned by the movie (`:1204`) and cannot close it until the movie ends. The held-key leak the helper was written for is bounded (`about_to_wait` clears `InputState` every tick); the discrete one-shot actions above are not.
