### LOW

#### NIF-D3-2026-09-29-01: #3461's FO76 `GeneratedMeshes` fix has no corpus pin — `parse_rate_fo76_all_meshes` still carries the pre-fix floors (0.945 / 0.0)
- **Severity**: LOW. This is a test-coverage gap; the code is correct today. The dispatch arm itself is unit-pinned.
- **Dimension**: Block Dispatch Coverage (baseline harness)
- **Game Affected**: Fallout 76 (bsver 155..=167)
- **Location**: `crates/nif/tests/parse_real_nifs.rs:544-551` (module note), `:579-594` (the two `ArchiveSpec`s)
- **Status**: NEW. It was first reported as NIF-2026-09-04-D3-01, but that finding was never published (no issue matches "floor" / "GeneratedMeshes" / "3461"), and it was not carried by the 09-11 or 09-21 reports.
- **Description**: #3461 (closed 2026-09-02) gave `BSDistantObjectExtraData` a dispatch arm and cleared the FO76 distant-LOD truncation tail. The gate was never updated to match:
  - `GeneratedMeshes01` is still floored at `min_clean: 0.945`;
  - `GeneratedMeshes02` is still floored at `min_clean: 0.0`, next to a comment reading "Raise it the moment the tail is fixed, or the fix has nothing pinning it";
  - the module note still says "0.00% clean — all 2,049 of its NIFs truncate".
- **Evidence**:
  - Today's run reports `GeneratedMeshes01` 20,270/20,270 clean and `GeneratedMeshes02` 2,055/2,055 clean (`corpus_parse.log`).
  - The per-type gates cannot see these archives: `Game::mesh_archives` for FO76 is `&["SeventySix - Meshes.ba2"]` (`tests/common/mod.rs:202`), and no baseline TSV contains `BSDistantObjectExtraData`.
  - The only pin is `dispatch_tests/extra_data.rs:710-746`, which catches deletion of the dispatch arm but not a layout regression.
- **Impact**: a regression that makes these 22,325 NIFs truncate again would pass every gate. Examples are a mis-read field in `BsDistantObjectExtraData` or in any other `GeneratedMeshes`-only block. Truncation counts as "recoverable", and the clean floor is 0.
- **Related**: #3461, #3466 (closed); #4628 (the same gate's archive list is stale); #4619 (the lane that would run this).
- **Suggested Fix**: raise both floors to 0.995, the measured value minus the usual 0.5%, and rewrite the module note and inline comments to the measured state.

#### NIF-D4-2026-09-29-01: two docs still describe Starfield BSGeometry streams as "decoded Y-up" after b9e961eeb moved the basis change to import
- **Severity**: LOW (doc-rot; behaviour is correct)
- **Dimension**: Geometry Handoff
- **Game Affected**: Starfield (bsver ≥ 172)
- **Location**: `crates/nif/src/import/mesh/tangent.rs:377-380` (`synthesize_tangents_yup` doc); `docs/engine/per-game-translation-survey.md:163`
- **Status**: NEW. The related #4554 was a different stale doc on `ImportedMesh.tangents`, and it is closed.
- **Description**: b9e961eeb, committed as "Enhance physical lighting documentation…", changed `import/mesh/bs_geometry.rs` so that positions, UDEC3 normals, UDEC3 tangents and the bounding-sphere centre all go through `zup_to_yup_pos` at import. The same commit corrected the parser-side field doc: `BSGeometryMeshData.vertices` is now "source mesh-local Z-up units". Two docs were not updated:
  - The `synthesize_tangents_yup` doc still says its Starfield inputs are "positions and normals decoded Y-up by the BSGeometryMeshData parser".
  - The survey still lists "UDEC3 Y-up (Starfield BSGeometry)" as one of the tangent paths.
- **Evidence**: `git diff f97775ca8..HEAD -- crates/nif/src/import/mesh/bs_geometry.rs` removes "Positions are already Y-up (decoded by the BSGeometryMeshData parser)" and "BSGeometry is Starfield-native Y-up". `blocks/bs_geometry.rs` performs no axis swap.
- **Impact**: none at runtime, because the synth's inputs are Y-up by the time it runs. The risk is to a future editor: the next person to touch the BSGeometry decode, trusting "parser decodes Y-up", would re-introduce a double or missing basis change.
- **Related**: #4554 (closed), #1232, #4394.
- **Suggested Fix**: reword both docs to "converted to Y-up at import (`import/mesh/bs_geometry.rs`)".
