### ECS-2026-10-21-01: idle-playback exclusives take `AnimationClipRegistry` under the `AnimationPlayer` write guard
- **Severity**: HIGH (skill rule: a wrong lock order is HIGH; precedent #6062 / #6101 were filed HIGH for a red lane)
- **Dimension**: 1 Lock Ordering & Deadlock Machinery
- **Location**: `byroredux/src/systems/cinematic.rs:64-98` (`idle_clip_playback_system`: the `one_shot` closure is called inside the `query_mut::<AnimationPlayer>()` block at :70), `:181-212` (`idle_resume_system`: the `finished` closure is called inside the block at :189)
- **Status**: NEW. The code was written in `d1b298921` (2026-10-18). The edge first reached the detector through `355f752d8` (Fix #6179, 2026-10-20), whose new test `scripted_one_shot_idle_marks_the_actor_until_it_finishes` is the first to drive both systems with a populated registry. That commit is the first red CI run (`51f97f708`'s run 39425702282 contains only this cycle).
- **Description**: `animation_system_inner` holds `AnimationClipRegistry` as its outermost lock for the whole function. Its doc (`systems/animation.rs:501-512`, #2400) states that nothing may acquire the registry while holding `AnimationPlayer`/`AnimationStack`. Both idle systems do exactly that. Each one's closure calls `world.try_resource::<AnimationClipRegistry>()` per request while `players` (a `QueryWrite<AnimationPlayer>`) is alive. Detector message: `attempted acquisition of AnimationClipRegistry while holding AnimationPlayer … closes a cycle AnimationClipRegistry → AnimationPlayer → AnimationClipRegistry`.
- **Evidence**:
  ```rust
  let one_shot = |handle: u32| { world.try_resource::<AnimationClipRegistry>() … };   // :64
  if let Some(mut players) = world.query_mut::<AnimationPlayer>() {                    // :70
      … if player.clip_handle != *handle && one_shot(*handle) { … }                   // registry under players
  ```
  `idle_resume_system` has the same shape with `finished(player.clip_handle, player.local_time)` inside the `players` loop.
- **Impact**: Today both systems are Update *exclusives*, and `animation_system` is Update's only parallel system, so the two never run on different threads in the same frame. There is no live deadlock. The damage is to the gate. The ABBA lane is the only mechanical check of the process-wide lock order, and it has been red for 22 consecutive `main` runs. Two more cycles have already landed while it was red (ECS-2026-10-21-02). A third cycle that *is* reachable across threads would not be noticed. The cycle becomes live if either system is ever promoted to parallel.
- **Related**: #2400 (the invariant), ECS-2026-10-21-02 (the other cycle keeping the lane red), `/audit-concurrency` Dim 3/5.
- **Suggested Fix**: Resolve the clip facts before taking the player guard: collect `(handle → is_clamp, duration)` for the request handles under one registry read, drop it, then take `query_mut::<AnimationPlayer>()`. `pick_idle_system` (:150-161) already does this.

### ECS-2026-10-21-02: `collect_victim_gpu_handles` takes `ParticleEmitter` under seven storage guards
- **Severity**: HIGH
- **Dimension**: 1 Lock Ordering & Deadlock Machinery
- **Location**: `byroredux/src/cell_loader/unload.rs:809-816` (eight read guards held together for the victim walk; `peq` is the eighth). The reverse order is at `byroredux/src/render/particles.rs:84-87` (`ParticleEmitter` then `TextureHandle`).
- **Status**: NEW, introduced by `5f7e01fbe` (Fix #6109, 2026-10-21 09:17). The CI run at `21b9743e0` (the first after it) shows 27 cycle panics through `ParticleEmitter`: `TextureHandle`, `GlobalTransform` and `WaterVolume`, the last two transitive through the new edges. At HEAD the local run shows 7 failures on the `TextureHandle → ParticleEmitter` cycle: `render::particles::quantize_fade_tests::*` (6) and `render::water_wave_params_tests::water_reemit_ignores_particle_draws_that_share_the_plane_id`.
- **Description**: The walk holds `MeshHandle`, `TextureHandle`, `NormalMapHandle`, `WaterNoiseMapHandles`, `MaterialTextureHandles`, `TerrainTileSlot` and `AnimatedTextureFlip` read guards, and #6109 added `ParticleEmitter` as an eighth. That records seven `X → ParticleEmitter` edges. The particle render pass takes `ParticleEmitter → TextureHandle`, and `systems/particle.rs:408`'s TypeId-sorted `query_2_mut::<GlobalTransform, ParticleEmitter>` adds a `ParticleEmitter`/`GlobalTransform` edge, so cycles close directly and transitively. The block comment above the guards ("pure reads have no such risk") is the premise the detector rejects: it records read→read edges too, and std's RwLock queues readers behind a waiting writer.
- **Evidence**: see the location above, and the panic text in `/tmp/audit/ecs/bin_lockcheck.log` (`attempted acquisition of TextureHandle while holding ParticleEmitter … TextureHandle → ParticleEmitter → TextureHandle`).
- **Impact**: The caller holds `&mut World` (`unload.rs:481`), so there is no live deadlock. The lane stays red for a second reason, which hides real regressions (see -01), and the comment misleads the next contributor who adds a ninth guard.
- **Related**: #6109, #883 (the single-walk consolidation the comment belongs to), ECS-2026-10-21-01.
- **Suggested Fix**: Collect the emitters' `greyscale_lut_index` in a separate pass under the `ParticleEmitter` guard alone, before or after the seven-guard walk. Then correct the comment: read guards are lock-order edges.

### ECS-2026-10-21-03: the #6101 contention test turns the Miri gate red
- **Severity**: MEDIUM (a broken defence-in-depth gate over the only `unsafe` in `ecs/`)
- **Dimension**: 3 Query Borrow Safety & the ECS `unsafe`
- **Location**: `crates/core/src/ecs/world_tests.rs:927-967` (`try_resource_2_does_not_deadlock_against_resource_2_mut`); `.github/workflows/ci.yml:326-327` (the Miri step runs every `ecs::world::tests` test except `resource_visible_to_system_via_scheduler`)
- **Status**: NEW, introduced by `824c620a5` (Fix #6101). CI Miri job: green on `7822695e4`, red on `21b9743e0`, `1be33af66` and HEAD.
- **Description**: The test spins two reader threads and one writer for 2000 iterations each, then waits on `recv_timeout(Duration::from_secs(20))`. Miri runs about three orders of magnitude slower, so the 6000 lock round-trips do not finish in 20 s of wall time and the test panics with `a sorted pair acquisition must not deadlock: Timeout` (CI run 39633944988). The panicking main thread then leaves the workers running, and Miri reports a second error: `the main thread terminated without waiting for all remaining threads`.
- **Impact**: The `ecs-query-miri` job exists to catch aliasing UB in the four cached-pointer derefs in `query.rs` (#1367). While it is red, a genuine Stacked/Tree-Borrows violation in a new `ecs::world::tests` case would land unnoticed. The test itself is sound on native.
- **Related**: #6101, #1367.
- **Suggested Fix**: Mark the test `#[cfg_attr(miri, ignore)]`. It tests lock order, not pointer provenance, so this does not widen the cached-pointer coverage. Alternatively, scale the iteration count with `if cfg!(miri) { 10 } else { 2000 }`. Either way, record the exception next to the CI skip-list comment.

### ECS-2026-10-21-04: the stack root-motion mix ignores the per-bone layer mask
- **Severity**: MEDIUM
- **Dimension**: 9 Animation Runtime
- **Location**: `byroredux/src/systems/animation.rs:912-931` (accumulation-root pick, `let ew = layer.effective_weight()` at :915), `:934-953` (weighted delta mix, `let weight = layer.effective_weight()` at :938). Compare `crates/core/src/animation/stack.rs:396-409` (`bone_layer_weight`).
- **Status**: NEW. Masks arrived in `49529db7c` (behavior graph: layered blends). The mixed root-motion path predates them and was not updated.
- **Description**: Since `49529db7c`, every weight site in `sample_blended_transform` goes through `bone_layer_weight`, which multiplies `effective_weight()` by `clip.weight` (#469) and by the layer's mask for that bone. The root-motion path still uses plain `effective_weight()`, in two places: when it picks the accumulation root, and when it averages each layer's `sampled_root_motion_delta`. A layer whose mask gives the root bone 0 (the upper-body half of a vanilla layered blend) still contributes its root delta at full layer weight. A low-`clip.weight` layer contributes as if it had weight 1.
- **Evidence**: Masks are live in production. `crates/scripting/src/animation_graph.rs:1317` sets `stack.bone_index`, and `:1361` / `:1419` set `layer.bone_weights` from the hkbBlenderGenerator children's `boneWeights` (`crates/hkx/src/behavior.rs:1310-1318`). `e8026e737` makes graph-driven actors consume the reference-frame root motion that this mix produces.
- **Impact**: For a graph-driven actor (Skyrim/FO4 behavior graph) in a layered blend whose upper-body clip carries an accumulation-root channel, the root delta is averaged with the masked-out layer's (usually stationary) root motion. The actor then translates slower than its locomotion clip, so feet slide. The bone pose is correct, which is why the tests pass: `bone_weights_mask_a_layer_per_bone` checks only `sample_blended_transform`, and `animation_stack_root_motion_is_the_weighted_mix_of_its_layers` uses unmasked layers.
- **Related**: #3703 / #469; the skill's "Root motion" and "Layer masks" bullets; NIFAL-D7-2026-10-21-01 (a different defect in the same FO4 graph root-motion chain: the clip conversion drops the reference-frame yaw).
- **Suggested Fix**: Expose `bone_layer_weight` from `stack.rs` (or a `layer_weight_for(stack, layer, clip, name)` wrapper) and use it at :915 and :938 with the accumulation-root name. Then add a masked case to the root-motion mix test.

### ECS-2026-10-21-05: `TrapMotionSamples` keeps unpruned, per-entity-untimed positions, so re-contact velocities are spurious
- **Severity**: MEDIUM
- **Dimension**: 4 Resources & World-Level State (per-entity fact in a global `EntityId` map)
- **Location**: `byroredux/src/systems/script_queries.rs:95-136` (`TrapMotionSamples`, `trap_contacts`); consumer `crates/scripting/src/obscript_more/extras.rs:300-333` (`trap_update`, ObScript `TrapUpdate` 0x110c)
- **Status**: NEW (added with the M47.3 `TrapUpdate` work, `8d32b3fe9`). It differs from PERF-D1-01, which is `trap_hits.rs`'s ancestor-chain rebuild.
- **Description**: `TrapMotionSamples` keeps `positions` and `velocities` as `HashMap<EntityId, Vec3>` plus a single shared `time`. Each call updates only the entities overlapping that trap *this* call, then sets `time = now`. An actor that left contact keeps its old position. When it touches any `TrapUpdate` trap again, its velocity is `(position_now − position_when_it_last_touched) / dt`. Here `dt` is the time since the *last call by any trap*, which is one frame while a trap's GameMode runs. The result is a velocity of thousands of units per second. Nothing removes entries, so the map also grows with every actor that ever touches a trap.
- **Evidence**: `samples.positions.get(&entity).map_or(Vec3::ZERO, |previous| (position - *previous) / dt)`, with `samples.time = now` written once per call (:120-129). `trap_update` gates both damage and the `PushActorAway` request on `contact.relative_speed < min_speed` (`extras.rs:308`).
- **Impact**: On Oblivion/FO3/FNV, a trap whose script uses `fTrapMinVelocity` so that it harms only while moving hits and knocks down an actor that walks into it at rest, on the first frame of any re-contact. The non-continuous case ("damage on first contact only") is exactly that frame. Memory growth is small, but it never shrinks and the soak gate does not see it.
- **Related**: GAME-D4-2026-10-21-01 (the knockdown that such a spurious push triggers can freeze the actor); the skill's Dim 4 "global map keyed by `EntityId`" rule. Gameplay semantics are `/audit-gameplay`; this report owns the shape.
- **Suggested Fix**: Store `(position, sampled_at)` per entity and treat a sample older than one frame as absent (velocity zero). Or move the sample onto a sparse component that despawn reclaims. At a minimum, `retain` the map to the entities involved in this frame's calls.

### ECS-2026-10-21-06: `ArchetypeIdleSeen.unmatched` grows for the whole session
- **Severity**: LOW
- **Dimension**: 4 Resources & World-Level State
- **Location**: `byroredux/src/systems/archetype_idle.rs:35-48` (the set and `note_unmatched`), `:56-63` (the only `clear`, taken when `AnimArchetypeOverrides` changes)
- **Status**: NEW
- **Description**: Every FO4 actor that has no archetype entry or no clip is inserted into a `HashSet<EntityId>` so it is not re-examined each frame. Entity ids are never recycled and the set is cleared only when a script changes the archetype overrides. It therefore keeps every unmatched actor ever streamed in, despawned ones included.
- **Impact**: About 8 bytes per unmatched actor spawn, unbounded over a long streaming session. The per-frame cost is still an O(1) probe. The finding is the pattern: a per-entity fact kept in a global map that despawn cannot reclaim.
- **Suggested Fix**: `retain` the set against the live `AnimationTarget` storage when its `structural_generation` changes, or replace it with a sparse `ArchetypeIdleUnmatched` marker component.

### ECS-2026-10-21-07: `obscript_hit_system` is not in the `HitEvent` ordering pin
- **Severity**: LOW (test gap; the live order is correct)
- **Dimension**: 5 System & Scheduler Wiring
- **Location**: `byroredux/src/boot/schedule/mod.rs:116-148` (`hit_event_consumers_run_after_every_producer`, 3 consumers listed); `byroredux/src/boot/schedule/update.rs:617` (registration)
- **Status**: NEW
- **Description**: M47.3 split `obscript_hit_system` out of `obscript_object_system` precisely so that it runs after the projectile and trap-hit producers (doc at `crates/scripting/src/obscript_objects.rs:433-436`, comment at `update.rs:613-616`). Today it does: :617 is after `pending_trap_hit_flush_system` (:604) and `projectile_flight_system` (:596). But the pin that turned the dart-trap bug (`ee6468fd1`) into a guard lists only `combat_damage_system`, `hit_event_system` and `reference_script_hit_system`. Moving the ObScript consumer back beside `obscript_object_system` (:525) would pass every test, and `OnHit`/`OnHitWith` for projectile and trap hits would silently stop firing.
- **Suggested Fix**: Add `"byroredux_scripting::obscript_objects::obscript_hit_system)"` to the pin's consumer list.
