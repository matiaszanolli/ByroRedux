### Dim 2 — ESM slice

#### FO3-2026-10-31-01: 486 FO3 INFOs are declined only by getters the ObScript VM already answers but the CTDA catalog lacks (435 on `GetIsCurrentPackage`, 161)
- **Severity**: MEDIUM
- **Dimension**: 2 (ESM slice) — mechanism `/audit-scripting`, consumer `/audit-gameplay`
- **Location**: `crates/scripting/src/condition/catalog.rs` (`ROWS`, no row for 161 / 300 / 214 / 159 / 45 / 409 / 101 / 244 / 286); VM bodies: `crates/scripting/src/obscript_effects/getters.rs:22` (`CMD_GET_IS_CURRENT_PACKAGE = 0x10a1`, `:524` `Games::Any`); gate: `is_modeled` in `crates/scripting/src/condition/eval.rs:95`
- **Status**: NEW (the same defect class as the fixed #6460; that commit bridged ten getters and left these)
- **Description**: #6460 made the fail-closed dialogue gates answer ten VM getters through `vm_getter_command()`. The VM table holds more getters than the ten that were bridged. Any INFO whose CTDA names one of the rest reads `Unknown` -> `is_modeled == false` -> the INFO is declined.
- **Evidence**: independent walker over `Fallout3.esm` INFO `CTDA` (function u32 at offset 8), catalogue indices read from `catalog.rs` `indices: &[..]` (82 indices), VM ids from the `Command { id: CMD_*, games }` tables (126 getter ids): 1 605 INFOs carry at least one uncatalogued function (the test's 1 777 additionally counts `is_modeled`-gated rows). **486 of them are declined only by functions the VM answers**: 161 `GetIsCurrentPackage` 435, 300 `IsInInterior` 17, 214 `HasMagicEffect` 10, 159 `GetSitting` 10, 45 `GetDetected` 9, 409 `IsKiller` 5, 101 `IsWeaponOut` 5, 244 `GetRestrained` 5, 286 `IsSneaking` 3. The other 1 119 are declined by functions the VM does not answer as getters, led by `GetScriptVariable` 53 (570 INFOs) — the known remainder named in `condition_catalog_real_data.rs:64-66`, which needs a per-reference script-variable read and is not this finding.
- **Impact**: ~2.2 % of FO3 dialogue (lines gated on "NPC is currently running package X") is unselectable. `GetIsCurrentPackage` is exactly the gate FO3 uses for package-context lines (sandbox / eat / sleep barks), so the lost lines are the ambient ones. FNV shares the catalog; its residual (650) will contain the same functions.
- **Related**: #6460 (`102e4f5cd`), FNV-2026-10-27-01.
- **Suggested Fix**: add `ConditionFunction` variants + `ROWS` rows for the nine, bridged with `vm_getter_command()` exactly like the ten of #6460 (FO3/FNV only, `Games::Any` getters whose param-1 FormID encoding is established — 161 takes a `PACK`), extend the plugin crate's param-1 FormID table for 161, and move the pinned counts (FO3 1 777 -> ~1 291; FNV 650).

### Dim 5 — Animation, NPC spawn, gameplay data, scripting

#### FO3-2026-10-31-02: Placed FO3 (and FNV) mines are `WEAP` references, but `MineBook` is keyed on `PROJ` bases, so every vanilla FO3 minefield is inert
- **Severity**: LOW (FO3-distinctive gap; the system's documented scope is FO4/Skyrim)
- **Dimension**: 5 — mechanism `/audit-gameplay`
- **Location**: `byroredux/src/systems/mines.rs:66-90` (`install_mine_book` keys `proj.form_id`), `:255-262` and `:308` (`book.get(&candidate.base_form_id)`); module doc `:24` ("only mines placed in the world data")
- **Status**: NEW (adjacent to GAME-D4-2026-10-31-01/-02, which cover the enable ledger and the HitEvent insert, not the base-type mismatch)
- **Description**: The M43 mine system reads a placed reference whose *base* is a `PROJ` with *Alt. Trigger* + proximity + explosion. That is how Fallout4.esm places its 390 mines. FO3/FNV place a mine as a **`WEAP` base** (`WeapMineFrag`) whose `DNAM` @36 names the mine `PROJ`; no `REFR` in `Fallout3.esm` points at a `PROJ`.
- **Evidence**: `Fallout3.esm`: 52 PROJ, 5 pass `is_proximity_mine` (`MineFragProjectile` 0x43fa, `MineBottleCapProjectile` 0x59449, `MinePlasmaProjectile` 0x403d8, `MinePulseProjectile` 0x33c4b, `MQ04OvenProjectile` 0x28357), **0 REFRs reference any of them**. `WeapMineFrag` 0x433c (54 REFRs), `WeapMineBottlecap` 0x433a (41), `WeapMinePulse` 0x433e (10) have `DNAM` @36 = 0x43fa / 0x59449 / 0x33c4b. `MineBook` therefore has 5 entries on FO3 and matches nothing.
- **Impact**: ~105 master-file minefield mines never trip or blast on FO3 (they spawn as pick-up weapons). Does not affect any other FO3 system. FNV shares the data shape.
- **Suggested Fix**: when `book` is built, also key each `WEAP` whose `DNAM` projectile is a mine (`index.weapons` + `proj.is_proximity_mine()`), or resolve base -> `WEAP.projectile` in `mine_system`; update the module doc to say which games' placement shapes it covers.

They no longer start at spawn, which is intended: `Fallout3.esm` carries 313 `PlayGroup` calls (`Forward` 133, `Backward` 79, `Left` 71, `Right` 11) and the ObScript VM runs them. #6133: reviewed above.
