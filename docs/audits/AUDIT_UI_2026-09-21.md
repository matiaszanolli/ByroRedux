## 3. Findings

### HIGH

### UI-D7-2026-09-21-01: MenuXml raster loop bounds come from the authored tile rect and are never clamped to the framebuffer; a huge or `inf` extent stalls or hangs every HUD render
- **Severity**: HIGH
- **Dimension**: MenuXml & HUD Drivers
- **Profile**: MenuXml
- **Location**: `crates/menuxml/src/raster.rs:178-215` (`blit` loop bounds), `crates/menuxml/src/raster.rs:295-309` (`blit_sub`), `crates/menuxml/src/layout.rs:138-144`, `crates/menuxml/src/parse.rs:281`
- **Status**: NEW
- **Description**: `blit` iterates `x0..x1 × y0..y1`, computed from `dst ∩ clip ∩ tile`. Only `blend` (`raster.rs:49-52`)
  bounds-checks, and it does so per pixel. The root clip is `None` (`layout.rs:108`) and only `<clipwindow>` tiles add
  one, so a stretched (`zoom < 0`, `&scale;`) or tiled image loops over its whole authored rect. Layout clamps
  `width`/`height` only with `.max(0.0)`, and `literal_from_text` parses with `str::parse::<f32>`, which accepts `inf`,
  `1e39` and `NaN`. `(inf).ceil() as i64` saturates to `i64::MAX`.
- **Evidence**: probe `/tmp/audit/ui/rasterprobe`, opt-level 3, 1280×720 framebuffer. On-screen work is 921,600 px in
  every case:
  - `blit` 1280² 7.6 ms · 4000² 70 ms · 16000² 1,116 ms · 32000² 4,428 ms (tiled: 7.0 / 64.5 / 976 / 3,971 ms).
  - End to end: `<image><width>16000</width><height>16000</height><zoom>&scale;</zoom>` → `MenuRenderer::render_frame`
    1,166 ms.
  - `"1e39".parse::<f32>()` = inf, and `.ceil() as i64` = 9,223,372,036,854,775,807.
- **Impact**: a main-thread stall at every HUD refresh (up to 30 Hz), or a permanent hang with an infinite extent,
  starting at the first render after `--hud` launch. The trigger is untrusted menu XML from a modified or replaced Misc
  BSA. Loose-file UI mods (common on Oblivion/FNV) are not read yet, but would widen the surface. Vanilla is unaffected:
  the corpus renders at normal cost. HIGH by analogy with the untrusted-input row: that row names an *allocation* sized
  directly from an on-disk field; here it is the loop bound. This is consistent with the HIGH on
  PAR-D1-2026-09-21-04's sibling hang.
- **Related**: PAR-D1-2026-09-21-04 (same surface, load-time explosion); UI-D7-2026-09-21-02; #4570 (preflight dedupe,
  no clamp)
- **Suggested Fix**: clamp `x0..x1` / `y0..y1` to `[0, width) × [0, height)` before iterating in both `blit` and
  `blit_sub` (the framebuffer becomes the outermost clip), and map non-finite layout values to 0. Pin the 16000² case
  with a test that counts `blend` calls.

### UI-D7-2026-09-21-02: layout's depth sort panics on a NaN `depth` that menu XML can author directly or compute
- **Severity**: HIGH
- **Dimension**: MenuXml & HUD Drivers
- **Profile**: MenuXml
- **Location**: `crates/menuxml/src/layout.rs:127-132`, `crates/menuxml/src/parse.rs:281`
- **Status**: NEW
- **Description**: `depth.sort_by(|a, b| a.1.partial_cmp(&b.1).unwrap_or(Ordering::Equal))` is not a total order once any
  depth is NaN. Since Rust 1.81, `slice::sort_by` may panic on such comparators; this workspace builds with rustc 1.96.
  A NaN depth comes straight from `<depth>NaN</depth>` (the parser accepts it) or from arithmetic such as `inf × 0` in an
  op chain.
- **Evidence**:
  - std-only probe `/tmp/audit/ui/sortprobe`: 943 of 2,800 random vectors (≈30 % NaN) panic, from length 21 upward, with
    "user-provided comparison function does not correctly implement a total order".
  - Public API (`rasterprobe nan`): a `<menu>` with 40 sibling images, every third `<depth>NaN</depth>`, makes
    `render_frame` panic with that message.
- **Impact**: engine panic on the first HUD render, on the main thread with no `catch_unwind`. The trigger surface is the
  same as PAR-D1-2026-09-21-05 and PAR-D2-2026-09-21-03, but this panic is on the render path, which those findings do
  not cover.
- **Related**: PAR-D1-2026-09-21-05, PAR-D2-2026-09-21-03, UI-D7-2026-09-21-01
- **Suggested Fix**: sort with `f32::total_cmp`, or normalise a non-finite `depth` to 0 at read. Add the 40-sibling NaN
  menu as a unit test.

### UI-D5-2026-09-21-02: the always-on Scaleform `--hud` re-renders and synchronously reads back the full Ruffle target at the movie's frame rate even when nothing changed
- **Severity**: MEDIUM
- **Dimension**: Render & Overlay Upload
- **Profile**: both
- **Location**: `crates/ui/src/player.rs:371-418` (`tick`: `dirty |= needs_render`), `crates/ui/src/player.rs:461-523` (`render` → `capture_frame` + compare), `byroredux/src/app_frame.rs:905-1070`
- **Status**: NEW
- **Description**: #2719 removed the *upload* for unchanged pixels. The Ruffle render, the blocking GPU→CPU readback, the
  unmultiply and the compare still run on every movie frame. At the pinned rev `0dde981`, Ruffle's `run_frame` sets
  `needs_render = true` unconditionally (`core/src/player.rs:2033`), and `Player::render` rebuilds and submits the full
  command list on every call (`:2037-2089`). `capture_frame` → `buffer_to_image` then does `map_async` +
  `poll(Wait)`, a row copy and `unmultiply_alpha_rgba` over the whole target (`render/wgpu/src/utils.rs:131-177`). The
  driver's 33 ms cadence gates only `push()`, not `ui.render()`.
- **Evidence**: probe `/tmp/audit/ui/hudprobe` (`SwfPlayer::from_resource_provider` + `set_stage_transparent`,
  1920×1080, 60 Hz ticks for 5 s, dependencies at opt-level 3):
  - FO4 `hudmenu.swf` (30 fps): 150 render+readback passes, **0** fresh uploads, 5.08 ms mean per pass (max 11.7 ms),
    2.54 ms per frame amortised.
  - Skyrim SE `hudmenu.swf` (24 fps): 120 passes, 29 uploads (each an #3429 reallocation plus fence), 8.26 ms mean per
    pass (max 16.4 ms).
- **Impact**: a periodic ~5-8 ms main-thread stall ahead of `draw_frame`, 24-30 times a second, for as long as `--hud` is
  on (Skyrim, FO4), scaling with output resolution. Before `62fc0bf22` this was a modal-menu cost; the HUD route makes it
  steady-state gameplay cost. Confirming it in-engine needs a bench with and without `--hud` on the m48-6/m48-7 fixtures
  (`bench_ui_ns`).
- **Related**: #3429 (OPEN, the `update_rgba` upload half); PERF-D1-2026-09-21-03 (the MenuXml sibling)
- **Suggested Fix**: cap the Scaleform HUD's `render()`/readback at the HUD cadence, and skip it when no push, input or
  Ruffle stage invalidation occurred. Longer term, replace the CPU readback with an exported shared image
  (external memory).

### UI-D7-2026-09-21-03: `--hud` splits FO3 from FNV by the `--esm` filename; FNV DLC and mod launches get the FO3 profile and a fully transparent HUD
- **Severity**: MEDIUM
- **Dimension**: MenuXml & HUD Drivers
- **Profile**: MenuXml
- **Location**: `byroredux/src/hud.rs:334-345` (discovery), `byroredux/src/hud.rs:152-163` (texture archive chosen by `label == "Fallout 3"`), `byroredux/src/hud.rs:411` (`Archive::open`, no numeric siblings)
- **Status**: NEW
- **Description**: the FNV profile is chosen only when the `--esm` path contains "falloutnv"; `--master` is never read.
  The documented DLC shape `--master FalloutNV.esm --esm HonestHearts.esm` (path `…/Fallout New Vegas/Data/HonestHearts.esm`)
  and any mod plugin therefore resolve to the FO3 profile. That profile defaults the menu-art archive to
  `Fallout - Textures.bsa` and opens it without numeric siblings. FNV keeps every HUD texture and every font in
  `Fallout - Textures2.bsa`. `ui.md` describes this as "game discovery from the corpus itself", but this split reads a
  filename.
- **Evidence**:
  - `/tmp/audit/ui/avm1probe` `bsalist`: FNV `Fallout - Textures.bsa` holds 0 `interface\hud\` / `textures\fonts\`
    entries (of 11,470 files); `Fallout - Textures2.bsa` holds 81.
  - `/tmp/audit/ui/fnvprobe` replays `launch_hud`'s FO3/FNV assembly (graft `meter.xml` ×2, instantiate
    `template_compass_window`, bars at 0.8, 1280×720): FNV profile + Textures2 = 15,562 opaque px; FO3 profile + Textures
    = **0** opaque px. `launch_hud` still logs `hud: loaded …`.
- **Impact**: a blank HUD on every FNV DLC or mod-plugin launch with `--hud`. The only workaround is an explicit
  `--hud-textures …Textures2.bsa`. No smoke or corpus test covers FNV (UI-D7-2026-09-21-04), so nothing notices.
  In-engine confirmation: an FNV twin of `m48-5-fo3-hud.sh` run with a DLC `--esm`.
- **Related**: UI-D7-2026-09-21-04, UI-D7-2026-09-21-05, PAR-D4-2026-09-21-03 (no FNV MenuXml corpus test)
- **Suggested Fix**: decide FO3 vs FNV structurally, from the `--master`/`--esm` chain or `FalloutNV.esm` in the data
  dir. Carry the texture archive as profile data instead of a label comparison, and open it with
  `open_with_numeric_siblings` as the texture provider does.

### UI-D1-2026-09-21-01: #3434's reserved callback band is keyed on a movie-spoofable prefix and counts every prefixed name, so 32 movie-registered `__byro*` names still lock the adapter's lifecycle callbacks out
- **Severity**: LOW
- **Dimension**: Profile & Bridge
- **Profile**: Fallout4Avm2
- **Location**: `crates/ui/src/host.rs:249-263` (admission test), `crates/ui/src/host.rs:58-62` (doc claim), `crates/ui/src/host/tests.rs` (#3434 tests)
- **Status**: NEW (partial fix of closed #3434, not a regression; the commit message acknowledges spoofing, but the doc and the skill checklist say the lock-out cannot happen)
- **Description**: once the main budget is full, a name is admitted only while
  `set.iter().filter(|n| n.starts_with(ENGINE_NAME_PREFIX)).count() < RESERVED_HOST_METHOD_NAMES`. That count includes
  movie-registered `__byro*` names, including any inserted while the set was still under the main cap. A movie that
  registers 32 such names therefore exhausts the band before the adapter's installer runs.
- **Evidence**: verbatim copy of `insert_bounded` (`/tmp/audit/ui/probe/probe.rs`).
  - Case A: 32 spoofed names first, then 992 plain ones. `__byroBGSAdapterLoaded`, `__byroBGSCodeObjReady` and
    `__byroBGSCodeObjDestroy` are all refused.
  - Case B: 1024 plain names, then 32 spoofed. Same result.
  The refusal is silent, because the one-shot `capped` error already fired for the movie's own names. The #3434 tests
  cover plain-name exhaustion and band boundedness, but not survival under a spoofed band.
- **Impact**: only hostile or malformed content triggers it, and it disables that movie's own readiness probe and
  destroy acknowledgement (`player.rs:649`, `:698-700`). No engine code consumes readiness today.
- **Related**: #3434 (CLOSED)
- **Suggested Fix**: reserve by exact membership in the compile-time list of engine callback names (`READY_CALLBACK`,
  `LOADED_CALLBACK`, `DESTROY_CALLBACK`). That is spoof-proof and bounded at 3. Add a spoofed-band test.
