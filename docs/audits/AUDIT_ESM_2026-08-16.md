### The one thing to take away

`EsmIndex::actor_value_form_id` — the single string→FormID resolver the whole
actor-value population rests on — **matches nothing in Fallout 3, Fallout New
Vegas, or Skyrim**, because those three games prefix every `AVIF` EditorID with
`AV` (`AVStrength`, `AVSmallGuns`, `AVHealth`) while the CHARAL roster it is
queried with uses the bare GECK display names (`Strength`, `Guns`, `Health`).
Fallout 4 is the only game whose `AVIF` EditorIDs are unprefixed, and it is the
only game where any of this works.

Measured off disk this session:

| Master | `AVIF` records | `…("Health")` | `…("AVHealth")` | `NPC_` | derived-**empty** | derived-nonempty |
|---|---:|---|---|---:|---:|---:|
| `Fallout3.esm` | 60 | `None` | `Some(1104)` | 1,647 | **1,647** | 0 |
| `FalloutNV.esm` | 64 | `None` | `Some(1104)` | 3,816 | **3,816** | 0 |
| `Skyrim.esm` (SE) | 149 | `None` | `Some(1000)` | 5,118 | 33 | 5,085 (1 pair each, keyed `24`) |
| `Fallout4.esm` | 359 | `Some(724)` | `None` | 3,015 | 0 | 3,015 (avg 12.3 pairs) |

100 % of FO3 and FNV actors therefore reach `npc_spawn::stamp_actor_values` with
an empty pair list and get **neither `ActorValues` nor `ActorVitals`** — so they
cannot be damaged by the P2 melee slice, every `GetActorValue` condition on them
returns the absent-AV default `0.0`, and the FNV `CharacterRuleset` resolves an
empty attribute/skill roster.

Skyrim looks green only because `health_actor_value_key` side-steps the broken
lookup with a hardcoded engine enum index (`24`), on the stated premise that
*"vanilla `Skyrim.esm` does not author a `Health` AVIF record"*. It authors
`AVHealth` at `0x000003E8`. And `docs/smoke-tests/p2-melee-core.sh` — the gate
that certified P2 combat core on 2026-08-16 — runs on `Skyrim.esm`, i.e. on the
one game whose actor values are supplied by that bypass.

### Why 693 green tests coexist with this

The same reason the prior audit gave for its four wrong decoders (ESM-D2-07),
one level up: `derives_special_and_skills_from_class`
(`actor_value_derive.rs:320-345`) builds its `EsmIndex` fixture with `AVIF`
EditorIDs `"Strength"`, `"Guns"`, `"Science"` — the parser's own assumption about
what vanilla contains. Its own comment even notes *"SmallGuns/BigGuns absent
here"*, which is the tell: the real FNV skill AVIFs are `AVSmallGuns` /
`AVBigGuns`. A fixture that encodes the hypothesis under test cannot falsify it.

### ESM-2026-08-16-D7-01: `AVIF` EditorIDs are `AV`-prefixed on FO3/FNV/Skyrim, so actor-value population resolves nothing and 5,463 vanilla actors get no stats at all
- **Severity**: HIGH
- **Dimension**: `EsmIndex` → ECS Handoff (corroborated by Real-Data Validation)
- **Record / Sub-record**: `AVIF` / `EDID`, `NPC_` / `ACBS`
- **Location**: `crates/plugin/src/esm/records/index.rs:575-591`
  (`actor_value_form_id` + its docstring); `crates/plugin/src/esm/records/actor_value_derive.rs:180-206`
  (`derive_autocalc_actor_values`)
- **Status**: NEW
- **Description**: `actor_value_form_id` resolves an actor value by exact
  (case-insensitive) `AVIF` EditorID. It is queried with the canonical CHARAL
  roster strings — `Attribute::editor_id()` returns `"Strength"`,
  `SkillDef::editor_id` returns `"Guns"`, `"Sneak"`, … — and its own docstring
  asserts *"the EditorIDs are the GECK names (`"Strength"`, `"Sneak"`, `"Guns"`,
  …)"*. That is true of Fallout 4 and of no other shipped game. Fallout 3,
  Fallout New Vegas and Skyrim SE prefix **every** `AVIF` EditorID with `AV`.
  Every `if let Some(fid) = index.actor_value_form_id(…)` in
  `derive_autocalc_actor_values` therefore takes the `None` arm, the function
  returns an empty `Vec`, and the FO3/FNV auto-calc path — the `#1663` reference
  path this whole module exists for — is dead on 100 % of real data.
- **Evidence**: *crates/plugin/examples/audit_esm_av_probe.rs* (throwaway, run
  and removed), release build, masters read from
  `_audit-common.md` § Game Data Locations:
  ```
  === FalloutNV.esm ===
  avif records = 64
  sample avif edids: ["AVActionPoints", "AVAggression", "AVAgility",
                      "AVAssistance", "AVBarter", "AVBigGuns", ...]
    actor_value_form_id("Health")     = None
    actor_value_form_id("AVHealth")   = Some(1104)
    actor_value_form_id("Strength")   = None
    actor_value_form_id("AVStrength") = Some(1000)
    health_actor_value_key            = None
  NPC_ = 3816 | derived-empty = 3816 | derived-nonempty = 0

  === Fallout3.esm ===   NPC_ = 1647 | derived-empty = 1647 | derived-nonempty = 0
  === Fallout4.esm ===   actor_value_form_id("Health") = Some(724)
                         NPC_ = 3015 | derived-empty = 0 | avg pairs = 12.3
  ```
  An independent raw-bytes walk of the top-level `AVIF` GRUP agrees:
  `FalloutNV.esm` ships `0x3e8 AVStrength`, `0x450 AVHealth`, `0x4b9 AVSmallGuns`,
  `0x44c AVActionPoints`; `Fallout4.esm` ships `0x2d4 Health`, `0x2d5 ActionPoints`.
  Nothing anywhere in the repository mentions the `AV` prefix — `grep -rl
  "AVStrength\|AVHealth"` over `docs/ crates/ byroredux/` returns nothing.
- **Impact**: Blast radius traced to four live consumers, all FO3/FNV-wide:
  1. `byroredux/src/npc_spawn.rs:100` — `pairs.is_empty()` returns early, so the
     actor gets **neither** `ActorValues` **nor** `ActorVitals`.
  2. `byroredux/src/combat.rs:200` requires `ActorVitals`; without it the melee
     damage system returns before touching the target. **No FO3/FNV actor can be
     damaged by the P2 combat slice.**
  3. `crates/scripting/src/condition.rs:429` — `GetActorValue` with no
     `ActorValues` component returns `0.0`, the absent-AV default, for every CTDA
     on every FO3/FNV actor.
  4. `byroredux/src/npc_spawn.rs:197` — `build_character_ruleset` passes the same
     resolver into `falloutnv_ruleset`; `AttributeSet::resolve` /
     `SkillSet::resolve` `filter_map` unresolved ids away
     (`crates/core/src/character/attribute.rs:147-152`), so the FNV
     `CharacterRuleset` is built with an empty roster.
  FNV is the project's declared reference title (`/audit-fnv`), which makes this
  a silent zero on the game the engine is calibrated against.
- **Related**: root cause shared with ESM-2026-08-16-D7-02. Test-fixture
  tautology is the same defect class as **ESM-D2-07** (2026-08-13). Hand-off to
  `/audit-character` Dim 4 — CHARAL's FNV ruleset is unwired against real data
  independent of anything CHARAL does. Not the same as **ESM-D8-04**, which is
  about `RACE`/`NPC_` sub-code coverage.
- **Suggested Fix**: Resolve per-game rather than by one literal: try the bare
  EditorID and the `AV`-prefixed form (FO3/FNV/Skyrim author the latter, FO4+ the
  former), and pin it with a `#[ignore]` real-data test that asserts
  `actor_value_form_id("Strength")` is `Some` on `FalloutNV.esm`. Do **not** fix
  it by re-spelling the CHARAL roster — the roster is canonical and shared with
  FO4, where the bare names are correct; the per-game spelling belongs at this
  parser-side boundary.

### ESM-2026-08-16-D7-02: `health_actor_value_key` returns an engine enum index in a FormID-keyed map, on a premise vanilla `Skyrim.esm` contradicts
- **Severity**: HIGH
- **Dimension**: `EsmIndex` → ECS Handoff
- **Record / Sub-record**: `AVIF`
- **Location**: `crates/plugin/src/esm/records/index.rs:365-372`
  (`SKYRIM_HEALTH_ACTOR_VALUE`), `:592-604` (`health_actor_value_key`);
  `crates/plugin/src/esm/records/actor_value_derive.rs:134-152`
  (`derive_skyrim_actor_values`)
- **Status**: NEW
- **Description**: The constant's doc says *"Skyrim addresses its built-in actor
  values by engine enum index rather than by an `AVIF` record. Vanilla
  `Skyrim.esm` therefore does not need to contain a `Health` AVIF for NPC health
  to be usable."* Vanilla `Skyrim.esm` contains 149 `AVIF` records and **one of
  them is `AVHealth`, FormID `0x000003E8`**. The lookup fails not because the
  record is absent but because of the `AV`-prefix mismatch in D7-01. The chosen
  workaround puts a bare enum index (`24`) into `ActorValues`, whose contract
  (`crates/core/src/ecs/components/actor_values.rs:64-77`, and the
  `actor_value_form_id` docstring) is that keys are **remapped global AVIF
  FormIDs — "the same space a remapped CTDA `param_1` … compares against"**.
- **Evidence**: Probe output and an independent raw `AVIF` GRUP walk both show
  `0x3e8 AVHealth` in `Skyrim.esm`. The two spaces are provably disjoint at the
  consumer: `param1_is_form_id`
  (`crates/plugin/src/esm/records/condition.rs:403-423`) lists
  `| 14  // GetActorValue — AVIF FormID`, so every Skyrim CTDA `GetActorValue`
  arrives at `crates/scripting/src/condition.rs:434` with
  `param_1 = remap(0x000003E8)`, while the map it indexes holds exactly one key,
  `24`. Measured: 5,085 of 5,118 `Skyrim.esm` NPCs carry exactly one derived pair,
  all keyed `24`.
- **Impact**: Every Skyrim `GetActorValue(AVHealth)` condition silently reads the
  absent-AV default `0.0` — quest gates, AI package conditions, and perk entry
  conditions on actor health are all evaluated against a value the actor does
  have but under a key nothing else uses. Combat is self-consistent (it reads the
  key back out of `ActorVitals`), which is precisely why the P2 gate is green:
  `docs/smoke-tests/p2-melee-core.sh:99` runs the melee-core check on
  `Skyrim.esm`, the one game whose actor values come from this bypass. The
  divergence is also serialized — `ActorValues` keys go to disk through
  `byroredux/src/save_io.rs:249`'s registry as plain `u32`.
- **Related**: same root cause as ESM-2026-08-16-D7-01; fix them together. The
  false-premise-in-a-comment shape is the `feedback_no_guessing` pattern.
- **Suggested Fix**: Delete the special case once D7-01 lands and resolve Skyrim
  Health through `AVHealth` like every other actor value. If a built-in enum key
  is genuinely wanted later, it needs its own key type, not a `u32` sharing a
  FormID map.

### ESM-2026-08-16-D3-01: VMAD Object-property FormIDs are never load-order remapped, at all six call sites
- **Severity**: HIGH
- **Dimension**: FormID Remap, Load Order & ESL Space
- **Record / Sub-record**: `VMAD` (`QUST`, `SCEN`, `REFR`, `ACTI`, …)
- **Location**: `crates/plugin/src/esm/records/script_instance.rs:161-163`
  (`ScriptInstanceData::parse`), `:489-505` (`property_value` type-1 arm);
  call sites `crates/plugin/src/esm/cell/support.rs:83`,
  `crates/plugin/src/esm/cell/walkers.rs:684`,
  `crates/plugin/src/esm/records/common.rs:289`,
  `crates/plugin/src/esm/records/misc/quest.rs:574`,
  `crates/plugin/src/esm/records/misc/scene.rs:170`
- **Status**: NEW (new instance of the class filed as **ESM-D3-03**, which cited
  `LTEX`/`SCOL`/`FLST` only; `script_instance.rs` was **explicitly excluded** from
  the 2026-08-13 Dim 2 sample — see that report's Cross-Audit Pointers)
- **Description**: `ScriptInstanceData::parse(data: &[u8])` has no `FormIdRemap`
  parameter and no call site supplies one, so a VMAD `Object` property's
  `form_id` stays in **plugin-local** space. Its consumers treat it as a
  **global** FormID.
- **Evidence**: The decoder reads the raw u32 and stores it verbatim:
  ```rust
  // script_instance.rs:493-504
  let (form_id, alias) = if object_format == 1 { … } else {
      let _unused = self.u16()?; let a = self.i16()?; let f = self.u32()?; (f, a)
  };
  PropertyValue::Object { form_id, alias }
  ```
  Consumers:
  - `crates/scripting/src/fragment.rs:234-239` — `resolve_quest`'s
    `QuestRef::Property` arm maps `object_form_id(name)` straight into a
    `QuestFormId`.
  - `crates/scripting/src/translate/recognizers/quest_stage_gate.rs:77-81` —
    the same value becomes `Condition::param_1` for `GetStageDone` (function 59),
    which `param1_is_form_id` remaps for **every other producer**.
  Contrast the correct shape landed in the same crate on 2026-08-16:
  `parse_omod_loose_item` (`items.rs:517-524`) takes `&Option<FormIdRemap>` and
  applies it, with a non-identity-remap test.
- **Impact**: Under any non-identity load order — every DLC, every multi-master
  stack, anything with an ESL — a raw `0x01xxxxxx` VMAD property is compared
  against a remapped index. It does not merely miss: `0x01` is a *valid* global
  slot, so the property can resolve to a **different plugin's record** and the
  fragment lowerer will advance the wrong quest with no diagnostic. `parse_esm`
  passes `None`, so single-master loads are unaffected, which is why every
  in-crate test passes.
- **Related**: **ESM-D3-01/#2906** (`XTEL`/`XESP`), **ESM-D3-02**, **ESM-D3-03**,
  **#2698** (`XPRI`) — all the same systematic omission: a decoder whose signature
  cannot remap. Fixing the signature class once is worth more than five point
  fixes. Cross-reference `/audit-scripting` Dim 7 for the consumer half.
- **Suggested Fix**: Add a `remap: &Option<FormIdRemap>` parameter to
  `ScriptInstanceData::parse` (keeping `parse` for the no-remap tests as a thin
  wrapper), apply it in the `property_value` type-1 arm only, and thread the
  walker's existing `remap` through the five call sites — `cell/walkers.rs` and
  `misc/quest.rs` already hold one.

## Dimension-by-Dimension Record

**Dimension 1 — Header Detection & GRUP Walk · 0 findings.**
`reader.rs` and `grup_walker.rs` unchanged since the audited tree, so
`EsmVariant::detect`, `record_header_size`/`group_header_size`,
`GameKind::from_header`'s bands, the compressed-record path and the nested-GRUP
recursion are exactly as filed on 2026-08-13. New structural check performed
this pass: for each of the eight `dispatch_*.rs` routers, the 4-char labels
routed to it by `records/mod.rs` were diffed against the 4-char literals it
matches. **All 8 have full parity (0 missing arms)**, so none of the eight
`unreachable!()` guards is reachable — including after the 2026-08-16 `OMOD`
addition, which is correctly paired (`records/mod.rs:386` label list +
`dispatch_items.rs:59` arm).

**Dimension 2 — Sub-Record Byte Accounting · 1 finding (LOW).**
First-ever sample of `records/script_instance.rs`, the 920-LOC `VMAD` decoder the
prior Dim 2 explicitly skipped for having "its own `take()`-based cursor rather
than `SubReader`". That cursor is sound: `take` is `checked_add` + `slice::get`,
there is no direct slice indexing in the file, `wstring` is length-prefixed and
bounds-checked, the array property arm clamps `Vec::with_capacity` to 4,096
against a `u32` count, and its recursion is depth-1 by construction. The four
arms that changed since were re-derived byte-by-byte: the new Skyrim `ACBS`
(flags@0 / magicka@4 / stamina@6 / level@8 / calc_min@10 / disposition@16 /
template@18 / health_offset@20), correctly ordered ahead of the same-length
generic FNV arm behind a `GameKind` guard; the generic FNV arm after the `#2955`
`calcMin` insertion (level@8, calc_min@10, skip 8 for calc_max+speed_mult+karma,
disposition@20, template@22 — exact); the FO4 and Oblivion `ACBS` arms; and
`RACE.DATA` `starting_health` at `f32 @ 36`, which decodes `ArgonianRace` 50.0 /
`AtronachFrostRace` 250.0 / `AlduinRace` 750.0 on vanilla — the correct Skyrim
base values, so the offset is confirmed by data and not only by arithmetic.

**Dimension 3 — FormID Remap, Load Order & ESL Space · 1 finding (HIGH).**
The new OMOD path is the correct shape end to end: keys go through
`read_record_header`'s single remap choke point (pinned by
`read_record_header_applies_installed_remap`), and `parse_omod_loose_item` takes
and applies an `Option<FormIdRemap>` with a non-identity test. The `VMAD` decoder
in the same crate does neither — ESM-2026-08-16-D3-01.

**Dimension 4 — Record Schema Dispatch & Coverage · 2 findings (LOW).**
`OMOD` has moved from the skipped bucket to partially decoded, correcting the
prior matrix's `OMOD | 2,409 K u12` row to `2,409` records decoded for `LNAM`
only. `ItemKind` gained `Junk` and `Mod`. Label↔arm parity clean (Dim 1).
`merge_from` re-measured and unchanged at 41 dropped maps.

**Dimension 5 — CELL / WRLD Walkers · 0 findings.**

`directional_azimuth/_elevation`. Decode is byte-identical

`LAND` quadrant paths are unchanged files; ESM-D5-01..D5-09 all still live.

## Disproved Candidates (recorded so they are not re-litigated)

- **`self.game` unset in the merged path.** Hypothesised that
  `classify_fallout_inventory_kinds`'s `matches!(self.game, Fallout4 | Fallout76)`
  guard would be a no-op inside `merge_from`, since
  `parse_record_indexes_in_load_order` seeds from `default()` (= `Fallout3NV`).
  **Disproved**: `merge_from` assigns `self.game = other.game` at
  `index.rs:760`, *before* the classify call at `:769`.
- **Unbounded allocation in the VMAD array property.** `Vec::with_capacity` there
  is clamped to 4,096 (`script_instance.rs:514`), unlike the compressed-record
  path that ESM-D1-03 covers.
- **Unbounded recursion in `property_value`.** The array arm recurses with
  `base = ptype - 10`, which is always in `1..=5` and never an array — depth is 1.
- **A misordered pair of same-length `ACBS` arms.** The Skyrim and generic FNV
  arms are both `>= 24`, but the Skyrim arm precedes it and is `GameKind`-guarded;
  the FO4 (`>= 20`) and Oblivion (`>= 16`) arms precede both. Order is correct.
- **`OMOD` value `0` conflating "absent `LNAM`" with "override cleared `LNAM`".**
  Bethesda override semantics replace a record wholesale, so an override with no
  `LNAM` genuinely *has* cleared it. The comment at `index.rs:44-46` is right.
- **`Vec::with_capacity(count)` in `parse_quest_fragments`.** `count` is a `u16`,
  so the allocation is bounded at 64 Ki entries.
- **A dispatch label with no matching arm** (a live `unreachable!()`). Checked
  across all eight routers: 0 gaps.
- **The `directional_azimuth`/`_elevation` rename changing decode.** Byte-for-byte
  identical; only identifiers and doc comments moved.
