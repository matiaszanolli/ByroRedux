| `DATA` 186 | 11 | `decode_data` → `decode_data_fo3nv` | 16..184 |

`DATA` is a 2-byte damage stub on exactly the 42 records that carry a `DNAM`.

#### FO3-2026-08-20-D3-01: FO3's water-quality mechanic has no data path — `WATR.XNAM` (the effect `SPEL` link) is never parsed, and the only decoded damage source is `0` on 100 % of vanilla FO3 water
- **Severity**: MEDIUM
- **Dimension**: ESM Record Coverage (Dim 3) — FO3-unique authoring
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:1282-1372`
  (`parse_watr`'s sub-record match — no `XNAM` arm), `:1329-1343` (the `DATA`
  arm that produces `legacy_damage`), consumed at
  `byroredux/src/cell_loader/water.rs:492-508` and `:825-841`
  (`WaterPlane::damage_per_second`)
- **Status**: NEW
- **Description**: In FO3, a water type's harm is not the `DATA` damage word —
  it is the `XNAM` link to a `SPEL` record ("water quality"). `parse_watr` has
  arms for `ANAM`, `FNAM`, `TNAM`, `NNAM`, `NAM0`–`NAM5`, `DATA`, `DNAM` and
  `GNAM`, but **none for `XNAM`**, so the link is dropped at the parse boundary.
  Meanwhile the one field that *is* decoded into
  `WaterPlane::damage_per_second` — `WatrRecord::legacy_damage`, from the
  2-byte `DATA` — is `0x0000` on all 42 records that carry it, and is left
  `None` on the 11 records whose `DATA` is the 186-byte visual payload (that
  branch never reaches the `len() == 2` damage arm). FO3 water is therefore
  harmless everywhere, by two independent routes.
- **Evidence**: `XNAM` census over `Fallout3.esm` (`dump_record_subs … WATR`):
  **51 of 53** records carry a 4-byte `XNAM`, resolving to six distinct `SPEL`
  records —
  ```
  0x00020517 SPEL WaterHeal2Good        0x00020D76 SPEL WaterHeal1Rads500
  0x00020D77 SPEL WaterHeal5Terrible    0x00020D78 SPEL WaterHeal3Average
  0x00045656 SPEL WaterHeal4Bad         0x000B878F SPEL WaterHeal1Purified
  ```
  (`0x00045656` alone is referenced by 27 records.) All 53 `DATA` damage words
  read `[00, 00]`. `MNAM` (material) is `[00]` on 53/53 and is likewise unparsed.
- **Impact**: The engine already ships both halves this would feed — a
  water-contact damage runtime (`byroredux/src/systems/character.rs:480`
  `water_damage_for_contact`, driven by `WaterContact::damage_per_second`) and a
  radiation affliction model (`crates/core/src/character/affliction.rs`). Only
  the FO3 source is missing, so `WaterTypeIrradiated`, `WaterTypeIrradiatedDirty`,
  `d5TerribleWater20r4h` and the Potomac read identically to purified water.
  This is FO3's single most title-defining environmental mechanic and it is
  currently a no-op. Applies to FNV identically (the same `XNAM` convention),
  but FO3 is where the gap is measured.
- **Related**: `ESM-2026-08-20-D5-06` (the mirror-image Oblivion damage gap —
  different sub-record, same "the damage path is dead for this title" shape);
  `#2872` (`WaterFlow.speed` unit seam, CLOSED).
- **Suggested Fix**: Add an `XNAM` arm capturing the effect `SPEL` FormID onto
  `WatrRecord` (name it for what it is — `effect_form`, not `damage`), and give
  `cell_loader/water.rs` a resolution step from that form's `EFIT` magnitude to
  `WaterPlane::damage_per_second` / a radiation channel. Keep `legacy_damage`
  as the Skyrim-era path; do not overload one field with two source semantics.

#### FO3-2026-08-20-D3-02: `decode_data_fo3nv`'s "the first sixteen bytes are opaque … not wind or wave controls" premise is falsified by every vanilla FO3 record
- **Severity**: LOW
- **Dimension**: ESM Record Coverage (Dim 3) — FO3-unique authoring
- **Location**: `crates/plugin/src/esm/records/misc/water.rs:550-556`
  (the doc-comment), `:555-568` (the arm starts reading at offset 16),
  `:648-651` (`wind_direction`/`wind_speed` sourced from the noise-layer-1
  fields instead), `:580-585` (`wave_amplitude`/`wave_frequency` sourced from
  the displacement simulator's force/velocity)
- **Status**: NEW — extends `ESM-2026-08-20-D5-01`'s "same-game divergence"
  consequence with the byte-level disproof of the premise that produced it
- **Description**: `decode_data_fo3nv` skips offsets 0..16 on the stated grounds
  that xEdit calls them opaque. Vanilla FO3 says otherwise: offsets 0/4/8/12
  are the GECK water defaults *Wind Velocity / Wind Direction / Wave Amplitude /
  Wave Frequency*, and offsets 16/20/24 are Sun Power / Reflectivity / Fresnel —
  which is exactly the field order `decode_dnam_pre_fo4` already reads from the
  same byte range. Because the arm treats them as opaque, it substitutes
  noise-layer-1 direction/speed for wind and the displacement simulator's
  force/velocity for wave amplitude/frequency, so the two FO3 arms disagree
  about where four canonical fields live.
- **Evidence**: Python walker over all 53 `Fallout3.esm` `WATR` visual payloads
  (`DNAM` and long `DATA` alike):
  ```
  offset  4 : distinct = 1  → 90.0 on 53/53          (Wind Direction, degrees)
  offset  0 : distinct = 3  → 0.1 ×46, 3.0 ×6, 2.0 ×1 (Wind Velocity)
  offset  8 : 0.5 / 0.2                               (Wave Amplitude)
  offset 12 : 1.0 / 0.25                              (Wave Frequency)
  ```
  `0.1 / 90.0 / 0.5 / 1.0` is the GECK's default water tuple verbatim — 46 of 53
  records never departed from it. The same file already treats FO3 direction
  fields as degrees (`:648` calls `.to_radians()` on the offsets-100/104/108
  triple), so the two readings of the same record cannot both be right.
- **Impact**: On the 11 FO3 records that ship the long `DATA` (and 8 on FNV),
  `wave_amplitude`/`wave_frequency` carry the displacement simulator's
  `0.4 / 0.6` instead of the authored `0.5 / 1.0`, and `wind_speed` carries a
  noise-layer scroll rate instead of the authored velocity. No crash — the
  values are plausible, which is why this survived. Its real cost is that a
  false sourcing claim sits directly on the function the `ESM-2026-08-20-D5-01`
  fix is supposed to collapse into `decode_dnam_pre_fo4` + a shared tail; an
  implementer who trusts the comment will preserve the divergence.
- **Related**: `ESM-2026-08-20-D5-01` (consequence 2, "same-game divergence"),
  `ESM-2026-08-20-D5-05` (the degrees/radians half), project memory
  `watr_data_layout_shift`.
- **Suggested Fix**: Delete the opaque-prefix claim and read 0..28 in
  `decode_data_fo3nv` exactly as `decode_dnam_pre_fo4` does — or, better, make
  `decode_data_fo3nv` *be* `decode_dnam_pre_fo4` plus the shared 52..196 tail,
  which is the fix `ESM-2026-08-20-D5-01` already proposes.

#### FO3-2026-08-20-D4-01: FO3 bakes a four-level LOD ladder out to ±64 cells; the ring can only ever request level 4 and stops at 48
- **Severity**: MEDIUM
- **Dimension**: FO3 Cell Loading End-to-End (Dim 4) — exterior
- **Location**: `byroredux/src/cell_loader/lod_bands.rs:130-135`
  (`LodBandLadder::for_game` returns `None` for everything but Skyrim/FO4),
  `byroredux/src/cell_loader/terrain_lod.rs:286-310` (the `None` arm of
  `desired_lod_quads`, which emits only `k = LOD_BLOCK_CELLS`), `:53`/`:59`
  (`LOD_BLOCK_CELLS = 4`, `LOD_RADIUS_BLOCKS = 12`), `:254-257`
  (`lod_ring_reach_cells`)
- **Status**: NEW — residual of `#3100` (CLOSED), narrower than `#2371` (OPEN)
- **Description**: `#3100` wired FO3's authored LOD *textures*, but only at the
  one level the ring can ask for. With no ladder, `desired_lod_quads` walks a
  fixed `LOD_RADIUS_BLOCKS`-deep square of level-4 blocks, so
  `lod_ring_reach_cells(Fallout3NV) = 12 × 4 = 48` cells and `level` is never
  anything but 4. FO3 ships three coarser bands whose whole purpose is the range
  beyond that. `translate_terrain_lod_textures`' `FalloutLegacy` arm is already
  level-generic (`if level > 0`), so the constraint is entirely on the caller.
- **Evidence**: archive census over `Fallout - Meshes.bsa` /
  `Fallout - Textures.bsa`:
  ```
  meshes\landscape\lod   : level4 1661 · level8 480 · level16 71 · level32 16   (2 232)

  ```
  Ring reach 48 cells vs authored extent 64 cells; 567 meshes and 832 texture
  files sit at levels the ring cannot name.
- **Impact**: Capital Wasteland's horizon ends ~65 500 BU short of the authored
  distance, and the coarse bands that vanilla uses to draw the far landmass are
  inert. Not a crash and not a regression — the level-4 ring is a working, and
  now correctly-textured, fallback — but the silhouette diverges from vanilla on
  every exterior, and `#3100`'s closure reads as "FO3 legacy LOD is done" when
  one of four bands is wired.
- **Related**: `#3100` (CLOSED — the texture-translation half, correct as far as
  it goes), `#2371` (OPEN — the umbrella, scoped to `.btr`/`.bto` bands and does
  not name this ladder), `#2086` (CLOSED — placement LOD, correctly Oblivion-only)
- **Suggested Fix**: Give `LodBandLadder::for_game` a `FalloutLegacy` arm whose

  `fBlockMaximumDistance` GMSTs (they are in `Fallout3.esm`, so this needs no
  guessed constant), and gate coarse-band availability on the authored quad
  existing — the same `has_btr`-shaped predicate the Skyrim/FO4 path already
  uses, pointed at `translate_terrain_lod_textures` instead.

## Disproved Candidates (investigated, not reported)

- **"FO3's `DATA`-186 and `DNAM`-196 payloads are different layouts."** They are
  the same structure; `PPurityWater01Murky` (`DATA` 186) and
  `PPurityWaterBase01` (`DNAM` 196) are the same authored water and agree field
  for field. The 186-byte form is simply truncated 10 bytes early, which costs
  only the three noise amplitude scales at 184/188/192.
- **"`WATR.MNAM` carries a material FormID FO3 needs."** It is a single byte and
  reads `0x00` on 53/53 vanilla records. Nothing to recover.
- **"The `AV`-prefix fallback could resolve ambiguously on FO3."** Enumerated all
  60 FO3 AVIF EditorIDs; no record's `AV`-stripped name collides with any other
  record's full name, so the `HashMap`-order-dependent `find` is deterministic
  in practice on this master.
- **"`worldspace_key` may not match FO3's LOD directory names."** It does — the
  archive ships `wasteland`, `washmontop`, `paradisefalls` and the `dcworldNN`
  set, all lowercase EditorIDs, matching the translator's
  `to_ascii_lowercase()`.
- **"FO3's level-4 quad grid may not align with the engine's block origin."**
  It does: `worldspace_lod_grid_origin` returns `(0, 0)` for non-combined games
  and `block_cell_origin` emits multiples of `LOD_BLOCK_CELLS = 4`; every
  vanilla FO3 level-4 quad coordinate is a multiple of 4.
