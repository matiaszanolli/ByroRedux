### ECS-2026-08-20-01: `player_controller_system` reads `WindField` undeclared while its parallel Stage::Early sibling `weather_system` writes it every tick
- **Severity**: HIGH
- **Dimension**: 5b — Scheduler Access Declarations
- **Location**: `byroredux/src/boot.rs:691-724` (declaration), `byroredux/src/systems/character.rs:911-916` (the undeclared read), `byroredux/src/boot.rs:726-740` + `byroredux/src/systems/weather.rs:690-692` (the concurrent writer)
- **Status**: NEW
- **Description**: The WATAL wave work added a `WindField` read to the character
  controller's water path. `character_controller_system` → `player_water_state`
  → `byroredux_physics::weather_wave_adjustment(world, time)` →
  `world.try_resource::<WindField>()`. `player_controller_system` is registered
  with `add_to_with_access(Stage::Early, …)` — i.e. it is in the **parallel
  batch** — and its `Access` declaration lists `TotalTime` (added in the same
  delta) but **not** `WindField`. `weather_system` is the second member of that
  same parallel batch and takes a `try_resource_mut::<WindField>()` write every
  tick.
- **Evidence**:
  `crates/physics/src/water.rs:323-326` — the read reached from the controller:
  ```rust
  pub fn weather_wave_adjustment(world: &World, time_secs: f32) -> ([f32; 2], f32) {
      let wind = world
          .try_resource::<WindField>()
  ```
  `byroredux/src/systems/character.rs:911-916` — unconditional on the
  `PlayerMode::Character` path (`player_water_state` is called at `:224`, before
  any early-return that could skip it):
  ```rust
  let wave_height = world
      .try_resource::<TotalTime>()
      .map(|time| {
          let (weather_scroll, wind_wave_scale) =
              byroredux_physics::weather_wave_adjustment(world, time.0);
  ```
  `byroredux/src/systems/weather.rs:690-692` — the writer, unconditional:
  ```rust
  if let Some(mut wind) = world.try_resource_mut::<WindField>() {
      *wind = WindField::from_weather_byte(weather_wind_speed, wind.direction);
  }
  ```
  Stage::Early's parallel batch is exactly three systems (`boot.rs:691`, `:726`,
  `:742`); `scheduler.rs:502-503` dispatches the batch through
  `par_iter_mut().for_each`.
- **Impact**: This is the #1787 / #2389 / #2676 defect class, but for the first
  time **with a live concurrent writer in the same stage**. `AccessConflict`'s
  resource rules (`crates/core/src/ecs/access.rs:198-213`) classify
  read-vs-write on the same resource as `ConflictKind::ReadWrite`, so declaring
  the read honestly would make `install_runtime_registries`'
  `debug_assert_eq!(known_conflict_count(), 0)` (#1602) **fail** — the fix is a
  schedule change, not a one-line declaration. Until then `sys.accesses` reports
  0 conflicts from an incomplete declaration, and the boot guard that is
  supposed to make cross-thread hazards structurally unreachable among parallel
  systems is computing its answer from a false premise. The runtime symptom is
  mild (`RwLock` prevents a torn read; the player's buoyancy/swim surface height
  samples either this frame's or last frame's gust, nondeterministically per
  frame) — the severity is driven by the broken invariant, which is the only
  thing standing between this stage and a real race the next time someone adds
  a parallel Early system.
- **Related**: #2676 (`camera_follow_system` reads `PlayerMode` undeclared —
  CLOSED; the fix is intact, `boot.rs:1295` carries the declaration and its
  rationale comment). #1787 (`ContactConfig` on `physics_sync_system`). #1602 /
  #1394 (the boot guards). Distinct from all three: those had no concurrent
  writer in the same stage; this one does.
- **Suggested Fix**: Either move `weather_system` to
  `add_exclusive_with_access(Stage::Early, …)` (it writes seven resources and
  reads none that a parallel sibling writes, so exclusivity costs nothing — the
  same treatment `audio_system` / `spin_system` got in M27 Phase 3), or hoist
  the `WindField` snapshot into a stage-earlier read. Then add
  `.reads_resource::<WindField>()` to `player_controller_system` and confirm
  `known_conflict_count()` is still 0.

### ECS-2026-08-20-02: the two new water death sites insert `Dead` without running `reconcile_dead_actor`, so a drowned actor keeps its AI behavior, its `AnimationPlayer`, and never ragdolls
- **Severity**: MEDIUM
- **Dimension**: 7 — Component Lifecycles
- **Location**: `byroredux/src/systems/water.rs:55-68` (`water_damage_system`), `byroredux/src/systems/character.rs:1027-1045` (`apply_player_drowning_damage`), against `byroredux/src/combat.rs:370-392` (`reconcile_dead_actor`)
- **Status**: NEW
- **Description**: The delta added two new producers of the alive→dead
  transition. Both do the same thing: apply damage to the `Health` ActorValue
  and, if it hits zero, `dead_q.insert(entity, Dead)` — and stop there. Neither
  calls `reconcile_dead_actor`, the function whose own doc comment declares
  itself the single reconciler for this transition:
  > "Both the combat transition and save-load drain call this one reconciler,
  > keeping those derived removals consistent (#3022)."
  There are now four death sites and only two of them go through it.
- **Evidence**: `byroredux/src/systems/water.rs:62-67` — the whole death branch:
  ```rust
  let killed = values.current(health) <= 0.0;
  drop(values_q);
  if killed {
      if let Some(mut dead_q) = world.query_mut::<Dead>() {
          dead_q.insert(entity, Dead);
      }
  }
  ```
  `byroredux/src/systems/character.rs:1039-1044` is the same shape for the
  player. Compare `byroredux/src/combat.rs:238-241`, which follows the same
  insert with `outcome.push_str(&reconcile_dead_actor(world, target));` —
  `reconcile_dead_actor` (`:376-388`) runs
  `npc_spawn::ai_package::clear_ambient_behavior` (all sixteen behavior
  components + the `SeatReservations` release), removes `AnimationPlayer` from
  the skeleton root, and calls `ragdoll::activate_ragdoll`.
  None of the seven M42 procedure systems filters on `Dead` —
  `grep -c Dead byroredux/src/systems/{sandbox,wander,travel,follow,escort,guard,patrol}.rs`
  returns `0` for all seven — so they rely entirely on the death path having
  removed the behavior component.
- **Impact**: With any `BYRO_WANDER` / `BYRO_TRAVEL` / … gate set, an NPC killed
  by FO3/FNV authored harmful water (`WaterPlane::damage_per_second`, the
  irradiated/chemical pools) keeps `WanderBehavior` + `WanderState` and its
  system keeps walking the corpse. In the default build the visible symptom is
  narrower but still real: no ragdoll, and the idle `AnimationPlayer` keeps
  playing on a dead actor. The state is also **inconsistent across a
  save/reload**: `reconcile_dead_actor_runtime_state` (`combat.rs:393-401`) runs
  the reconciler over every `Dead` actor after a load, so the corpse
  spontaneously ragdolls and loses its AI on reload — the same actor, two
  different runtime states, depending on whether the session was reloaded.
  `water_damage_system` is registered unconditionally
  (`boot.rs:1335`, `Stage::Late` exclusive), so this needs no opt-in gate.
- **Related**: #3029 / #3030 (the 2026-08-16 combat-teardown pair — both CLOSED
  and both fixes verified intact this run: `disable_actor_ai` now delegates to
  the shared `clear_ambient_behavior`, and `ambient_ai_package_system` gained
  its `Dead` filter at `ai_package.rs:543`). This finding is the *next* instance
  of the same class, introduced by code written after those closed.
- **Suggested Fix**: Make `reconcile_dead_actor` `pub(crate)` and call it from
  both new sites, exactly as `combat_damage_system` does. The player site can
  take the same call — `reconcile_dead_actor` degrades to "no ragdoll target"
  when `HavokAnimationTarget` is absent, so it is safe on any actor.

### ECS-2026-08-20-03: `WEAPON_EQUIP_SLOT = 31` is not a free bit — it is Skyrim/FO4 BOD2 body-part 61 (FX01), so an armor in that slot silently unequips the player's weapon
- **Severity**: MEDIUM
- **Dimension**: 7 — Component Lifecycles (P2 gameplay slice)
- **Location**: `byroredux/src/inventory.rs:20-24`, `:146-150`, `:422-424`
- **Status**: NEW
- **Description**: #3032's fix gave weapons an equip slot by carving out bit 31
  of the `EquipmentSlots` occupancy mask, on the stated premise that it is
  outside the record contract:
  ```rust
  /// Dedicated equipment bit for the currently wielded weapon. Biped slot
  /// masks occupy the lower 32-bit contract in legacy records; keeping this
  /// bit separate prevents a weapon toggle from displacing body armor.
  const WEAPON_EQUIP_SLOT: usize = 31;
  ```
  The premise is self-contradictory — bit 31 *is* in "the lower 32-bit
  contract". `EquipmentSlots::occupants` is `[Option<InventoryIndex>; 32]`
  (`crates/core/src/ecs/components/inventory.rs:171,184`), and the armor mask
  that indexes it is the raw parsed `biped_flags` u32, not a truncated low half:
  `describe_kind` returns `(*biped_flags != 0).then_some(*biped_flags)`
  (`inventory.rs:146-150`). On Skyrim+ that u32 is BOD2's first word, whose 32
  bits map to `BSDismemberBodyPartType` 30…61 — bit 31 is slot **61 / FX01**
  (`crates/plugin/src/esm/records/items.rs:370-377` parses BOD2 into
  `biped_flags`; `crates/plugin/src/equip.rs:24-36` documents the 30-based
  mapping).
- **Evidence**: `inventory.rs:422-424` — the reconcile step reads occupant 31
  unconditionally after every toggle:
  ```rust
  let equipped_weapon = equipment.occupants[WEAPON_EQUIP_SLOT];
  drop(equipment_query);
  reconcile_equipped_weapon(world, player, equipped_weapon);
  ```
  `reconcile_equipped_weapon` (`:428-459`) then looks the occupant's form id up
  in `InventoryCatalog` and, finding `weapon_damage: None` for an armor, takes
  the `else` arm at `:457`: `let _ = world.remove::<EquippedWeapon>(player);`.
- **Impact**: On a Skyrim/FO4 load order, equipping any ARMO whose BOD2 sets bit
  31 writes the armor's `InventoryIndex` into occupant 31 and immediately
  **removes** the player's `EquippedWeapon`, dropping melee damage back to
  `UNARMED_DAMAGE` with no player-visible cause. The reverse direction also
  holds: equipping a weapon writes occupant 31 and displaces the armor from that
  slot. `combat::attack_damage` (`combat.rs:274-287`) is the direct consumer, so
  this is a live gameplay defect in the P2 slice, not a bookkeeping one.
- **Related**: #3032 (CLOSED — the equip path it added is otherwise intact and
  verified this run: `describe_kind` gives weapons a mask, `apply_action`
  reconciles `EquippedWeapon` on both branches, and `EquippedWeapon` is no
  longer spawn-frozen). This is a defect in that fix's choice of bit, not a
  regression of it.
- **Suggested Fix**: Move the weapon occupancy out of the biped-slot array
  entirely — either a separate `Option<InventoryIndex>` field on
  `EquipmentSlots`, or widen `occupants` and put the weapon at index 32+ so no
  authored mask can ever address it. Whichever shape, the invariant to pin with
  a test is "no value producible by `describe_kind` for an `ItemKind::Armor` can
  collide with the weapon slot."

### ECS-2026-08-20-05: the new F5/F9 quicksave path calls `SaveCommand::execute` from the winit event handler, breaking the "sole caller is the exclusive lane" invariant its own comment names as the safety argument
- **Severity**: MEDIUM
- **Dimension**: 1 — Lock Ordering & Deadlock / 7 — Lifecycles
- **Location**: `byroredux/src/app_events.rs:285-302`, against `byroredux/src/save_io.rs:618-641`
- **Status**: NEW
- **Description**: `save_io::quicksave` is a one-line wrapper —
  `SaveCommand.execute(world, "")` — and the delta wired it straight into
  `ApplicationHandler::window_event` on the F5 binding. `SaveCommand::execute`
  carries an explicit, load-bearing comment stating that its very wide lock hold
  is safe *only* because of who calls it:
  > "`registry` (SaveRegistry) stays held through `save_world`/`encode` below,
  > alongside the ~26 component-storage + ~7 resource read locks … the widest
  > single-hold edge fan-out in the process. Safe today **only because command
  > dispatch (the sole caller of `execute`)** runs on the exclusive
  > `DebugDrainSystem` lane … Moving command dispatch off the exclusive lane, or
  > adding a parallel system that also touches `SaveRegistry`, needs this
  > re-derived. SAVE-D3-02 / #2154."
  There is now a second caller, and it is not on that lane.
- **Evidence**: `byroredux/src/app_events.rs:288-296`:
  ```rust
  let save_output = match save_action {
      Some(crate::interaction::InputAction::Quicksave) => {
          Some(crate::save_io::quicksave(&self.world))
      }
  ```
  `byroredux/src/save_io.rs:618-620`:
  ```rust
  pub fn quicksave(world: &World) -> CommandOutput {
      SaveCommand.execute(world, "")
  }
  ```
- **Impact**: No live deadlock: winit `window_event` and `Scheduler::run` are
  both driven from the main thread, and `run` joins its rayon batch before
  returning, so no ECS system is live while the handler executes. But that is a
  *different* safety argument from the one the code documents, it is nowhere
  written down, and nothing enforces it — the checked-in invariant now reads as
  satisfied while being factually false, which is precisely the condition the
  #2154 comment was written to prevent. The equivalent hazard would become real
  the moment save is invoked from anywhere with a live scheduler (a scripted
  autosave system, a background quicksave, a debug-UI button dispatched off the
  drain lane).
- **Related**: #2154 / SAVE-D3-02 (the invariant). #3022 (the P2-slice save
  work). Not a duplicate of either — both predate this call site.
- **Suggested Fix**: Route the F5/F9 actions through the same deferred queue
  `quickload_latest` already uses (`queue_load_slot`, `save_io.rs:832`) so the
  snapshot is taken on the drain lane, and update the `SaveCommand::execute`
  comment to name the *actual* set of callers rather than "the sole caller".

### ECS-2026-08-20-06: the two `SplashEvent` producers disagree with each other, and with the component's own doc, about which entity hosts the marker
- **Severity**: LOW
- **Dimension**: 7 — Component Lifecycles
- **Location**: `crates/scripting/src/events.rs:45-56` (contract), `byroredux/src/systems/water.rs:275-292` (producer A), `byroredux/src/systems/water.rs:419-432` (producer B)
- **Status**: NEW
- **Description**: `SplashEvent`'s doc is unambiguous: *"The event lands on the
  water-plane entity so audio, gameplay and presentation systems can consume the
  same source interaction without inventing a second queue."* `submersion_system`
  honours that — it inserts on the `WaterVolume`/plane entity. But
  `make_water_interaction_system`, in the same file, inserts `SplashEvent` on
  the **body** entity while inserting its sibling `RippleEvent` on
  `surface_entity`. So within one function the two markers use different host
  classes, and one of them contradicts the documented contract.
- **Evidence**: `byroredux/src/systems/water.rs:424-432` — `entries`' first
  tuple element is the body, its second is `surface_entity`; the splash loop
  binds the first and discards the second:
  ```rust
  for &(entity, _, position, intensity, entering, _) in &entries {
      if entering {
          q.insert(
              entity,
              SplashEvent { actor: entity, intensity, position: [...] },
  ```
  The ripple loop directly above (`:409-418`) keys on `surface_entity`. Two of
  `entries`' six tuple fields (`surface_entity` and the trailing
  `submerged_fraction < 0.98` flag) are never read at all.
- **Impact**: The only consumer today, `water_audio_system`
  (`byroredux/src/systems/audio.rs:244-256`), reads the event payload's own
  `position` and ignores the host entity, so nothing is visibly wrong. The cost
  is future: the contract exists so a scripting/quest consumer can attach to a
  water surface the way `OnTriggerEnterEvent` attaches to a volume, and that
  consumer would silently see half the splashes. Also, because insert
  overwrites, a `RippleEvent` written by `submersion_system` in PostUpdate is
  clobbered by `make_water_interaction_system` in Late whenever a dynamic body
  shares the plane — the camera's disturbance is dropped without trace.
- **Related**: none — both producers are new in this delta.
- **Suggested Fix**: Insert `SplashEvent` on `surface_entity` with
  `actor: entity` (matching `RippleEvent`'s existing shape and the doc), drop
  the two dead tuple fields, and apply the same strongest-wins dedup the ripple
  path already uses so two bodies entering one plane in the same frame do not
  silently collapse to whichever iterated last.

### ECS-2026-08-20-07: `WaterMaterial` grew 18 → 63 fields this delta, and `WaterContact` copies all 436 bytes of it into per-body ECS storage every physics tick
- **Severity**: LOW
- **Dimension**: 8 — Hot-Path Performance Invariants
- **Location**: `crates/core/src/ecs/components/water.rs:88-368` (`WaterMaterial`), `:564-594` (`WaterContact`), `crates/physics/src/water.rs:581`, `:724-760`, `:802-808`
- **Status**: NEW
- **Description**: The WATAL authored-parameter work took `WaterMaterial` from
  18 fields at `adbc3f77` to 63 at HEAD — 436 bytes by field sum, all `Copy`.
  `WaterContact` embeds `Option<WaterMaterial>` and `Option<WaterFlow>`, so each
  per-body contact is now roughly half a kilobyte, and the buoyancy phase
  rebuilds and re-inserts one for **every wet dynamic body, every physics tick**,
  through a freshly-allocated `Vec<(EntityId, WaterContact)>`.
- **Evidence**: field counts measured directly against the two revisions (18 at
  `adbc3f77`, 63 at HEAD). `crates/physics/src/water.rs:581`:
  ```rust
  let mut writes: Vec<(EntityId, WaterContact)> = Vec::new();
  ```
  then `:802-807` drains it into `query_mut::<WaterContact>()` one insert at a
  time. `SubmersionState` (`components/water.rs:531-543`) carries the same
  `Option<WaterMaterial>` and is whole-struct assigned each frame
  (`systems/water.rs:334`) — one entity, so negligible there; the per-body path
  is the one that scales.
- **Impact**: Modest today (a few dozen floating bodies ⇒ low tens of KB of
  memcpy per tick, plus one `Vec` growth) and `Vec::new()` costs nothing on the
  dry-scene fast path. Flagged because it is a 4× growth in a per-body,
  per-tick component that landed without the scratch-reuse treatment every other
  per-frame buffer in this codebase got (#932 `FootstepScratch`, #3059
  `InteractionCandidateScratch`, #828 `animation_system`), and because the
  duplicated payload is already reachable through `WaterContact::surface_entity`
  → `WaterPlane::material`.
- **Related**: #932, #3059 (the scratch-reuse precedent). Not a duplicate — no
  prior issue names `WaterContact`'s size.
- **Suggested Fix**: Either hold the surface's material by reference through
  `surface_entity` (the field already exists and every consumer has `World`), or
  keep the embedded copy but hoist `writes` into a scratch `Resource` the way
  `FootstepScratch` does, so the capacity survives across ticks.

## Premises checked and disproved (not reported)

Recorded so a later sweep does not re-derive them.

- **Double water damage on the player** — `player_controller_system` (Early) and
  `water_damage_system` (Late) do not both hit the player. The kinematic
  controller never receives a `WaterContact`: the buoyancy phase filters to
  `body.body_type() == RigidBodyType::Dynamic` (`crates/physics/src/water.rs:594`)
  and `player_water_state` is documented as *"mirrors the dynamic-body
  `WaterContact` calculation without creating a transient component for the
  kinematic player"* (`character.rs:886-887`).
- **`SplashEvent` / `RippleEvent` leaking past their frame** — both are drained
  by `event_cleanup_system` (`crates/scripting/src/cleanup.rs:35-36`), which is
  the last Late exclusive (`boot.rs:1422`), after all three water systems and
  `audio_system`. Producer→consumer→drain ordering is correct.
- **Quicksave/quickload binding collisions** — `Quicksave`/`Quickload` are not
  in `InputAction::CONFIGURABLE` and F5/F9 are not in `SUPPORTED_KEYS`, so
  `parse_key_id` can never route a rebind onto them and `rebind_key` can never
  displace them. Their empty `setting_id()` is unreachable from
  `action_for_setting`, which only iterates `CONFIGURABLE`.
- **F5 sticking in `InputState.keys_held`** — the quicksave arm returns before
  the `match event` block, so F5 is never *added* to `keys_held`; the release
  event does not take the early-return path and its removal is a harmless no-op.
- **`recenter_lod_water` desynchronising a water volume** —
  `spawn_lod_water_plane` deliberately attaches no `WaterVolume`
  (`cell_loader/water.rs:862-867` documents why), so translating the LOD annulus
  cannot move a gameplay water column. It writes `Transform` through
  `query_mut`, which marks the `TRACK_CHANGES` dirty bit, so propagation picks
  it up.
- **`geometry_bases` unbounded growth in `make_billboard_system`** — pruned
  every pass via `retain(|entity, _| mesh_q.contains(*entity) && swq.contains(*entity))`
  (`billboard.rs:150-152`), and entity ids are never recycled, so a stale key is
  impossible rather than merely unlikely.
- **`SeatReservations` prune regression** — `prune_seat_reservations`
  (`cell_loader/references/mod.rs:850-871`) still checks *both* liveness halves
  (furniture resident **and** claimant still `Seated` on that furniture) and is
  still called from `load_references` (`:381`).
- **`inventory.rs` as a second source of truth** — re-confirmed. The delta's
  additions (`weapon_damage` / `weapon_reach` / `weapon_speed`) are immutable
  record metadata on `InventoryItemDefinition`, and `EquippedWeapon` is now
  properly *derived* from `EquipmentSlots` by `reconcile_equipped_weapon` rather
  than being a parallel authority.
- **`CombatState` unbounded trace growth** — still a single
  `Option<CombatTraceEntry>`, not a collection.
- **`AnimationClipRegistry` unbounded growth across streaming** — #790's
  lowercased-path interning is unchanged.
- **`camera_follow_system` losing its `PlayerMode` declaration (#2676)** — the
  declaration and its rationale comment are both present at `boot.rs:1284-1295`.
