## Findings

### MEDIUM

### ESM-2026-10-27-01: BPTD `BPND` decoded with Flags↔Part Type and To-Hit↔Health Percent swapped
- **Severity**: MEDIUM
- **Dimension**: Sub-Record Byte Accounting
- **Record / Sub-record**: `BPTD` / `BPND`
- **Location**: `crates/plugin/src/esm/records/misc/equipment.rs:274-293` (`parse_bptd`); field docs `:174-196`
- **Status**: NEW
- **Description**:
  - xEdit gives one `BPND` layout for both games (`wbDefinitionsFNV.pas:5963-5982`, `wbDefinitionsFO3.pas:5368-5386`):

    | Offset | Field (xEdit) |
    |---|---|
    | @0 | Damage Mult `f32` |
    | @4 | **Flags** `u8` (Severable, IK Data, IK Biped, Explodable, IK Is Head, IK Headtracking, To-Hit Absolute) |
    | @5 | **Part Type** `s8` (`wbBodyLocationEnum`) |
    | @6 | **Health Percent** `u8` |
    | @7 | Actor Value `s8` |
    | @8 | **To Hit Chance** `u8` |
    | @9 | Explosion Chance `u8` |
    | @10 | Debris Count `u16` |
    | @12 / @16 | Debris / Explosion FormIDs |

  - The decoder reads `part_type = @4`, `flags = @5`, `to_hit_chance = @6` and `health_percent = @8`. Debris count is read as a `u8`.
  - The struct doc says the layout is "corpus-established" by value-shape clustering (#6350 spike), and that "bit0 tracks severable exactly (head = 1, torso = 0)". That pattern is the Part Type enum (Torso 0, Head 1), not a flag. Right Leg is Part Type 10, so bit 0 is clear on it.
- **Evidence**: raw `BPND` bytes, `DefaultBodyPartData` (`0x1D`). The rows are identical in FalloutNV.esm and Fallout3.esm:

  | Part | b4 (Flags) | b5 (Part Type) | b6 | b8 |
  |---|---|---|---|---|
  | Head | 59 = Sev+IK+Expl+IsHead+Headtrack | 1 | 20 | 30 |
  | Torso | 8 = Explodable | 0 | 60 | 60 |
  | Left Arm | 9 | 3 | 25 | 45 |
  | Left Leg | 15 | 7 | 25 | 50 |
  | Right Leg | 15 | 10 | 25 | 50 |
  | Right Arm | 9 | 5 | 25 | 45 |

  - b4 decodes cleanly as the flag set: only the head carries IsHead and Headtracking, and the torso is not severable.
  - b5 is exactly the body-location enum.
  - b8 is the same on `PlayerBodyPartData` (`0x1C`): 30/60/45/50. That fits a per-part to-hit chance.
  - b6 differs between the two records: the player has 75/255/100/150, NPCs have 20/60/25/25. That fits a share of the actor's health, with the player's limbs sturdier.
- **Impact**:
  - `byroredux/src/systems/vats.rs` (`vats_scan`, `part_to_hit: part.to_hit_chance as f32`) feeds the health share into `VatsModel::to_hit_chance`.
  - Every NPC limb is priced at 25 instead of 45–50, and the head at 20 instead of 30.
  - `flags` and `part_type` are wrong for every part. That matters for the Phase-4 dismemberment consumer the doc names. The FNV VATS gate has been live since `59d69f763`.
- **Related**:
  - ESM-2026-10-27-02, the same formula's weapon term.
  - #6350 (tracker; the spike's layout table records the swapped reading).
  - #6403 (the to-hit ground-truth pin is `#[ignore]`d, so nothing caught this).
  - The real-data pins encode the wrong reading: `crates/plugin/tests/parse_real_esm.rs:6311-6346`.
- **Suggested Fix**:
  - Read the struct per xEdit: flags @4, part_type @5, health_percent @6, to_hit_chance @8, debris_count `u16` @10.
  - Re-pin the census test against the values above.
  - Drop the "severable = bit0" claim, or re-derive it from the real flags byte.

### ESM-2026-10-27-02: WEAP `DNAM`@28 is Sight FOV, not Base VATS To-Hit Chance
- **Severity**: MEDIUM
- **Dimension**: Sub-Record Byte Accounting
- **Record / Sub-record**: `WEAP` / `DNAM` (FO3/FNV)
- **Location**: `crates/plugin/src/esm/records/items.rs:442-449` (`parse_weap` `DNAM` arm); consumer `byroredux/src/systems/vats.rs:245-266` (`resolve_weapon`)
- **Status**: NEW
- **Description**:
  - xEdit labels the `DNAM` offsets the same way in both games (`wbDefinitionsFNV.pas:8749-8755`, `wbDefinitionsFO3.pas:7581-7584`):

    | Offset | Field |
    |---|---|
    | {16} | Min Spread |
    | {20} | Spread |
    | {24} | Unused |
    | {28} | **Sight FOV** (`f32`) |
    | {32} | Unused |
    | {36} | Projectile FormID |
    | {40} | **Base VATS To-Hit Chance** (`u8`) |

  - The decoder stores @28 as `vats_base_to_hit`. The commit cites "wiki tables", but no definition source is given for the offset.
- **Evidence**: FalloutNV.esm, measured with an independent walker:

  | Weapon | @28 `f32` | @40 `u8` |
  |---|---|---|
  | 10mm pistol | 65 | 15 |
  | Sniper rifle | 25 | 16 |
  | Laser rifle | 40 | 45 |
  | Hunting rifle | 38 | 42 |
  | Minigun | 45 | 45 |
  | Super sledge | **0** | 45 |
  | Ripper | **0** | 27 |
  | Lead pipe | **0** | 21 |

  - Every melee weapon has @28 = 0. Flamers and missile launchers are 55, and Miss Fortune's gun and the Mesmetron are 70.
  - The GECK wiki *Weapons* page defines Sight FOV as "the angle of view when using iron sights … 0 essentially disables iron sights". Its Base VATS To-Hit Chance "is set based upon the size of the weapon", which matches @40: pistol 15, minigun and sledge 45.
  - @36 resolves to a `PROJ` record on all 173 non-null FNV weapons, so xEdit's offsets in this blob are aligned.
- **Impact**:
  - `vats_base_to_hit` is the first factor of `VatsModel::to_hit_chance` (`crates/core/src/character/vats.rs:351`).
  - Every ranged weapon gets its zoom angle as its VATS accuracy. A scoped sniper rifle (25) is priced worse than a 10mm (65).
  - Any melee weapon that reaches the scan has a base chance of 0. The scan has no melee filter; only its doc says "ranged weapons only".
- **Related**:
  - ESM-2026-10-27-01, the same formula's part term.
  - The real-data pins `parse_real_esm.rs:2046-2071` (`weapon_stat` table) encode the @28 reading.
  - The GECK note that Base VATS To-Hit is the chance "to hit the weapon when it's held by another actor" should be weighed by `/audit-character` before the field is wired into the player's formula.
- **Suggested Fix**:
  - Decode @28 as `sight_fov` and @40 (`u8`) as `vats_base_to_hit`.
  - Have CHARAL decide whether that field is a factor in the player-attack formula at all.
  - Re-pin the real-data table.

### LOW

### ESM-2026-10-27-03: FNV `WEAP` `VATS` sub-record is the melee VATS special attack; `DNAM`@68 is the Override AP
- **Severity**: LOW
- **Dimension**: Sub-Record Byte Accounting
- **Record / Sub-record**: `WEAP` / `VATS`, `DNAM`
- **Location**: `crates/plugin/src/esm/records/items.rs:450-497` (`DNAM`@68 → `ap_cost`; `VATS`@12 → `WeaponVats::ap_override`); consumer `byroredux/src/systems/vats.rs:256-266`
- **Status**: NEW
- **Description**:
  - xEdit FNV `VATS` (`wbDefinitionsFNV.pas:8881-8889`) is *Effect (SPEL), Skill, Dam. Mult, AP, Silent, Mod Required*.
  - All 45 FalloutNV.esm weapons with a non-zero `VATS` AP are melee weapons, such as Super Sledge, Ripper, Lead Pipe, knives and machetes. All have skill requirement 50, damage multipliers of 0.5–2.0, and `MaulerKnockdownSpell` / `VictoryRifleKnockdownSpell` effects. That is the FNV melee VATS special-attack block.
  - xEdit names `DNAM`@68 "Override - Action Points", gated by Flags 2 `0x8` "Override - Action Points" (@56). On FalloutNV.esm @68 is non-zero on exactly the 203 records with the bit set; the 58 without it read 0. Fallout3.esm shows the same pattern: 117 with the bit, 43 without, @68 = 0 on all 43.
  - The code calls @68 the "standard cost" and the `VATS` AP the "Override-tab value".
  - `resolve_weapon` prefers `ap_override` when it is above 0, so a melee VATS attack would be charged its special-move cost (super sledge 48 instead of 38).
- **Impact**: none on ranged weapons today, because no ranged weapon authors a `VATS` AP and the values themselves are right. The labels and docs are inverted, and the override flag is ignored. This becomes live when melee VATS lands.
- **Suggested Fix**:
  - Rename the field to the special-attack AP and keep it out of the standard cost.
  - Document @68 as the Override AP, honoured when Flags 2 `0x8` is set, with the engine default otherwise. The code already does this, because 0 falls back to the default.
