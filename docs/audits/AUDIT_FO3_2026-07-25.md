## Executive Summary

**Compatibility level: HIGH — parity with FNV, no new correctness defects.** FO3
ships at `bsver = 34`, the identical NIF/BSA/ESM stamp FNV uses, and rides the shared
code path end-to-end with essentially no surface for an FNV-only assumption to
diverge. Every divergence this skill flags as a risk — inline-shader-only material
universe, Capital Wasteland worldspace, FO3-era particle/collision authoring, pre-FNV
record subforms, the Oblivion-only `.lod` placement scheme — was traced against
current code and found either already handled/regression-pinned, or (in two cases)
already correctly identified and closed by a prior audit cycle whose premise this run
independently re-verified rather than re-filing.

This run additionally drove the **real engine headless** against real FO3 GOTY data
for both an interior (`MegatonPlayerHouse`) and a 3×3 Capital Wasteland exterior grid
— both loaded, rendered, and torn down cleanly with no crash, no Vulkan validation
error, and no leaked thread. The exterior run produced the first fresh GPU bench
numbers for FO3 exterior this cycle (ROADMAP has flagged this as pending since
R6a-stale-15): **7 132 entities @ 91.7 wall FPS / 10.91 ms**.

**Delta vs FNV**: The only *functional* FO3-distinctive gap is the **Obscript
scripting runtime** (1 257 SCPT records parse; the disassembler that would execute
them is a designed-for-but-unbuilt later phase) — a known, tracked blocker, not a
bug. Everything else FO3 needs is shared with FNV and green.

**Findings: 1 new (LOW, documentation-only).** Zero CRITICAL / HIGH / MEDIUM. Two
checklist items whose premise this audit found to be stale were traced back to
already-closed issues (#1887, #2086) from a prior `/audit-fo3` cycle — both
confirmed still correctly resolved, cited as "Existing" rather than re-filed. One
minor ROADMAP count-drift noted (informational, not filed).

## Dimension Findings

### Dimension 1 — FO3 Rendering Path (Inline Shaders) · 0 new findings

All checklist items PASS:
- `BSShaderPPLightingProperty`/`BSShaderNoLightingProperty` flag layouts
  (`crates/nif/src/shader_flags.rs`) correctly use the legacy FO3/FNV single-u32-pair
  vocabulary, distinct from Skyrim/FO4/FO76+ layouts, with cross-game bit-collision
  tests pinned (bit 21 Alpha_Decal vs Anisotropic_Lighting, etc.).
- Normal maps resolve from the dedicated `BSShaderTextureSet` slot 1 (same as
  Skyrim), not the Oblivion bump-texture fallback.
- `BSShaderNoLightingProperty` routes through `material_kind = 102` (fullbright,
  post-#c351e0b6) with the flags2 `Alpha_Decal` check intact (post-#454).
- NIFAL single boundary holds: `Material.metalness`/`.roughness` are plain `f32`,
  fed the `f32::NAN` sentinel with no BGSM override, resolved once via
  `Material::resolve_pbr`.
- `EmissiveSource::Material` is the only discriminator the FO3/legacy path sets.
- **Disney-BSDF gate (`MAT_FLAG_PBR_BSDF`) confirmed unreachable for FO3**:
  `ImportedMesh::is_pbr` defaults `false` everywhere and is flipped only inside the
  BGSM/BGEM merge path, which FO3 content never triggers (no `.bgsm`/`.bgem`
  authoring).
- `WaterShaderProperty` routes through `MaterialInfo` for a distinct `GpuMaterial`
  (not collapsed with glass) — **Existing: #1856** (LOW, OPEN) covers the narrower,
  already-tracked gap that `water_shader_flags` itself has no consumer yet on any
  game; re-verified still accurate, not re-filed.

`cargo test -p byroredux-nif --lib material` → 169 passed. `cargo test -p
byroredux-nif --lib shader_flags` → all pass.

#### FO3-D4-NEW-01: `object_lod.rs` module doc still frames the FO3/FNV `.lod` scheme as if it works, contradicting the now-fixed #2086 gate
- **Severity**: LOW
- **Dimension**: FO3 Cell Loading End-to-End
- **Location**: `byroredux/src/cell_loader/object_lod.rs:16-18`
- **Status**: NEW (a completeness-check follow-up flagged inside CLOSED #2086 —
  "SIBLING: object_lod.rs's Skyrim+/FO4 `.bto` path... confirm consistent framing" —
  was left unchecked/undone)
- **Description**: The module doc comment reads: "**Oblivion / FO3 / FNV**: a
  different scheme entirely — per-cell `DistantLOD\*.lod` placement lists instancing
  `_far.nif` meshes, handled by the sibling [`super::placement_lod`] module (#1726)."
  This groups FO3/FNV with Oblivion as if the sibling module actively provides object
  LOD for all three, when #2086 established the sibling module's gate now excludes
  FO3/FNV entirely (zero vanilla `.lod` files exist for those titles) — for FO3/FNV

- **Evidence**: `placement_lod.rs:305-307` (`placement_lod_supported` returns `true`
  only for `GameKind::Oblivion`) vs. `object_lod.rs:16-18`'s comment still listing
  "Oblivion / FO3 / FNV" together with no hedge.
- **Impact**: Documentation-only; no functional bug (the gate itself is correct). A
  future contributor reading `object_lod.rs` first (its module doc is the more
  prominent LOD-scheme overview comment) would incorrectly believe FO3/FNV get
  object LOD via `placement_lod`.
- **Related**: #2086 (closed, left this exact follow-up unchecked).
- **Suggested Fix**: Update the `object_lod.rs` module comment's third bullet to
  note that Oblivion is the only title with real `.lod` content; FO3/FNV fold

## FNV-Shared Surface

FO3 inherits essentially the entire compatibility surface from the FNV-shared code
path with no FO3-only gap found inside it:

- **NIF parser**: identical v20.2.0.7/BSVER-34 block set, identical dispatch table
  (274 arms), identical stream-position guarantees (0 drift across 10 989 real
  files).
- **ESM parser**: identical `crates/plugin/src/esm/` pipeline; FO3's earlier
  authoring conventions (pre-FNV NPC_/DIAL/INFO subforms) parse cleanly through the
  same soft/strict truncation semantics.
- **Shader/material translation**: identical `BSShaderPPLightingProperty`/
  `BSShaderNoLightingProperty` inline-shader path, identical NIFAL single-boundary
  translation, identical Disney-BSDF gate (both games: 0 BGSM authoring, so
  unreachable).
- **Collision**: identical classic `bhk*CollisionObject` → `BhkRigidBody` chain,
  identical motion-type mapping.
- **Cell loading**: identical interior/exterior/streaming code, identical
  `CachedNifImport` LRU cache, identical WTHR→CLMT resolution.
- **Animation/NPC spawn**: identical B-spline/registry/hand-mesh guards.

The two record-format items that diverge inside otherwise-shared code
(XATO/XTNM/XTXR REFR overrides, `.lod` distant-object placement) both turned out to
be **absent from FO3 content entirely** rather than present-but-broken — FO3 simply
doesn't exercise those branches, so there is nothing to regress.

## FO3-Distinctive Gaps

1. **Obscript scripting runtime** — 1 257 SCPT records parse; the bytecode
   disassembler that would make them executable is a designed-for-but-unbuilt later
   phase (`ScriptSource::Obscript`). This is FO3's (and FNV's, and Oblivion's)
   largest functional gap for quest/world interactivity — tracked, not a bug.
2. **Inline-shader-only material universe** — confirmed provably unreachable for
   Disney-BSDF/BGSM paths (verified this session via the `is_pbr` default-false
   trace).
3. **Capital Wasteland worldspace** — confirmed distinct WRLD form ID loads and
   streams correctly via a live 3×3 grid bench this session; no FNV-hardcoded
   name/coord found.
4. **FaceGen**: runtime-recipe model (shared with Oblivion/FNV, distinct from
   Skyrim+/FO4's prebaked-mesh model) — `EsmVariant::has_runtime_facegen_recipe`
   correctly gates this; FO3's `headhuman.egm`/`.egt`/`.tri` are byte-identical to
   FNV's already-tested fixtures.
