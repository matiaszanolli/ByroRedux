### FNV-2026-08-24-D1-01: FNV `WaterKind` vocabulary partially repaired — `creek` added, `spill`/`potomac`/`fountain` still missing

- **Severity**: LOW
- **Dimension**: 1 — Cell Loading End-to-End (WATAL flow classification)
- **Location**: `byroredux/src/material_translate.rs:189-204` (`water_kind_from_name`,
  the shared token classifier `LC-D5-02` asked to be hoisted — now is one function,
  reached by both the CELL/WATR path and the mesh-name path)
- **Status**: Partial fix of `FNV-2026-08-20-D1-02` (that finding's Status was
  NEW and unfiled as a GitHub issue at the time; not found in the current
  200-issue dedup window either)
- **Description**: The 2026-08-20 finding censused all 78 vanilla FNV `WATR`
  EditorIDs and found zero matches against the then-current token list
  (`rapid`/`waterfall`/`falls`/`river`/`stream`), meaning `WaterFlow` was
  unreachable on the reference title even for records FNV itself names as
  moving water (`CreekWater01`, `CreekWater02nv`, `CreekWater02AVGnv`,
  `CreekWater02nvbetter`, `RockCreekEstatesWater`). The suggested fix was
  "add at minimum `creek`, `canal` ... and `spill`."
  Since then `canal` and `creek` were added (now present at
  `material_translate.rs:197-198`) via the `LC-D5-02` shared-token-list
  hoist (`water_kind_from_cell_record_name` now delegates to the same
  `water_kind_from_name` the mesh path uses). This closes the primary
  evidenced case — every `Creek*` FNV water record now classifies `River`.
  `spill` was not added. Re-running the same EditorID roster from the prior
  finding against the current token list: `ToxicSpillPuddle` (0 direct
  `XCWT` refs found previously) and the `Potomac`/`PotomacNRShallow`/
  `DLC03TBPotomacWater` family still classify `Calm` — notably `Potomac`
  (`00030009`) is still the `WRLD` `NAM2` default water for `WastelandNV`
  and nine other worldspaces, so FNV's default exterior water is still
  `Calm`.
- **Evidence**: `grep -n water_kind_from_name -A 15
  byroredux/src/material_translate.rs` shows the current token set is
  `rapid`, `waterfall`/`falls`, `river`/`stream`/`canal`/`creek` — no
  `spill`, `potomac`, or `fountain`.
- **Impact**: Reduced from the prior HIGH-adjacent framing (the `Creek*`
  family — the clearest, most-cited evidence — is now fixed) to a narrow
  residual gap. `ToxicSpillPuddle` is plausibly correctly `Calm` (a puddle,
  not a current); `Potomac` as WastelandNV's worldspace-default water is the
  one item worth another look, since it backs every exterior cell that
  doesn't author its own `XCWT` override.
- **Related**: `FNV-2026-08-20-D1-02` (superseded by this entry — do not
  re-file both), `LC-D5-02` (the token-list unification this fix already
  completed).
- **Suggested Fix**: Add `potomac` (and optionally `spill`) to
  `water_kind_from_name`'s token list if a design decision confirms FNV's
  Potomac River water should carry current; otherwise document the
  `Calm`-by-default classification as intentional rather than leaving it as
  an open question with no test pinning either way.

### FNV-2026-08-24-D4-01: LVLI multi-pick semantics fix (#3217) has no FNV-specific test coverage despite a 229-record blast radius on `FalloutNV.esm`

- **Severity**: LOW
- **Dimension**: 4 — ESM Record Parser (this game's data through the shared
  mechanism)
- **Location**: `crates/plugin/src/equip.rs:343-420` (`expand_leveled_inner`),
  fix commit `1d0c5d4b` ("feat(equip): update flag for item calculation
  method in LVLI"), tracked as `#3217`
- **Status**: NEW
- **Description**: `#3217` changed `multi_pick` from `flags & (0x02 | 0x04)
  != 0` to `flags & 0x04 != 0` — i.e. `LVLF` bit 1 ("calculate for each item
  in count") no longer triggers "select every eligible entry"; only bit 2
  ("Use All") does. The commit's justification and both new/changed tests
  (`expand_leveled_calculate_each_item_still_picks_one_tier`) are entirely
  Skyrim-sourced ("over-equipped 1,491 vanilla Skyrim NPCs"). `expand_
  leveled_inner` is shared, game-agnostic code — FO3/FNV `LVLI` uses the
  identical `LVLD`/`LVLF`/`LVLO` sub-record layout
  (`crates/plugin/src/esm/records/container.rs::parse_leveled_list`).
  A direct byte-level census of `FalloutNV.esm` (2738 `LVLI` records) found
  **229 records** that set bit `0x02`, clear bit `0x04`, and carry entries
  at more than one distinct level — meaning this fix changes their selection
  output from "every eligible tier" to "the single highest eligible tier."
  These are not obscure records: `LeveledNVRangerCivilianOutfitArmor`,
  `LeveledLegionArmorDecanus`, `LeveledLegionArmorRecruitPrime`,
  `LL2WastelanderVipersLeaderArmorNV`/`WeaponNV`, `LootWeaponNCRRangerVeteran`
  (×2), `188NCRArmsMerchantMods`, and nine `VendorAmmo*High/Mid/Low` ladders
  are all in the set.
- **Evidence**: FNV `LVLF` byte histogram over all 2738 `LVLI` records:
  `{4: 528, 0: 445, 3: 1128, 2: 540, 1: 97}` (bit `0x04` alone or in
  combination with bit `0x01` covers most records; the 229-record set is
  bit `0x02`-only or bits `0x01|0x02`, i.e. flag values 2 and 3). Sample:

  ```
  0x17b7de LeveledLegionArmorRecruitPrime 0x3
    entries: (1,975996,1)×4  (9,1307556,1)×4
  0x17b7e1 LeveledNVRangerCivilianOutfitArmor 0x3
    entries: (1,1177723,1) (1,1177724,1) (1,1177725,1) (9,845139,1)
  ```

  Under the pre-#3217 code, an actor at level ≥9 selecting
  `LeveledLegionArmorRecruitPrime` got **both** the level-1 and level-9
  armor form IDs simultaneously (arguably itself a pre-existing bug — two
  armor tiers stacked on one NPC). Under the current code it gets only the
  level-9 tier. This audit could not determine with confidence which
  behavior matches real FO3/FNV engine semantics without GECK-level
  documentation of "calculate for each item in count" — the true mechanic
  is RNG-driven (roll N times against a caller-supplied count this codebase
  does not thread through), so neither the old nor the new deterministic
  approximation is a perfect model. The single-highest-tier read is at
  least self-consistent with "don't stack two armor tiers on one actor."
- **Impact**: Loot/vendor ammo ladders and Legion/NCR outfit bundles change
  shape on FNV NPCs and containers after this fix, unverified against any
  FNV fixture or real-game expectation — pure test-gap risk, not a
  confirmed-wrong behavior.
- **Related**: none filed.
- **Suggested Fix**: Add an FNV-sourced regression fixture (e.g. pin
  `LeveledLegionArmorRecruitPrime`'s current single-highest-tier output, or
  research/confirm the correct GECK-era "calculate for each item" semantics
  against xEdit/OpenMW docs) so a future change to this shared function has
  FNV coverage, not only Skyrim coverage, given the 229-record blast radius.

### FNV-2026-08-24-D2-01: `MAX_MATERIALS` doc comment cites a dead symbol and a stale byte size, in a comment that documents FNV/FO3 material budgets by name

- **Severity**: LOW
- **Dimension**: 2/3 — NIFAL / RT Lighting (material dedup budget)
- **Location**: `crates/renderer/src/vulkan/scene_buffer/constants.rs:173-183`
- **Status**: NEW (doc-rot; violates the Path-Reference Convention's symbol
  rule in `.claude/commands/_audit-common.md` — a backticked symbol
  asserting it exists right now)
- **Description**: The `MAX_MATERIALS` doc comment reads:

  ```rust
  /// Maximum number of unique materials per frame in the
  /// [`super::super::material::MaterialTable`] SSBO. 16384 × 348 B ≈ 5.7 MB
  /// per frame × MAX_FRAMES_IN_FLIGHT (2) ≈ 11.4 MB total — well inside the
  /// 4 GB total VRAM budget (`feedback_vram_baseline.md`). The per-material
  /// size is pinned by `gpu_material_size_is_348_bytes`; it was 300 B until
  /// twelve supplemental texture-role indices landed (`1d94eb24`).
  ///
  /// Observed unique-material counts (post-Disney-PBR; #1248-#1251 added
  /// ior / subsurface / sheen / sheen_tint / anisotropic, each a fresh
  /// dedup-distinguishing axis):
  /// * FNV / FO3 interior cell — 50-200
  /// * FNV / FO3 3×3 exterior grid — 300-600
  ```

  `GpuMaterial` is 364 B today (`crates/renderer/src/vulkan/material.rs:45`,
  pinned by `gpu_material_size_is_364_bytes` at `material.rs:1421`), not
  348 B — it grew again after the "animated-sink draw-path" work (`348 →
  364 B`, `7fbc5baf`, per ROADMAP's Session 71 R6a-stale-20 fold). No test
  named `gpu_material_size_is_348_bytes` exists anywhere in the tree
  (`grep -rn gpu_material_size_is_348_bytes crates/` → zero hits) — the
  comment's own citation is unresolvable. The 16384×348≈5.7 MB /
  11.4 MB-total arithmetic is also stale (16384×364 ≈ 6.0 MB / 11.9 MB
  total — still comfortably inside budget, so no capacity concern, just a
  wrong number in a budget-justification comment).
- **Evidence**: see grep above; `material.rs:45` docstring: "Pinned by
  `gpu_material_size_is_364_bytes`."
- **Impact**: None functional — this is a pure documentation-drift finding
  in a comment that specifically calls out FNV/FO3 material counts by name,
  which is why it is filed under this audit rather than left for a general
  tech-debt sweep.
- **Related**: none filed; same drift class as the `#3047` shader-include
  count example `_audit-common.md` already cites as the reason this rule
  exists.
- **Suggested Fix**: Update the comment to `364 B` / `gpu_material_size_is_
  364_bytes` / recomputed totals (~6.0 MB / ~11.9 MB), or better, drop the
  hardcoded byte arithmetic entirely and reference the pin test by name only
  so a future struct-size change can't strand a wrong number.
