#### Candidates examined and disproved

2. **#6555: `collision_authoring.external = 1` set only by `geometry_only_cached`.**
   - Both the main-thread job and the worker drain (`partial.rs`) build precombine entries through `geometry_only_cached`, so the two routes agree.
   - The only path that would not carry `external` is the walk fallback for a baked-variant `_oc.nif`. Measured: 0 of 176,569 vanilla bakes lack CSG filename hashes. The baked variant is mod-only, and the walk importer emits no meshes for `BsPackedCombinedPayload` (only `Shared` is handled). Such a bake is a zero-mesh entry, `baked_hashes` omits it, and its REFRs are un-skipped. There is no collider consequence.
3. **#6690 shared spawn step.** The old `spawn_mesh_instance` sequence is reproduced in `attach_mesh_components`: LocalBound, WorldBound seed, SceneFlags, billboard, SpeedTreeWind, Parent, Name, Material, `IsFxMesh`, texture handles, water, debug info, roughness/MSN resolvers, markers, and the small-static plus decal layer escalation. `PrecombinedPlacement` still reaches it via `spawn_mesh_instance` with `collision_fallback = ArchitectureTriMesh`. 4. **#6590 registry eviction.** `eviction_rank` is tier 0 for a precombine `_oc.nif` with no clip handle, tier 1 for any other handle-less entry, tier 2 for an entry with a clip handle, oldest tick first. That is exactly the three-sweep policy it replaced. `select_nth_unstable(excess-1)`, then `truncate`, then `sort_unstable` yields the `excess` lowest ranks in eviction order. #### f70d041de `extract_dx10_mips` / 36b55c728 `dx10_layout` review

- Guard `dx10_extract_mip_range_reads_only_tail_chunks` exists and is live. It asserts: same 148-byte header as a full extract; payload equals `full[header + 2048 + 512..]` (tail of full extract); `first_mip` 0 equals `extract` exactly with covered 0; a mid-chunk level keeps the whole spanning chunk (covered 2, len header+184); with head chunks made un-inflatable the full extract errs while the floor extract still succeeds and equals the clean floor (proves head chunks are never read or inflated).
- Header identity is real, not coincidental: `pitch_or_linear_size_for` depends on dxgi/width/height only (BC and uncompressed both), never on `pixel_data.len()`, so the tail header is byte-identical to the full header. `declared_size` still reports the full-chain size, which is correct as an upper bound for a tail read.
- Hostile `first_mip`: it is a `u32` compared against `u32::from(end_mip)`; no arithmetic. `position(..).unwrap_or(len.saturating_sub(1))` then `&chunks[keep_from..]`: `keep_from <= len-1` for non-empty and `0` for empty (a zero-chunk record, `chunks[0..]` on an empty slice is valid, yields a header-only DDS, no panic). `first_mip = u32::MAX` keeps only the last chunk (floor read); documented.
- Hostile chunk offsets / sizes: sizes capped at open (per chunk and per record sum), so `vec![0; n]` in `read_chunk_payload` is bounded; an offset past EOF yields an `UnexpectedEof` error from `read_exact_at`, not a panic. Non-monotonic or inverted `start_mip`/`end_mip` (e.g. `(2,1)`, which the layout test itself builds) only changes which chunks `position` selects; no index can leave the slice. The corrupt-chunk path returns `Err` (guarded by the corrupt-heads test).
- Callers: `extract_texture_floor_or_warn` only calls it for non-cubemap multi-chunk records with `last.start_mip` (derived from the same table); `extract_texture_from_or_warn` guards `first > 0 && dx10_layout().is_some()`. A GNRL entry gets `InvalidInput` (never reached from either caller).
- Candidate disproved (not a finding): the doc comment says chunks are "in mip-0-first order (validated at open)" but open only `warn!`s on a non-monotonic `start_mip` sequence (#1176, deliberately tolerant). Consequence for a repacked archive: a tail read could select a different chunk set than the intent. Not a finding: the archive is already flagged at open, `position` on `end_mip` stays in bounds, and vanilla census is monotonic (the census tool `ba2_mip_chunk_census` came with 36b55c728).
