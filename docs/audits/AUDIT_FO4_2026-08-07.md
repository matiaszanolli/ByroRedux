# FO4 Compatibility Audit — 2026-08-07

Per-game audit of ByroRedux readiness for **Fallout 4** content. 9 dimensions,
run per `.claude/commands/audit-fo4/SKILL.md`. Dimension reports:
`/tmp/audit/fo4/dim_1.md` through `dim_9.md`.

## Executive Summary

FO4 remains one of the more complete game paths. NIF (BSVER 130 + Next-Gen
patch range, half-float vertices, BSTriShape/BSGeometry, inline tangents,
BSSubIndexTriShape) + BA2 (exhaustive `{1,2,3,7,8}` version match, GNRL +
DX10) + the external BGSM/BGEM material parser crate + SCOL/PKIN prefab
expansion + the **M49 CSG precombine pipeline** all remain landed and were
re-confirmed as regression-guard-clean by this sweep, not re-proposed as
missing.

**Parse rate**: `parse_rate_fo4_all_meshes` re-run this session (not cited
from a stale baseline) — **159,866 / 159,866 NIFs clean (100.00%)** across
both vanilla mesh archives (`Fallout4 - Meshes.ba2`: 34,995/34,995;
`Fallout4 - MeshesExtra.ba2`: 124,871/124,871), 0 truncated, 0 failed in
either. Matches the #1457 baseline with no drift since 2026-06-14.

**Headline new finding**: Dimension 6 measured real vanilla-corpus impact on
a previously LOW-triaged, closed issue (**#973**) and found the actual blast
radius is far larger than assessed at closure — 152,084 of 152,086
(99.9987%) vanilla REFRs carrying an `XMSP` material-swap reference never
get that swap applied at spawn time, because the only code path that applies
it requires a co-occurring `XATO`/`XTNM` that vanilla content essentially
never ships. This is reported as **FO4-D6-001 (HIGH)**, recommending #973 be
reopened and relabeled from `low` to `high` rather than filed as a new
issue. Dimension 8 confirmed the same gap applies identically, with no new
interaction, to SCOL/PKIN-expanded synthetic children — cross-referenced
only, not double-counted.

Two MEDIUM findings surfaced in the NIFAL material-translation boundary
(Dimension 7): a Skyrim-era spawn-time roughness heuristic
(`normal_alpha_spec_*`) that lacks a BGSM/`from_bgsm` exclusion and can
overwrite FO4's authored PBR roughness (FO4-D7-01), and BGSM-authored
subsurface/rim data that is parsed but never forwarded into the
now-permanently-live Disney BSDF lobe, which every FO4 BGSM surface now
routes through (FO4-D7-02). A verification gap flagged by dim7 — whether
`ImportedMaterial::default().env_map_scale` makes FO4-D7-01 live or latent —
was checked during merge: the default is `0.0`
(`crates/nif/src/import/types.rs:569`), and nothing in the BGSM merge path
overwrites it (that omission is FO4-D7-03 itself), so the finding's
`env_map_scale <= 0.3` gate condition is satisfied by default for BGSM
content. **FO4-D7-01 is confirmed LIVE, not latent.**

One further MEDIUM (Dimension 2: a REFR-texture-overlay BGSM-fill helper
drops 5 of 11 forwarded texture roles that the primary merge captures) and
one MEDIUM (Dimension 4: the `#621` `data_size`-derived vertex-stride
override can turn a recoverable stride mismatch into a hard whole-mesh parse
failure) round out the MEDIUM tier. All remaining findings are LOW
(doc-rot, hygiene, hardening, and one documented/tracked known gap
re-confirmed present). Dimension 9 (real-data validation) is clean — 0
findings.

**Pending / forward scope** (do not re-propose as new): `_precomb.nif`
collision + `.uvd` occlusion volumes, MOVS physics runtime, FaceGen NIF
truncation tail (confirmed gone, 0 truncated this run), deeper cell coverage
(LIGH power state / CONT leveled items / NPC_ face morph),
`BSBehaviorGraphExtraData` (confirmed parse-only, zero consumers). The CSG
reader, BGSM parser, and SCOL/PKIN expansion are shipped — never list them
as pending.

### Dimension 2 — BGSM/BGEM Consumption + Metalness-from-Chromaticity

**MEDIUM**

- **FO4-D2-2026-08-07-01** — `RefrTextureOverlay::fill_from_bgsm`
  (`byroredux/src/cell_loader/refr.rs:185-225`) forwards only 6 of the 11
  BGSM/BGEM texture roles that `merge_external_material` forwards on the
  primary per-mesh import path — it never reads `specular_texture`,
  `lighting_texture`, `flow_texture`, `wrinkles_texture`, or
  `greyscale_texture` (BGSM), nor `specular_texture`/`lighting_texture`
  (BGEM), and drops the BGEM greyscale-as-LUT forwarding entirely. Its own
  doc comment claims parity with `merge_external_material`'s "first-wins
  policy"; the implementation doesn't deliver that parity for v>2 standalone
  roles. Reachable only when a REFR's XATO/XTNM `TextureSet` is MNAM-only
  (sets `material_path` but none of the 8 classic slots) — an FO4 REFR in
  that shape overlaying a BGSM/BGEM that authors a standalone
  specular/lighting/flow/wrinkle map or a creature/NPC greyscale colour-LUT
  silently loses that role for that specific placement, while the same
  BGSM reached via the ordinary per-mesh import path gets full coverage.
  Cosmetic-only (missing detail/lighting map or NPC colour remap on
  specific overlaid placements), not a crash or invisible-mesh regression.
  *Fix*: extend `RefrTextureOverlay` with the missing fields and forward
  them, or narrow the doc comment's parity claim.

**LOW**

- **FO4-D2-2026-08-07-02** — `fill_from_bgsm` has zero test coverage
  exercising an actual BGSM/BGEM chain: every test in
  `refr_texture_overlay_tests.rs` calls `build_refr_texture_overlay` with
  `mat_provider: None`, so the `fill_from_bgsm` branch is never exercised —
  precisely how FO4-D2-2026-08-07-01 went unnoticed. *Fix*: add a test with
  a real `MaterialProvider` fixture asserting the overlay's texture fields
  populate from the chain.

### Dimension 4 — NIF BSVER 130 + Half-Float Vertices + FO4 Collision

Substantially GREEN. Half-float vertex path is byte-exact against nif.xml
for both `BSVertexData` and `BSVertexDataSSE`, `BSSubIndexTriShape`
segmentation matches nif.xml field-for-field, packed `VF_SKINNED` layout and
renormalization are correct, the `#1242` `FO4_ENV_SCALE`→`FO4_DLC_UPPER`
rename is complete (zero stale references under `crates/`), and both
`BhkMultiSphereShape` and `BhkConvexListShape` produce live `CollisionShape`
values rather than falling to the unsupported-log drop.

**MEDIUM**

- **FO4-D4-02** — The `#621` `data_size`-derived stride override
  (`crates/nif/src/blocks/tri_shape/bs_tri_shape.rs:336-368`) is applied
  unconditionally whenever `(data_size - triangles*6)` divides evenly by
  `num_vertices`, not only in the over-padded direction it was written for.
  When `data_size` is understated-but-divisible, the derived stride can be
  smaller than the attribute set needs, and the `consumed > vertex_size_bytes`
  guard (`:1085-1096`) then hard-errors instead of the pre-#621 degraded
  (misaligned-but-present) geometry — the whole `BSTriShape` is dropped.
  Not observed on vanilla data (100% clean parse rate); exposure is mod
  content / non-vanilla patches. *Fix*: only apply the derived stride when
  `derived >= vertex_size_quads * 4`, or fall back to the descriptor stride
  on the `consumed > vertex_size_bytes` branch when the stride was derived
  rather than continue to `Err`.

**LOW**

- **FO4-D4-01** — The FO4-DLC subsurface/rimlight/backlight gate
  (`crates/nif/src/blocks/shader.rs:1026`) uses a bare `(130..=139)` literal
  instead of the named `(FALLOUT4..FO4_DLC_UPPER)` constants its three
  sibling gates in the same file use. Values are correct today; divergence
  hazard only if the constants ever change. *Fix*: replace with the named
  range.
- **FO4-D4-03** — A third independent copy of `half_to_f32` exists in
  `crates/facegen/src/lib.rs:72`, alongside the canonical
  `crates/nif/src/import/mesh/decode.rs:18` (post-#945 dedup) and its
  `crates/nif/src/blocks/tri_shape/mod.rs:93` re-export. Not covered by the
  canonical decoder's IEEE-754-class test pins. *Fix*: have facegen call the
  canonical `nif` decoder, or hoist it to `byroredux-core`.
- **FO4-D4-04** — `ImportedMesh::bs_sub_index` (FO4 `BSSubIndexTriShape`
  segmentation payload) is parsed, deep-cloned per mesh
  (`crates/nif/src/import/mesh/bs_tri_shape.rs:208-211`), and has **no
  reader anywhere** in the tree. Documented as deliberate (parse-path landed
  ahead of the dismemberment consumer) — coverage note, not a defect, but
  the deep-clone wastes allocations on every FO4 actor mesh import. *Fix*:
  land the consumer, or box the payload behind an `Arc` so the clone is a
  refcount bump.
- **FO4-D4-05** — FO4's primary collision path
  (`bhkNPCollisionObject → bhkPhysicsSystem`/`bhkRagdollSystem`,
  `BhkSystemBinary`) remains an undecoded Havok-serialised blob; collision
  fidelity is proxy-quality via the render-geometry census, not
  authored-quality. Re-confirmed present, already documented (PHYSAL design
  note: "FO4+ blocked on BhkSystemBinary blob") and reflected in the compat
  matrix — informational re-confirmation, not a new gap.

### Dimension 5 — FO4 Shader Flags & BGSM PBR Routing (Disney path)

Four checklist items verified clean: F4SF1 bit 12 / F4SF2 bit 25 correctly
OR'd and gated on `bsver >= FALLOUT4` (the #2091 residual is fixed); decal /
two-sided helpers use the correct FO4 flag-word vocabulary with no
cross-vocabulary leak from the FO3/FNV path; FO4's HairTint (`shader_type ==
6`) routing is correct and structurally distinct from the FO76 type-5
SkinTint/HairTint numbering bug found in the Skyrim audit; `#1244`'s
`BSShaderPropertyBaseOnly` routes through `MaterialInfo`, not a hardcoded
default (and is neutral for FO4 — not reachable from the dedicated FO4
shader path).

**MEDIUM**

- **FO4-D5-01** — A BGSM-authored FO4 material whose `.bgsm` cannot be
  resolved (missing archive, partial `--bsa` args, unarchived mod/DLC path)
  silently falls back to the legacy Lambert + keyword-classifier path
  (`byroredux/src/asset_provider/material.rs:787-807` returns `false` before
  `is_pbr = true` is ever written), with no distinguishing diagnostic
  between "authored non-PBR" and "BGSM lookup failed" — the unresolved-path
  case produces no per-material warning at all, unlike the unknown-extension
  arm. This is the documented failure signature behind the "chrome/posterized
  FO4 surface" bug class. *Fix*: emit `unresolved_material_warning`-class
  telemetry on the resolve-failure arm, and consider treating a `.bgsm`-path
  reference as itself sufficient evidence of authored-PBR intent regardless
  of resolution success.

**LOW**

- **FO4-D5-02** — The HairTint (`material_kind == 6`) consumer defaults to
  black albedo (`[0.0;3]`) when `hair_tint_color` is missing, unlike its
  SkinTint sibling's safe identity default; FO4 does not currently trip this
  (see clean check V3), so this is hardening rather than a live defect.
  *Fix*: default to `[1.0,1.0,1.0]`.
- **FO4-D5-03** — BSVER 131 (`FO4_SHADER_GAP`) content carries zero shader
  flags by format design, but the `bsver >= FALLOUT4` consumer gate reads as
  active for that band regardless — every flag-derived signal
  (`Double_Sided`, `Decal`, `Model_Space_Normals`, `Alpha_Test`, etc.) is
  unconditionally false with no diagnostic. BGSM-merge coverage masks this
  for vanilla content; exposure is inline/modded BSVER-131 NIFs with no
  `.bgsm`. *Fix*: a comment note or `debug!` breadcrumb.
- **FO4-D5-04** — The fire-refraction override in
  `crates/nif/src/import/material/dedicated_shader.rs:328-358`
  unconditionally overwrites the `shader_type`-derived `material_kind`
  (SkinTint/HairTint/ParallaxOcc/etc.) when F4SF1 bits 15+16 are both set,
  losing the variant branch entirely for that combination. Not observed in
  vanilla FO4 authoring. Secondary hygiene nit: the mask is built from
  `skyrim_slsf1::` constants applied to an FO4 property (numerically
  identical, but violates the module's own "caller must know which
  vocabulary it holds" rule — the exact pattern that produced #414).
- **FO4-D5-05** — BSVER 140–154 forces `shader_type = 0`, which
  `parse_shader_type_data_fo4` maps to `ShaderTypeData::None` — no
  SkinTint/HairTint/ParallaxOcc/MultiLayerParallax/SparkleSnow/EyeEnvmap
  payload can ever be produced in that band. Documented as a dead band with
  no shipping game; would matter only for hypothetical FO4-era modded
  content at 140+, with no current diagnostic if it appeared.

One open, non-asserted research item: the `BSShaderTextureSet` slot map
(`dedicated_shader.rs:89-206`) applies one slot layout to every game era,
branching on `shader_type` not `bsver`; nif.xml documents only one slot map
and the code matches it, so there is no spec basis to claim FO4 divergence —
logged for research, not filed as a bug, per the no-guessing policy.

**HIGH**

- **FO4-D6-001** — `RefrTextureOverlay.material_swaps`
  (`byroredux/src/cell_loader/refr.rs:76`), the resolved per-REFR MSWP
  substitution table, is computed correctly at overlay-build time
  (`refr.rs:307`) but has **zero production consumers**:
  `spawn.rs::resolve_mesh_paths` (the function that actually walks each
  placed NIF's shapes and resolves per-shape material paths,
  `spawn.rs:1084-1088`) reads `ov.material_path` and
  `mesh.material.material_path` but never `ov.material_swaps`. **Status:
  Existing #973** (closed 2026-05-24 as LOW, framed as "at most one shape
  gets swapped" on multi-shape REFRs) — not a regression, the code hasn't
  changed since closure, but a real-data probe run this session
  (`XMSP total=152086 with_xato_or_xtnm=2 alone=152084`) shows the eager
  single-shape substitution path that #971 landed only ever fires when a
  REFR's `material_path` is *already* set by a co-occurring XATO/XTNM — true
  for 2 of 152,086 vanilla XMSP-bearing REFRs. For the other 152,084
  (99.9987%), the resolved swap table is built, cloned onto the overlay, and
  discarded unread. **Real-world impact is not a multi-shape edge case; it
  is effectively the entire vanilla MSWP feature** — Raider armor color
  variants, settlement clutter recolors, vehicle rust patterns, Vault decay
  overlays — rendering with unswapped base materials.
  **Recommendation: reopen #973 and relabel its severity from `low` to
  `high`**, rather than filing a new issue; #973's own suggested fix shape
  (thread `ov.material_swaps` + `MaterialSwapRecord.path_filter` into
  `spawn.rs::resolve_mesh_paths`'s per-shape resolution loop) remains valid,
  only the priority framing needs to change.

### Dimension 7 — NIFAL Canonical Material Translation (FO4 is PBR-canonical)

The NIFAL material boundary itself is in good shape: `translate_material`
is genuinely the single `ImportedMesh → Material` site (two production call
sites, no surviving verbatim struct literals, raw-tier field reads at exact
parity between the cell-spawn and loose-NIF paths); the BGSM `PBR_BSDF` flag

contract holds (plain `f32`, NaN seed, single clamp in `resolve_pbr`, no
render-time re-classify, idempotence pinned by tests); glass classification

*Dedup note*: the source dim7 report flagged its own dedup pass against
`/tmp/audit/issues.json` as incomplete. Checked during merge: no open issue
title-matches on `subsurface`/`rim`/`sheen`/`anisotropic`/`env_map_scale`/
`environment_mapping_mask_scale`/`BGSM_AUTHORED`/`particles.rs`/
`normal_alpha`/`material_translate` beyond **#2330** (OPEN, LOW,

*Verification-gap resolution*: dim7 flagged that FO4-D7-01's live-vs-latent

`env_map_scale <= 0.3`, the default of `0.0` satisfies it. **FO4-D7-01 is
confirmed LIVE**, not latent.

**MEDIUM**

- **FO4-D7-01** — `normal_alpha_spec_applies`/`resolve_normal_alpha_spec_roughness`
  (`byroredux/src/material_translate.rs:256-372`, called from both spawn
  paths) has no `from_bgsm`/`BGSM_AUTHORED` exclusion. A BGSM material that
  ships a normal map, authors no `smooth_spec_texture`
  (`gloss_map_index == 0`), and reads dielectric under the chromaticity
  metalness rule (`metalness < 0.3` — includes white-spec steel, a
  documented under-read) re-enters this Skyrim-era roughness derivation at
  spawn and has its already-resolved canonical roughness overwritten: the
  `normal_has_alpha == true` arm mostly coincides with the authored value
  but with a narrower clamp band (`[0.05,0.95]` vs the authored `[0.04,1.0]`,
  silently losing fully-smooth/fully-rough BGSMs); the far more common FO4
  case (`normal_has_alpha == false` — BC5 two-channel normals have no
  alpha) falls to a `specular_mult`-keyed guess in `[0.4, 0.85]` that has no
  contractual roughness meaning in BGSM, e.g. a polished `smoothness = 0.9`
  surface (authored roughness 0.10) becomes 0.75. Confirmed LIVE per the
  verification-gap resolution above. *Fix*: add a `from_bgsm`/
  `BGSM_AUTHORED` early-out so authored FO4/Starfield PBR roughness is never
  re-derived; keep the heuristic for the inline-shader Gamebryo/Skyrim
  population it was written for.
- **FO4-D7-02** — BGSM's subsurface/rim-lighting suite
  (`crates/bgsm/src/bgsm.rs:57-61`: `rim_lighting`, `rim_power`,
  `subsurface_lighting`, `subsurface_lighting_rolloff`) is parsed but never
  forwarded by `merge_external_material` onto `ImportedMaterial` (which has
  matching `subsurface_rolloff`/`rimlight_power` slots, filled only from the
  NIF-native `BSLightingShaderProperty` path, #2284). `translate_material`
  therefore always copies zeros, and `render/static_meshes.rs` hardcodes
  `subsurface: 0.0` / `sheen: 0.0` / `sheen_tint: 0.0` / `anisotropic: 0.0`
  regardless. This specifically matters for FO4 because `MAT_FLAG_PBR_BSDF`
  is now set unconditionally for every BGSM material (#1352) — the Disney
  lobe is live for all FO4 architecture but permanently fed the degenerate
  parameterization, and BGSM is the one format in the corpus that actually
  authors these parameters. *Fix*: forward `subsurface_lighting_rolloff`/
  `rim_power` (gated on their enable bools) in the BGSM merge arm, and
  source the draw-builder's `subsurface`/`sheen` from `Material` instead of
  literal zeros.

**LOW**

- **FO4-D7-03** — BGSM's `environment_mapping_mask_scale`
  (`crates/bgsm/src/base.rs:120-121`) is parsed and dropped — the merge only
  forwards the env-map *textures*, not the scale. `Material.env_map_scale`
  for FO4 content therefore always carries the NIF shader property's value
  (typically 0.0, since FO4 NIFs generally defer this to the BGSM), which is
  load-bearing for two downstream gates (FO4-D7-01's heuristic and
  `classify_pbr_keyword`'s `env_map_scale` arm). Same drop-at-boundary class
  as FO4-D7-02, weaker rendering consequence.
- **FO4-D7-04** — `BGSM_AUTHORED` is set identically on both the BGSM and
  BGEM merge arms, but only the BGSM arm actually writes
  `metalness_override`/`roughness_override`; the BGEM arm sets `from_bgsm`
  with both overrides left `None` by design (falls to the keyword
  classifier). Any future consumer reading `BGSM_AUTHORED` as "PBR scalars
  are authored, don't re-derive" — exactly the shape of the FO4-D7-01 fix —
  would be wrong on BGEM content. *Fix*: split the bit, or gate on
  `metalness_override.is_some()` instead of `from_bgsm`.
- **FO4-D7-05** — `byroredux/src/render/particles.rs:234` hardcodes
  `effect_shader_flags: 0` on emitted particle `DrawCommand`s instead of
  sourcing it from the emitter's canonical `Material`, dropping a BGEM
  particle effect's palette-remap, `EFFECT_SOFT`, `EFFECT_LIT`, and
  `PBR_BSDF` bits at the last hop after `translate_material` correctly
  packed them. LOW — particle shading is largely `material_kind`-driven
  today — but a genuine canonical-value drop at a non-boundary site.
