## 3. Findings

### MEDIUM

### UI-D1-2026-10-17-01: The #5719 ceiling only gates the shim's own inflate; every other decode path still honours the header's `u32` (up to ~4 GiB)
- **Severity**: MEDIUM (defence-in-depth gap on untrusted archive content; the fix as closed does not deliver its stated guarantee)
- **Dimension**: Profile, Prepare & Host Bridge Transport (also Resource Navigator, dependency path)
- **Profile**: both (it hits whatever CWS movie is opened)
- **Location**: `crates/ui/src/prepare.rs` (`decompress_zlib_after_header_capped`, `MAX_SWF_BODY_BYTES` at `:120`; `prepare_movie`, `swf::decompress_swf(swf_data)` at `:290`); `crates/ui/src/navigator.rs` (`prepare_import_asset_swf` ~`:585-590`, `import_asset_paths` ~`:530-532`); `crates/ui/src/profile.rs:25`; `crates/ui/src/avm2_host.rs:79`, `:372`; `crates/ui/src/avm1_host.rs:122`; `crates/ui/src/player.rs` (`SwfMovieData::from_data`)
- **Status**: Regression of #5719 (closed by `d601b45ab` as LOW; the fix is incomplete). Related open #5480. Orchestrator re-read `prepare_movie`: after `normalize_scaleform_dialect` returns `None` it falls back to the original bytes and calls `swf::decompress_swf` on them; the raw call sites above were confirmed by grep.
- **Description**: The new ceiling returns `None` from the shim when the header claims more than 128 MiB, and its doc says `None` hands the movie to the stock loader. The stock loader has no such cap: `swf::decompress_swf` (ruffle `2edfd97d`, `swf/src/read.rs:72`) does `decompress_stream.take(body_len as u64).read_to_end(...)` with `body_len` from the header's own `u32`; `MAX_DATA_CAPACITY` only limits the pre-allocation. So a CWS header claiming `u32::MAX` over a small zlib bomb is "declined" by the shim and then inflated to the claimed size on the next line, and Ruffle's `from_data` decodes it again. On the dependency path `load_archive_resource` calls `prepare_import_asset_swf` first, which runs `swf::decompress_swf` on the raw bytes and never sees the shim or its ceiling; `import_asset_paths` then runs it again after the shim declines. ZWS (LZMA) has the same exposure. The tests pin the shim in isolation (`cws_header_claiming_u32_max_over_a_bomb_is_declined` calls `decompress_zlib_after_header` directly), so they pass while the load path stays unbounded.
- **Evidence** (measured with a scratch crate against the same pinned `swf` rev, outside the repo): a CWS header with length `u32::MAX` over a 1,042,919 B zlib body (1 GiB of zeros) goes through plain `swf::decompress_swf` as `Ok`, `data.len()` = 1,073,741,819 B, in 0.62 s, peak RSS 1.1 GB. Scaling to the header's 4 GiB claim is arithmetic, not measured. Corpus context: the largest shipped movie measured here is 17,139,629 B (Skyrim `fonts_cn.swf`), so 128 MiB is ~7.8x headroom; the documented FO76 `fonts_zhhant.swf` (65,902,267 B) was not verified (FO76 not installed).
- **Impact**: A crafted movie in a user-installed or mod interface archive can still force a multi-GiB allocation (potentially a process abort) when a menu or HUD opens. The 128 MiB constant looks like a bound but bounds only the shim's own, redundant buffer. Needs a malicious archive, hence MEDIUM rather than HIGH.
- **Related**: #5719 (closed, incomplete), #5480 (open: the dependency path hands Ruffle un-normalised bytes), #5456, `/audit-parsers`, `/audit-safety`.
- **Suggested Fix**: Add one shared pre-check, "container header declared length <= `MAX_SWF_BODY_BYTES`", for CWS, ZWS and FWS. Call it at the top of `prepare_movie`, `prepare_import_asset_swf`, `import_asset_paths`, `ScaleformProfile::detect`, `avm2_host.rs` and `referenced_host_methods`, and before any `SwfMovieData::from_data`. Make an over-ceiling claim a hard `Err` (a recorded degraded dependency on the import path) rather than a `None` fall-through. Add a `prepare_movie`-level test with the bomb and `u32::MAX`.

### LOW

### UI-D1-2026-10-17-02: `SwfDecodeCounts::decompresses` is a hard-coded literal and no `prepare_movie` test feeds a CWS movie
- **Severity**: LOW (test-fidelity gap; the code is correct by reading)
- **Dimension**: Profile, Prepare & Host Bridge Transport
- **Profile**: both
- **Location**: `crates/ui/src/prepare.rs:310` and `:338` (`decompresses: 1` literals); tests at `:402`, `:430`
- **Status**: NEW (adjacent to closed #5479)
- **Description**: Both `prepare_movie` return arms construct `SwfDecodeCounts { decompresses: 1, .. }` unconditionally; the comment at `:259` says it "measures the real work". The three `SwfDecodeCounts` guards build movies with `swf::write_swf` (uncompressed FWS) and assert the literal against itself. The only CWS pin is `conforming_cws_returns_its_decode_with_an_untouched_body`, which tests the shim in isolation, not `prepare_movie`. Nothing turns red if a stage re-inflates raw CWS bytes (the #5479 shape), or if the shim declines and the stock decode runs (which inflates twice while still reporting 1). Shipped content is CWS: 51 of 53 Skyrim and 311 of 311 FO4 interface movies.
- **Impact**: The documented single-decode floor is not machine-checked on the compressed path that matters.
- **Related**: #5479, UI-D1-2026-10-17-01
- **Suggested Fix**: Add a `prepare_movie` test over a real zlib-compressed AVM2 and AVM1 movie asserting `prepared.data` starts with `FWS`; derive `decompresses` from whether the shim returned `Some` for a CWS input, or count through a wrapped reader, instead of a literal.

### UI-D6-2026-10-17-01: `ExplicitStartPin::release` fires before the loading-cover, bench-harness and modal-UI input quarantines
- **Severity**: LOW
- **Dimension**: Engine Wiring & Input Routing
- **Profile**: n/a (matters for Skyrim-style Start Game Enabled quests)
- **Location**: `byroredux/src/app_events.rs:347-395` (`window_event`; release at `:362-365`, quarantines at `:366` and `:379`); `byroredux/src/components/explicit_start.rs:1-20`
- **Status**: NEW (`c1c5e8d8c`, 2026-10-13; no open or closed issue mentions it). Orchestrator re-read the block and confirmed the order.
- **Description**: The pin is documented as held "until the player takes control (the first key or mouse press)", and a benchmark or debug-server session "never presses a window key". The release sits at the top of `window_event`, before the `loading_screen.active()` return (which discards key and mouse input) and before the `harness_owns_input` return (whose own comment says matrix runs create focus-stealing windows and a coincident press must not act). So any pressed key or mouse button releases the pin, including presses the loading cover discards, presses the bench harness quarantines, and presses that egui, the F3 overlay or a native page (pause, inventory, barter, message box) consumes, none of which is the player taking control.
- **Evidence**: `window_event` order at HEAD: `Focused(false)` handling -> `ExplicitStartPin::release` on a pressed key / mouse -> `loading_screen.active()` return -> `harness_owns_input` return -> egui forward -> modal / overlay handling. `step_player_move_request` (`app_step.rs`, ~`:911`) reads `ExplicitStartPin::active`. Not reproduced (no engine launched): reachability on a real Skyrim `--cell` launch is unconfirmed.
- **Impact**: A stray press during a bench or a loading cover, or a key used only to dismiss a modal, can let the first MQ101 start-up `MoveTo` run and relocate a player who launched with `--cell` / `--grid`; a bench's world state is then no longer the one the harness measures. Narrow: Skyrim-class start quests plus an explicit location, first scripted move only.
- **Related**: `bench::harness_owns_input`, the #5409 modal teardown family.
- **Suggested Fix**: Move the release below the loading-cover, bench, egui and modal-surface early returns (for example into the existing world-input arms for `KeyboardInput` / `MouseInput`, after `route_scaleform_window_event`); add a source-order test next to `bench_camera_startup_order_tests`.
