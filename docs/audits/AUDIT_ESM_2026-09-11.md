### HIGH

#### ESM-2026-09-11-D6-01: companion-strings language token is still hardcoded `"english"` — FO4/FO76/Starfield ship `_en` and resolve nothing

- **Severity**: HIGH
- **Dimension**: Localized Strings
- **Record / Sub-record**: every lstring site (`FULL`/`DESC`/`NAM1`/`CNAM`/`NNAM`/`BPTN`/…)
- **Location**: `byroredux/src/cell_loader/load_order.rs:533-534`; consumed at `crates/plugin/src/esm/strings_table.rs:242-251`
- **Status**: Existing — filed originally as ESM-D6-02 (`AUDIT_ESM_2026-08-13.md:829`), carried as ESM-2026-09-09-D6-01, re-confirmed unchanged at HEAD by direct source re-read (not by issue absence — no GitHub issue exists for this specific item in the cached window).
- **Description**: `load_order.rs` builds the companion-file language segment from one literal, `"english"` (overridable only via `BYRO_STRINGS_LANG`). Skyrim SE's tables are named `<stem>_english.STRINGS`; every Creation-Engine title from Fallout 4 onward instead ships a two-letter ISO tag (`_en`, `_de`, `_ja`, `_ptbr`, `_zhhans`, `_zhhant`). There is no alias table and no per-game mapping anywhere in the tree.
- **Evidence**:
  ```rust
  // byroredux/src/cell_loader/load_order.rs:533-534
  let strings_language =
      std::env::var("BYRO_STRINGS_LANG").unwrap_or_else(|_| "english".to_string());
  ```
  ```rust
  // crates/plugin/src/esm/strings_table.rs:242-251 — exactly one candidate name, then give up
  let mut load_file = |ext: &str, has_prefix: bool| -> Option<StringsTable> {
      let name = format!("{stem}_{language}.{ext}");
      let path = strings_dir.join(&name);
      let (data, source) = match std::fs::read(&path) {
          Ok(data) => (data, path.display().to_string()),
          Err(_) => {
              let archive_path = format!(r"strings\{name}");
              (read_archive(&archive_path)?, archive_path)
          }
      };
  ```
  Measured archive contents confirm the discovery half is fine and only the language
  segment is wrong: `Fallout4 - Interface.ba2` holds `strings\fallout4_en.strings` etc.
  (35 `strings\` files, zero containing `"english"`); `Starfield - Localization.ba2`
  holds `strings\starfield_en.*`; `SeventySix - Localization.ba2` holds
  `strings\seventysix_en.*`/`nw_en.*`. Test coverage still only exercises the Skyrim
  spelling (`load_order.rs:921,949`); no FO4/Starfield-spelled fixture exists anywhere.
- **Impact**: On Fallout 4, Fallout 76 and Starfield, every localized field is
  `<lstring 0xNNNNNNNN>` — cell display names, NPC names, item names, book/terminal/
  message text, quest log entries. This is the single largest localization defect in
  the dimension by blast radius (three of four modern titles, every lstring field).
- **Related**: CLOSED #2912 (fixed the loose-file-vs-archive discovery half); ESM-2026-09-11-D6-05 shares the "one literal candidate" shape.
- **Suggested Fix**: Replace the single literal with a small per-game (or per-plugin) candidate list — try the two-letter tag first, fall back to the long English spelling — and log which candidate hit. A one-line alias table (`english`⇄`en`, `german`⇄`de`, …) covers all six shipped languages.

#### ESM-2026-09-11-D4-01: FO4/Starfield `INFO` `TRDA` still has no segment-opening arm

- **Severity**: MEDIUM
- **Dimension**: Record Schema Dispatch (with Dimension 2 byte-accounting consequences)
- **Record / Sub-record**: `INFO` / `TRDA` (vs `TRDT`), `NAM1`, `NAM2`
- **Location**: `crates/plugin/src/esm/records/misc/dialogue.rs:196-232`
- **Status**: Existing: **#4068** (OPEN). Re-verified against current code, not against issue absence — `git log` shows no commit touching `misc/dialogue.rs` since `1da0ebad` (2026-09-06, the original #3616/#3614 fix); this session's dense same-day commit run touched an adjacent DIAL-label remap bug (#4079) in `grup_walker.rs` but not this file.
- **Description**: `misc/dialogue.rs`'s segment state machine still recognizes only `TRDT` as the per-segment opener (`NAM1`/`NAM2` write into `current_response.get_or_insert_with(Default::default)`; only the `TRDT` arm calls `.take()` to push a finished segment). FO4 (20-byte `TRDA` payload, 74,996 occurrences) and Starfield (12-byte `TRDA`, 130,284 occurrences) have no `TRDA` arm at all, so every repeated `NAM1` on those two titles overwrites the same lazily-created segment — the pre-#3616 behaviour, confined to the two newest titles.
- **Evidence**: `grep -rn 'TRDA' crates byroredux docs` → matches only inside audit report markdown, zero in any `.rs` source file.
- **Impact**: `crates/scripting/src/dialogue.rs` (the live consumer) sees `responses.len() <= 1`, `emotion_type == 0`, `response_number == 0` on every FO4/Starfield `INFO` record with more than one authored segment — a combined 16,552+ records affected, 24,199+ authored response segments discarded.
- **Related**: #4068 (OPEN), #3616, #3614; `/audit-scripting` Dim 7 owns the consumer.
- **Suggested Fix**: (1) zero-risk, layout-free: add `TRDA` to the segment-opening arm alongside `TRDT`, recovering all discarded segments immediately. (2) Separately, once a cited FO4/Starfield `TRDA` layout is in hand, decode its emotion/response-number fields.

#### ESM-2026-09-11-D5-01: `PlacedRef.group_type` is still `6` for every real placement — #3728/#4077's premise fix didn't touch the sibling bug

- **Severity**: MEDIUM
- **Dimension**: CELL / WRLD Walkers & Placement Data
- **Record / Sub-record**: CELL/WRLD child GRUPs 6/8/9/10 — `REFR`/`ACHR`/`ACRE`/`PGRE`/`PHZD`/`PMIS`
- **Location**: `crates/plugin/src/esm/cell/walkers.rs:161-177,702-738`; `crates/plugin/src/esm/cell/wrld.rs:276-329`; `crates/plugin/src/esm/cell/mod.rs:391-406,320-322`; `crates/plugin/src/esm/cell/tests/cell.rs:198-199`
- **Status**: Regression of #3728 (CLOSED) — same finding as `AUDIT_ESM_2026-09-09.md` ESM-2026-09-09-D5-01, re-verified still present at HEAD today. Not superseded by `6c3584ec`/#4077, which fixed the *topology* premise (a related but distinct bug, tracked below as fixed) in the immediately neighbouring code, but left this bug and its stale legend comments untouched.
- **Description**: `parse_refr_group_inner` receives `group_type` once, at the point the outer 6/8/9 container group is entered, and threads that same value **unchanged** through its own nested-group recursion without ever re-reading `sub.group_type`. Real Bethesda content always nests 8 (Persistent) / 9 (Temporary) / 10 (Visible Distant) *inside* a type-6 "Cell Children" container — never as its direct sibling — so every placement in every shipped master is stamped `group_type = 6`, discarding exactly the persistent/temporary/visible-distant distinction #3728 was filed to add.
- **Evidence**: `walkers.rs:711-716`'s comment still documents the bug as intended behaviour ("Fixed for the entire recursion … threaded unchanged (unlike `depth`, which increments)"); the recursive call at `:728-738` passes `group_type` straight through. The regression fixture (`tests/cell.rs:198-199`) still builds two direct CELL children (type 6 and type 8 as siblings) — a shape that occurs zero times in any shipped master, which is why the test stays green while the bug stays live. No live consumer exists yet (`grep -rn '\.group_type'` outside walker/reader/tests finds only two `0xFF`-sentinel test fixtures).
- **Impact**: A field that looks authoritative, is guarded by a green but unrepresentative test, and is uniformly wrong. It will silently misinform the first streaming-residency or save-restore consumer that reads it.
- **Related**: #3728 (closed, inert fix), `AUDIT_ESM_2026-08-30.md`/`AUDIT_ESM_2026-09-09.md` D5-01 (original + most recent prior write-up), #4077/`6c3584ec` (fixed the neighbouring false-topology premise but not this bug).
- **Suggested Fix**: Re-derive `group_type` at each nested group inside `parse_refr_group_inner` — when `sub.group_type` is 8/9/10, pass that value into the recursive call instead of the inherited one. Correct the legend at the four remaining sites (see ESM-2026-09-11-D5-02) and rebuild the test fixture as CELL → GRUP 6 → {GRUP 8, GRUP 9, GRUP 10}, the only nesting shape the real corpus contains.

#### ESM-2026-09-11-D6-03: `.STRINGS` family is still decoded via `String::from_utf8_lossy`, corrupting real cp1252 content

- **Severity**: MEDIUM
- **Dimension**: Localized Strings
- **Record / Sub-record**: `FULL`/`DESC`/`NAM1` (any lstring-bearing field)
- **Location**: `crates/plugin/src/esm/strings_table.rs:155,161`
- **Status**: Existing — ESM-D6-03 (`AUDIT_ESM_2026-08-13.md`), re-confirmed live at HEAD. No GitHub issue exists for it.
- **Description**: Both the prefixed and non-prefixed decode arms call `String::from_utf8_lossy`. Bethesda's companion files are Windows-1252; any byte in `0x80..=0xFF` that isn't a valid UTF-8 continuation becomes U+FFFD. Measured corrupting real English content: 75 FO4 + 228 Starfield entries with U+FFFD (curly apostrophes, ellipses, RobCo glitch-art characters); 0/67,414 on Skyrim.
- **Evidence**: both decode arms (`:151-161`) call `from_utf8_lossy` with no cp1252 mapping anywhere in the file.
- **Impact**: Latent behind D6-01 today for FO4/FO76/Starfield (nothing resolves there yet), but becomes immediately visible the moment the language-token fix lands — every apostrophe-bearing name would render with a replacement-character glyph, reading as a *new* bug introduced by that fix.
- **Related**: ESM-2026-09-11-D6-01 (fixing that exposes this).
- **Suggested Fix**: Decode with a cp1252→`char` mapping instead of `from_utf8_lossy`; optionally probe UTF-8 first and fall back for genuinely-UTF-8 community tables.

- **Dimension**: Localized Strings
- **Record / Sub-record**: `TERM` — `ANAM`, `DNAM`, `MNAM` (wrongly read); `ITXT`, `BTXT`, `RNAM` (never read)
- **Location**: `crates/plugin/src/esm/records/misc/world.rs:1504-1541`
- **Status**: Existing — ESM-D6-07 (`AUDIT_ESM_2026-08-13.md`, FO4-only), extended with FNV evidence in `AUDIT_ESM_2026-09-09.md`. Re-confirmed unchanged at HEAD.

#### D3-NEW-01: `CommonNamedFields::from_subs` (identity-remap) is still callable and used by ~40 production parsers

- **Severity**: LOW
- **Dimension**: FormID Remap, Load Order & ESL Space
- **Record / Sub-record**: `SCRI`/`VMAD` (via the shared `CommonNamedFields` decoder)

- **Status**: NEW (not filed under any existing issue found in the cached issue list)
- **Description**: `CommonNamedFields::from_subs(subs)` is a thin wrapper over `from_subs_with_remap(subs, &None)` — it silently discards whatever real `FormIdRemap` the calling parser has in scope.
