## Findings

### ECS-2026-09-21-D7-01: `PickedUp` lands on the placement root, but both render skips test only the mesh entity, so a picked-up or tombstone-restored item keeps drawing
- **Severity**: MEDIUM
- **Dimension**: 7 (Component Lifecycles: marker placement vs consumer granularity)
- **Location**: `byroredux/src/inventory.rs:913-915` (producer), `byroredux/src/cell_loader/reference_state.rs:221` (re-stamp on respawn); consumers `byroredux/src/render/static_meshes.rs:320,415`, `byroredux/src/render/skinned.rs:86,104`
- **Status**: NEW. #4536 (closed) added the two-site lockstep tests. Its tests insert the marker on the mesh entity, so they do not exercise the production insert site. The same-week renderer audit rated this skip "sound" (REN-D9-02).
- **Description**: `pickup_loot` only accepts a `target` that carries `SceneAliasCandidate`
  (`inventory.rs:894-899`). Only `stamp_quest_reference(world, placement_root, …)` puts that
  component on a placed item (`cell_loader/references/synth_child.rs:832`), so `target` is the
  placement root. The placement root never carries a `MeshHandle` (`spawn_placement_root`,
  `cell_loader/spawn.rs:898-1040`). Every mesh is its own entity with `Parent(placement_root)`
  (`cell_loader/spawn/mesh_instance.rs:619,629`). Both render passes run
  `picked_up.get(entity)` on the mesh or skinned entity itself, and neither looks at ancestors.
  The marker is therefore never seen by the only code that reads it for hiding.
  - The sibling marker `NpcAppearanceHidden` avoids this deliberately: its producer walks the
    subtree (`mesh_entities_under` / `set_hidden`, `npc_spawn/loot_appearance.rs:105-131`),
    "because consumed by the render passes per mesh entity".
  - The guard tests do not cover the production path. `picked_up_placements_stay_hidden_even_when_animation_says_visible`
    (`render/static_mesh_fx_skip_tests.rs:118`) and `picked_up_body_gets_its_first_skin_upload_only_when_dropped`
    (`render/bone_palette_overflow_tests.rs:57`) insert `PickedUp` on the mesh directly.
  - No test drives `pickup_loot` on a root that has a child mesh.
- **Evidence**:
  ```rust
  // inventory.rs:913 — target is the SceneAliasCandidate carrier = placement root
  if let Some(mut markers) = world.query_mut::<PickedUp>() {
      markers.insert(target, PickedUp);
  }
  // static_meshes.rs:415 — entity is the MeshHandle entity (a child of that root)
  || picked_up.as_ref().is_some_and(|q| q.get(entity).is_some())
  ```
- **Impact**: after `script.activate <root>` or a scripted `Activate()` on a loose item, the item
  goes into the inventory and interaction ignores it. Its meshes stay in the raster pass and the
  TLAS, and its colliders stay too. After an eviction or reload the tombstone re-stamps the new
  root, and the item reappears the same way. Reachability is limited today because loose items are
  not E-key interaction candidates (`populate_candidates` has no pickup arm), so this is MEDIUM
  rather than HIGH.
- **Related**: #4536, REN-D9-02 (`AUDIT_RENDERER_2026-09-20.md`), #3319 (the same "marker that
  silently does nothing" class). Owner overlap: `/audit-gameplay` (pickup) and `/audit-renderer`
  (skip sites).
- **Suggested Fix**: stamp the render-hiding marker on every mesh under the root, the way
  `set_hidden` does for `NpcAppearanceHidden`. Do this in both `pickup_loot` and
  `reference_state::restore`, and keep `PickedUp` on the root for interaction and capture. Add a
  test that goes through `pickup_loot` on a root with a child mesh and asserts `build_render_data`
  drops the mesh.

### ECS-2026-09-21-D3-01: the new `apply_placed_water_type` subtree walk skips both cycle guards, and three older walks have the same shape
- **Severity**: LOW (defence in depth; no live code path builds a cycle)
- **Dimension**: 3 (hierarchy walks: `HierarchyTraversalGuard` rule)
- **Location**: `byroredux/src/cell_loader/water.rs:731-749` (new, `ec9ed8524`, 2026-09-14); siblings `byroredux/src/ragdoll.rs:629-653` and `:673-718` (both inside `ragdoll_writeback_system`, run every frame while a ragdoll is active), `byroredux/src/anim_convert.rs:21-54` (`build_subtree_name_map`)
- **Status**: NEW. #3700's fix covered only the three core walks.
- **Description**: the skill's rule is "A new hierarchy walk without it, or without a visited set,
  is an unbounded-loop hazard". The Skyrim river-activator path added this walk:
  `let mut stack = vec![placement_root]; while let Some(entity) = stack.pop() { … stack.extend(kids.0.iter().copied()); }`.
  It has no `seen` set and no `HierarchyTraversalGuard`. Contrast `loot_appearance.rs::mesh_entities_under`,
  added two days later with a visited set. Save load still does no acyclicity check
  (`crates/save/src/validate.rs::validate_hierarchy` only checks that Parent and Children agree,
  plus dangling ids). A corrupt save therefore remains the cycle source #3700 named for the
  per-frame ragdoll walks.
- **Impact**: on a cyclic Children graph, each of these walks loops forever and its stack or queue
  grows until OOM, with no diagnostic. A duplicated Children edge re-walks the subtree, and in the
  water case it pushes duplicate `(entity, WaterPlane)` targets. The water walk runs over a freshly
  spawned subtree, so its hazard is theoretical.
- **Suggested Fix**: bound all four walks with
  `HierarchyTraversalGuard::new(world.next_entity_id() as usize, child_refs)` or a visited set.
  Optionally, add the acyclicity check to `validate_hierarchy`.

### ECS-2026-09-21-D5-01: `every_parallel_system_declares_everything_it_acquires` ignores read vs write and matches names by substring
- **Severity**: LOW (test gap; the live schedule is clean)
- **Dimension**: 5 (declared-access guard)
- **Location**: `byroredux/src/boot/schedule/mod.rs:616-640` (`acquired_in` records type names only), `:702` (`declared.contains(*ty)` over the raw registration block text)
- **Status**: NEW. #4064 (closed) was about which systems the table covers, not how it compares them.
- **Description**: the guard is the mechanical backing for the boot RELEASE assertion
  `known_conflict_count() == 0`. It has three blind spots:
  - **Mode**: it checks only that a type name appears somewhere in the `add_to_with_access(...)`
    block. A parallel system that takes `query_mut::<T>` / `resource_mut::<T>` while declaring only
    `.reads::<T>()` passes. `analyze_pair` then treats a real write as a read, and a same-stage
    reader pairs as non-conflicting.
  - **Substring**: `Transform` is satisfied by `GlobalTransform`.
  - **Comments**: the block includes comment lines. Take the skill's own precedent `ac1d44f5c`. If
    early.rs dropped only `.writes::<GlobalTransform>()`, the adjacent comment
    "`fly_camera_system` publishes its pose to `GlobalTransform`" would keep the test green.
- **Evidence**: `types.push(short)` at :638 carries no mode. At :702,
  `types.iter().filter(|ty| !declared.contains(*ty))` runs where `declared = declaration(system)`
  is the balanced-paren block text. A mode-aware re-implementation (exact names, read/write,
  `get`/`has`/`query_2_mut`/`resource_2_mut` forms, same-file callees to depth 3) finds
  **0 undeclared and 0 write-declared-as-read** across all 9 parallel systems at HEAD.
- **Impact**: none live. The next write-for-read slip in a parallel body ships green, with the
  soundness proof silently void.
- **Suggested Fix**: have `acquired_in` return `(type, mode)`, parse the
  `.reads/.writes/.reads_resource/.writes_resource::<…>` calls (with comments stripped) into exact
  short-name sets, and require write-mode acquisitions to appear in the write set.

### ECS-2026-09-21-D5-02: declared `Access` rows of five exclusive systems omit types their own bodies acquire
- **Severity**: LOW (exclusives are never paired; this affects `sys.accesses` diagnostics and the basis for promoting a system to a parallel lane)
- **Dimension**: 5 (declared access)
- **Location**: `byroredux/src/boot/schedule/update.rs:107-` (`interaction_system`), `:145-` (`container_loot_system`), `:164-` (`combat_input_system`), `:194-` (`npc_combat_ai_system`); `byroredux/src/boot/schedule/late.rs:191-` (`reconcile_pending_dead_actors_system`)
- **Status**: NEW. Precedents: #3951 and #3275, both LOW.
- **Description**: update.rs:102-105 states that the P2 declarations "cover the system body and
  the helpers it calls directly". A body scan says otherwise:
  - `combat_input_system`: `MeleeState` is read and written in its own body (`combat.rs:153`,
    `:184`). It has been undeclared since #3709's split (2026-09-03). `CreatureAttack`
    (`attack_damage`) is also missing.
  - `interaction_system`: `PhysicsSourceForm` (`interaction.rs:1070`).
  - `container_loot_system` (new, 09-19): writes `PickedUp` (`pickup_loot`), and reads `Owned` and
    `FactionRanks` (`transfer_is_theft`).
  - `npc_combat_ai_system` (new, 09-13): reads `WalkSpeed` (`combat_ai.rs:111`).
  - `reconcile_pending_dead_actors_system`: reads `AnimationTarget` (`combat.rs:556`), before the
    ragdoll activation that its scope comment excludes.

  The same comment says that activation's "own physics surface is declared by
  `ragdoll_writeback_system`". But `late.rs:121` registers that system with plain `add_exclusive`,
  so the surface is declared nowhere. Only `papyrus_provider_system` and
  `legacy_obscript_load_order_system` have a completeness test (#3951).
- **Impact**: `sys.accesses` understates the hold set of the newest gameplay systems, and any
  future promotion to a parallel lane would start from an incomplete declaration.
- **Suggested Fix**: add the missing types, correct the ragdoll sentence (or declare
  `ragdoll_writeback_system`), and run `assert_declares_everything_it_acquires` over the declared
  P2 exclusives as well.
