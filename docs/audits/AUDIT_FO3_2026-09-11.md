# FO3 Compatibility Audit — 2026-09-11

**Scope**: ByroRedux readiness for Fallout 3, focused on the FO3-vs-FNV
**divergences** (FO3 rides the FNV path almost end-to-end — same NIF era
v20.2.0.7/BSVER 34, same BSA v104, same ESM parser, same cell loader, same
RT lighting). This is not a re-run of `/audit-fnv`; it hunts where FO3
content exercises a path FNV doesn't, where shared code carries an
FNV-only assumption, and where a feature verified on FNV is only *assumed*
on FO3.

**Dimensions run**: all 7 (1 rendering/inline-shaders, 2 NIF parser block
subset, 3 ESM record coverage, 4 cell loading end-to-end, 5 collision
import, 6 BSA v104 + real-data validation, 7 animation/NPC-spawn +
scripting gap). Dimensions 4 and 5 were carried over from a prior run of
this audit that crashed mid-session; both scratch files were reviewed in
full before reuse and found sound (real source citations, real corpus
numbers, no fabrication). Dimensions 1, 2, 3, 6, 7 were run fresh this
session.

**Real data used**: `/mnt/data/SteamLibrary/steamapps/common/Fallout 3 goty/Data/`
(base game + all 5 DLCs — Anchorage, BrokenSteel, PointLookout, ThePitt,
Zeta). Every dimension either ran real tooling against this install or
cross-referenced a same-session dimension that did.

**Dedup baseline**: `gh issue list --repo matiaszanolli/ByroRedux --limit 200`
(`/tmp/audit/issues.json`), cross-checked per-dimension.

---

## Executive Summary

**FO3 compatibility is high and the shared FNV surface holds up well under
targeted probing.** Of 7 dimensions, 3 came back with zero findings after
real verification (ESM record coverage, cell loading end-to-end, BSA +
real-data validation), and the remaining 4 surfaced only MEDIUM/LOW issues
— **no CRITICAL or HIGH finding** in this audit. Several checklist items
that could plausibly have regressed (SCPT SCHR u16 flags, XATO/XTNM/XTXR
absence, `havok_motion_type` full-enum mapping, `placement_lod`
Oblivion-only gating, B-spline reachability) were independently
re-measured against the live GOTY install rather than assumed, and all
held.

The nine findings below are all forward-looking correctness gaps in
otherwise-working paths: an authored particle-azimuth field that's decoded
but never forwarded (3/4 of FO3's particle emitters), a texture-precedence
inversion that can re-open the Oblivion bump-map path on mixed-property
FO3/FNV shapes, an unfilled window/eye env-mapping signal, two decoded
shader fields with no consumer, and — the one finding with a real
corruption vector — an ungated B-spline **rotation** sample that can
produce a NaN quaternion on the animation-decode path that carries 83% of
FO3's `.kf` corpus.

**Delta vs FNV**: nothing found here is unique to FO3's byte layout — FO3
and FNV are confirmed to share `NPC_`/`DIAL`/`INFO` subforms byte-for-byte,
`CELL.XCLL`/`RCLR`, the WRLD/CLMT/WTHR chain, and the object-LOD scheme
(via `GameKind::Fallout3NV`). The MEDIUM/LOW findings below are *reachable*
on FO3 (measured against FO3 corpora specifically) but the code paths are
shared with FNV — a fix benefits both titles, and a regression would hit
both.

## Dimension Findings

### Dimension 1 — FO3 Rendering Path (Inline Shaders)
**Verdict**: 3 findings (1 MEDIUM, 2 LOW). Ten checklist items (C1–C10)
verified clean with cited evidence: legacy two-`u32` flag layout (not the
FO4 pair), decal-bit mapping on both legacy shader blocks, two-sided
correctly sourced from `NiStencilProperty` (not the FO3 flag word),
alpha-test correctly gated by `NiAlphaProperty`, `NoLighting` fullbright
route with no distance term, single NIFAL boundary with plain-`f32` PBR
scalars, correct `EmissiveSource::Material` with no Skyrim/FO4 bleed,

routed away from the glass/dedup path.

#### FO3-D1-2026-09-11-01: `NiTexturingProperty` outranks the FO3 `BSShaderTextureSet` for base + normal textures, re-opening the Oblivion bump-slot path
- **Severity**: MEDIUM
- **Location**: `crates/nif/src/import/material/legacy_properties.rs:73-88` (dispatch order), `:179-191`, `:405-417`
- **Status**: NEW
- **Description**: `apply_legacy_property_chain` runs `apply_texturing_property` before `apply_pp_lighting_property`; both texture writers are first-writer-wins (`if info.texture_path.is_none()` / `if info.normal_map.is_none()`). On any FO3/FNV shape carrying both a `NiTexturingProperty` and a `BSShaderPPLightingProperty`, the legacy chain's diffuse/normal-or-bump wins and the shader's own `BSShaderTextureSet` slots 0/1 are discarded. The `bump_texture` fallback is explicitly Oblivion-era and carries no game/BSVER gate.
- **Evidence**: dispatch order at `legacy_properties.rs:78-88`; the file's own #3517 note documents the mixed-family exposure ("FNV ships 58,706 `BSShaderPPLightingProperty` and 3,018 `NiTexturingProperty`"). `texture_clamp_mode`/`env_map_scale` got `_consumed` latches for this exact precedence problem (#2328/#3516/#3517); `texture_path`/`normal_map` did not.
- **Impact**: On any FO3/FNV shape binding both property families, material sampling uses the wrong diffuse/normal slot, potentially with wrong normal-map encoding (bump vs tangent-space). Blast radius unmeasured (no per-shape corpus census run) — hence MEDIUM, not HIGH.
- **Related**: #3517, #2328, #131, #208.
- **Suggested Fix**: Latch `texture_path`/`normal_map` per-source like the scalar fields, or reorder so `apply_pp_lighting_property` runs first on FO3+; gate the Oblivion `bump_texture` fallback on `TextureSlotLayout`/BSVER.

#### FO3-D1-2026-09-11-02: `Window_Environment_Mapping`/`Eye_Environment_Mapping` decoded but never reach the glass classifier
- **Severity**: LOW
- **Location**: `crates/nif/src/import/material/legacy_properties.rs:19-30`, `crates/nif/src/shader_flags.rs:36-40`, `byroredux/src/material_translate.rs:649-666`
- **Status**: NEW
- **Description**: Both flags are parsed and only feed `env_map_scale`'s on/off decision; `classify_glass_into_material` never receives them, so window glass with a non-keyword-matching filename is misclassified as opaque dielectric instead of glass.
- **Impact**: Visual only, partially masked by filename-keyword classification.
- **Suggested Fix**: Carry `window_env_mapping: bool` through `MaterialInfo`/`ImportedMaterial` as an additional positive signal into `classify_glass_into_material`.

#### FO3-D1-2026-09-11-03: three FO3 shader-flag bits decode with no sink (`External_Emittance`, F2 `Wireframe`, F2 `Premult_Alpha`)
- **Severity**: LOW
- **Location**: `crates/nif/src/shader_flags.rs:33-84`, `crates/nif/src/import/material/legacy_properties.rs:386-670`
- **Status**: NEW
- **Impact**: Small, bounded — alternative sources exist for wireframe/premult-alpha; `External_Emittance` affects a handful of cell-lit emissive surfaces.
- **Suggested Fix**: No action required now; documented for the next auditor.

#### FO3-2026-09-11-D2-01: authored emitter azimuth (`planar_angle`/`planar_angle_variation`) decoded, finite-checked, never forwarded — 319/422 FO3 emitters spawn a full ring where the file authors a wedge
- **Severity**: MEDIUM
- **Location**: decoded at `crates/nif/src/blocks/particle.rs:94-95`; finite-swept but not copied at `crates/nif/src/import/walk/emitter.rs:315-325` (`ImportedEmitterParams` ctor) vs `:418-419` (sweep); consumer `byroredux/src/systems/particle.rs:477-481`
- **Status**: NEW. Distinct from CLOSED #1445 (which only fixed the finite-sweep half); the forwarding half was never filed. The 2026-06-14 FO3 report scored this LOW as "inert" — that premise is disproved by the census below.
- **Description**: `nif.xml` defines `Planar Angle`/`Planar Angle Variation` as the emission cone's azimuth mean/spread. Decoded, but `extract_emitter_params` only reads them to reject NaN and drops both before constructing `ImportedEmitterParams`. The spawn loop hardcodes a uniform `phi = rng() * TAU` draw.
- **Evidence**: census over all 422 `NiPSysEmitter` blocks (162 meshes) in `Fallout - Meshes.bsa`: 386/422 (91.5%) author a sub-circle azimuth window; **319/422 (75.6%)** additionally author non-trivial declination spread, i.e. azimuth is geometrically observable; 12 author a non-zero mean. Real examples: `meshes\mps\mpsspitattack.nif` (var=π), `meshes\effects\ambient\fxambdust01.nif` (var=0.377), Paradise Falls signage, underwater explosion FX.
- **Impact**: Three-quarters of FO3's authored emitters emit omnidirectionally where the file specifies a directional fan — spit/spray attacks, steam vents, directional dust, sign sparks, and `meshes\mps\` weapon-impact FX (highest-frequency combat particle content). Per `_audit-severity.md`'s "translatable block silently dropped by NIFAL" row, MEDIUM floor; not escalated because the emitter still renders, only misdirected.
- **Related**: #1445 (closed, finite-sweep half only), #1402, `docs/engine/nifal.md`.
- **Suggested Fix**: Add both fields to `ImportedEmitterParams`/`ParticleEmitter`, forward in `extract_emitter_params`, bias the spawn draw to `phi = planar_angle + (rng()-0.5) * planar_angle_variation`, default variation to `TAU` for unauthored emitters to preserve today's behavior exactly where nothing was authored.

#### FO3-2026-09-11-D2-02: `BSShaderPPLightingProperty.refraction_fire_period` decoded, zero consumers workspace-wide

#### FO3-2026-09-11-D7-01: B-spline **sampled rotation** arm has no finite guard; a NaN quaternion is reachable from inputs that pass `channel_slice`'s gate
- **Severity**: MEDIUM
- **Location**: `crates/nif/src/anim/bspline.rs:371-401` (the gap), vs `:341-349`/`:404-416` (the two sibling arms that ARE guarded), and `:511-544` (`channel_slice`, whose docstring incorrectly claims to be the sufficient single choke point for all four callers)
- **Status**: NEW — this is the rotation half that CLOSED #3765 (`SAFE-2026-08-30-D9-01`) left uncovered; #3765 fixed translation, scale, and the scalar float channel, but never covered rotation. Not a regression.
- **Description**: `channel_slice` validates `offset`/`half_range` as individually finite via `is_key_value_sane`, but `dequant` computes `offset + (raw/32767) * half_range`, whose *result* is unbounded by that check. For the translation/scale/float arms, #3765 added a post-sample `is_key_value_sane` check; the rotation arm relies instead on quaternion normalization to absorb a bad sample — but normalization converts an overflowed (inf) component into NaN rather than catching it, and the `len_sq > f32::EPSILON` guard is *satisfied* by `inf` (only pure-NaN inputs fail that check), so the NaN key is pushed unconditionally.
- **Evidence**: with `offset = half_range = 2.9e38` (both individually pass `is_key_value_sane`) and `raw = 32767`: `dequant` overflows to `inf` (2.9e38 + 2.9e38 > f32::MAX), `len_sq` → `inf`, `inv = 1/sqrt(inf)` → `0.0`, `w = inf * 0.0` → `NaN`. All four quaternion components become NaN and are pushed to `rotation_keys` with no downstream filter — the NaN propagates through `TransformChannel` → `AnimationClip` → `sample_blended_transform` into `Transform`, the bone palette, and TLAS refit.
- **Impact**: A NaN bone rotation collapses the mesh to nothing and poisons the per-entity skinned BLAS refit — exactly the blast radius #3765 itself named. Requires a corrupt or hostile `.kf`/`.nif` (vanilla quantization parameters are small) — same threat model #3765 was accepted under — but the exposure is real on FO3 specifically: B-splines decode 83.4% of the FO3 `.kf` corpus, so this is the primary animation path, not a rare arm, and it's the only one of the four sampled channels where the failure is silent (siblings drop the bad key and interpolate across the gap; this one doesn't).
- **Related**: #3765 (CLOSED, siblings only), #1443 (`is_key_value_sane` introduction), #772 (FLT_MAX pose-fallback family — correctly gated separately, not affected).
- **Suggested Fix**: Gate the sampled quaternion the same way its siblings are gated — check `[w,x,y,z]` (or pre-normalization `p`) with `is_key_value_sane` and skip the key on failure so the sampler interpolates from finite neighbors. Alternatively, move the finiteness check into `dequantize_channel` itself so `channel_slice`'s "single choke point for all four callers" docstring claim becomes true.

**Scripting gap (recorded, not filed)**: FO3's 1,257 SCPT records still have
no real executing gameplay runtime. Mechanism correction to the skill's
framing: FO3 *does* reach a live compile path via preserved `SCTX` source
text (dialect-independent — 8,716 raw `SCTX` tags against 1,258 `SCPT`),
so the absent `ObscriptDialect` is not what blocks it. What actually blocks
it is `LegacyObscriptCall`'s two-arm vocabulary (`LoadOrder`/`Extension`
only — no arm for any vanilla ObScript function) combined with an
all-or-nothing statement parser that rejects the whole program on one
unrecognized statement. This remains a known blocker for FO3 quest/world
interactivity, owned by `/audit-scripting`, not a bug filed here.

Confirmed shared with FNV, with FO3 riding the same code path (verified,
not assumed) and no FO3-only gap found inside:

- NIF v20.2.0.7 parser: dispatch table, `BSShaderPPLightingProperty`/

  arm).

  hand-mesh load.
