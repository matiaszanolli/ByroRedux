## Findings

### SAFE-2026-10-19-01: two new ECS lock-order inversions turn the ABBA detector lane red
- **Severity**: HIGH — `_audit-severity` Special Rules: "ECS deadlock potential → HIGH minimum". **Latent at runtime today**: both systems are registered `add_exclusive` (see Impact), so no production schedule runs either beside another system. The severity follows the table and the detector's own verdict ("Threads acquiring these locks in these orders will deadlock"), not an observed hang.
- **Dimension**: Dim 3 adjacent. The shared severity table lists ECS deadlock potential as HIGH. Owner for the fix is `/audit-concurrency` (Dim 2, lock ordering).
- **Location**:
  - `byroredux/src/systems/head_look.rs:36-49` (`find_head`): `let names = world.query::<Name>()?;` is held for the whole traversal, then `world.get::<Children>(entity)` is taken inside the loop (`:43`).
  - `byroredux/src/systems/magic_shader.rs:23-35` (`mesh_entities`) called from `magic_shader_tint_system` at `:62-66` **inside** `let Some(materials) = world.query::<Material>()`: `mesh_entities` takes `Children` (`:30`) and a second same-thread read on `Material` (`world.has::<Material>`, `:27`) while the outer `Material` read guard is live.
- **Status**: NEW. Both from `d1b298921` (2026-10-18, "Implement new ObScript features and state management"). Not in the open list; #6003 is a different pair (`StoryManagerNodeState <-> QuestStageState`). The 10-17 scripting audit predates the commit.
- **Description**: The tracker (`crates/core/src/ecs/lock_tracker.rs`, `global_order::record_and_check`) records process-wide acquisition orders and aborts when a new edge closes a cycle. The established orders in this binary are `Children → Name` and `Children → Material`: for example `byroredux/src/anim_convert.rs:40-41` takes `children_q` before `name_q`. The two new systems take the pairs the other way round (`Name → Children`, `Material → Children`), so the graph contains both directions and the detector panics the owning test.
- **Evidence**: CI job 118240323405 (run 39305200056) and a local reproduction:
  ```
  BYRO_LOCK_ORDER_CHECK=1 cargo test -p byroredux --bin byroredux
  test systems::head_look::tests::the_head_turns_toward_the_target_within_the_necks_range ... FAILED
  test systems::magic_shader::tests::a_playing_shader_lights_the_meshes_and_gives_them_back ... FAILED
  ECS cross-thread deadlock risk (lock-order cycle): attempted acquisition of `…hierarchy::Children` while holding `…name::Name` … `Children → Name → Children`
  ECS cross-thread deadlock risk (lock-order cycle): attempted acquisition of `…hierarchy::Children` while holding `…material::Material` …
  test result: FAILED. 3033 passed; 2 failed; 63 ignored
  ```
  Registration: `boot/schedule/update.rs:620` (`add_exclusive(Stage::Update, magic_shader_tint_system)`) and `:841` (`add_exclusive(Stage::Update, head_look_system)`).
- **Impact**: At runtime today none: an exclusive system runs alone, so no second thread can hold the opposite order. The cost is (1) the lane is red, and a lane that is red on a known cycle is exactly what masked the FormIdPool and #4546 cycles for 18 days (#4603), so a *real* new cycle in a parallel system would be hidden; (2) moving either system into the parallel batch later reintroduces a true ABBA (a structural writer on `Children` or `Name` against these readers); (3) `magic_shader_tint_system` also re-acquires `Material` read while its own `materials` read guard is live — a same-thread recursive read that std/parking_lot `RwLock` documents as able to deadlock when a writer queues between the two reads.
- **Disproof attempted**: Checked whether the inversion was a tracker false positive from the test-only `World`. It is not: the production callers are the same functions, and the opposing `Children → Name` edge comes from production code (`anim_convert.rs`), not a fixture. Checked the schedule: both systems are exclusive, which is why the severity note says latent. The local run reproduces the CI result with the exact CI command shape (`BYRO_LOCK_ORDER_CHECK=1`).
- **Related**: #313 / #2675 (tracker design), #4603 (lane-blinding precedent), #5535 (the sixth red, fixed 2026-10-12), #6003 (separate open cycle). Both failing tests also fail in the `cf1a234d0` run.
- **Suggested Fix**: In `find_head`, read each node's `Name` through a transient `world.get::<Name>(entity)` (or collect the subtree first with `byroredux_core::ecs::collect_subtree`, then take the `Name` query). In `magic_shader_tint_system`, call `mesh_entities(world, owner)` **before** taking `world.query::<Material>()`, then look the materials up in a second pass; `mesh_entities` should use no guard that outlives its own loop iteration.

### SAFE-2026-10-19-02: `ShadowFilterPipeline` destroys possibly-pending images on a `MaybeInFlight` failure
- **Severity**: LOW. The trigger is `vkWaitForFences` failing with an out-of-memory error after a successful submit, which no normal run produces; `ERROR_DEVICE_LOST` is spec-safe. Same class and severity as closed #5947 (the #4891 policy, `OneTimeCommandError::may_be_in_flight`).
- **Dimension**: Dim 3 (drop ordering) / Dim 5 (VUID class #4891 / #5201 / #5270).
- **Location**:
  - `crates/renderer/src/vulkan/shadow_filter.rs:91-96` (`new`): any `new_inner` error, including the one from `initialize_layouts` (`:179` → `with_one_time_commands`, `:262-283`), runs `partial.destroy(...)` unconditionally; the SAFETY comment says "nothing created so far has been submitted", which is false for the `MaybeInFlight` arm.
  - `crates/renderer/src/vulkan/context/resize.rs:717-740` (the resize recreate): on `Err` it calls `filter.destroy(...)` under the comment "the resize path waited both frames in flight", which covers frame work but not the pending one-time layout submit.
- **Status**: NEW. The pass first landed in `ee0ba7069` (2026-10-15, a commit whose message describes docs; it added the 449-line file, the shader and the `r.shadowfilter` command). #5947 fixed this exact pattern for volumetrics only (`context/init.rs:1100-1108` and `context/resize.rs:962-975` now consult `may_be_in_flight` and `mem::forget`).
- **Description**: The one-time command buffer clears nothing, but it transitions the filter's six images (ratio A, ratio B and correction, per frame in flight) UNDEFINED → GENERAL. If the submit succeeded and the fence wait failed, the transition may still be executing against the images that `destroy` frees, which is VUID-vkDestroyImage-image-01000 territory. The other passes avoid the bug by a different route: on a failed `initialize_layouts` they log and keep running (`taa.rs:818`, `svgf.rs:1431`, `caustic.rs:1190`), so they never free in that arm. The shadow filter is the first one that frees.
- **Evidence**: no `may_be_in_flight` reference in `shadow_filter.rs` (grep: none); `ShadowFilterPipeline::new` and `recreate_on_resize` both propagate a bare `?` from `initialize_layouts` into a destroying caller.
- **Disproof attempted**: Checked that `GpuImage::destroy` is the only free path (it is) and that `with_one_time_commands` leaks its own fence and command buffer on the same arm (it does, per its comment at `texture.rs:933-960`), so the caller is the only party that would free live-referenced memory. The window is real but needs a fault injection.
- **Suggested Fix**: Mirror `init.rs:1100-1112`: `std::mem::forget` the pipeline (or its image set) when `OneTimeCommandError::may_be_in_flight(&e)`, destroy otherwise, in both `new` and the resize arm; pin it with the same source-scan style used for `cloud_noise.rs`.
