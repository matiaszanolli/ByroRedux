# Fallout 4 Compatibility Audit — 2026-08-16

**Scope**: all 9 `/audit-fo4` dimensions, plus two cross-sweep leads routed here
by the `comprehensive` audit-suite orchestrator (FO4 WEAP decode; `slot_to_role`
per-game gating).

**Game data**: `/mnt/data/SteamLibrary/steamapps/common/Fallout 4/Data/`
(`Fallout4.esm` 330,776,415 B; `Fallout4 - Meshes.ba2`; `Fallout4 - MeshesExtra.ba2`).

**Method note**: no engine instance was launched. All findings are static
analysis plus direct measurement over vanilla on-disk data — a standalone Python
ESM walker (GRUP recursion, `0x00040000` zlib record decompression, `XXXX`
sub-record size override) and a throwaway `crates/nif` example run against both
mesh archives and then deleted. Record field order is taken from **xEdit
`dev-4.1.6` `Core/wbDefinitionsFO4.pas`**, retrieved via `gh api`, and every
offset asserted below is independently validated against shipped bytes. Offsets
that could not be confirmed are called out as unconfirmed rather than asserted.

## Executive Summary

The FO4 **rendering and geometry** path is in good shape and every shipped
regression pin still holds: the M49 CSG precombine pipeline, the BA2 exhaustive
version match, the BGSM metalness-from-chromaticity rule (#1476), the
identity-narrowing blend-factor pass-through (#1823), both FO4 collision arms,
SCOL/PKIN expansion, and the `BSConnectPoint` attach-graph spawn. Both vanilla
mesh archives parse **159,866 / 159,866 = 100.00%** clean, re-measured this
session.

The problems are in two places the audit's shipped-feature framing did not
cover:

1. **The FO4 item-record family is systematically mis-bucketed into the FO3/FNV
   parser arms.** WEAP is the worst case — Fallout 4 emits **no `DATA`
   sub-record on WEAP at all**, so all 252 vanilla weapons decode to damage 0 /
   value 0 / weight 0 / clip 0, which is now live in the P2 combat and inventory
   slice. But it is not alone: ARMO reads **weight and health swapped**, AMMO
   reads its 8-byte `DATA` through a 13-byte FO3/FNV layout, and BOOK reads an
   8-byte `DATA` through a 10-byte one. This report supplies the complete,
   byte-validated 132-byte WEAP `DNAM` layout so the fix does not have to guess.

2. **The 2026-08-14 texture-role unification collapsed the per-game slot tables
   into one table measured on Skyrim, and FO4 is where its rules break.** The
   premise that this "only bites inline/loose/modded NIFs" is false: measured
   across 810,489 vanilla `BSLightingShaderProperty` blocks, **zero** are
   material-reference stubs, so the shared table is a fully live FO4 path. Three
   of its arms are wrong on FO4 — most seriously, slot 3 carries a
   greyscale-to-palette gradient on FO4 (not a height field) and is routed into
   the POM parallax role on 31,303 properties.

**Total findings: 8** — 3 HIGH, 5 MEDIUM, 0 CRITICAL, 0 LOW.

### FO4-D6-2026-08-16-01: Every Fallout 4 weapon decodes to all-zero stats — the 132-byte `DNAM` is never read

- **Severity**: HIGH
- **Dimension**: 6 — ESM item records
- **Location**: `crates/plugin/src/esm/records/items.rs:166-234` (the `b"DATA"`
  and `b"DNAM"` arms of `parse_weap`)
- **Status**: NEW
- **Description**: `parse_weap` folds `GameKind::Fallout4` into the
  `GameKind::Fallout3NV` arm of the `b"DATA"` match, and gates the `b"DNAM"` arm
  on `matches!(game, GameKind::Fallout3NV)` alone. Fallout 4 emits **no `DATA`
  sub-record on WEAP** — its entire weapon stat block is a 132-byte `DNAM`.
  Neither arm ever executes, so `common.value`, `common.weight`, `damage`,
  `clip_size` and `anim_type` all fall through to their zero initializers on
  every FO4 weapon. The parser's own comment acknowledges the mis-bucketing
  ("FO4 groups here pending its own per-game arm") but the referenced follow-up
  never landed.
- **Evidence** — measured, `Fallout4.esm`:
  ```
  WEAP records          252
  with a DATA sub-record  0
  with a DNAM sub-record 252   (all exactly 132 bytes)
  ```
  The xEdit `wbStruct(DNAM, 'Data', …)` for FO4 WEAP sums to **exactly 132
  bytes**, matching the measured length on 252/252. It is a packed, unaligned
  struct:

  | Off | Type | Field | | Off | Type | Field |
  |---|---|---|---|---|---|---|
  | 0 | u32 | Ammo (`AMMO`\|NULL) | | 69 | u32 | Sound Level |
  | 4 | f32 | Speed | | 73 | u32 | Sound - Attack (`SNDR`) |
  | 8 | f32 | Reload Speed | | 77 | u32 | Sound - Attack 2D |
  | 12 | f32 | Reach | | 81 | u32 | Sound - Attack Loop |
  | 16 | f32 | Min Range | | 85 | u32 | Sound - Attack Fail |
  | 20 | f32 | Max Range | | 89 | u32 | Sound - Idle |
  | 24 | f32 | Attack Delay | | 93 | u32 | Sound - Equip |
  | 28 | f32 | Unused | | 97 | u32 | Sound - UnEquip |
  | 32 | f32 | Damage - OutOfRange Mult | | 101 | u32 | Sound - Fast Equip |
  | 36 | u32 | On Hit (enum) | | 105 | u8 | Accuracy Bonus |
  | 40 | u32 | Skill (`AVIF`\|NULL) | | 106 | f32 | Animation Attack Seconds |
  | 44 | u32 | Resist (`AVIF`\|NULL) | | 110 | `[2]` | *unknown* |
  | 48 | u32 | Flags | | 112 | f32 | Action Point Cost |
  | 52 | u16 | Capacity | | 116 | f32 | Full Power Seconds |
  | 54 | u8 | Animation Type | | 120 | f32 | Min Power Per Shot |
  | 55 | f32 | Damage - Secondary | | 124 | u32 | Stagger (enum) |
  | 59 | f32 | **Weight** | | 128 | `[4]` | *unknown* |
  | 63 | u32 | **Value** | | | | |
  | 67 | u16 | **Damage - Base** | | | | |

  Three independent validations, none of them inference:

  1. **FormID membership against the real tables in the same file.** At exactly
     these offsets, offset 0 is `0` or a genuine `AMMO` FormID on **252/252**,
     and the eight `SNDR` slots at 73…105 are `0` or a genuine `SNDR` FormID on
     **2016/2016**. A misalignment control re-running the same membership test
     shifted by −4/−2/−1/+1/+2/+4 bytes fails in every case (154 / 723 / 425 /
     698 / 890 / 239 bad). Only the xEdit offsets are clean.
  2. **A semantic anchor independent of any published stat table.** The VR
     shooting-range clones author their damage as `base + 1000`, and offset 67
     reproduces that relationship exactly across the whole family: 10mm
     18→1018, Combat Rifle 33→1033, Combat Shotgun 50→1050, Missile Launcher
     15→1015, Minigun 8→1008.
  3. **Cross-check of known vanilla values.** `10mm` reads damage 18 / weight 3
     / value 45 / capacity 12 / AP 28 / anim 9 (`Gun`); `Fatman` weight 30 /
     value 500 / capacity 1 / AP 60 (the highest in the game); `BaseballBat`
     damage 16 / weight 3 / anim 5 (`TwoHandSword`) / reach 0.8;
     `Switchblade` damage 8 / weight 1 / anim 1 (`OneHandSword`).

  **Explicitly unconfirmed** (do not encode these as semantics): offsets 110
  `[2]` and 128 `[4]` are byte-constant across all 252 records (`0x0000` and
  `ff ff 7f 7f`), so nothing about their meaning is observable from this corpus
  — xEdit likewise calls both `wbByteArray('Unknown')`. Offsets 40 and 44
  (Skill / Resist `AVIF`) are `0` on 100% of vanilla, so their position is
  supported only by the fields bracketing them, not by a non-zero payload.
- **Impact**: All 252 FO4 weapons carry damage 0, value 0, weight 0, clip 0.
  This is live in the P2 gameplay slice, not latent:
  `byroredux/src/inventory.rs:224` (`prefer_weapon`) and
  `byroredux/src/npc_spawn.rs:782` both select the equipped weapon by "highest
  base damage, then lowest FormID"; with damage uniformly zero the rule
  degenerates to lowest-FormID, so *which* weapon an FO4 actor equips is
  arbitrary. `byroredux/src/combat.rs:269` (`attack_damage`) then reads
  `EquippedWeapon.damage` and clamps with `.max(0.0)` → **0.0**, so an armed FO4
  actor deals strictly less damage than the `UNARMED_DAMAGE = 8.0` fallback,
  which only applies when no `EquippedWeapon` component exists at all. Inventory
  presentation (`inventory.rs:106`) renders every FO4 weapon as "Damage 0".
- **Related**: `PAT-D6-2026-08-16-01` (`/audit-legacy-compat`, same sweep) first
  identified the missing-`DATA` mechanism; this finding adds the validated
  decode, the misalignment control, and the P2 blast radius. Sibling gap
  `PAT-D6-2026-08-16-02` (no canonical reach/speed field) is unblocked by the
  layout above — reach is offset 12, speed offset 4.
- **Suggested Fix**: Add a `GameKind::Fallout4` arm to the `b"DNAM"` match
  decoding the table above, and drop `Fallout4` from the FO3/FNV `b"DATA"` arm
  (it is unreachable for WEAP anyway). Add a real-data assertion in
  `crates/plugin/tests/parse_real_esm.rs` that no game's WEAP population decodes
  to a uniformly-zero `damage` — that single assertion would have caught this,
  and catches the four siblings below at the same time.

### FO4-D6-2026-08-16-02: FO4 ARMO reads `weight` and `health` swapped — every armor piece weighs 0.0

- **Severity**: HIGH
- **Dimension**: 6 — ESM item records
- **Location**: `crates/plugin/src/esm/records/items.rs:333-339`
- **Status**: NEW
- **Description**: The shared `GameKind::Fallout3NV | GameKind::Fallout4` arm
  reads FO4 ARMO `DATA` as `value(u32), health(u32), weight(f32)`. xEdit's FO4
  ARMO `DATA` is `Value(i32) @0, Weight(f32) @4, Health(u32) @8`. The **length
  matches (12 bytes) but the field order does not**, so the last two fields are
  read through each other's types.
- **Evidence**: measured `Armor_Leather_TorsoE3` — authored `(value 25,
  weight 5.0, health 0)`; the parser yields `weight = 0.0` (the `health` u32 `0`
  reinterpreted as `f32`) and `health = 1084227584` (the raw IEEE-754 bits of
  `5.0f32`). `DATA` is 12 B on 688/688 FO4 ARMO records, so this is total, not
  partial. The same shape reproduces on every sampled record
  (`Clothes_InstituteLabCoat*`: authored weight 3.0 → parsed weight 0.0,
  health 1077936128).
- **Impact**: Every FO4 armor piece has weight 0.0 and a ~1e9 nonsense health.
  Carry-weight and encumbrance computed off `common.weight` see zero for all
  worn gear; any consumer of `ItemKind::Armor::health` sees a value nine orders
  of magnitude out of range. Unlike the WEAP case this fails *silently and
  plausibly* — 0.0 is a legal weight.
- **Related**: `AUDIT_LEGACY_COMPAT_2026-08-16.md` (line 331) explicitly cleared
  `parse_armo`'s FO4 bucketing as "found **correct**" on the strength of the
  12-byte length agreeing with the arm's layout. That check compared sizes, not
  order, and is a false negative — worth recording, because "the byte count
  matches" is exactly the reasoning that will be applied to the four other
  records in this section.
- **Suggested Fix**: Give FO4 its own arm reading `value, weight, health`;
  keep FO3/FNV on `value, health, weight`.

### FO4-D6-2026-08-16-03: FO4 armor rating lives in `FNAM` and is never read

- **Severity**: MEDIUM
- **Dimension**: 6 — ESM item records
- **Location**: `crates/plugin/src/esm/records/items.rs:361-376` (the ARMO
  `b"DNAM"` arm), and the absence of any `b"FNAM"` arm in `parse_armo`
- **Status**: NEW
- **Description**: The FO4 branch of the ARMO `b"DNAM"` arm decodes `dt`/`dr`,
  but **FO4 ARMO carries no `DNAM` at all** (0 of 688). Its armor rating is a
  `u16` at offset 0 of `FNAM` (present on 688/688), which `parse_armo` has no
  arm for.
- **Evidence**: sub-record census above; measured `FNAM` armor ratings
  `Armor_Leather_TorsoE3` = 3, `Armor_Leather_ArmRightE3` = 1,
  `Clothes_InstituteLabCoat*` = 0. xEdit FO4 ARMO: `wbStruct(FNAM, '', [
  wbInteger('Armor Rating', itU16), wbInteger('Base Addon Index', itU16),
  wbInteger('Stagger Rating', itU8, wbStaggerEnum), … ])`.
- **Impact**: `armor_rating_x100`, `dt` and `dr` are all 0 for every FO4 armor
  piece, so `byroredux/src/inventory.rs:90-104` falls through both protection
  branches and renders the bare string `"Armor"` for all 688. Any future damage
  mitigation has no input. Note FO4's `FNAM` rating is a **raw** `u16`, not the
  ×100 convention `armor_rating_x100` implies — the field name will mislead
  whoever wires it.
- **Related**: FO4-D6-2026-08-16-02 (same record, same arm cluster).
- **Suggested Fix**: Add an `b"FNAM"` arm gated on `GameKind::Fallout4` reading
  `Armor Rating (u16)`, and either scale by 100 on the way in or rename the
  field to make the unit explicit.

### FO4-D6-2026-08-16-04: FO4 AMMO `DATA` is decoded through the 13-byte FO3/FNV layout, and its `DNAM` has no arm

- **Severity**: MEDIUM
- **Dimension**: 6 — ESM item records
- **Location**: `crates/plugin/src/esm/records/items.rs:433-438` (`DATA`),
  `:454-460` (`DAT2`, FNV-gated)
- **Status**: NEW
- **Description**: FO4 AMMO `DATA` is 8 bytes — `Value(u32) @0, Weight(f32) @4`.
  The shared FO3/FNV arm reads `speed(f32)` over the value and
  `flags_pad(u32)` over the weight, consuming the whole buffer; the subsequent
  `value` and `clip_rounds` reads hit EOF and take their `_or_default` zero. The
  `DAT2` weight fallback is gated `matches!(game, GameKind::Fallout3NV)` and FO4
  emits no `DAT2`. Separately, FO4 AMMO's 16-byte `DNAM`
  (`Projectile(FormID), Flags(u8), unused[3], Damage(f32), Health(u32)`) has no
  parser arm of any kind.
- **Evidence**: `DATA` 8 B on 57/57, `DNAM` 16 B on 57/57. Authored values the
  parser discards: `Ammo10mm` value 2 / weight 0.025; `Ammo556` 2 / 0.035;
  `AmmoMissile` 25 / 7.0; `AmmoFusionCore` 200 / 4.0 with `DNAM` health 500.
- **Impact**: All 57 FO4 ammo types decode to value 0 and weight 0, so ammo is
  weightless and worthless in inventory. The `DNAM` `Health` field (fusion-core
  charge) is unreachable. `damage` staying 0 is *not* itself wrong — FO4 moved
  per-shot damage onto the weapon — but nothing records that, so the zero is
  indistinguishable from the two real bugs beside it.
- **Related**: FO4-D6-2026-08-16-01 (same "FO4 shares the FO3/FNV arm" root).
- **Suggested Fix**: Add a `GameKind::Fallout4` `DATA` arm (`value, weight`) and
  a `DNAM` arm for projectile/health; comment the deliberate `damage = 0`.

### FO4-D6-2026-08-16-05: FO4 BOOK `DATA` is read as a 10-byte record when it is 8

- **Severity**: MEDIUM
- **Dimension**: 6 — ESM item records
- **Location**: `crates/plugin/src/esm/records/items.rs:600-607`
- **Status**: NEW
- **Description**: `parse_book`'s single `DATA` arm is un-gamed and assumes the
  FNV layout `flags(u8), skill(u8), value(u32), weight(f32)` = 10 bytes. FO4
  BOOK `DATA` is 8 bytes: `Value(u32) @0, Weight(f32) @4`. `flags` and
  `skill_bonus` take the low two bytes of the value; `value` is read from
  offset 2, straddling the Value/Weight boundary; `weight` runs off the end and
  defaults to 0.
- **Evidence**: `DATA` 8 B on 327/327 FO4 BOOK records; xEdit FO4 BOOK
  `wbStruct(DATA, 'Data', [wbInteger('Value', itU32), wbFloat('Weight')])`. The
  FO4 skill/perk teach data lives in the 13-byte `DNAM`, not in `DATA`.
- **Impact**: All 327 FO4 books carry a garbage value composed of two bytes of
  the real value and two bytes of the weight's mantissa, plus weight 0 and
  meaningless `flags`/`skill_bonus`.
- **Related**: FO4-D6-2026-08-16-04.
- **Suggested Fix**: Make `parse_book` game-aware (it currently takes no
  `GameKind`); FO4/Skyrim read `value, weight` from `DATA` and teach data from
  `DNAM`.

**Verified correct on FO4, no finding**: `MISC` and `KEYM` `DATA` (8 B,
`value + weight`) match the parser exactly; `ALCH` `DATA` (4 B) is `Weight` and
matches; `ARMO` `BOD2` is 4 B on FO4 so `armor_type` degrades gracefully to
`None`; `ARMO` `MODL` is a 4-byte `ARMA` FormID on 967/967 and
`is_skyrim_or_later` correctly includes `Fallout4`.

## Dimension 5 — FO4 shader flags and slot→role routing (lead B)

Measured across both vanilla mesh archives: **810,489** `BSLightingShaderProperty`
blocks, **782,631** inline `BSShaderTextureSet` blocks (all with
`Num Textures == 10`).

> **The framing premise is false and this matters.** The `/audit-fo4` SKILL text
> says of the FO4 shader-flag arm that "vanilla FO4 is BGSM-backed so this only
> bites inline/loose/modded NIFs". That is true of the *flag* arm. It does **not**
> extend to the texture-set slot table: `material_reference` is set only for
> `BSVER >= 155` (Starfield), so the early return at
> `crates/nif/src/import/material/dedicated_shader.rs:112-114` never fires on FO4
> — measured **0 of 810,489**. Every FO4 mesh walks the full `slot_to_role` loop,
> and 88% of them *also* name a `.bgsm`/`.bgem`, so the NIF slots and the external
> material both contribute under a first-wins policy.

### FO4-D5-2026-08-16-06: FO4 slot 3 is a greyscale-to-palette gradient, and `slot_to_role` routes it into the POM height role

- **Severity**: HIGH
- **Dimension**: 5 — shader flags / slot routing
- **Location**: `crates/nif/src/import/material/slot_role.rs:118-121`;
  consumed at `crates/nif/src/import/material/dedicated_shader.rs:144-176`
  (`TextureRole::Height => &mut info.parallax_map`)
- **Status**: NEW
- **Description**: `slot_to_role(ty, 3, _)` returns `Some(TextureRole::Height)`
  for every shader type except `FACE_TINT`. That arm's evidence is Skyrim-only
  (nif.xml calls slot 3 "Height/Parallax" and #2694 measured FaceTint against
  `Skyrim - Meshes0.bsa`). On FO4, slot 3 carries the **greyscale-to-palette
  LUT** for the `GREYSCALE_TO_PALETTE_COLOR` / `_ALPHA` feature — a colour
  gradient strip, not a height field.
- **Evidence** — slot-3 occupancy and what actually occupies it:

  | Archive | type 0 | type 1 | type 2 | type 6 |
  |---|---|---|---|---|
  | `Fallout4 - Meshes.ba2` | 1,990 | 1,415 | 731 | 1,320 |
  | `Fallout4 - MeshesExtra.ba2` | 10,333 | 15,514 | — | — |

  **31,303 properties** total. Every sampled path is unmistakably a palette
  gradient, across both archives and every type:
  ```
  Architecture/Buildings/LargeBrickGrad01.dds
  Architecture/Buildings/Bricks01Grad01.dds
  Architecture/Buildings/PaintedWoodGrad01.dds
  Architecture/Buildings/Hightech/HitTechMetalPanel_01LGrad.dds
  Interiors/HighTech/Grads/FlatMetalPanels01Grad.dds
  Interiors/HighTech/Grads/MetalFloorTiles01Grad.dds
  SetDressing/Crates/CrateLarge01LGrad.dds
  Vehicles/Automotive/Rust01LGrad.dds
  Actors/Character/Hair/HairColor_Lgrad_d.dds
  textures\Actors\PowerArmor\PA_palette_d.dds
  ```
  Corroborating engine-side signal: `fo4_slsf1::GREYSCALE_TO_PALETTE_COLOR`
  (`0x10`) and `_ALPHA` (`0x20`) already exist at
  `crates/nif/src/shader_flags.rs:163-164`.

  **The correct canonical role already exists and is structurally unreachable.**
  `MaterialTextureSet::greyscale_lut` (`crates/nif/src/import/types.rs:328`,
  bindless index 15) has a live renderer consumer —
  `byroredux/src/cell_loader.rs:289-294` sets `EFFECT_PALETTE_COLOR` /
  `EFFECT_PALETTE_ALPHA` from it. But the `TextureRole` enum
  (`slot_role.rs:37-54`) has no `GreyscaleLut` variant, so the shared table
  cannot name it; today the *only* producer of `greyscale_lut` is the BGSM/BGEM
  merge.
- **Impact**: The slot-3 path writes `MaterialInfo::parallax_map` →
  `GpuMaterial::parallaxMapIndex`. `crates/renderer/shaders/triangle.frag:208`
  gates POM on `mat.parallaxMapIndex != 0u && (dbgFlags & DBG_BYPASS_POM) == 0u`
  — no material-kind, shader-flag or height-scale check — and
  `GpuMaterial::default()` (`crates/renderer/src/vulkan/material.rs:369`) sets
  `parallax_height_scale = 0.04`, so the branch is unconditionally live. FO4
  brick facades, painted wood, hi-tech metal panelling, vehicles, crates, power
  armour and hair therefore ray-march parallax occlusion against the red channel
  of a colour palette, displacing UVs by an unrelated signal. Simultaneously the
  authored palette remap is lost from the NIF side. This is the same defect
  class as #2694 (POM over a face complexion map), on FO4, 31,303 properties
  wide — and it reaches the densest, most-visible architecture set in the game.
- **Related**: #2694 (the Skyrim FaceTint slot-3 fix that established the
  method); #2108 / `bgsm_greyscale_lut_enabled` (the existing palette-remap
  consumer); FO4-D5-2026-08-16-08 (same "Skyrim evidence generalised to FO4"
  root cause).
- **Suggested Fix**: Add a `TextureRole::GreyscaleLut` variant routed to
  `MaterialTextureSet::greyscale_lut`, and make the slot-3 arm game-aware. Since
  `slot_to_role` deliberately takes no game parameter, the cleanest seam is the
  one `normalize_shader_type` already uses — normalise at the call site in
  `dedicated_shader.rs`, which has `bsver` in scope, rather than widening the
  shared table's signature.

### FO4-D5-2026-08-16-07: Slot 7 carries the specular map on FO4 but is gated on `model_space_normals`, which 99.99% of FO4 content does not set

- **Impact**: `(_, false) => None` drops the specular map on ~757,568 of 757,629

### FO4-D5-2026-08-16-08: The FaceTint slot-4/5 `None` arms rest on Skyrim occupancy that is false on FO4 — heads lose their cubemap and wrinkle map

- **Severity**: MEDIUM
- **Dimension**: 5 — shader flags / slot routing
- **Location**: `crates/nif/src/import/material/slot_role.rs:126-133`
- **Status**: NEW
- **Description**: Slots 4 and 5 return `None` for shader types 4/5/6, justified
  in-code (#1350) as "FaceTint's slots 4/5 are absent on 100% of vanilla
  properties" and defended as guarding against a mis-exported NIF binding a
  spurious env cube. That occupancy claim is a Skyrim measurement. On FO4 both
  slots are routinely authored on FaceTint heads and carry real, distinct data.
- **Evidence** (`Fallout4 - Meshes.ba2`, shader type 4, n = 1,229):
  - slot 4: **623 non-empty (50.7%)**, all
    `Shared/Cubemaps/mipblur_DefaultOutside1_dielectric.dds` — a genuine
    environment cubemap.
  - slot 5: **981 non-empty (79.8%)**, all `_n`, all wrinkle/crease normals:

    `Actors/Character/BaseHumanMale/HeadWrinkles_n.dds`,
    `Actors/Synths/Gen2SkinHeadCrease_n.dds`,
    `Actors/Supermutant/SupermutantHeadCrease_n.dds`.
  - `MeshesExtra` reproduces both (type 4: 15 and 66 respectively).
  - Type 1 slot 5 additionally holds 40 `_m` entries.
  As with slot 3, the canonical destination already exists and is unreachable:

  authors. Because the arm returns `None` the loss is invisible — no warning, no

- **Related**: #1350 (the arm being generalised); FO4-D5-2026-08-16-06.
- **Suggested Fix**: Add a `TextureRole::Wrinkle` variant, and gate the
  slots-4/5 `None` on the Skyrim-family path rather than applying it to every

## Disproved candidates (investigated, then withdrawn)

Recorded so they are not re-derived next sweep:

1. **"FO4 BGSM-backed meshes short-circuit before the slot→role loop, so
   `slot_to_role` only affects loose/modded NIFs."** False, and the single most
   consequential correction in this report. `material_reference` is set only for
   `BSVER >= 155` (Starfield); measured **0 of 810,489** on FO4. The early
   return at `dedicated_shader.rs:112-114` never fires for FO4.
2. **"`ImportedMaterial::shader_type` is left at its default for BGSM-backed FO4
   meshes because the `material_reference` return precedes the assignment."**
   Structurally true of the code, but moot on FO4 for the reason above. Retained
   only as a note for a future Starfield reader.
3. **Slot 2 → `Emissive` on FO4.** Checked, correct. Type 2 (GlowShader) slot 2
   is 2,633/2,646 occupied and dominated by `_g` (1,787) and `_f` (729);
   non-glow types populate it only ~580 times archive-wide.
4. **Slot 4 → `Environment` on non-tint types.** Checked, correct — every sample
   is under `Shared/Cubemaps/`.
5. **Slot 6 (MultiLayerParallax inner layer) on FO4.** Zero occupancy across
   every shader type in both archives; the arm is simply inert on FO4, not
   wrong. The overlay-side gap is already #2713 (OPEN).
6. **FO4 `MODEL_SPACE_NORMALS` read from the wrong bit.** Suspected when 1,079
   `_msn.dds` files appeared against 61 flag hits; disproved by the equality
   assertion at `shader_flags.rs:426-427` — FO4 and Skyrim share `0x1000`. The
   flag genuinely is unset on that content.
7. **FO4 WEAP `DNAM` offsets 110 and 128.** Investigated as candidate fields;
   both are byte-constant across all 252 records, so no semantics are derivable
   from this corpus. Deliberately reported as unconfirmed rather than guessed.
8. **`parse_armo` FO4 bucketing "correct".** The opposite of a disproved
   candidate — a *prior* clean finding disproved here. See
   FO4-D6-2026-08-16-02.
