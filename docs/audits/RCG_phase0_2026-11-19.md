## V3 — TLAS membership, at HEAD on 2026-11-19

Read from code; every row names its proof.

| Draw class | In the TLAS? | Proof |
|---|---|---|
| Distant-LOD terrain blocks, object LOD, tree LOD (all carry `IsLodTerrain`) | Only while within `LOD_SHADOW_CASTER_DISTANCE` of the camera, which is `SHADOW_FADE_END` plus `DIRECTIONAL_SHADOW_TRACE_DISTANCE`; none beyond. Spawned with no BLAS. A block with no `WorldBound` is excluded. | `byroredux/src/render/static_meshes.rs:48` (`lod_shadow_caster_in_range`), `:72` (`TlasExclusion::DistantLodBlock`), `crates/renderer/src/shader_constants.rs:33`; spawns at `cell_loader/terrain_lod.rs:1326`, `object_lod.rs:748`, `placement_lod.rs:713` |

| Authored decals; fire-refraction; water; particles; UI quads | No, by design | `tlas_exclusion` (`static_meshes.rs`); `draw_command_eligible_for_tlas` (`crates/renderer/src/vulkan/acceleration/predicates.rs:718`) |
| A rigid draw whose mesh has no BLAS (budget, failed recovery) | **Dropped from the TLAS silently**; it still rasterises, so it is invisible to GI and occlusion. Counted as `missing_rigid_blas`, with up to a fixed number of sample names | `acceleration/tlas.rs` (the `missing_rigid_blas += 1` arm, near line 576); `rt.integrity` reports it (`byroredux/src/commands/world_info.rs:757`) |

| FO4 precombined meshes | Their spawn job builds BLAS in bounded batches (`spawn_timings.blas`), and exterior loads apply a BLAS mesh-count cap, so a mesh past the cap has no BLAS (**Phase 0: verify** on the live run which meshes the cap drops). The synthesised colliders are mesh-free ghost entities outside BLAS and TLAS | `cell_loader/precombined.rs:~730` (the cap comment), `:55` (ghost colliders) |
| Skinned actors | In the TLAS once their per-entity BLAS exists; otherwise dropped for that frame | `tlas.rs` (`missing_skinned_blas`) |

**What this adds to V1.** The PRD named three candidate causes for the Lexington walls. This table sharpens the second one: a large wall mesh that loses its BLAS to the exterior mesh-count cap, or to the BLAS memory budget, is invisible to GI and occlusion with no gate involved, and the engine already counts it. `rt.integrity` on the Lexington view reads `tlas_emitted` against `tlas_eligible` and `missing_rigid_blas`; `rt.masks` and `mesh.info` give the per-instance detail.

**For RCG-LOD-006.** The out-of-TLAS classes to report as separate coverage rows are: LOD blocks beyond the caster distance, ground cover, decals, any capped or evicted rigid mesh.

## V4 — SHaRC details and cascade seams

### Provenance note (read before using this section)

The research for V4 read SHaRC's published integration guide and, beyond it, its shader header files, whose licence notice reads that NVIDIA "retain all intellectual property and proprietary rights" in the software and that "any use, reproduction, disclosure or distribution … without an express license agreement from NVIDIA CORPORATION is strictly prohibited"; the repository's licence file is titled "NVIDIA RTX SDKs LICENSE". This document records **none of the source text** and none of its specifics (key layout, hash function, bucket structure, adjacent-level blending, extension lists). Q2 chose a clean-room cache written from the published description, so the facts below come from the integration guide only. **Decided by the owner, 2026-11-19:** the include is written by the owner from Binder et al. (2019) and the integration guide only, and nothing learned from the headers is used. Nobody else should write or review the include against this document's source-derived omissions; do not fetch or quote those files again.

### What the published integration guide states

Source: <https://raw.githubusercontent.com/NVIDIA-RTX/SHARC/main/docs/Integration.md>, read 2026-11-19.

| Topic | Statement in the guide | Section |
|---|---|---|
| Passes | An update pass (a modified path tracer over a subset of pixels), a resolve pass (compute), and a render / query pass | "Integration Steps", "Render Loop Change" |
| Update fraction | Example: one random pixel per 5×5 block, about 4% of paths, varied between frames | "SHaRC Update" |
| Level parameters | `sceneScale`, `logarithmBase`, `levelBias`; the base "does not affect the average voxel size"; voxel size is controlled with `sceneScale`; `levelBias` adds near-camera levels or clamps the minimum voxel size | "Hash Grid Visualization" |
| Distance to voxel size | **Not stated** in the guide | — |
| Memory | Three buffers: 8-byte hash entries, 16-byte accumulation, 16-byte resolved; 40 B per voxel; 2^22 entries is 160 MiB (64 B and 256 MiB with directional encoding) | "Memory Usage" |
| Eviction | `staleFrameNumMax` controls a cached element's lifetime; a lower value evicts more aggressively | "SHaRC Resolve", "Parameters Selection and Debugging" |
| Accumulation | History capped by a maximum accumulated-frame count whose default is not stated; radiance, not irradiance; 32-bit integer accumulation with a premultiplied scale | "SHaRC Resolve", "Parameters Selection and Debugging" |
| 64-bit atomics | A lock buffer is bound when `HASH_GRID_ENABLE_64_BIT_ATOMICS` is 0 | "Resource Binding" |
| Half float | "requires native fp16 shader type support"; resolved data is stored as half float | "Shader Compiler Requirements" |
| Primary hit | The query is typically made on hits other than the primary one | "SHaRC Render" |

**V4a closes as follows.** The guide does not say how distance maps to voxel size. The answer exists only in the licensed source and is not taken. It is not needed: RCG-LOD-001 and -003 fix the contract (logarithmic levels, camera distance only, a stated screen-space band), the mapping is this project's own derivation, and Q3 decided the scheme. Phase 1 publishes the band.

### V4b — cascade-boundary artefacts

Not settled by a primary source. Findings, with their reliability:

| Source | What it says | Reliability |
|---|---|---|
| Cascaded light-propagation-volume patent, <https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10049491> | The fine grid's boundary is interpolated into the coarser grid; the authors report no visible artefacts | Search summary only; the text was not read |
| Flax Engine, DDGI cascade blending commit <https://git.flaxengine.com/Flax/FlaxEngine/commit/3aa8e675514c41aa7897bae46d6da90c4b509f05> and its [docs](https://docs.flaxengine.com/manual/graphics/lighting/gi/realtime.html) | Without smooth blending the cascade transition is dithered; smooth blending can expose rounded cascade boundaries when adjacent cascades differ | Search summary; the commit page was not opened |
| Leadwerks cascaded voxel cone tracing, <https://www.leadwerks.com/community/blogs/entry/2756-voxel-cone-step-tracing-cascaded-volumes> | The boundary between stage 1 and 2 is visible on a wall | Search summary; a different technique (cone tracing) |
| Lumen translucency clipmap fade, <https://indxzero.github.io/ue544cvarwiki/articles/r.lumen.translucencyreflections.clipmapfadesize> | A dithered fade band exists at the clipmap transition | Third-party CVar wiki |

**Reading.** Cascaded structures show a transition at their edges and engines add a blend or dither band to hide it. That is consistent with Q3's reasoning and no primary source contradicts it. It does not prove a "visible ring" for this engine's case, so the PRD's wording stays at "whether a ring shows is open"; Phase 1's RCG-LOD-002 measurement is what settles it for the chosen scheme.

## V5 — the original engines' lighting LOD

Every claim cites the local wiki dump (`/mnt/data/src/reference/`). "Not documented" means the dumps do not say.

| Question | Finding | Source |
|---|---|---|
| Dynamic-light fade by distance | **Oblivion:** `fLightLOD1` / `fLightLOD2` set the distances at which dynamic lights apply to objects; defaults 1000 and 1500; values much past 4500 give "large colored blobs over LOD objects" | `uesp-wiki/Oblivion/Ini Settings.wiki`; `uesp-wiki/Oblivion Mod/Oblivion.ini.wiki` |
| | **FO3 / FNV (the GECK INI page is FNV):** `fLightLODStartFade` 1080, `fLightLODRange` 500, with min / max / default start-fade values; the same for shadows (`fShadowLOD*`, start fade 220, range 200). Defaults only; no descriptions | `geckwiki/(main)/INI Settings.wiki` |
| | **Skyrim:** cells and lighting templates carry Light Fade Distances (start, end); a zero start defaults to `fLightLODStartFade` and a zero end to `fLightLODStartFade` plus `fLightLODRange`; "no impact on shadow casters"; a light reference can be flagged Never Fades | `ck-uesp-wiki/(main)/Cell Lighting.wiki`, `Lighting Template.wiki`, `Light.wiki` |
| | **FO4:** cells carry Light Fade Distances and a Directional Fade; the `fLightLOD*` / `fShadowLOD*` values are not documented | `falloutck-uesp-wiki/(main)/Cell.wiki` |
| Lighting on distant (LOD) objects | Landscape LOD textures are captured from the editor's render window; many meshes are pre-lit or vertex-painted; terrain vertex shading is used for the look of shadows. Which lighting terms apply to LOD object meshes is **not documented** | `cs-uesp-wiki/(main)/Landscape LOD Tutorial.wiki`, `Working With Nifs 201 : Meshes, Data, and you.wiki`, `Terrain Texturing.wiki`; `geckwiki/Category/Landscape.wiki` |
| Caps on lights and shadows | **FNV:** `iActorShadowCountInt` and `iActorShadowCountExt` are 6; the GECK lighting tutorial says each light that casts on a piece of geometry "effectively doubles the rendering cost of that piece". **Skyrim:** shadow-casting omni lights "only four can be visible at any given time"; the optimisation tutorial advises no more than two lights per object (advice, not a cap). **Oblivion:** actor-shadow counts by preset (0 to 3 exterior, 0 to 5 interior). No per-object cap number is documented for FO4 | `geckwiki/(main)/INI Settings.wiki`, `Bethsoft Tutorial Lighting.wiki`; `ck-uesp-wiki/(main)/Bethesda Tutorial Lights and FX.wiki`, `Bethesda Tutorial Optimization.wiki`; `uesp-wiki/Oblivion Mod/Oblivion.ini.wiki` |
| AO and GI | None documented as an engine feature before Skyrim SE ("Screen space ambient occlusion (SSAO) is now supported"); bounce light is simulated with ambient or attenuation-only fill lights. **What this settles for §6 row 1 of the PRD.** The documented original mechanism is a distance fade of dynamic lights and shadows through INI and cell settings, plus baked lighting for static and distant content, and no GI. The PRD's contrast stands, stated with sources: the original cuts dynamic lighting by distance and bakes the rest. What the original applies to LOD object meshes is not documented and stays unclaimed.

## V6 — device features

**Engine side, at HEAD on 2026-11-19** (`crates/renderer/src/vulkan/device.rs`):
- `shaderInt64` is already **required**; a device without it is rejected at selection (`missing_required_features`, `:177`–`:203`).
- `shaderFloat16` is requested only when the device advertises `VK_KHR_shader_float16_int8` and the feature (`:658`–`:659`); it is optional today.
- No 64-bit buffer atomics and no 16-bit storage access are requested.

**Measured on the dev machine** (`vulkaninfo`, 2026-11-19), per device:

| Device | shaderInt64 | shaderBufferInt64Atomics | shaderFloat16 | storageBuffer16BitAccess |
|---|---|---|---|---|
| NVIDIA GeForce RTX 4070 Ti | true | true | true | true |
| AMD RADV (Raphael iGPU) | true | true | true | true |
| llvmpipe | true | true | true | true |

**RT-minimum GPU (the 6 GB target): not settled.** The Vulkan feature databases build their tables with scripts and could not be read from here; weak third-party evidence exists for older NVIDIA drivers, and an Intel thread says integrated Xe lacks hardware 64-bit atomics (Arc unverified). **Phase 0: verify** stays open for this row: run `vulkaninfo | grep -iE "Int64Atomics|shaderInt64|shaderFloat16|16BitAccess"` on a Turing-class card and on the lowest RT-capable AMD and Intel cards the project means to support, or ask owners of them. Until then the design keeps both layouts open: native 64-bit atomics, and a lock-buffer or 32-bit key fallback (the guide documents the lock-buffer path).

## V1 — measured on a live engine, 2026-11-19

Tools: `byro-dbg` (`cam.where`, `rt.integrity`, `rt.masks`, `screenshot`) and the `rt-lod-telemetry:` line (`--rt-test-lod-telemetry`).

**Findings.**
1. **Cause 2 (TLAS absence) is ruled out for these scenes.** Every eligible instance is emitted and `missing_rigid` is 0 at both poses.
2. **Cause 1 (the footprint gate) holds, and it is total in this view.** With GI eligible (tier 3) no fragment is traced (`gi_traced` 0) and the gate culls about three quarters of all fragments. No fragment has `rtLOD` below 2; 98% sit in the far bin. The tier-0 and tier-3 screenshots (`rcg_v1_dt1.png`, `rcg_v1_dt_t3.png`) differ by 2.5/255 on average, with 22% of pixels off by more than 2/255 and 0.9% by more than 32/255. An amplified difference shows the change sitting in moving or noisy regions (clouds, grass, silhouette edges, one distant strip at the right edge) and not on the large lit surfaces, the walls and stairs, which is what no traced GI predicts.
3. **A fourth cause, not on the PRD's list: the adaptive budget never leaves tier 0 here, so GI is off before the gate is reached** (filed as #7076). At the default run `gi_traced` and `gi_lod_culled` are both 0: no fragment is GI-eligible, because tier 0 sets `max_path_segments` and `max_shaded_hits` to 0. The controller targets 11 ms of main-lighting time and raises a tier only when the smoothed time stays under 0.68 of it (7.48 ms) for 45 frames (`AdaptiveRayBudget`, `crates/renderer/src/vulkan/scene_buffer/ray_budget.rs`). The tier-0 main pass is already 8.1 ms (run A) and 11.8–13.1 ms (run B) on this GPU, with 115 lights submitted in run B, so it cannot climb. The controller's signal is `max(main_render_ms, volumetrics_ms)` (`context/build_and_upload_instances.rs:1397`), the whole main pass. Run A was read at bench frame 120 (the bench's `rt_tier_hist` only samples past frame 240, which is why it reads 0/0/0/0 on a 120- or 180-frame run; that is a bench setting, not a controller warm-up), so "stuck" is proven for run B and probable for run A, whose 8.1 ms is above the 7.48 ms threshold.
4. **Cause 3 (weak AO) is ruled out as a cause, and SSAO is doing nothing on the architecture.** Run D (Downtown, default tier, AO toggled live with `r.dbg +0x800`, the AO texture shown with `r.dbg +0x200`; two poses, captured seconds apart):

   | Pose | Mean AO-on versus AO-off difference | Pixels differing by more than 8/255 | Where the difference is |
   |---|---|---|---|
   | A, as run B (about 21 m from the structure) | 3.5/255 | 7.4% | the lawn, silhouette edges, sky and cloud motion, one moving cable |
   | B, about 5 m closer to the structure | 1.8/255 | 4.4% | the grass and edges; the walls and booth are near-black in the amplified difference |

   The AO texture view (white is unoccluded) is white across the walls, stairs and the concave corners of the booth, so SSAO finds no occlusion where the owner expects it, and removing it changes nothing there. It reads black over the whole lawn at pose A and over the sky, which is why the lawn changes with AO off. Whether that black lawn is correct is not judged here. For the owner's complaint (walls neither bounce light nor occlude) the AO term supplies neither, and the untraced share it multiplies is itself not occluded by geometry, so the cache, not an AO retune, is what changes it. Evidence files: `rcg_ao_on_a.png`, `rcg_ao_off_a.png`, `rcg_ao_viz_a.png` and the `_b` set in `screenshots/` (untracked).
5. **Tier 3 is not a fix.** Pinning it costs 42 ms in this scene with no traced GI at all, so the other tier-3 work (direct shadow samples, glass) is what is expensive.

**What this means for the PRD.** Both stacked causes are removed by the design: RCG-COV-002 removes the footprint gate, and RCG-COV-004 with Q5 stops a tier-0 budget from taking the lookup away. Together they are why the cache must be cheap enough to run at tier 0: in this scene the main pass at tier 0 already costs more than the controller's upgrade threshold.

**Still open for V1.** The owner's own pose and wall, and run A's tier read past the bench's first frames.

**V2 steps** (not run; needs the acceptance scenes): on each acceptance scene, `RENDER_DEBUG_SHADOW_VISIBILITY`, `RENDER_DEBUG_DIRECT_ONLY`, `RENDER_DEBUG_INDIRECT_ONLY` and `RENDER_DEBUG_TRACED_SHARE` per visibility class; tabulate which of direct sun, local lights, sky ambient and traced GI reach each of the six classes.
