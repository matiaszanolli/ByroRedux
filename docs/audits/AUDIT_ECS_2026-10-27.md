## Findings

### ECS-2026-10-27-01: `apply_pending_group_swaps` re-enters `AnimationPlayer` under the `PendingGroupSwap` guard
- **Severity**: HIGH (ECS deadlock potential; reddens the scripting and workspace detector lanes)
- **Dimension**: 1 Lock Ordering
- **Location**: `crates/scripting/src/obscript_anim.rs:185-212` (the collect block), `:84-94` (`sequence_player`)
- **Status**: NEW (introduced by 92173d61f, #4128 `PlayGroup` flag 0)
- **Description**: The collect block opens `players = world.query::<AnimationPlayer>()` and then `pendings = world.query::<PendingGroupSwap>()`, which records the edge `AnimationPlayer → PendingGroupSwap`. Inside `for (object, pending) in pendings.iter()` it calls `sequence_player(world, object)`. That function takes `NamedSequences` (via `world.get`) and then `world.query::<AnimationPlayer>()` again, while `PendingGroupSwap` is still held. This records `PendingGroupSwap → AnimationPlayer` and a recursive read of `AnimationPlayer`. The block comment above it says it scopes reads to avoid the read/write self-deadlock, but the helper call inside the loop reintroduces the nested acquisition.
- **Evidence**: The detector panics in `obscript_anim::tests::a_held_request_applies_at_a_loop_wrap_and_the_latest_wins` and `flag_zero_waits_for_the_cycle_end_before_the_swap`: "attempted acquisition of `AnimationPlayer` while holding `PendingGroupSwap` … `AnimationPlayer` → `PendingGroupSwap` → `AnimationPlayer`". The same two failures appear in CI at `c7463c04d` and at `fa6be4a6b`.
- **Impact**: The system is an Update exclusive, so no live cross-thread deadlock is reachable today. But under a writer-preferring `RwLock`, a recursive read of the same storage blocks once a writer queues. The red lane also hides every later inversion.
- **Suggested Fix**: Snapshot the pending list first: `(object, clip_handle)` pairs, with the guard dropped. Then resolve each object's `sequence_player` and read the player with no other guard held. Alternatively, have `sequence_player` take the already-held `&QueryRead<AnimationPlayer>`.

### ECS-2026-10-27-02: `vats_scan` takes a dozen storages and resources under the `GlobalTransform` guard
- **Severity**: HIGH (ECS deadlock potential; 7 bin tests red)
- **Dimension**: 1 Lock Ordering
- **Location**: `byroredux/src/systems/vats.rs:339-427` (the `actors` guard and loop), plus `bone_position` `:436-444` and `visible_fraction` `:450-491`, both called inside the loop
- **Status**: NEW (introduced by 7eb4de261, Refs #6350; reached from `vats_mode_system`, an Early exclusive, and from the `vats.scan` / `vats.queue` console commands)
- **Description**: `let Some(actors) = world.query::<GlobalTransform>()` stays alive for the whole loop body. Under it the loop takes `ActorVitals`, `FormIdComponent`, `Dead`, `CreatureActor` (`world.get`), the `FormIdPool` resource, and `StringPool` + `SubtreeCache` + a second `GlobalTransform` read (`bone_position`). It also takes `PhysicsWorld`, `RapierHandles` and `ActorColliderOwner` (`visible_fraction`). The edge `GlobalTransform → ActorVitals` closes the existing `ActorVitals → RapierHandles → GlobalTransform` chain. The `RapierHandles` read under `GlobalTransform` adds a second inversion edge on top of that.
- **Evidence**: The detector panics in all seven `systems::vats::scan_tests::*` with "attempted acquisition of `ActorVitals` while holding `GlobalTransform` … `ActorVitals` → `RapierHandles` → `GlobalTransform` → `ActorVitals`". The same failure is in CI from `c7463c04d` to `fa6be4a6b`.
- **Impact**: As in -01, the callers are serial today, so the risk is latent. The lane is red, though, and the function is the template for the Phase-4 VATS work.
- **Related**: #6429 (the same function's understated exclusive declaration; a fix here should declare the reads it keeps); #6422.
- **Suggested Fix**: Gather `(entity, translation)` from `GlobalTransform` into a `Vec` and drop the guard. Then filter and price each actor with nothing held (the #5954 pattern). `visible_fraction`'s `target_bodies` set can likewise be built once per scan, before the loop.

### ECS-2026-10-27-03: `weather_system` reads `SkyParamsRes` under the `CloudSimState` write guard
- **Severity**: HIGH (ECS deadlock potential; 3 bin tests red)
- **Dimension**: 1 Lock Ordering
- **Location**: `byroredux/src/systems/weather.rs:1264-1285` (the write guard on `CloudSimState` at :1264, then `try_resource::<SkyParamsRes>()` at :1271). The opposing order is `byroredux/src/render/sky.rs:128` (`SkyParamsRes`, held) → `:165` (`CloudSimState`, in `outdoor_sky_params`)
- **Status**: NEW (introduced by 4f2596bf6, 2026-10-26, which added the 20 m/s cloud-drift cap that reads the tile scales)
- **Description**: `cap_cloud_layer_drift` needs `SkyParamsRes.cloud_tile_scale*`. The read was placed inside the `if let Some(mut clouds) = world.try_resource_mut::<CloudSimState>()` block. `build_render_data`'s sky pass has always taken `SkyParamsRes` first and `CloudSimState` second.
- **Evidence**: The detector panics in `render::sky::tests::{the_portal_sun_is_the_sun_above_the_clouds, interior_only_session_bakes_procedural_outdoor_sky, interior_only_boot_uses_live_clock_for_portal_sun}` with "attempted acquisition of `CloudSimState` while holding `SkyParamsRes` … `CloudSimState` → `SkyParamsRes` → `CloudSimState`".
- **Impact**: `weather_system` (Early exclusive) and the render collection both run on the main thread today, so the risk is latent. Any move of render collection off-thread, or a parallel sky consumer, turns it into a real write/read deadlock.
- **Suggested Fix**: Read the four tile scales into a local array before taking the `CloudSimState` write guard. Then compute and cap the scroll vectors and advance under the write guard only.

### ECS-2026-10-27-04: `GearImportLoader.failed_forms` keeps despawned wearers for the session
- **Severity**: LOW
- **Dimension**: 4 Resources & World-Level State
- **Location**: `byroredux/src/npc_spawn/loot_appearance.rs:1045` (field), `:1058-1085` (`hold_out` / `failed_set`, the only pruning)
- **Status**: NEW (ec88863a3, #5721 follow-up)
- **Description**: A wearer's failed-import forms are pruned against its worn slots only inside `failed_set`. That runs only when the same wearer hits another failed import. An NPC that streams out with a still-worn failed piece keeps its `Vec<u32>` entry until process exit, because entity ids are never recycled. Nothing on the release path (`step_releases`) or the cell unload path touches the map.
- **Impact**: One entry per NPC spawned with a gear mesh that every archive is missing. On a modded load order with missing archives this can be most NPCs over a long streaming session. The memory cost is small. The finding is the pattern the skill names: a per-entity fact held in a global `EntityId` map that despawn cannot reclaim. It has the same shape as the closed #6292.
- **Suggested Fix**: Retain the map against a live storage (e.g. `EquipmentSlots` / `GlobalTransform`) once per `step`, or when that storage's `structural_generation` moves. Or drop a wearer's entry when its import queue releases it.

### ECS-2026-10-27-05: `player_controller_system` omits the `PendingScriptStoryEvents` write from its declaration
- **Severity**: LOW (declaration gap; no parallel peer touches the resource today)
- **Dimension**: 5 System & Scheduler Wiring
- **Location**: `byroredux/src/boot/schedule/early.rs:21-110` (the row). Call path: `byroredux/src/systems/character.rs:1644-1664` (`apply_player_drowning_damage`) → `systems/story_events.rs:258` (`raise_kill_story_event`) → `crates/scripting/src/story_manager.rs:150-170` (`raise_story_event`, collision arm: `try_resource_mut::<PendingScriptStoryEvents>()`)
- **Status**: NEW (the skill records it as a by-hand check; no issue or report has filed it)
- **Description**: The row declares `writes::<StoryEvent>` for the #5641 hop. It does not declare the queue that `raise_story_event` writes when the player entity already carries a `StoryEvent` that frame. The hop is cross-crate and has no turbofish at the call site, so `every_parallel_system_declares_everything_it_acquires` cannot see it. Only the Late dialogue exclusive declares the resource (`late.rs:678`).
- **Impact**: None today. The Early parallel peer, `timer_tick_system`, does not touch the queue, so `known_conflict_count() == 0` still holds. A future parallel system that drains or appends to the queue would be scheduled beside the player controller with no conflict reported.
- **Suggested Fix**: Add `.writes_resource::<byroredux_scripting::story_manager::PendingScriptStoryEvents>()` next to the `StoryEvent` write, with a `#5647` comment. Optionally list `raise_story_event` as a cross-file hop in `PARALLEL_SYSTEMS`.
