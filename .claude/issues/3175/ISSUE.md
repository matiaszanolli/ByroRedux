# NIF-D3-2026-08-20-02: #2562's RTTI restoration invalidated all six per_block_baselines/*.tsv — the opt-in gate now fails ParsedShrank on every game

Issue: https://github.com/matiaszanolli/ByroRedux/issues/3175
Finding: NIF-D3-2026-08-20-02
Labels: medium,nif-parser,nif,bug
Source: docs/audits/AUDIT_NIF_2026-08-20.md

Filed from `docs/audits/AUDIT_NIF_2026-08-20.md` (Dimension 3 — Block Dispatch Coverage).

**Severity**: MEDIUM — the regression gate that exists specifically to catch silent per-type parse loss is now red on six of seven games, so a *real* regression is indistinguishable from this known-benign reclassification.
**Game Affected**: all six sized games with an `NiSingleInterpController` baseline row (Oblivion, FO3, FNV, Skyrim SE, FO4, FO76). Starfield has no such row and is unaffected.

**Location**:
- `crates/nif/tests/data/per_block_baselines/{oblivion,fallout_3,fallout_nv,skyrim_se,fallout_4,fallout_76}.tsv`
- comparison logic: `crates/nif/tests/common/mod.rs:809-815`
- keying: `crates/nif/tests/common/mod.rs:670-683`

## Why this matters more than it reads — it will fail LOUD and waste an afternoon

This does not degrade silently. The **first** person to run the opt-in baseline gate on a machine with game data will get a `ParsedShrank` regression on **every game**, headlined by Oblivion's entire 3,034-row `NiSingleInterpController` count collapsing to ~0. That looks exactly like a catastrophic parser regression and is not one. Whoever hits it first will burn an afternoon bisecting a non-bug unless the baselines are regenerated (or this issue is found). Fix it before that happens.

## Description

`PerBlockHistogram::record_scene_blocks` keys parsed blocks on the **struct's** `block_type_name()`:

```rust
// tests/common/mod.rs:677-682
} else {
    self.counts
        .entry(block.block_type_name().to_string())
        .or_default()
        .parsed += 1;
}
```

Before `e32e2b1f` (#2562 / #2563, 2026-08-19), `NiKeyframeController` / `NiTransformController` / `NiVisController` / `NiAlphaController` all parsed into a bare `NiSingleInterpController`, so every one of their blocks was counted on the `NiSingleInterpController` row — the RTTI erasure that commit's own message calls out. `e32e2b1f` gave them a dedicated `NiPreSplitDataController` whose `block_type_name()` returns their real name (`blocks/controller/mod.rs:310-313`, dispatch at `blocks/mod.rs:772-784`). Those blocks now land on four new rows, and the `NiSingleInterpController` row shrinks by exactly that count.

`compare_histograms` treats any shrink as a hard regression:
```rust
// tests/common/mod.rs:809
if cur_counts.parsed < base_counts.parsed {
    regressions.push(BaselineRegression::ParsedShrank { … });
```
The four *new* rows being absent from every baseline is harmless. The shrink is not.

## Evidence

```
$ grep -nE "NiSingleInterpController|NiAlphaController|NiVisController|NiKeyframeController|NiTransformController" \
      crates/nif/tests/data/per_block_baselines/*.tsv
fallout_3.tsv:55:NiSingleInterpController    7138  0
fallout_4.tsv:64:NiSingleInterpController   11086  0
fallout_76.tsv:62:NiSingleInterpController  17439  0
fallout_nv.tsv:58:NiSingleInterpController  11598  0
oblivion.tsv:43:NiSingleInterpController     3034  0
skyrim_se.tsv:59:NiSingleInterpController    5640  0
# zero rows for any of the four renamed types on any game — all folded into the row above.
```

The Oblivion case is unambiguous: the only three types that still parse as a bare `NiSingleInterpController` are `BSMaterialEmittanceMultController`, `BSRefractionStrengthController` and `BSFrustumFOVController` (`blocks/mod.rs:786-791`), and all three are Skyrim-era Bethesda extensions absent from Oblivion. So Oblivion's entire **3,034 must come from the four renamed types**, and that row drops to ~0 — a guaranteed `ParsedShrank` of ~3,034 on the next `--ignored` run.

`block_coverage_baselines` is unaffected (it gates on `NiUnknown` rate and the truncating-file set, neither of which is RTTI-keyed), and `oblivion_truncations.tsv` *was* correctly regenerated by `17cb417d` — so the omission is specific to the `per_block_baselines` sibling.

## Impact

The gate whose entire purpose is *"a parser regression where a previously-handled type starts under-consuming registers as a successful recoverable parse … the geometry is silently missing; the gate stays green"* (`per_block_baselines.rs:3-8`) now fails on six of seven games for a known-benign reason. Until re-baselined, a genuine regression in any of those six is invisible in the noise.

Note this **cannot** be caught by `cargo test` — the tests are `#[ignore]`d and need game data, which is exactly why it slipped.

## Suggested Fix

On the machine with game data:
```sh
BYROREDUX_REGEN_BASELINES=1 \
  cargo test -p byroredux-nif --test per_block_baselines -- --ignored --nocapture
```
and check the six regenerated TSVs in.

Then add a line to the `## How the rows are keyed` section of `per_block_baselines.rs` noting that **any change to a `block_type_name()` return value requires regeneration**, alongside the existing aliased-type caveat — that section already documents the aliasing direction (`bhkSPCollisionObject` -> `BhkPCollisionObject`) but not the de-aliasing one.
