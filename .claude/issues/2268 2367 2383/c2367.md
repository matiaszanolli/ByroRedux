Re-measured before bisecting. **The regression is gone — HEAD is now ~2× faster than the control on both scenes.** Closing; the range is not worth bisecting.

## Why re-measure first

The filed range ends at `28155b79` (2026-08-04). HEAD is now `7019eb84` — **1496 commits later**. Bisecting `3a02b02d..28155b79` would have located a commit inside a window that a year's worth of renderer work has since passed over, so the first question had to be whether the condition still exists.

## Method

Same-session, same-machine, TAA config, median of 3 × 300 frames, matching this project's control methodology.

One wrinkle worth recording: the control binary **predates `--bench-mode`**, which today's harness passes (`f19f7f15`, 2026-08-11 — *after* the filed comparison). Today's harness therefore cannot drive it. Both binaries were instead driven by the pre-`f19f7f15` harness, byte-identical on both sides (same md5), with the config list narrowed to `taa`. HEAD infers `BenchMode::SystemLive` for that flag set, which `boot.rs` documents as deliberate: *"canonical legacy combinations are inferred during migration so old screenshot/smoke tooling remains usable."*

## Control validation

Before trusting any delta, the control was checked against this issue's own control figures:

| Scene | #2367 control | This control | Agreement |
|---|---|---|---|
| Dugout | 30.44 ms | **31.23 ms** | +2.6% — within noise |
| MedTek | 40.17 ms | **44.38 ms** | +10.5% — looser |

Dugout reproduces cleanly. MedTek runs ~10% heavier here, consistent with the shared-desktop confound ROADMAP already flags for this class of run. That direction *flatters* HEAD, so the correction is applied below rather than ignored.

## Result

| Scene | Control `3a02b02d` | HEAD `7019eb84` | Delta | Entities (ctrl → HEAD) |
|---|---|---|---|---|
| Dugout Inn | 31.23 ms (fence 29.22) | **14.32 ms** (fence 7.22) | **−54.1%** | 6978 → 11592 (**+66%**) |
| MedTek Research 01 | 44.38 ms (fence 35.75) | **21.78 ms** (fence 0.82) | **−50.9%** | 31495 → 39537 (**+26%**) |

Against what this issue reported, the sign has flipped on both:

- **Dugout**: filed as 30.44 → 40.79 ms (+34%). Today 31.23 → 14.32 ms (−54%).
- **MedTek**: filed as 40.17 → 53.58 ms (+33%). Today 44.38 → 21.78 ms (−51%).

Correcting MedTek for the ~10% heavy control (i.e. taking this issue's 40.17 ms as the control), HEAD is still 1.84× faster. The conclusion does not depend on that correction.

**The comparison is not content-flat, and that strengthens it rather than weakening it.** Both scenes now load substantially *more* entities — Dugout +66%, MedTek +26% — and are still half the frame time. A content-flat comparison could only move the result further in HEAD's favour. The collapse in `fence_ms` (29.2 → 7.2 and 35.8 → 0.8) is where the time went: these scenes were GPU-bound at the control and are no longer waiting on the GPU.

## Checklist disposition

- **BISECT** — not done, deliberately. The condition it would localize no longer reproduces.
- **WHITERUN-ENTITY-COUNT** — partially answered, and it was not a Whiterun anomaly. Dugout (+66%) and MedTek (+26%) show the same growth over this range, so whatever changed is systemic content loading, not one scene misbehaving. The specific cause is still unidentified.
- **PROSPECTOR-IMPROVEMENT** — not re-measured; only the two regressed scenes were in scope for this run.

## Separate finding, not part of this issue

Every HEAD run segfaults **after** measurement completes. The bench emits its full summary and `rt-integrity: … verdict=PASS`, then teardown logs:

> GPU allocator has 2 outstanding references — leaking allocator + device + surface + instance to avoid use-after-free on driver-side `vkFreeMemory` of late natural-Drop allocations. Process must terminate to reclaim.

so the numbers above are unaffected. The control does not do this. That path is from #1749 and is a deliberate leak-then-die, but it does mean a clean shutdown is not happening on FO4 cells at HEAD — worth its own issue rather than being buried here.
