### 1 — loose loads never flushed queued uploads

Confirmed exactly as described. `flush_pending_uploads` had two call sites (`cell_loader/references/mod.rs`, `streaming_helpers.rs`) and the loose path calls `resolve_texture` through `scene/nif_loader.rs`, so it enqueued and never drained.

Added `flush_pending_loose_textures`, called right after `load_nif_from_args`. It mirrors the cell-loader body rather than calling it: that one carries a `force`/threshold policy for mid-load batching across an edge crossing, which a single-batch loose load has no use for. What is shared is the six-argument `flush_pending_uploads` contract, so a change there breaks both sites together.

### 2 — `bufferDeviceAddress` gated on ray-query

Half of this was already fixed: `shaderInt64` is requested unconditionally now, and device suitability *rejects* hardware lacking it.

The other half is real but cannot fire upstream, for a reason specific to this project: `is_device_suitable` returns `None` for any device without ray-query, so `caps.ray_query_supported` is `true` at every call that reaches `create_logical_device`. RT is mandatory here by design — `triangle.frag` declares `RayQueryKHR` and `triangle.vert` declares `PhysicalStorageBufferAddresses`, so there is no partial-render fallback to preserve. Your RX 590 is declined at selection, before that line runs.

But the line still *read* as though an RT-less device were supported, which is exactly why you reported it — and on your fork, which removed the RT requirement, it really does disable a Vulkan 1.2 core feature the main pass needs. It is now `.buffer_device_address(true)`, matching `shader_int64(true)` beside it, with a comment saying suitability owns the decision. That also clears one of the "now-unreachable `ray_query_supported == false` branches" our own comment had listed as a follow-up. Pinned so re-coupling either feature to the RT flag fails the suite.

### 3 — backslash path splitting

Not applicable here: `--loose-textures`, `add_loose_texture_root` and `TextureProvider::add_loose_texture_root` do not exist in this repo and never have — `git log -S` across all refs finds nothing, including at your fork point `9f619355`. That path is your fork's own addition, so the bug is real but lives on your side.

Worth saying the analysis is right regardless: `Path::file_stem()` does not treat `\` as a separator on Unix, and Bethesda-convention `textures\...\foo.dds` paths are common enough that anything doing stem extraction on them needs the manual split. If you do open a PR that upstreams the loose-texture indexer, `rsplit(['\\', '/'])` is the right shape for it.

### 4 — spawn orientation baked in roll

Confirmed at `scene.rs`'s `Quat::from_rotation_arc(-Vec3::Z, forward)`, and it is broader than the report claims: that line ran on *every* spawn path, so cell loads and harnesses had it too — loose loads just hit steep initial directions more often, which is where it becomes visible.

Fixed as you describe, decomposing into the same `Quat::from_rotation_y(yaw) * Quat::from_rotation_x(pitch)` form `fly_camera_system` composes, and seeding `InputState.yaw`/`.pitch` to match. The seeding is the half that makes it stick — composing the right quaternion but leaving the scalars at `0` would still snap on the first frame, just to a different wrong pose.

Two tests: one round-trips eight directions (including the steep ones you call out) through the real convention rather than restating the algebra, and one pins the *defect* — that a shortest-arc rotation aims identically but carries measurable roll, which is what made the camera appear to spin.

### 5 — `cam_center` never set on the loose path

Confirmed: assigned only on the ESM/cell, harness and Studio paths, so a plain loose load kept `Vec3::ZERO`.

Fixed slightly differently from your fork. Rather than aiming level-forward from `cam_pos`, the bounds walk that was already there behind the `studio_mode` gate is hoisted to run for any loose load, and its midpoint becomes `cam_center`. The reason to prefer that: the spawn code already places the camera at `cam_center + (0, 100, 200)` when `has_nif_content` — an offset that only means anything if `cam_center` *is* the content. So the framing logic had always assumed the value this path failed to supply, and supplying it correctly fixes the framing rather than replacing it with a different arbitrary one.

### A — `StagingGuard` non-coherent flush

Already fixed upstream, before your fork point: `StagingGuard::flush_if_needed` exists in `buffer.rs` and is called on the DDS-write path. Your reasoning about the spec contract is right; you were reading a tree that had already grown the fix.

### B — `.tga` in the loose indexer

Not done. It is feature-shaped rather than a correctness bug, and it attaches to the loose-texture indexer from item 3, which does not exist upstream — so there is nothing here to extend yet. Flagging that it is consciously skipped rather than lost.
