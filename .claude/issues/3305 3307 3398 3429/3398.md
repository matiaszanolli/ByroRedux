## RE spike done — Phase 2 is unblocked (c5cd4e6f)

Full findings: [`docs/audits/SF_CDB_PHASE2_SPIKE_2026-08-29.md`](docs/audits/SF_CDB_PHASE2_SPIKE_2026-08-29.md). Measured against the vanilla 105 MB `materialsbeta.cdb` and 3,085 material paths read off real NIFs in `Starfield - Meshes01.ba2`. Summary:

### The lookup key exists and is computable

`BSMaterial::Internal::CompiledDB.HashMap` is a **48,749-entry `BSResource::ID → u64`** index, and `DBFileIndex::ObjectInfo.PersistentID` carries the same `BSResource::ID`. Chain: path → `BSResource::ID` → `ObjectInfo.DBID` → every `ComponentInfo` with that `ObjectID` → `ComponentTypes[Type]` names the class → `Edges` expand layers/texture-sets/blenders.

**The hash**: reflected CRC-32, poly `0xEDB88320`, **init 0, no final XOR**, over the lowercased backslash path, directory and stem hashed separately. Three normalisations × three CRC parameterisations tried; exactly one matched — **3032/3084 (98.3%)** of real NIF-named paths. The reversed column assignment matches 0/3084, so it isn't coincidence.

**`BSResource::ID`'s field labels are rotated** relative to their contents — do not trust them:

| Our label | Distinct | Actually holds |
|---|---|---|
| `.Dir` | 48,423 | CRC-32 of the **file stem** |
| `.Ext` | 2,168 | CRC-32 of the **directory** |
| `.File` | **1** (`0x0074616d`) | the **extension**, packed ASCII `"mat"` |

The one-distinct-value column is what made this decidable rather than guessed.

### Finding for #3230

The extension column is *always* `"mat"`, so the lookup ignores the reference's own suffix — **17 of 57 `.bgsm`/`.bgem`-named paths in the sample resolve to real CDB materials** (16 `.bgsm`, 1 `.bgem`). So neither "always CDB" nor "always BGSM" is right for those paths; it has to be try-then-fall-through, as #3230 suggests. Worth settling together with the merge arm.

### Values were already fully decoded

The "schema and counts only" framing was wrong — leaves are materialised with field names resolved from the class layout. 61 `BSMaterial::*` classes reached; ~20 relevant, tabulated in the doc against their `ImportedMaterial` targets with real field names and value shapes (`MRTextureFile.FileName`, `AlphaSettingsComponent`, `DecalSettingsComponent`, `EmissiveSettingsComponent`, `EffectSettingsComponent.IsGlass`, `ShaderRouteComponent.Route`, `TranslucencySettings`, …). Enum fields are **strings** (`"Deferred"`, `"AlphaBlend"`, `"MATERIAL_LAYER_0"`), so each needs an explicit arm plus a documented default.

### What's still hard (unchanged, now well-specified)

`parse` peaks at **9.19 GB RSS** on a 105 MB CDB, and `ParseLimits` is a pre-walk reject, not a streaming budget — so it cannot run on the cell-load path, and there are 13 CDBs to index, not one. **The indexed/streaming reader is the actual Phase-2 project**; the merge arm itself is still ~80 lines mirroring the BGSM arm.

### Revised sequencing

1. Confirm the 12 `.mat` misses live in the DLC CDBs; settle load-order last-wins across all 13.
2. Streaming/indexed reader in `crates/sfmaterial` (+ re-export `Class`/`Field`/`ObjectInstance`/`Ref`/`TypeReference`, private today).
3. Fix the `BSResource::ID` label rotation in the reader.
4. Provider plumbing — build the index at `discover_starfield_cdbs`, cache beside `sf_cdb_cache`.
5. The `.mat` merge arm; settle #3230 here.
6. Invert the pinned invariants in `tests/starfield_mat.rs:177-188`.

Reproducible via the three `_tmp_*` examples the doc names. Leaving this issue **open** — the spike is the unblock, not the feature.

## Scoping input from `/audit-starfield` 2026-08-30 (SF-D9-01) — the CDB is not *one of several* material sources on Starfield, it is the **only** one

Filed as a comment rather than a new issue: the missing per-field extraction is this issue and #1289, and is deliberately not re-filed. What is new is the **exclusivity**, which changes how Phase 2 should be designed.

**Measured across all 129 installed Starfield archives:**

- **Zero `.bgsm` and zero `.bgem` files exist in any Starfield archive** — yet **283 meshes reference them**: `{"mat": 68441, "bgsm": 255, "bgem": 28}` over 69,170 sampled meshes. Every one of those 283 references is a guaranteed archive miss that falls through to `apply_cdb_pbr_fallback`, joining the 68,441 `.mat` references at `MergeOutcome::PresenceOnly`.
- Confirmed at the canonical boundary: `meshes with >=1 texture role filled: 0 (0.00%)`, `is_pbr=0`, `from_bgsm=0`.

**Consequences for the Phase 2 design:**

1. **100% of Starfield materials reach the Disney lobe with zero authored texture roles.** There is no partial-coverage state today and no BGSM fallback to degrade to — Phase 2 is a **step function**, not an incremental improvement over a working baseline.
2. `BGSM_AUTHORED`, `TRANSLUCENCY` (+2 variants) and `MODEL_SPACE_NORMALS` can never be set on Starfield content by the existing path.
3. **Starfield has no glass-classification signal at all** — BGEM `glass_enabled` is structurally unreachable. Whatever Phase 2 produces has to carry the glass signal itself; nothing else can.

Please do not assume a BGSM fallback exists when scoping the reader.

**Related sizing correction filed separately**: the spike doc scopes Phase 2 against one 105 MB CDB at 9.19 GB peak; there are two full-size CDBs and 13 in total (3,077,172 chunks, ~232 MB), projecting ~18 GB for a naive whole-corpus `parse`. See #3781.

**Also re-confirmed this run for this issue's own premise**: `read_user_class` (`reader.rs:520-590`) still ignores `Field::offset`. Independently reproduced across all 13 CDBs — **821 classes, `decl != offset` for exactly 2, both `XMCOLOR`**. Sharper characterisation than the issue currently carries: the fields declare `r,g,b,a` at offsets **2,1,0,3**, i.e. a straight **R↔B transposition** (green and alpha survive).
