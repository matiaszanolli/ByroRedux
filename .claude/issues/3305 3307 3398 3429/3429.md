Investigated, not fixed — leaving open deliberately.

The cheap version of this fix is **unsafe**, and that is worth recording so nobody lands it. Reusing the existing `VkImage` and recording a staged `cmd_copy_buffer_to_image` into `with_one_time_commands` (keeping the current submit+fence structure) would remove the per-frame image/view create-destroy pair, the 3-live-copies residency and the descriptor rewrite — but it races. `update_rgba` is called from `app_frame.rs` *before* `ctx.draw_frame`, and `with_one_time_commands` fence-waits only on its own submission, not on prior frames. `draw_frame`'s both-slots `wait_for_fences` has not run yet at that point, so an in-place copy can land while frame N-1's fragment shader is still sampling the image. A per-FIF pair of images does not rescue it either, for the same reason: at `MAX_FRAMES_IN_FLIGHT == 2` the slot being written is the slot still in flight.

So the finding's own suggested fix is the correct one and the minimum viable one: the upload has to move *after* the fence wait, i.e. into the frame's own command buffer, with the per-FIF staging ring. That is a real restructuring of the pre-draw path.

I did not attempt it because its failure mode (torn or stale UI, a sync hazard) is invisible to `cargo test`, and sync-validation is not a reliable oracle for this class here — under #3646 it did not flag a structurally identical cross-submission hazard that was covered by the same both-slots wait. Landing it on reasoning alone would be exactly the speculative renderer change this repo avoids.

Two things from this pass that help whoever takes it: the only production caller is `app_frame.rs`, so the blast radius is small; and the resident cost is now ledgered in `docs/engine/memory-budget.md`'s new Scaleform UI section (#3431, 6cdb598c), including the deferred-destroy copies this issue is about.
