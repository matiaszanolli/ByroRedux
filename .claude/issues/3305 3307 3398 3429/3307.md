## Investigated before implementing (staged review point) — not closing, still open

Two findings against building this now, recorded in c27ec637:

**1. Reframed value.** Redux's current architecture (full REFRs spawn only inside `radius_unload`, both LOD rings load only outside it, #1866) already prevents the z-fighting vanilla's VWD flag exists to suppress — just structurally, via ring separation, instead of vanilla's active per-object cull. This isn't a correctness bug; it's a fidelity/performance optimization (wider effective full-detail radius, or closer matching to vanilla's exact transition distance) with no concrete driving complaint behind it.

**2. A more fundamental blocker than the issue's own "needs radius decoupling + real-game visual validation" framing.** `object_lod.rs` spawns a `.bto` quad as one merged, per-quad draw with no per-source-object identifiers (`object_lod.rs:320-345`). There's no hook to suppress *one specific* VWD-flagged object's contribution within an already-baked quad mesh at the granularity the marker was designed for. The only technically available lever is coarser than per-object — hide the whole quad once any full REFR inside it is resident — which pops out every *other*, unrelated object in that quad: trading one visual regression for another, not a net improvement. A real per-object cull needs the LOD bake (or its generation-time source data) to carry per-object boundaries — a separate, larger investigation.

Recorded both findings as dated corrections in `VisibleWhenDistant`'s doc comment and `exal.md` §5.2, so a future session doesn't re-derive this from scratch. Doc-only change, no functional change — `cargo check`/`cargo test` both clean.

## Investigation: the premise was wrong in a load-bearing way (`b0a30fd5`)

The `VisibleWhenDistant` component doc pointed here for "the full writeup" of the 2026-08-26 investigation, but that writeup was never actually posted. Writing it now — because two of its measured claims turn out to be wrong, and the conclusion they supported does not follow.

Evidence: new `crates/nif/examples/bto_segment_census.rs`, over Skyrim SE `Skyrim - Meshes1.bsa` — 1078 `.bto` quads, 1856 level-4 sub-meshes.

### What was wrong

1. **"A `.bto` quad spawns as one merged, per-quad draw."** It does not. `spawn_object_lod_block` calls `world.spawn()` once per `imported.meshes` entry — a level-4 quad spawns 1–5 entities, one per material/type group.

2. **"The only technically available lever is coarser than per-object — hide the whole quad."** Also wrong. `BSSubIndexTriShape` carries a segment table which nif.xml describes, for LOD, as *"segmented in a **grid**"*. Measured at level 4 (`4x4 = 16` cells per quad): `num_segments` caps at exactly **16**, and the non-zero segments exactly partition the sub-mesh's triangles.

```
level  4: 1856 sub-meshes, max num_segments=16
   histogram: 16:631  15:290  14:186  13:142  12:114  10:67
level  8:  384 sub-meshes, max num_segments=1   (1:384)
level 16:  152 sub-meshes, max num_segments=1   (1:152)

worked example — tamriel.4.-32.40.bto
  [0] objsnowHD-LargeRef  segments=4  tris=264  non-empty=[cell#3:264tri]  sum=264
```

**One segment per cell** — precisely the granularity this engine's streaming already works at, since full REFRs spawn per cell.

### What survives

There is genuinely **no per-source-object identity**. Sub-mesh names are material/type groups (`Obj`, `obj-LargeRef`, `objsnowHD-LargeRef`, …), never object names, and nothing carries a FormID — `BSDistantObjectLargeRefExtraData`, despite the name, is a single `bool` per nif.xml.

But a *per-object* cull was never what this engine needs. Full REFRs stream **per cell**, so per-cell suppression is sufficient — and the bake exposes it.

### The real constraint (new, and nobody could have stated it before)

The per-cell grid is **level-4 only**. Levels 8 and 16 ship exactly one segment on every sub-mesh (384/384 and 152/152 measured), so there the lever really is per-quad, with the pop-out cost the old note describes.

**So a radius-decoupling design must keep full REFRs under level-4 quads, and never under a level-8/16 quad.** That is a hard constraint on step 1 of this issue's suggested approach.

### Why the cull still isn't built

Consuming per-cell segments means drawing a LOD sub-mesh as index sub-ranges. That, plus the radius decoupling, is a render-visible change whose failure modes — pop, seam, z-fight at the transition — are invisible to `cargo test`. It needs the live validation EXAL §5.2 asks for and this issue lists as step 3.

Leaving this open. The blocker is now step 3 (live validation) and a bounded renderer change, not the "needs the bake to carry per-object boundaries, a separate and larger investigation" dead end the docs previously recorded. `LodCoverageStats::vwd_full_model_overlaps` remains the regression gate throughout.
