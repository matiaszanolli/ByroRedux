## Fourth pass: what drives low-process updates (2026-11-16), still NOT settled

Driver (confirmed): `0x8da860` is the ProcessLists low-level update. Settings: `iLowProcessingMilliseconds` (value word default 2, read at 0x8da8d0; a per-frame time budget, the loop stops when it is spent) and `bRunMiddleLowLevelProcess` (default 1). Callers 0x8b79e2 (the same routine holds the FastTravel string "FastTravel: Could not compute path length to Cell", at 0x8b7814), 0x8bf98c, 0x8db841. It walks the actor array, resumes where it stopped last frame (index stored at 0x1228ac0), skips deleted / disabled actors, and defers actors whose flags & 0x820 are set. For an actor whose process level ([process+0x28]) is 3 it either calls the Low update `0x87d640` directly or, when the process's last-update time is set, calls Actor virtual +0x25c(dt) once at least 1.0 s has passed since that time (constants 0xf3ccfc = 1.0, 0xf3f6ac = -1.0). So the cadence is per-actor elapsed time, not a fixed 120 s. The GECK page's "about every 120 seconds" is NOT visible in this loop.

Low-process travel evaluator: Low and MiddleLow vtable slot 0x79c = `0x880db0` (about 0x4f0 bytes, same address in both). It reads the actor's package list ([process+0x40]), reads the package location through three package accessors (0x649070, 0x648b70, 0x648ca0), computes cross-space route length with `0x692220` -> `0x68dd80`, which builds a `TeleportDoorSearch` (A* over teleport links; ctor 0x6b1a80, vtable 0xf64280), turns it into a duration, and compares it with the elapsed time (`0x75c3b0` result vs the parameter). When the elapsed time covers the route it calls `0x7f4310` -> `0x8a1e10`, which allocates a pathing request (0x69c030 / 0x89fa40 / 0x69c250). It also calls process virtual +0x284 (change current package) in several branches.

Same cross-space search is used by: `0x8b21c0` (called from Activate 0x755f70 and from the script MoveTo handler 0x79ba90, and from 0x759f50 / 0x75aa90 / 0x7914d0 / 0x7a0330), `0x8b1750`, `0x8c54b0`, `0x78f590` (the Travel package description, which is how "Estimated Travel Time" gets its distance).

So, supported by code: the original does estimate an unwatched Travel's duration from a door-graph route length and compares it with elapsed game time, which matches XCT-OFF-001's model (route length / speed, no positions in between). NOT supported or refuted: where the actor stands afterwards. The final call in the evaluator queues a pathing request rather than writing a position, so the relocation is in the pathing / process-level change code (what runs when a request completes, or when the actor's cell loads), not here.

Suggested next if continued: (1) decode `0x8a1e10` and the pathing-request completion handler; (2) find where an actor is re-added to a cell when it changes process level (callers of Actor virtual +0x25c and the "process level 3 -> 0" transition); (3) otherwise in-game observation.

## Fifth pass: the process-level change (2026-11-16), a placement routine found, NOT fully decoded

Step 1 (0x8a1e10): it only builds and queues a pathing request (calls 0x69c030, 0x89fa40, 0x89f540, 0x69c250; the same RTTI family as `PathingRequestCoveredMove`). It writes no position. I did not decode the completion handler.

Step 2 (process-level change). `0x89a6f0` is `Actor::SetProcessLevel(level)` (level 0 High, 1 MiddleHigh, 2 MiddleLow, 3 Low; it constructs the process object: High 0x45c bytes via 0x85bb10, MidHigh 0x254 via 0x884800, MidLow 0xc8 via 0x896c50, Low 0xb4 via 0x87b720, or calls an Actor virtual when one of that level already exists). The Actor vtable is 0xf88514 (0xf88a74 etc. are string tables, not vtables). Transition slots: +0x240 -> 0x7e9660 (to High), +0x244 -> 0x7e9e30 (to Low), +0x248 -> 0x7ea8b0 (to MidLow), +0x24c -> 0x7ea2a0 (to MidHigh).

`0x7e9660` (to High) calls `0x7e9260(actor, flag)` BEFORE it builds the High process, when the actor's own rotation/position fields do not hold the "unset" sentinels (FLT_MAX at 0xf458b8, words at 0x1325340..48) and a scene-state flag test passes. `0x7e9260` is the only routine I found that writes an actor's position on a level change:
- It fetches the current package through process virtual +0x228 and asks it (package virtual +0x13c) whether it applies. It returns without moving the actor when the package is type 6 (Travel; package type byte at [package+0x20]) and the destination equals the player reference (global 0x1225ac8), or when a package of kind 3 has no value from 0x648eb0.
- Otherwise it reads the actor's position (virtual +0x1f4) and parent space (0x75e540), tests the position with 0x693430, builds a path object (0x6972b0), measures a distance with 0x7dd960 (a per-actor float used as the movement step) and 0x692de0, and computes a displacement. A second path object is built against the PLAYER (global 0x123c674, via 0x69d430 / 0x69d0c0), scaled by 1.5 and 3.0 (constants 0xf527ec, 0xf4b368), and resolved by 0x692420 into a position at [ebp-0x20].
- It then places the actor: when 0x7ffaf0() is true it hands (actor, &pos) to the manager at global 0x123cde8 (0x9c9f80 then 0x9c9e30), otherwise it calls Actor virtual +0x2a8 with &pos. +0x2a8 is almost certainly SetPosition (unverified).

Reading, with its limits: the promotion places an actor at a position COMPUTED from a path and the player's location, not unconditionally at the package location and not at a door marker. It looks like a "do not pop the actor in on top of the player" adjustment (distance multipliers 1.5 and 3.0 against the player), and it is skipped for a Travel package whose target is the player. I have NOT decoded 0x692420, 0x6972b0, 0x693430 or 0x7dd960, so I cannot yet say whether the computed position is on the way to the package destination, at the destination, or merely a clear point near it. I also have not shown that this routine runs for an actor that arrived in a different cell (the cross-space case), only that it runs on promotion.

What this means for the PRD: nothing here supports "at the package location" as stated in XCT-OFF-002, and nothing here shows "at the far-side door". Treat that default as unverified, not as contradicted. XCT-OFF-001's route-length-versus-elapsed-time model is supported by the Low-process evaluator (fourth pass).

Suggested next: decode 0x692420 (what position it returns), 0x6972b0 and 0x7dd960, then 0x7e9e30 (the actor going the other way, to Low), which may record where the actor stands when it is unloaded. Otherwise the in-game observation.

## Sixth pass: the four helpers and the to-Low transition (2026-11-16)

Helpers (Fallout3.exe):
- `0x7dd960` = the actor's movement speed. It returns a float read from the process movement data ([process+0x2c] -> [+0]) when its flag bit is clear, else through the ActorValueOwner subobject at actor+0xA0 (virtual +0). Called on the player and on the actor.
- `0x6972b0` constructs a `PathingLocation` (RTTI vtable 0xf45794) from a position and an actor.
- `0x693430` is a point test against the pathing grid for a parent space and position (it builds PathingLocations and tests them with 0x697280 / 0x697fd0 / 0x697a90 / 0x698620). Treat it as "is this position usable for pathing"; I did not decode its exact predicate.
- `0x692de0` advances along a path by a distance (speed argument) and returns a point (used with the speed as the distance).
- `0x69d430` constructs a `PathingRequestClosePoint` (RTTI vtable 0xf63dd8; default minimum radius 128.0 at +0xB0, maximum 2048.0 at +0xB4). `0x69d0c0(request, reference)` sets its centre from the reference.
- `0x692420(request, &out)` resolves a close-point request: it first tries 0x692580, then picks a RANDOM angle and a random radius between the request's two radii around the centre, takes the centre's Z, and snaps the height with 0x745250.

So `0x7e9260` reads as follows (decoded, not guessed, except where marked): S = player's speed + actor's speed. If the actor is within 1.5 x S of the player ((1.5 S)^2 > squared distance, compare at 0x7e9577), it builds a `PathingRequestClosePoint` centred on the PLAYER with radii 1.5 S and 3.0 S, resolves it, and places the actor at the returned random point (queued through manager 0x123cde8 or Actor virtual +0x2a8). When the actor is farther than 1.5 S the routine writes the actor's own position back unchanged ([ebp-0x20] was initialised to the actor's current position at 0x7e9361). Net effect: promotion never moves an actor to its package location or to a door marker; it only pushes an actor that would pop in right next to the player out to a random point 1.5 to 3 combined-speed-seconds away. Unverified: the segment 0x7e948b..0x7e94df, which may adjust the position along the actor's own path before the proximity test; and that 0x2a8 is SetPosition.

To-Low transition `0x7e9e30`: scanned its whole body (0x7e9e30..0x7ea280) for calls to 0x7e9260, 0x76bb00 (SetPackageStartLocation), 0x5e16d0, 0x9c9f80, 0x75e540 and for virtual calls +0x2a8 / +0x2a4 / +0x2ac / +0x2b0: none. It does not record or write a position when an actor goes to Low. (It does touch package state: it tests the package type byte against 0x1c and 0x15, calls the actor's process-flag virtuals, and various cleanup; I did not decode those branches.)

Conclusion for #6893. Within Fallout3.exe's process-level code there is NO branch that places a newly promoted actor at its package location or at the far-side door. An unloaded actor keeps the position and parent space it last had; the only cell-crossing logic found is the route-length evaluator (fourth pass) that queues a pathing request. So either the arrival relocation happens in code I have not located (a cell-change / persistent-reference path, for example the CellChange handling of an actor whose parent space is rewritten), or the original simply leaves the actor where it was, which would be a third answer to the issue's question. This pass supports neither "at its package location" nor "at the far-side door"; only an in-game observation, or a decode of whatever rewrites the actor's parent space, can decide.

Where to look if continuing: writers of the actor's parent-space field [actor+0x3c]; start from callers of `0x75e540`'s inverse (the setter) and the "MoveTo cell" code used by Actor package execution (0x8b21c0 is the cross-space route helper called by Activate and MoveTo, and it ends in a position/space change for those two).

## Seventh pass: writers of the parent-space field (2026-11-16), package-location placement FOUND

Method: [ref+0x3c] is the parent cell (`0x75e540` reads it, falling back to the base object's value, then goes through `0x7462a0` to the worldspace). Raw store scan gave 661 functions, too many, so I followed the cell membership functions instead: `0x74b0a0` (adds a reference to a cell) and `0x73ecc0` (removes one), both taking the `CellRefLockEnter` lock. The functions that call BOTH are the cell-change routines. The one that matters: `0x765090(ref, cell, space)` = MoveToCell. Its callers include the script MoveTo handler (0x79bef7), the Activate/door code (0x7529d0), `0x7eee70` (Actor::Update, vslot +0x25c), `0x882350`, `0x884250`, `0x8a1480`, `0x8a27d0`, `0x7e24c0`, `0x7e8bc0`, `0x7fb290`, `0x9c1b30`.

Package-location accessors (TESPackageLocation, switch on the location type returned by 0x651040): `0x648ca0(pkg, actor)` = location POSITION; `0x648b70(pkg, actor)` = location CELL ([ref+0x3c] of the referenced object); `0x649070(pkg, actor)` = location parent SPACE (via 0x75e540). `0x76b710(actor, pos)` stores a position on the actor.

Two routines place an actor at its package location (position AND cell):
1. `0x7e24c0(flag)` (Actor method; callers 0x8d4ab0 and the SAVE-LOAD function 0x9bdc40 at 0x9be77f, i.e. it runs when a save is loaded): it first calls process virtual +0x14, then, when the current package type [pkg+0x20] is above 2 (not Find / Follow / Escort), is not 0xd, and its location type from 0x651040 is not 1, it calls Actor virtual +0x2a8 with the position from 0x648ca0 (consistent with SetPosition) and then `0x765090(actor, 0x648b70 result, 0x649070 result)`. Read directly: the actor is moved to the package location's position and cell.
2. `0x884250` (virtual slot +0x14 of ALL FOUR process classes, plus Low slot +0x8f0): it builds a list of the actor's packages for the current time (0x7dd590 with a time value from [ebx+0x24]), then dispatches on package type through a byte table at 0x884778 / pointer table 0x88475c: Find -> branch 0x88445a, Follow -> 0x884549, Eat -> 0x884501, Sleep -> 0x884544, Wander and Travel (types 5 and 6) -> 0x88440f, Guard (14) -> 0x8845ba, the rest fall through. For Travel the 0x88440f branch takes the package location's position (0x648ca0), position-sets the actor (0x76b710), takes its cell (0x648b70) and space (0x649070), and finally calls `0x765090(actor, cell, space)` at 0x8846ef. For Find (a target reference) the actor instead takes the TARGET REFERENCE's cell and space, and if that target is a door-like object whose virtual +0x100 test fails and whose flags & 0x820 are clear, it ACTIVATES it (0x755f70 with the actor) first. So the Find case reaches the far side of the target door, not the package location.

Who triggers them: `0x7e24c0` is reached from save-load (the engine places actors at their package locations after loading a save; this matches the INI setting `bFixAIPackagesOnLoad`). `0x884250` is reached through the virtual slot from `0x7e24c0`, `0x75aa90` (a REFR initialisation routine that also builds the Low process when [ref+0x60] is null, calls the cross-space route helper 0x8b21c0, and calls the actor update), and `0x87b3f0` (Low-process area). I did NOT identify any caller in the live per-frame path (the low-process loop 0x8da860 calls the Low update 0x87d640, and for actors with the 1.0 s gate the actor update 0x7eee70, which does call 0x765090); and I did NOT decode the argument that chooses between the two.

What this settles and what it does not:
- SUPPORTED by decoded code: when the original places an actor according to its package (save load, and the process placement slot), a Travel (and Wander) package puts the actor at the package LOCATION's position and cell; a package whose target is a reference puts it in that reference's cell, activating a door target on the way.
- NOT shown: that this placement is what an UNWATCHED Travel arrival uses during ordinary play, or when the player later enters the destination space. The path from "route finished" to "0x884250 runs" is not decoded. So "at the package location" now has code support for the placement itself but not for the trigger.
- The far-side-door alternative: the Find-type branch above is the only door case found; Travel does not take it.

For the PRD (XCT-OFF-002): the engine's default (package location) agrees with the one placement routine found for Travel packages. Still unverified for the live arrival trigger.

Next if continued: decode `0x75aa90` (why it calls slot +0x14 and the route helper 0x8b21c0 together), and what happens at the end of the low-process travel evaluator (0x880db0) after it queues the pathing request: whether a completed request reaches 0x7e24c0 / 0x884250.

## Eighth pass: 0x75aa90 and the Low evaluator tail (2026-11-16)

0x75aa90 = `TESObjectREFR::Enable`. It tests form flag bit 11 (0x800, "initially disabled / currently disabled"), clears it through virtual +0xc8(1), notifies the parent cell (0x74b3d0), recurses into linked children found through the extra-data list at [ref+0x40] (0x5d2500; "enable parent" chain), calls virtual +0x208(1) for actors, builds a Low process (0xb4 bytes, ctor 0x87b720) when [ref+0x60] is null, and for an actor with a package calls process slot +0x14 (= 0x884250, the placement at the package location), then the actor update (+0x25c) and the cross-space route helper 0x8b21c0. This is consistent with the CK wiki's note that MoveToPackageLocation is meant for use right after Enable. It is NOT an unwatched-Travel path.

Correction: [ref+0x40] is the reference's ExtraDataList (ExtraPackage type 0x19 sits there), not a package list. Earlier notes calling it a package list are wrong.

Low evaluator tail (0x880db0, Low/MidLow slot +0x79c): after a package applies (package virtual +0x13c) it either starts the package through `0x7f04e0` and then process virtual +0x284 (Low: 0x87ba20; High: 0x885660) to change package, or, on the route branch, compares the TeleportDoorSearch route time with elapsed time and queues `0x7f4310` -> `0x8a1e10`. Process virtual +0x3c8 is a no-op for Low and MidLow (Base stub 0x4b7b20) and real only for High and MidHigh (0x875b00).

What the queued request does: `0x8a1e10` builds a request through `0x89f540`, which calls the path handler `0x8a2270` (callers also 0x89fe20, 0x8a0030, 0x8a01a0, 0x8a0720, 0x8a0880). `0x8a2270(flag)` stores the flag at [handler+0x70]; when set and the actor's process level (`0x8993c0` = GetProcessLevel, [process+0x28]) is 3 (Low), the actor's parent cell is missing or flagged, and the actor's position is the placeholder (x>>12 == 0 and y>>12 == 0), it moves the actor to the path's start position and cell with `0x7e8bc0` (which itself ends in MoveToCell at 0x7e916d). Separately `0x8a1480` (a DetailedActorPathHandler method, class vtable 0xf92e78, slot +0x74 -> 0x8aae10) moves the actor to the next path node's cell with MoveToCell when it differs from the actor's current cell (used by HighProcess slot 0x7cc at 0x86c001).

So, in code: (a) an actor with no real position that starts a path as a Low process is placed at the path's start; (b) actors that follow a path through cells are moved to each node's cell by the handler. I could NOT show whether a Low-level actor's route is consumed that way (virtually crossing teleport links with a cell change per node) or whether the evaluator's "elapsed time covers the route" check is followed by a single placement at the package location. The final link (route-finished -> which placement routine) remains undecoded; the candidates are the 0x7e24c0 / 0x884250 package-location placement and the per-node cell moves.

Stopping point: eight static passes have decoded the placement routines, the process-level machinery and the pathing handlers, and found real package-location placement code (save-load and Enable) but no direct unwatched-arrival trigger. Further static tracing would mean following the DetailedActorPathHandler through several large virtuals (0x89f540, 0x8aae10) with no string anchors. An in-game check (one Travel actor leaving a cell, waiting, then entering the destination) is now cheaper than another pass.
