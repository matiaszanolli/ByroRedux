## Collision already had a completeness harness

`import::collision`'s `dispatch_coverage_tests` — specifically `every_dispatched_bhk_shape_has_resolve_arm` — has existed since #1360/#1361 and does exactly what this issue asks for: it fails if any `bhk*Shape` the parser dispatches lacks a `downcast_ref` arm in `resolve_shape_inner`. Its own doc names the failure mode as "the NIFAL *parsed then dropped* leak class".

The evidence here was `grep -rln "kitchen_sink"` returning only `material_translate.rs`. That's true, but `kitchen_sink` is the name of the Material harness's *fixture*, not the only shape a completeness harness can take. The Collision guard is structural rather than value-based, so it contains no such string while testing a strictly stronger property for that boundary.

Worth stating because the priority order in the suggested fix put Collision first at "highest historical bug count, 4/6" — and that work is already done.

## So Lights was the real first extension

`light_dispatch_coverage_tests` (`crates/nif/src/import/walk/mod.rs`) mirrors the collision guard: every `Ni*Light` the dispatcher constructs must reach a `LightKind` arm. Verified by deleting the `NiAmbientLight` arm, which fails naming it.

Structural rather than kitchen-sink-value, deliberately. At both of these boundaries the thing that rots is *a whole type going missing* — a per-field value harness would pass happily while an entire light kind stopped being imported. The Material harness is value-based because its failure mode is different (a field silently stopping receiving its source value).

One detail worth recording: the first extractor returned an empty set, because light dispatch arms are module-qualified (`light::NiPointLight::parse`) where shape arms are not. The anti-vacuity assertion copied from the collision sibling caught it immediately — which is the argument for copying that pattern rather than trimming it.

The real constraint is a **crate boundary**, not an absent one: `resolve_shape_inner` and `LightKind` resolution both live in `crates/nif`, below `byroredux`, so their guards cannot live in that module and this harness cannot be extended to cover them.
